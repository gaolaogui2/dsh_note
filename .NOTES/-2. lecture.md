# Harness Engineering：以 DeepSeek Harness 为解剖标本

## 1、总览

Agent 由 Model 和 Harness 共同构成。

- Model 提供「推理、决策和生成」能力。
- Harness 为 Model 服务，准备输入、提供行动能力，管理「执行过程、状态和风险」，压制 Model 产出质量波动。

Harness 需要回答 4 类问题。

- 系统由哪些职责组成，各部分如何连接。
- 程序和模型分别控制哪些执行步骤。
- 权限、取消、失败和资源释放由谁处理。
- 执行事实如何记录，进程退出后能够恢复什么。

这些问题不会有「脱离现实业务场景」限定的唯 1 最优解。

- 直接组装强调简单和低开销，
- 插件化强调替换和组合，
- Workflow 可以增强可预期，
- Agent Loop 强调动态决策。
- 持久化增强连续性和恢复能力，
- 「隔离与审批」可以降级错误操作的影响。

每项收益都会增加对应的「实现、运行或维护」成本。

评价 harness 架构时，需要先圈定现实业务场景：任务类型、变化频率、性能预算、安全要求、恢复范围和团队成本。

Harness 的许多架构思想并非为 Agent 专门创造，而是既有软件架构经验在新场景中的应用与调整。
相比快速变化的业务需求，这些思想相对稳定，可以为不同实现提供共同基础。
社区因此不必从零建立全部设计原则，有条件更快形成共识与规范。

举例：DSH 是当前社区中少有的「完全开源&高度插件化」且正在高速迭代的 Harness ，
「完全开源」可以提高社区信任程度与参与热情，
「插件化」架构提供的可替代性可以在最大程度扩展针对真实业务场景的兼容范围，
「运行时生命周期」进 1 步提高了插拔性，实现了插件的运行时替换。

DSH 尚在早期内测阶段，若可以保持接口的稳定性，有概率成为社区认可的通用 Harness Base 基建。
即使最终社区没有选择 DSH ，也会是与其相似的「开源&高度插件化&接口稳定&基础能力完整&开箱即用」的 Harness 。

## 2、宏观架构

不同取舍的 Harness 在实现上差异很大，
这里忽略细节，从更宏观的角度来划分稳定职责：「宿主与入口、场景协调、Agent 执行、上下文与模型、能力执行、数据管理、运行控制和运行保障」。

这些职责是逻辑分工，不等同于固定的目录结构、进程或服务：

- 这些职责可以在 1 个进程中直接组装，也可以按资源、风险或团队边界拆成多个服务。

宏观划分的收益是识别稳定关系和真实变化点：

- 模型供应商、工具集合、执行环境、存储方式、交互入口和 Agent 策略都是常见变化点。

只有变化足够频繁，或者存在独立责任主体时，抽象接口和独立生命周期才会产生足够收益。

组件可以直接组装，也可以通过依赖注入或插件 Runtime 管理。
直接组装简单，依赖注入集中管理实例和依赖，插件 Runtime 进 1 步支持动态组合与生命周期管理。
动态程度越高，依赖、作用域、生命周期、诊断和兼容成本通常也越高。

语义稳定但实现需要替换的能力，可以用稳定接口分开调用方和实现方，例如 DSH 的 Capability Seam 隔离。

1 个完整的 Capability Seam 包含 Definition、Provider 和 Consumer。

- Definition 定义调用约定，Provider 实现能力，Consumer 使用结果并决定后续行为。

接口应由 Consumer 的真实需要驱动，而不是复制某个 Provider 的完整 API。

还需要明确运行资源和可变状态的所有者。

- 由其管理生命周期、维护有效状态，并处理失败后的清理或恢复；

## 3、链路

Harness 先把代码、配置和运行环境组装成可接收工作的 Runtime，
再接收外部输入整理上下文推进 Agent 执行工作，并在执行过程中记录事实、处理控制请求和交付结果。

工作可能正常完成，也可能被取消、超时或故障中断。

进程或执行实例重新创建后，Harness 再根据已经确认的事实恢复可继续使用的状态。

「启动、请求、运行中控制和中断后恢复」属于稳定存在的最重要的运行链路节点，

### 3.1 启动主链

启动主链把代码、配置和运行环境转换为可接收工作的 Runtime。

系统需要解析组成和参数，创建运行基础，装配组件，解析依赖，初始化资源，并检查必需能力是否就绪。

启动函数返回或模块导入成功，都不等于 Runtime 已经可以接收工作。

启动成功表示必需能力已经可用。

启动失败需要报告失败阶段、相关组件和已完成的清理。

受控退出需要停止继续装配，并释放已经登记的资源。

已经提交到文件、进程或远程系统的外部副作用，不能仅靠释放内存对象撤销。

例如：DSH 用 Profile、Bundle 和 Patch 构成配置输入，再由 Loader 和 Entry 完成插件装配，Cordis 和 Fiber 实现生命周期管理。

当然这里存在很多设计上的细节，比如配置来源需要明确优先级、合并顺序，插件装配需要确认依赖和可用条件，生命周期管理需要登记资源并在卸载时完成清理。

### 3.2 请求主链

请求主链把外部输入转换为 Agent 工作，并持续向调用方返回「接收状态、执行进展和最终结果」。

入口先关联身份、会话和执行主体，再决定立即处理输入，还是先排队等待执行。

- 立即处理路径短，适合独立请求；排队可以解耦输入到达与处理时机，适合持续交互和运行中干预；
- 这里的输入被记录不表示 agent 已经接纳并开始执行；

Workflow 由程序决定节点走向，Agent Loop 由模型根据中间结果选择下 1 步，混合架构在程序控制的节点颞部开放局部决策。

模型发起能力调用时，执行器需要校验请求、调用能力、记录结果，再决定继续或结束。
程序也可以直接调用能力，不需要把所有操作都转换为 Tool Call。

影响后续执行、恢复或审计的输入、模型输出、能力调用和结果需要形成持久事实。

举例 DSH ，Controller 作为适配入口，将外部意图映射为 `followup`、`steer`、`inject` 和 `cancel`，入口 Agent 通过 Inbox 接收并接纳输入。
默认 ReactLoopAgent 通过 Driver 推进 Turn 和 Step，调用模型和 Tool，记录能力调用及其结果，并根据结果决定继续执行还是结束当前工作。
Session 记录已接纳输入、模型输出、能力调用和执行结果，再将这些事实投影为模型历史和场景输出。

### 3.3 控制与恢复主链

控制主链处理停止和失败，恢复主链负责在释放或重启后重建可信状态。

- 取消只表示停止请求已经发出；工作停止、资源清理且迟到回调无法修改状态后，停止才算完成。
- 局部超时限制单项等待，端到端 Deadline 则需要向模型、能力和子进程传播剩余时间。
  - 局部错误由能够解释其语义的执行方处理，依赖不可信结果的后续工作不能继续。
- 恢复根据已确认事实创建新的运行对象，不会复活旧连接、句柄、计时器或进程，也不会重新执行历史调用。
  - 缺少结果记录不代表外部操作没有发生，相关能力还需要提供幂等、状态复查、补偿或人工确认。
  - 会话恢复不等于任务续行，后台任务跨进程继续还需要持久状态和重新接管规则。

举例 DSH ，AbortSignal 传播取消，Fiber 释放登记资源，Session Persistence 修复并加载 Session Log，
DSH 可以恢复会话事实，但进程内 Job 和 Goal continuation 不会自动续行。

## 4、领域

主链由若干单点职责共同支撑，每项职责集中处理 1 类状态、规则和生命周期。

这些职责可以粗略分为 4 类：

- 「系统基础」负责装配系统并接入能力。
- 「Agent 执行」负责保存事实、组织上下文和推进工作。
- 「交互协作」负责连接参与者并协调任务。
- 「运行保障」负责限制风险、收敛故障和提供诊断依据。

不同 Harness 根据场景选择所需领域，并非所有领域都必须存在。

### 4.1 运行时组成：依赖与生命周期

任何 Harness 都需要创建并连接接收输入、调用模型、执行工具等运行组件，但不一定需要独立的运行时组成机制。

- 组成固定、依赖关系和释放责任容易明确时，可以在启动代码中直接创建对象并管理资源。
- 依赖关系和实例共享规则难以手动维护时，可以使用 DI 容器集中管理对象创建、依赖注入和实例范围。
- 需要响应运行期间的依赖变化，或卸载和替换组件时，可以使用支持动态装配的插件 Runtime。

集中管理减少了重复组装和实例管理的不一致，也增加注册、解析和生命周期协调的复杂度。

无论采用哪种方案，都需要明确依赖何时可用、资源由谁拥有，以及退出或失败时如何完成释放。

动态装配还需要处理依赖失效的影响，并决定组件重新激活后重建状态还是延续状态。

DSH 使用 Cordis 根据「Service 依赖」激活插件，通过 Context 控制可见范围，由 Fiber 和 Effect 管理插件拥有的注册关系与资源。

### 4.2 能力：语义与实现解耦

Harness 需要调用模型、工具或其他服务。

- 实现固定时可以直接调用，不一定需要独立的能力接口。
- 当调用需求保持稳定，而具体实现需要替换，或者同一套调用逻辑需要复用于不同实现时，可以用稳定接口分开调用方和实现方。
- 多个实现需要同时被使用时，可以根据请求或运行环境选择具体实现。

接口解耦可以减少「替换实现」对调用方的影响，但也增加了适配、兼容和差异处理的成本。

能力接口应由调用方的实际需要驱动，并明确输入、结果、失败、取消和资源所有权。

共同处理同一工作区的文件、命令和代码分析服务（LSP）需要指向一致的执行环境，避免文件在本地修改，命令却在远端运行。

DSH 通过 Capability Seam 分别组织模型、文件、进程和终端等能力。

- 由 Definition 定义调用约定、Provider 提供实现、Consumer 使用能力。

统 1 接口不表示不同 Provider 的功能、平台限制和资源访问限制相同。

### 4.3 组合：系统配置与 Agent 配置

Harness 需要确定实际使用哪些能力及其实现。
当这些选择随产品场景或 Agent 需求变化，不适合固定在代码中时，可以通过配置文件声明。
当配置进一步来自默认值、场景配置、用户配置和启动覆盖等多个来源时，需要规定优先级、应用顺序和合并规则，计算最终生效配置。

- 系统配置组合决定产品启动哪些入口、共享服务和 Provider。
- Agent 配置组合决定单个执行实例取得哪些模型、工具、指令和策略。

组合越灵活，越需要处理来源顺序、依赖完整性、冲突诊断和兼容成本。

无论采用哪种方式，系统都应能确定实际的「生效组合」，并在恢复旧会话时明确要沿用历史选择还是采用当前组合。

DSH 通过 Profile、Bundle 和 Patch 组织系统配置组合，通过 Agent Preset 为实例选择能力和策略。

> 指令告诉模型怎么做，策略规定程序允许怎么做、如何执行。

### 4.4 运行设置：动态修改与生效

需要在运行期间修改参数时，可以通过设置机制管理更新与生效。

动态设置提高了可调整性，也带来并发修改、持久化失败和运行实例是否立即采用新值的问题。

需要跨重启保留的设置，应先校验并保存候选值，再通知消费组件应用。

保存成功不等于组件已经应用成功，消费组件需要明确生效时点、影响范围和应用失败的处理方式。

模型请求还需要记录实际采用的配置，不能用当前设置推断过去的请求。

DSH 的 Settings 按命名空间登记设置项和默认值，由所属插件定义校验与应用方式。

> 举例：
>
> - 修改会破坏约束：协议插件已与对端约定使用 JSON，单方面修改编码配置会使后续通信解析失败。
> - 修改不生效：HTTP 插件启动时按配置监听 8080，之后只把配置改为 9090，已有服务仍监听 8080。
> - 修改可生效：请求插件每次读取超时配置，将其从 10 秒改为 30 秒后，新请求使用新时限，已有请求不受影响。

### 4.5 Agent：执行主体与生命周期

Agent 是接收输入并推进任务的执行主体。

一次性模型调用可以由普通函数完成；需要持续交互、运行中控制、会话恢复或多种执行实现并存时，独立 Agent 实例更有价值。

> 运行中控制：Agent 正在执行时，如何接收新的用户输入，决定它何时生效，以及如何暂停、取消、结束和恢复执行。

多种 Agent 实现共用的接口，只保留它们都能表达且调用方需要的输入、状态和控制操作。

暂停等可选操作需由具体实现明确支持，不能仅凭公共接口的存在推断。

独立执行主体便于持续控制和替换实现，但需要管理「身份、并发创建、发布时机和释放责任」。

运行实例与持久会话具有不同的存续时间。

Agent 空闲只表示当前没有活动，不代表业务目标已经达成。

DSH 以 Agent 接口承接输入和控制，由 AgentFactory 创建或恢复实例，AgentRegistry 定位活跃实例，AgentHandle 交付「访问与释放」责任，默认实现是 ReactLoopAgent。

### 4.6 数据管理：记录、保存与复用

Harness 运行会产生执行数据，但一次性任务可以只向调用方返回最终结果；需要「连续会话、恢复、查询或审计」时，可以引入持久数据管理。

- 组件的临时运行状态由运行实例管理，通常不直接持久化。
- 需要保存的领域状态：任务状态、调度配置、工作区信息等，由所属服务更新并保存，必要时用于重建运行状态。
- 执行事实：收到什么输入、调用了什么工具、取得什么结果，通常以「日志追加」的形式记录。
- 大体积内容适合单独存储并通过稳定引用来关联消费。

「查询和索引」是根据用途从「原始 SSOT 事实」派生的能力。

持久化提高了连续性和可核查性，也增加了「一致性、迁移、保留、删除和敏感数据治理」的成本。

一次操作涉及多个存储时，需要明确原子提交或允许延迟更新的范围，以及部分提交后的处理方式。

以 Tool 结果的记录、返回和索引更新为例：

- 权威记录：将完整报告，或指向已可靠保存报告的稳定引用，写入会话日志。
- 结果输出：根据已记录结果生成并返回报告正文。
- 搜索索引：根据已提交记录更新检索数据。

DSH 用 Session Log 保存执行事实，由 Session Persistence 持久化；Storage 和 Workspace 管理可编辑状态，Attachment 与 Spill 保存大型内容，Session Query 提供历史读取和搜索。

### 4.7 模型上下文：组装与压缩

上下文管理负责选择和组织模型输入，并为输出预留容量。

内容过多时，可以按需读取、裁剪或摘要，但需要权衡信息损失和处理成本。

无论采用哪种方案，模型可见内容都应能够从记录重建，引用需要遵守当前权限，工具描述也必须与实际可调用能力一致。

DSH 在每个 Step 由 SystemPrompt、Tools 和 Session Projection 重新组装上下文，通过 Token Meter 估算占用，由 Basic Compaction 按需压缩历史。

### 4.8 执行控制：自治度与确定性

执行控制决定哪些步骤由模型选择，哪些由程序规定。

ReAct 由模型选择后续行动，适合路径难以预先枚举的任务，但执行过程更难预测。

Workflow 由程序规定流程，适合步骤稳定或关键操作必须受控的任务，但需要预先编写执行路径。

混合方式由程序控制整体流程，在局部开放模型决策。

决策权如何分配，取决于业务场景的开放程度、风险和可重复执行要求。

DSH 默认使用 ReactLoopAgent 推进模型与工具循环，也允许通过公共 Agent 接口替换执行实现。

### 4.9 用户交互：命令、询问、批准与反馈

需要人工补充信息、批准操作或调整执行方向时，需要用户交互机制。

- 命令：用户直接触发系统操作。
- 询问：系统向用户请求所需信息。
- 批准：用户决定是否允许某项操作。
- 反馈：用户评价执行过程或结果。

这些行为可以复用消息通道，通过不同事件类型区分，并由对应处理器落实各自规则。

需要答复的交互应关联具体问题或操作，并明确取消、过期和无人应答时的处理方式。

交互内容是否持久保存、是否进入模型上下文，也需要按用途分别确定。

DSH 通过 Commands、User Questions、User Approval 和 Feedback 分别承接这些职责，以不同事件通知对应入口；审批许可用于本次操作，反馈用于评价与分析，不直接引导后续执行。

### 4.10 执行安全机制

受信任的本地任务可以采用较简单的安全机制；涉及「外部副作用、敏感数据或多租户」时，需要明确管理访问权限和执行限制。

「身份、授权、凭证、审批、执行策略和隔离机制」承担不同职责。

提示词可以告知模型规则，但不能代替确定性的授权检查和平台隔离。

更严格的安全机制可以降低误操作和越权影响，也会增加交互、部署和平台适配成本。

策略需要在真实能力调用点执行，沙箱强度则取决于文件、网络、进程和凭证的具体隔离机制。

凭证还需要限制可见范围和使用位置，不能因插件位于同一进程就默认允许访问。

分设安全服务便于独立演进，但需要协调规则；统一安全入口便于集中检查和审计，但内部仍需区分不同职责的状态与生命周期。

DSH 分别提供凭证存取、获取凭证的交互流程、工具策略、审批和沙箱机制，没有用单一服务包办所有安全职责。

当前 DSH 将进程内插件和部署配置视为受信任代码，Sandbox 主要限制经其启动的进程及子进程。

### 4.11 编排：任务组织与执行委派

任务可以由单个 Agent 按指令推进；需要由系统控制「阶段衔接、后台任务调度、定时触发或执行委派」时，可以引入独立的编排机制。

执行委派包括创建子 Agent、投递任务、等待结果，以及取消和释放实例。

编排让任务推进更可预期，也能支持并行和持续执行，但会增加依赖协调、结果归属和失败传播的复杂度。

DSH 分别用 Goal、Job、Schedule、Workflow 和 Subagent 承载持续目标、后台任务、时间触发、程序化流程和子 Agent 委派。

### 4.12 Controller：场景协调与入口适配

内嵌调用可以直接使用 Agent 接口；需要适配 CLI、GUI、API 或自动化协议时，可以由 Controller 转换入口请求。

Controller 将调用者、会话和入口 Agent 关联起来，并处理结果返回、连接结束及实例释放责任。

多个入口可以共享业务处理，不同 Controller 分别适配各自协议，代价是增加连接和状态管理成本。

DSH 的 Controller 将外部意图映射为 `followup`、`steer`、`inject` 和 `cancel` 等 Agent 操作，并为不同入口提供对应的交互方式。

### 4.13 运行可靠性：故障、取消与恢复

任何 Harness 都会遇到失败，「异步工作、外部副作用和持久恢复」需求越多，越需要独立的可靠性机制。

简单调用可以直接返回成功或失败；长链路还要区分取消、超时、部分完成和结果未知，并决定故障影响范围。

恢复、重试、幂等和补偿解决不同问题，不能相互替代。

增加自动恢复和重试可以提高可用性，也可能重复外部操作或掩盖不可信状态。

以 Tool 结果的记录、返回和索引更新为例，部分环节失败不代表 Tool 执行失败。

- 派生数据更新失败时，根据权威记录重试或重建，不重新执行 Tool。
- 权威记录提交失败时，复用已有结果重试提交，或核查记录是否已提交。
- 若 Tool 结果已经丢失，需要通过 Tool 提供的核查机制确认副作用状态。
- 只有确认原操作未执行且不会继续执行，或满足 Tool 声明的幂等重试条件时，才能重新执行 Tool。
- 无法确认时，应标记结果未知并停止依赖该结果的后续工作。

DSH 将普通 Tool 失败记录为结构化结果供后续 Step 处理，模型请求无法继续时结束当前 Turn，并通过 AbortSignal、Fiber 和 Session Persistence 分别处理取消传播、资源释放与会话修复。

DSH 可以恢复会话事实，但进程内 Job 和未记录的外部操作结果不会因此自动恢复。

### 4.14 运行观测与诊断

本地短任务可以采用简单的诊断输出；链路变长、组件增多或进入生产运行后，独立的观测与诊断机制更有价值。

- 会话事实：保存执行记录，支持历史重建。
- 运行事件：提供状态变化信息，供观测模块采集。
- 日志：记录操作和异常，帮助定位问题。
- 指标：汇总次数、耗时和资源用量，观察趋势。
- Trace：关联跨组件调用，追踪执行路径和耗时。

上述手段按诊断需求选择，复杂链路可以增加调用追踪，并控制粒度与采样范围。

异常定位需要可关联的运行信息，状态恢复则以可靠保存的事实为依据。

增加观测可以缩短定位时间，但会带来采集成本、数据噪声和敏感信息治理问题。

观测模块的失败不应改写业务执行结果。

诊断还应指出「受影响对象、已知影响、未知状态和安全的下一步」，而不只是输出异常文本。

DSH 用 Session Events 保存可重建事实，以 Agent 和 Capability Events 通知运行变化，通过日志报告局部问题，并由 Session Telemetry 将选定记录交给外部 Backend。

### 5.1 配置服务 - 通用

配置服务将「组织规则」和「存储方式」组合起来，统 1 执行「校验 → 保存 → 发布有效值 → 通知消费方。

有效配置供运行时装配和下游服务消费。

- 初始配置可以由启动代码直接传入，也可以从文件读取。
- 运行期间的修改若需要跨重启保留，就需要写入文件等方式持久存储。

「默认值、场景配置和用户配置」同时存在时，需要进 1 步管理来源顺序与覆盖关系。

配置服务在启动阶段直接使用基础文件操作，不依赖尚未装配的业务存储服务。

#### 5.1.1 对外接口

下面以「模型 Provider 」和「请求超时」为例，展示配置的读取、修改与通知。

消费方通过同 1 个接口使用配置，不需要知道配置来自几个来源或保存在哪里。

```ts
interface Config {
  readonly model: string;
  readonly timeoutSeconds: number;
}

type ConfigPatch = Partial<Config>;
type Listener = (config: Config) => void;

interface Settings {
  read(): Config;
  // 保存失败抛错且不发布新值；通知失败单独返回。
  update(patch: ConfigPatch): { notificationErrors: unknown[] };
  subscribe(listener: Listener): () => void;
}
```

`read` 返回不可变的有效配置快照，`update` 提交修改，`subscribe` 登记变更监听并返回取消订阅函数。

配置组织决定有效值如何计算，配置存储决定修改如何保留，两者可以独立组合。

#### 5.1.2 配置计算：解析、合并与校验

单 1 来源适合由 1 份配置完整描述运行选择，多来源适合保留默认值、场景选择和用户覆盖之间的关系。

2 种方式都需要检查配置项和取值。

```ts
const defaults: Config = Object.freeze({
  model: "provider-a",
  timeoutSeconds: 10,
});

function parsePatch(value: unknown): ConfigPatch {
  if (!value || typeof value !== "object" || Array.isArray(value)) {
    throw new Error("配置必须是对象");
  }
  const patch: ConfigPatch = {};
  for (const [key, item] of Object.entries(value)) {
    if (key === "model" && typeof item === "string" && item.trim()) {
      Object.assign(patch, { model: item });
    } else if (
      key === "timeoutSeconds" &&
      typeof item === "number" &&
      Number.isFinite(item) &&
      item > 0
    ) {
      Object.assign(patch, { timeoutSeconds: item });
    } else {
      throw new Error(`未知配置项或无效值：${key}`);
    }
  }
  return patch;
}
```

单 1 来源要求 1 份配置包含全部必需字段，不引入隐式默认值。

```ts
type ConfigResolver = (saved: ConfigPatch) => Config;

const resolveSingle: ConfigResolver = (saved) => {
  const parsed = parsePatch(saved);
  if (parsed.model === undefined || parsed.timeoutSeconds === undefined) {
    throw new Error("单一来源必须提供 model 和 timeoutSeconds");
  }
  return Object.freeze({
    model: parsed.model,
    timeoutSeconds: parsed.timeoutSeconds,
  });
};

const singleConfig = resolveSingle({
  model: "provider-a",
  timeoutSeconds: 10,
});
```

单 1 来源容易阅读和排查，但不同场景需要维护各自的完整配置。

多来源方案将「用户覆盖」应用在「默认值」和「场景配置」之后。

```ts
function createLayeredResolver(sceneInput: ConfigPatch): ConfigResolver {
  const scene = Object.freeze({ ...parsePatch(sceneInput) });
  return (user) =>
    Object.freeze({
      ...defaults,
      ...scene,
      ...parsePatch(user),
    });
}

const resolveLayered = createLayeredResolver({
  model: "provider-b",
  timeoutSeconds: 20,
});
const layeredConfig = resolveLayered({ timeoutSeconds: 30 });
```

多来源适合多个产品场景共享默认值，同时允许用户独立调整。

代价是排查有效值时需要确认来源和覆盖顺序。

本例字段都是标量，后面的来源按字段覆盖前面的来源。

嵌套对象和数组需要另行规定合并规则，不能直接套用标量覆盖。

#### 5.1.3 配置存储

存储只负责读取和保存可修改的那份配置，不决定来源优先级。

单 1 来源保存完整配置，多来源方案只保存用户覆盖，不将合并结果反写到其他来源。

```ts
interface ConfigStore {
  load(): ConfigPatch;
  // 失败抛错；不得将未完成的保存报告为成功。
  save(value: ConfigPatch): void;
}

function createMemoryStore(initial: ConfigPatch): ConfigStore {
  let saved = Object.freeze({ ...parsePatch(initial) });
  return {
    load: () => saved,
    save(value) {
      saved = Object.freeze({ ...parsePatch(value) });
    },
  };
}

const memoryStore = createMemoryStore({
  model: "provider-a",
  timeoutSeconds: 10,
});
```

- 内存存储不需要文件和序列化，适合测试、临时运行或由上游重新提供配置的场景。代价是进程退出后修改丢失。
- 文件存储启动时读取 JSON，更新时通过同目录临时文件替换目标文件，避免直接覆盖时出现异常留下不完整 JSON 。

```ts
import {
  existsSync,
  readFileSync,
  writeFileSync,
  renameSync,
  unlinkSync,
} from "node:fs";
import { randomUUID } from "node:crypto";

function saveConfigFile(path: string, value: ConfigPatch): void {
  const temporary = `${path}.${randomUUID()}.tmp`;
  try {
    writeFileSync(temporary, JSON.stringify(value, null, 2) + "\n", {
      flag: "wx",
      mode: 0o600,
    });
    renameSync(temporary, path);
  } catch (error) {
    try {
      if (existsSync(temporary)) unlinkSync(temporary);
    } catch (cleanupError) {
      throw new AggregateError(
        [error, cleanupError],
        "配置保存与临时文件清理失败",
      );
    }
    throw error;
  }
}

// 当前示例不支持多进程并发更新。
// 对同 1 份配置的并发控制需覆盖读取、合并、保存全过程，不能只锁 save。
function createFileStore(path: string): ConfigStore {
  return {
    load() {
      // 缺失表示没有已保存配置；单一来源解析器仍会拒绝缺少必需字段。
      if (!existsSync(path)) return {};
      return parsePatch(JSON.parse(readFileSync(path, "utf8")));
    },
    save(value) {
      saveConfigFile(path, parsePatch(value));
    },
  };
}

// 父目录必须已存在；本例只创建配置文件，不创建目录。
const fileStore = createFileStore("./user-settings.json");
```

「文件存储」适合配置写入责任能集中管理的场景，修改后可以在重启时重新读取。

- 多用户或多租户可以在同 1 个配置根目录下，按租户和用户分别保存文件；
- 配置服务根据已验证的用户身份定位其个人配置文件，不能允许用户通过指定路径访问其他用户的配置；
- 配置体积很大时可以按职责、类型或更新频率拆成多个小配置文件 ，每次只读取和更新受影响的部分，避免读写配置时耗时过大；
- 代价是依赖文件权限和文件系统状态，文件读写失败则配置更新失败；

单进程应对同 1 份配置串行更新，多进程修改共享配置则需要锁或版本检查，也可以采用数据库事务。

#### 5.1.4 更新链路

收到修改请求后，先解析修改项，将其合并到可写来源，并计算、校验候选有效值。

校验通过后保存可写来源，再更新有效配置快照，最后通知消费方。

```ts
function createSettings(store: ConfigStore, resolve: ConfigResolver): Settings {
  let saved = parsePatch(store.load());
  let current = resolve(saved);
  let updating = false;
  const listeners = new Set<Listener>();
  return {
    read: () => current,
    update(patch) {
      if (updating) throw new Error("配置通知期间不能再次修改配置");
      updating = true;
      try {
        const nextSaved = { ...saved, ...parsePatch(patch) };
        const next = resolve(nextSaved);
        store.save(nextSaved);
        saved = nextSaved;
        current = next;
        const notificationErrors: unknown[] = [];
        for (const listener of [...listeners]) {
          try {
            listener(next);
          } catch (error) {
            notificationErrors.push(error);
          }
        }
        return { notificationErrors };
      } finally {
        updating = false;
      }
    },
    subscribe(listener) {
      listeners.add(listener);
      return () => {
        listeners.delete(listener);
      };
    },
  };
}

// 单 1 来源 + 内存存储。
const memorySettings = createSettings(memoryStore, resolveSingle);

// 多来源合并 + 文件存储；也可以换成 createMemoryStore({})。
const fileSettings = createSettings(fileStore, resolveLayered);
const unsubscribe = fileSettings.subscribe((config) => {
  console.log("新超时值：", config.timeoutSeconds);
});
try {
  const result = fileSettings.update({ timeoutSeconds: 30 });
  console.log(fileSettings.read(), result.notificationErrors);
} finally {
  unsubscribe();
}
```

校验或保存失败时，不替换进程内快照，也不发送通知。

1 个订阅者失败不阻止其他订阅者收到通知，也不撤销已经保存的配置。

通知错误单独返回，由更新发起方报告和处理。

通知只表示新配置可用，不代表消费方已经应用成功。

配置变更是否需要重建实例、何时影响新请求，以及应用失败如何处理，由消费方负责。

需要跟踪实际生效状态时，应由消费方提供应用结果，不能用有效配置代替运行状态。

### 5.2 运行时服务 - 通用

运行时服务负责把选定的服务实现装配成可用系统，并管理这些实例的创建、依赖连接和释放。

它消费配置服务给出的装配选择。

- 装配固定时，这项职责可以由 1 个启动函数完成，不必建设通用容器。
- 实例共享和依赖关系难以手工维护时，可以引入 DI 容器。
- 需要在运行期间装卸或替换 Provider 时，可以使用动态插件 Runtime。

#### 5.2.1 共同接口与示例约定

对消费方而言，运行时需要提供可用的服务入口，并在关闭时释放自己创建的资源。

下面用“执行服务依赖模型服务”展示装配关系，不展开真正的 Agent 执行循环。

```ts
interface Model {
  complete(input: string): string;
  dispose(): void;
}

interface Execution {
  run(input: string): string;
  dispose(): void;
}

interface Runtime {
  // 关闭或依赖不可用时抛错；调用方不负责释放取得的服务。
  readonly execution: Execution;
  // 尝试释放全部资源；重复调用不重复释放，清理失败向上报告。
  dispose(): void;
}

type ModelFactory = () => Model;
type ExecutionFactory = (model: Model) => Execution;

function createModel(name: string): Model {
  let closed = false;
  return {
    complete(input) {
      if (closed) throw new Error("模型服务已关闭");
      return `${name}: ${input}`;
    },
    dispose() {
      closed = true;
    },
  };
}

function createExecution(model: Model): Execution {
  let closed = false;
  return {
    run(input) {
      if (closed) throw new Error("执行服务已关闭");
      return model.complete(input);
    },
    dispose() {
      closed = true;
    },
  };
}
```

示例使用同步调用和内存状态，以便集中观察装配行为。

工厂成功返回才转移资源所有权，工厂内部创建失败时由工厂清理尚未交出的资源。

各方案复用同 1 个资源作用域，按创建顺序的逆序释放实例。

```ts
class Scope {
  private resources: { dispose(): void }[] = [];
  private closed = false;

  assertOpen(): void {
    if (this.closed) throw new Error("运行时已关闭");
  }

  own<T extends { dispose(): void }>(resource: T): T {
    this.assertOpen();
    this.resources.push(resource);
    return resource;
  }

  dispose(): void {
    if (this.closed) return;
    this.closed = true;
    const errors: unknown[] = [];
    for (const resource of this.resources.splice(0).reverse()) {
      try {
        resource.dispose();
      } catch (error) {
        errors.push(error);
      }
    }
    if (errors.length) throw new AggregateError(errors, "资源清理失败");
  }
}

function rollback(scope: Scope, cause: unknown): never {
  try {
    scope.dispose();
  } catch (cleanupError) {
    throw new AggregateError([cause, cleanupError], "装配失败且清理失败");
  }
  throw cause;
}

const exampleScope = new Scope();
try {
  // Model 创建成功后已经归 exampleScope 所有。
  const model = exampleScope.own(createModel("A"));
  exampleScope.own(createExecution(model));
} catch (error) {
  // 创建失败时，释放这个 Scope 中已登记的资源，再报告错误。
  rollback(exampleScope, error);
}
```

真实服务存在在途请求时，关闭接口应返回 Promise，并等待请求结束或取消收敛后再释放依赖。

#### 5.2.2 直接装配

启动函数按照依赖顺序创建实例，并通过构造参数连接服务。

```ts
function createDirectRuntime(
  makeModel: ModelFactory,
  makeExecution: ExecutionFactory = createExecution,
): Runtime {
  const scope = new Scope();
  try {
    const model = scope.own(makeModel());
    const execution = scope.own(makeExecution(model));
    return {
      get execution() {
        scope.assertOpen();
        return execution;
      },
      dispose: () => scope.dispose(),
    };
  } catch (error) {
    return rollback(scope, error);
  }
}

const direct = createDirectRuntime(() => createModel("A"));
try {
  console.log(direct.execution.run("你好"));
} finally {
  direct.dispose();
}
```

装配关系直接可见，创建失败时也容易确定需要回收哪些实例。

代价是依赖连接和实例共享规则需要在启动代码中维护。

它适合组合固定、资源所有权清楚的 Harness，不必仅因服务数量增加就更换方案。

#### 5.2.3 DI 容器

「服务注册规则」声明「工厂、依赖关系和实例共享范围」，DI 容器按规则创建并缓存实例。

下面仍只注册模型和执行服务，每项注册在 1 个容器内共享 1 个实例。

注册规则用代码声明，不是配置文件。

```ts
type Disposable = { dispose(): void };
type Resolver<S> = <K extends keyof S>(key: K) => S[K];
type Registrations<S> = {
  [K in keyof S]: {
    lifetime: "singleton";
    factory: (resolve: Resolver<S>) => S[K];
  };
};

class Container<S extends { [K in keyof S]: Disposable }> {
  private scope = new Scope();
  private instances: Partial<S> = {};
  private resolving = new Set<keyof S>();

  constructor(private rules: Registrations<S>) {}

  resolve<K extends keyof S>(key: K): S[K] {
    this.scope.assertOpen();
    const existing = this.instances[key];
    if (existing !== undefined) return existing;
    if (this.resolving.has(key)) throw new Error(`循环依赖：${String(key)}`);
    this.resolving.add(key);
    try {
      const instance = this.scope.own(
        this.rules[key].factory((dependency) => this.resolve(dependency)),
      );
      this.instances[key] = instance;
      return instance;
    } finally {
      this.resolving.delete(key);
    }
  }

  dispose(): void {
    try {
      this.scope.dispose();
    } finally {
      this.instances = {};
    }
  }
}

interface Services {
  model: Model;
  execution: Execution;
}

function registerServices(
  makeModel: ModelFactory,
  makeExecution: ExecutionFactory,
): Registrations<Services> {
  return {
    model: {
      lifetime: "singleton",
      factory: () => makeModel(),
    },
    execution: {
      lifetime: "singleton",
      factory: (resolve) => makeExecution(resolve("model")),
    },
  };
}

function createDiRuntime(
  makeModel: ModelFactory,
  makeExecution: ExecutionFactory = createExecution,
): Runtime {
  const container = new Container(registerServices(makeModel, makeExecution));
  try {
    // 启动时解析必需入口，避免将装配错误推迟到首个请求。
    container.resolve("execution");
    return {
      get execution() {
        return container.resolve("execution");
      },
      dispose: () => container.dispose(),
    };
  } catch (error) {
    try {
      container.dispose();
    } catch (cleanupError) {
      throw new AggregateError([error, cleanupError], "装配失败且清理失败");
    }
    throw error;
  }
}

const di = createDiRuntime(() => createModel("A"));
try {
  console.log(di.execution.run("你好"));
} finally {
  di.dispose();
}
```

工厂和依赖关系集中在注册规则中，Container 不再直接认识 Model 和 Execution。

新增服务或调整依赖主要修改注册规则，启动入口和容器机制可以保持稳定。

本例只支持容器内单例，其他实例范围需要扩展容器的生命周期管理。

代价是增加注册与解析层，通用容器还需要处理作用域、循环依赖和缺失注册的诊断。

它适合多个入口复用服务、不同实例范围并存，或需要集中替换工厂进行测试的场景。

容器缓存本身不提供热替换能力，修改注册也不会自动更新已注入其他对象的旧引用。

> DI 容器的核心价值，是将服务装配从手工编排，转为注册规则驱动的自动解析。
> 它包含 2 部分：
>
> - 规则注册：将外部提供的工厂登记为服务，声明依赖关系、实例范围和清理方式。
> - 规则消费：按规则解析依赖，调用工厂创建、连接和复用实例，并管理释放。
>
> 每个服务只声明自己的直接依赖，由容器按实例范围创建或复用依赖，再注入消费方，不由消费方自行创建。
>
> - 新增服务或调整依赖时，主要修改注册规则；
> - 替换具体实现时，由调用方更换传给 Runtime 的工厂，注册规则和 Container 的通用机制可以保持稳定。
>
> 如果装配简单，启动函数就够了；当依赖关系和实例共享规则难以手工维护时，DI 容器的收益才更明显。

#### 5.2.4 动态插件 Runtime

动态插件 Runtime 不仅在启动时根据依赖关系装配服务，还会在运行期间根据依赖变化激活或停用服务。

Provider 被替换时，Runtime 先停用依赖它的服务，再释放旧 Provider，并在新依赖就绪后重建消费方。

下面只展示模型 Provider 与执行服务的装配和替换，具体实现由外部工厂提供。

本例采用等待完成的策略，替换期间拒绝新任务，不取消已经开始的任务。

```ts
interface AsyncModel {
  complete(input: string): Promise<string>;
  dispose(): Promise<void>;
}

interface AsyncExecution<State> {
  run(input: string): Promise<string>;
  // 同步停止接收新任务；返回的 Promise 在已有任务结束后完成。
  stop(): Promise<void>;
  // 停稳后导出状态；状态内容由执行服务定义。
  snapshot(): State;
  // 向尚未发布的新实例恢复状态，失败时抛错。
  restore(state: State): Promise<void>;
  // 停止并等待任务结束，释放自身资源；允许重复调用。
  dispose(): Promise<void>;
}

type AsyncModelFactory = () => AsyncModel;
type AsyncExecutionFactory<State> = (
  model: AsyncModel,
) => AsyncExecution<State>;

// 复用 5.2.3 的注册规则类型；容器关闭改为等待异步清理。
class AsyncContainer<
  S extends { [K in keyof S]: { dispose(): Promise<void> } },
> {
  private instances: Partial<S> = {};
  private resources: { dispose(): Promise<void> }[] = [];
  private resolving = new Set<keyof S>();
  private closed = false;
  private disposal: Promise<void> | undefined;

  constructor(private rules: Registrations<S>) {}

  resolve<K extends keyof S>(key: K): S[K] {
    if (this.closed) throw new Error("容器已关闭");
    const existing = this.instances[key];
    if (existing !== undefined) return existing;
    if (this.resolving.has(key)) throw new Error(`循环依赖：${String(key)}`);
    this.resolving.add(key);
    try {
      const instance = this.rules[key].factory((dependency) =>
        this.resolve(dependency),
      );
      this.instances[key] = instance;
      this.resources.push(instance);
      return instance;
    } finally {
      this.resolving.delete(key);
    }
  }

  dispose(): Promise<void> {
    this.closed = true;
    return (this.disposal ??= (async () => {
      // 依赖先创建，消费方先释放；清理失败时停止，避免提前关闭依赖。
      while (this.resources.length) {
        await this.resources[this.resources.length - 1].dispose();
        this.resources.pop();
      }
      this.instances = {};
    })());
  }
}

interface AsyncServices<State> {
  model: AsyncModel;
  execution: AsyncExecution<State>;
}

function registerAsyncServices<State>(
  makeModel: AsyncModelFactory,
  makeExecution: AsyncExecutionFactory<State>,
): Registrations<AsyncServices<State>> {
  return {
    model: {
      lifetime: "singleton",
      factory: () => makeModel(),
    },
    execution: {
      lifetime: "singleton",
      factory: (resolve) => makeExecution(resolve("model")),
    },
  };
}

interface PreparedServices<Entry, State> {
  readonly entry: Entry;
  stop(): Promise<void>;
  snapshot(): State;
  dispose(): Promise<void>;
}

async function prepareServices<State>(
  rules: Registrations<AsyncServices<State>>,
  state: State,
): Promise<PreparedServices<AsyncExecution<State>, State>> {
  const container = new AsyncContainer(rules);
  try {
    const execution = container.resolve("execution");
    await execution.restore(state);
    return {
      entry: execution,
      stop: () => execution.stop(),
      snapshot: () => execution.snapshot(),
      dispose: () => container.dispose(),
    };
  } catch (error) {
    try {
      await container.dispose();
    } catch (cleanupError) {
      throw new AggregateError(
        [error, cleanupError],
        "装配或恢复失败且清理失败",
      );
    }
    throw error;
  }
}

async function createPluginRuntime<Services, Entry, State>(
  initialRules: Registrations<Services>,
  prepare: (
    rules: Registrations<Services>,
    state: State,
  ) => Promise<PreparedServices<Entry, State>>,
  initialState: State,
) {
  let rules = initialRules;
  // 替换失败时仍保留旧状态；本例不提供重试恢复接口。
  let savedState = initialState;
  let current: PreparedServices<Entry, State> | undefined = await prepare(
    rules,
    savedState,
  );
  let replacing = false;
  let disposal: Promise<void> | undefined;

  return {
    get entry() {
      if (!current) throw new Error("执行入口不可用");
      return current.entry;
    },
    async replaceProvider<K extends keyof Services>(
      key: K,
      factory: Registrations<Services>[K]["factory"],
    ) {
      if (replacing) throw new Error("请先等待当前替换完成");
      if (!current) throw new Error("执行入口不可用");
      const nextRules = {
        ...rules,
        [key]: { ...rules[key], factory },
      };
      const previous = current;
      replacing = true;
      current = undefined;
      try {
        await previous.stop(); // 禁止新任务，等待在途任务结束
        savedState = previous.snapshot();
        await previous.dispose();
        const next = await prepare(nextRules, savedState);
        rules = nextRules;
        current = next; // 准备成功后才发布入口
      } finally {
        replacing = false;
      }
    },
    dispose() {
      // 本例拒绝并发管理操作；调用方须等替换结束后再关闭。
      if (replacing) return Promise.reject(new Error("请先等待当前替换完成"));
      if (disposal) return disposal;
      const previous = current;
      current = undefined;
      return (disposal = previous?.dispose() ?? Promise.resolve());
    },
  };
}

// 应用侧选择工厂和状态；Runtime 不认识 Model 或 Execution 的业务逻辑。
async function startExample<State>(
  makeModel: AsyncModelFactory,
  makeExecution: AsyncExecutionFactory<State>,
  newModel: AsyncModelFactory,
  initialState: State,
) {
  const runtime = await createPluginRuntime(
    registerAsyncServices(makeModel, makeExecution),
    prepareServices<State>,
    initialState,
  );
  try {
    await runtime.entry.run("任务1");
    await runtime.replaceProvider("model", () => newModel());
    await runtime.entry.run("任务2");
  } finally {
    await runtime.dispose();
  }
}
```

模型调用实现在 5.10 展开，任务接纳、等待和状态恢复实现在 5.13 展开。

注册规则描述依赖，DI 容器负责实例装配和异步释放，`prepareServices` 取得入口并恢复状态。

Runtime 接收注册规则和装配函数，通过 `replaceProvider` 接受调用方选定的新工厂，协调停用、状态交接和重新发布。

本例每次替换都会重建传入规则对应的容器，因此规则只包含 Model 和依赖它的 Execution。

完整系统还需根据依赖关系确定受影响范围，不能把全系统规则交给这个简化实现后声称支持局部重建。

本例以接口占位，需要传入满足这些约定的工厂和初始状态才能运行。

调用方每次执行任务时，都通过 `runtime.entry` 取得当前入口，不跨替换过程缓存旧实例。

状态由 Execution 解释和恢复，Runtime 只负责保存快照并协调交接。

替换和关闭必须串行调用，并发管理操作会被拒绝。

替换失败保持入口不可用，不自动回退；新实例恢复失败时清理其资源。

清理失败会报告错误，不保证失败资源已释放。

示例只提供进程内状态交接，不包含重启恢复、状态格式迁移或外部资源就绪检查。

真实请求还需要超时或取消机制，不能无限等待，也不能提前释放仍被使用的资源。

动态方案适合需要在进程存活期间装卸 Provider 或调整依赖组合的场景。

代价是依赖失效可能触发级联停用，还要协调在途请求、状态恢复和重新发布。

实际插件 Runtime 还需要通用依赖图、作用域和异步生命周期管理，不应把这个固定依赖关系的示例当作完整插件框架。

DSH 使用 Cordis 的依赖声明驱动插件激活，并由 Fiber 和 Effect 管理插件资源。

### 5.3 业务存储服务 - 通用

业务存储服务保存可编辑的业务对象，例如工作区信息和项目记录。

它提供按标识读写数据的能力。

- 内存存储适合只在当前运行中使用，或可从其他来源重建的数据。
- 文件存储适合需要跨重启保留、由单 1 存储实例集中管理且更新不频繁的数据，例如本地项目清单和工作区信息。
- 数据库存储适合需要多个实例共享、频繁局部更新、复杂查询或跨记录事务的数据，例如多人使用的项目管理系统。

如果业务需要处理并发冲突，而不是遇到冲突就简单地终止更新动作，可以根据数据结构和协作需求选择 OT 或 CRDT 等方案。

- 但 OT 和 CRDT 的实现与维护成本更高。

#### 5.3.1 对外接口与数据归属

业务服务定义记录内容和修改规则，存储服务负责保存内容并检查版本。

下面用字符串正文简化业务数据结构，各方案提供相同的读写操作。

```ts
import { randomUUID } from "node:crypto";

interface BusinessRecord {
  readonly id: string;
  readonly body: string;
  readonly version: string;
}

interface BusinessStore {
  read(id: string): BusinessRecord | undefined;
  // expected 为 null 时只允许创建，否则只允许修改指定版本。
  put(id: string, body: string, expected: string | null): BusinessRecord;
  remove(id: string, expected: string): void;
  dispose(): void;
}

class VersionConflict extends Error {
  constructor(id: string) {
    super(`记录不存在、已存在或版本已变化：${id}`);
  }
}

function checkVersion(
  id: string,
  current: BusinessRecord | undefined,
  expected: string | null,
): void {
  if (
    expected === null ? current !== undefined : current?.version !== expected
  ) {
    throw new VersionConflict(id);
  }
}

function nextRecord(id: string, body: string): BusinessRecord {
  return Object.freeze({ id, body, version: randomUUID() });
}
```

版本是每次写入生成的不透明标识，删除后重新创建也不会沿用旧版本。

消费方读取记录后携带版本提交修改，冲突时重新读取并决定如何处理，不默认覆盖别人的修改。

接口只保证单条记录操作，不保证连续几次调用构成一个事务。

内存和 SQLite 示例使用同步接口，文件示例使用对应的异步接口。

异步操作通过 Promise 返回结果和错误，关闭后拒绝新的操作。

#### 5.3.2 内存存储

内存方案用 Map 保存记录，每次修改先检查版本，再替换对应记录。

```ts
function createMemoryBusinessStore(): BusinessStore {
  const records = new Map<string, BusinessRecord>();
  let closed = false;
  function assertOpen() {
    if (closed) throw new Error("存储已关闭");
  }

  return {
    read(id) {
      assertOpen();
      return records.get(id);
    },
    put(id, body, expected) {
      assertOpen();
      checkVersion(id, records.get(id), expected);
      const record = nextRecord(id, body);
      records.set(id, record);
      return record;
    },
    remove(id, expected) {
      assertOpen();
      checkVersion(id, records.get(id), expected);
      records.delete(id);
    },
    dispose() {
      closed = true;
      records.clear();
    },
  };
}

const memoryBusiness = createMemoryBusinessStore();
try {
  const created = memoryBusiness.put("project-a", "项目说明", null);
  const updated = memoryBusiness.put(created.id, "新的说明", created.version);
  memoryBusiness.remove(updated.id, updated.version);
} finally {
  memoryBusiness.dispose();
}
```

内存存储直接读写进程内数据，不涉及异步 I/O。

- 读取与提交之间仍可能发生其他修改，版本检查会拒绝基于旧记录的提交。
- 版本检查和新记录构造发生在修改之前，失败时保留旧记录，不需要另做回退。

内存方案适合测试、临时数据或由其他权威来源重新构建的业务状态。

- 代价是进程退出后数据丢失，也不能直接在多个进程间共享。

#### 5.3.3 文件存储

文件方案将 1 组记录保存为 JSON，每次先构造候选集合，保存成功后才替换内存集合。

下面复用 5.1.3 的临时文件替换思路，并通过异步文件 API 执行读写。

```ts
import { readFile, writeFile, rename, unlink } from "node:fs/promises";

interface AsyncBusinessStore {
  read(id: string): Promise<BusinessRecord | undefined>;
  put(
    id: string,
    body: string,
    expected: string | null,
  ): Promise<BusinessRecord>;
  remove(id: string, expected: string): Promise<void>;
  dispose(): Promise<void>;
}

function parseRecords(value: unknown): Map<string, BusinessRecord> {
  if (!Array.isArray(value)) throw new Error("记录文件必须是数组");
  const records = new Map<string, BusinessRecord>();
  for (const item of value) {
    if (
      !item ||
      typeof item !== "object" ||
      typeof item.id !== "string" ||
      typeof item.body !== "string" ||
      typeof item.version !== "string" ||
      !item.version ||
      records.has(item.id)
    ) {
      throw new Error("记录内容无效或标识重复");
    }
    records.set(
      item.id,
      Object.freeze({
        id: item.id,
        body: item.body,
        version: item.version,
      }),
    );
  }
  return records;
}

async function saveRecords(
  path: string,
  records: Map<string, BusinessRecord>,
): Promise<void> {
  const temporary = `${path}.${randomUUID()}.tmp`;
  let created = false;
  try {
    // 写入失败也可能留下部分临时文件，需在 catch 中清理。
    await writeFile(temporary, JSON.stringify([...records.values()]) + "\n", {
      flag: "wx",
      mode: 0o600,
    });
    created = true;
    await rename(temporary, path);
  } catch (error) {
    // wx 遇到已有文件时不能删除不属于本次操作的文件。
    const alreadyExists =
      error instanceof Error && "code" in error && error.code === "EEXIST";
    try {
      if (created || !alreadyExists) {
        try {
          await unlink(temporary);
        } catch (cleanupError) {
          if (
            !(
              cleanupError instanceof Error &&
              "code" in cleanupError &&
              cleanupError.code === "ENOENT"
            )
          ) {
            throw cleanupError;
          }
        }
      }
    } catch (cleanupError) {
      throw new AggregateError([error, cleanupError], "保存与临时文件清理失败");
    }
    throw error;
  }
}

// 父目录须已存在；同一文件只能由一个存储实例负责写入。
async function createFileBusinessStore(
  path: string,
): Promise<AsyncBusinessStore> {
  let text: string;
  try {
    text = await readFile(path, "utf8");
  } catch (error) {
    if (
      !(error instanceof Error && "code" in error && error.code === "ENOENT")
    ) {
      throw error;
    }
    text = "[]";
  }
  let records = parseRecords(JSON.parse(text));
  let closed = false;
  let tail: Promise<void> = Promise.resolve();
  let disposal: Promise<void> | undefined;

  function enqueue<T>(operation: () => Promise<T>): Promise<T> {
    if (closed) return Promise.reject(new Error("存储已关闭"));
    const result = tail.then(operation);
    // 错误通过 result 交给调用方，队列仍允许后续操作继续执行。
    tail = result.then(
      () => {},
      () => {},
    );
    return result;
  }
  async function commit(next: Map<string, BusinessRecord>) {
    await saveRecords(path, next);
    records = next;
  }

  return {
    async read(id) {
      if (closed) throw new Error("存储已关闭");
      return records.get(id);
    },
    put(id, body, expected) {
      return enqueue(async () => {
        checkVersion(id, records.get(id), expected);
        const record = nextRecord(id, body);
        const next = new Map(records);
        next.set(id, record);
        await commit(next);
        return record;
      });
    },
    remove(id, expected) {
      return enqueue(async () => {
        checkVersion(id, records.get(id), expected);
        const next = new Map(records);
        next.delete(id);
        await commit(next);
      });
    },
    dispose() {
      closed = true;
      return (disposal ??= tail.then(() => {
        records.clear();
      }));
    },
  };
}

const fileBusiness = await createFileBusinessStore("./projects.json");
try {
  const record = await fileBusiness.read("project-a");
  await fileBusiness.put("project-a", "项目说明", record?.version ?? null);
} finally {
  await fileBusiness.dispose();
}
```

「文件存储」方案适合写入责任集中、更新不频繁且需要跨重启保留的数据的本地场景。

- 通常是单个存储实例集中管理文件的场景，如「桌面应用保存本地项目清单、CLI 保存工作区信息」。

本例通过队列协调异步更新，并用版本检查处理旧数据提交。

异步 I/O 避免文件操作阻塞当前线程，更新队列则让版本检查、文件保存和内存发布按顺序完成。

- 读操作不进入更新队列，直接返回当前已发布的内存记录。
- 正在保存的更新尚未发布时，读取可能返回旧版本；需要读取更新后的结果，应先等待该更新完成。

关闭时停止接纳新操作，等待已接纳的操作结束，再清空内存引用。

保存失败时不发布候选集合，原文件保留，调用方收到错误。

#### 5.3.4 数据库存储

数据库方案将记录分别保存为行，利用事务在同 1 个受保护的过程内读取版本并修改。

下面使用 Node.js 的 SQLite 接口，多连接访问同 1 数据库时由数据库协调写入。

```ts
import { DatabaseSync } from "node:sqlite";

// 数据库路径的父目录须已存在。
function createSqliteBusinessStore(path: string): BusinessStore {
  const db = new DatabaseSync(path);
  try {
    db.exec(`
      PRAGMA busy_timeout = 1000;
      CREATE TABLE IF NOT EXISTS business_records (
        id TEXT PRIMARY KEY,
        body TEXT NOT NULL,
        version TEXT NOT NULL
      ) STRICT;
    `);
  } catch (error) {
    try {
      db.close();
    } catch (cleanupError) {
      throw new AggregateError([error, cleanupError], "初始化与关闭失败");
    }
    throw error;
  }
  let closed = false;
  let failed = false;
  function assertOpen() {
    if (closed || failed) throw new Error("存储已关闭或事务状态不可信");
  }
  function read(id: string): BusinessRecord | undefined {
    assertOpen();
    const row = db
      .prepare("SELECT id, body, version FROM business_records WHERE id = ?")
      .get(id);
    if (!row) return undefined;
    if (
      typeof row.id !== "string" ||
      typeof row.body !== "string" ||
      typeof row.version !== "string"
    )
      throw new Error("数据库记录类型无效");
    return Object.freeze({ id: row.id, body: row.body, version: row.version });
  }
  function transaction<T>(operation: () => T): T {
    assertOpen();
    db.exec("BEGIN IMMEDIATE");
    try {
      const result = operation();
      db.exec("COMMIT");
      return result;
    } catch (error) {
      try {
        db.exec("ROLLBACK");
      } catch (rollbackError) {
        failed = true;
        throw new AggregateError([error, rollbackError], "操作失败且回退失败");
      }
      throw error;
    }
  }

  return {
    read,
    put(id, body, expected) {
      return transaction(() => {
        checkVersion(id, read(id), expected);
        const record = nextRecord(id, body);
        db.prepare(
          `
          INSERT INTO business_records (id, body, version) VALUES (?, ?, ?)
          ON CONFLICT(id) DO UPDATE SET body = excluded.body, version = excluded.version
        `,
        ).run(id, body, record.version);
        return record;
      });
    },
    remove(id, expected) {
      transaction(() => {
        checkVersion(id, read(id), expected);
        db.prepare("DELETE FROM business_records WHERE id = ?").run(id);
      });
    },
    dispose() {
      if (closed) return;
      closed = true;
      db.close();
    },
  };
}

const sqliteBusiness = createSqliteBusinessStore("./business.sqlite");
try {
  const record = sqliteBusiness.read("project-a");
  sqliteBusiness.put("project-a", "项目说明", record?.version ?? null);
} finally {
  sqliteBusiness.dispose();
}
```

事务先取得写入资格，再读取最新版本，避免其他连接在版本检查与保存之间插入写入。

版本变化报告业务冲突，锁等待超时报告存储错误。

- 操作失败时尝试回退，回退失败则标记连接状态不可信并拒绝继续读写。

SQLite 适合同机多连接、频繁局部修改或需要事务的场景，但写入仍受单写入者限制。

- 跨机器共享数据时，改为使用服务端操作数据库。

数据库方案还需要维护数据格式与迁移，代价高于简单内存或文件存储。

### 5.4 会话服务 - Harness 特化

会话服务保存交互中的执行事实，供「历史查看、模型输入重建和执行恢复」使用。

- 记录范围：不只是窗口中的聊天消息，还包括模型调用、工具调用和任务执行中的事实。
- 记录内容：模型及有效配置、请求输入与输出，工具及调用参数与结果，任务输入与执行状态。
- 关联关系：通过会话、执行和调用标识，明确每条事实的归属及请求与结果的对应关系。
- 生命周期：记录与 Agent 实例分开管理，实例关闭不删除已保存的记录。

这些事实的记录语义属于 Harness 特化，顺序追加、去重、保存和读取则可复用通用存储机制。

1 次性调用不 1 定需要独立的会话服务，是否保存记录取决于「历史查看、输入重建和中断恢复」等需求。

- 内存会话适合临时交互，不要求进程退出后保留记录。
- 文件存储和数据库存储没有脱离需求的绝对优劣，选择取决于后续需求的实现与维护成本。
  - 主要按会话顺序「追加、读取和重放」时，文件存储通常更直接。
  - 需要大量「条件查询、跨记录事务或并发访问协调」时，数据库已有成熟能力，可以减少「自行实现和维护」的成本。

> 单次行为涉及多份权威记录，且这些写入必须整体成功时，需要「跨记录事务」；任 1 步失败，就回退本次修改。

```ts
type SessionEventType = "user" | "assistant" | "tool-result";

interface SessionInput {
  readonly eventId: string;
  readonly type: SessionEventType;
  readonly body: string;
}

type SessionEvent = Readonly<SessionInput>;

interface SessionService {
  readonly id: string;
  append(input: SessionInput): SessionEvent | Promise<SessionEvent>;
  read(): readonly SessionEvent[] | Promise<readonly SessionEvent[]>;
  dispose(): void | Promise<void>;
}

// 追加与读取共用顺序队列，关闭时等待所有已接纳的操作结束。
function createQueuedSession(storage: SessionService): SessionService {
  let tail: Promise<void> = Promise.resolve();
  let closed = false;
  let disposal: Promise<void> | undefined;

  function enqueue<T>(operation: () => T | Promise<T>): Promise<T> {
    if (closed) return Promise.reject(new Error("会话已关闭"));
    const result = tail.then(operation);
    tail = result.then(
      () => {},
      () => {},
    );
    return result;
  }

  return {
    id: storage.id,
    append(input) {
      const submitted = { ...input };
      return enqueue(() => storage.append(submitted));
    },
    read() {
      return enqueue(() => storage.read());
    },
    dispose() {
      closed = true;
      return (disposal ??= tail.then(() => storage.dispose()));
    },
  };
}

class SessionConflict extends Error {
  constructor(readonly eventId: string) {
    super(`同一事件标识不能携带不同内容：${eventId}`);
  }
}

// 根据调用方输入生成待追加事件，重复提交时返回已存在的事件。
function prepareEvent(
  input: SessionInput,
  existing?: SessionEvent,
): SessionEvent {
  if (!input.eventId) throw new Error("事件标识不能为空");
  if (existing) {
    if (existing.type !== input.type || existing.body !== input.body) {
      throw new SessionConflict(input.eventId);
    }
    return existing;
  }
  return Object.freeze({ ...input });
}

// 校验并还原文件或数据库中的已保存事件。
function parseSessionEvent(value: unknown): SessionEvent {
  if (
    !value ||
    typeof value !== "object" ||
    !("eventId" in value) ||
    typeof value.eventId !== "string" ||
    !value.eventId ||
    !("type" in value) ||
    !("body" in value) ||
    typeof value.body !== "string"
  ) {
    throw new Error("会话记录格式无效");
  }
  const type = value.type;
  if (type !== "user" && type !== "assistant" && type !== "tool-result") {
    throw new Error("会话事件类型无效");
  }
  return Object.freeze({
    eventId: value.eventId,
    type,
    body: value.body,
  });
}
```

会话服务按实际追加顺序保存和读取事件。

多路追加请求先进入顺序队列，由 1 个消费者依次完成查重和追加；前 1 项完成后才处理下 1 项。

内存、文件和数据库实现都接入这个队列，具体存储实现只负责单项追加，不重复处理多路请求的排队。

同 1 `eventId`、类型和正文再次提交时返回原记录，不重复追加。

同 1 `eventId` 携带不同内容时报告冲突，调用方不能通过重试改变已记录的事实。

调用方在首次提交前生成 `eventId`，重试沿用该标识；新的事实使用新的标识。

#### 5.4.2 内存会话

内存方案用数组保存有序事件，检查重复标识后追加记录。

```ts
function createMemorySession(id: string): SessionService {
  let events: SessionEvent[] = [];
  let closed = false;
  function assertOpen() {
    if (closed) throw new Error("会话已关闭");
  }

  return createQueuedSession({
    id,
    append(input) {
      assertOpen();
      const existing = events.find((event) => event.eventId === input.eventId);
      const event = prepareEvent(input, existing);
      if (!existing) events.push(event);
      return event;
    },
    read() {
      assertOpen();
      return [...events];
    },
    dispose() {
      closed = true;
      events = [];
    },
  });
}

const memorySession = createMemorySession("session-a");
try {
  const input: SessionInput = {
    eventId: "input-1",
    type: "user",
    body: "查看项目状态",
  };
  const first = await memorySession.append(input);
  const retry = await memorySession.append(input);
  console.log(first === retry); // true，仅保存一条事实。
  console.log(await memorySession.read());
} finally {
  await memorySession.dispose();
}
```

内存操作不涉及异步 I/O，检查与追加之间也没有异步等待。

`createMemorySession` 内部接入公共队列，多路提交按入队顺序依次完成查重和追加。

冲突检查发生在追加之前，失败不会改变已有记录。

读取返回新的数组，事件对象只读，调用方不能通过修改返回数组改变内部顺序。

内存方案适合测试或不要求跨重启保存的临时交互。

代价是会话随进程退出而丢失，记录数量增长也会持续占用内存。

#### 5.4.3 文件会话

文件方案为每份会话保存 1 个 JSONL 文件，每行包含会话标识与 1 条事件。

同 1 个存储实例负责该文件，通过公共队列串行执行查重和追加，不缓存完整历史。

单次追加的事务函数在写入前记录文件长度，写入失败时截断回原长度。

```ts
import { type FileHandle } from "node:fs/promises";

class FileRollbackFailure extends AggregateError {
  constructor(writeError: unknown, rollbackError: unknown) {
    super([writeError, rollbackError], "文件追加与回退均失败，文件状态不可信");
  }
}

// 只保护单次文件追加，调用方须确保期间没有其他写入者。
async function appendFileTransaction(
  file: Pick<FileHandle, "stat" | "appendFile" | "truncate">,
  content: Buffer,
): Promise<void> {
  const { size } = await file.stat();
  try {
    await file.appendFile(content);
  } catch (writeError) {
    try {
      await file.truncate(size);
    } catch (rollbackError) {
      throw new FileRollbackFailure(writeError, rollbackError);
    }
    throw new Error("文件追加失败，已回退本次写入", { cause: writeError });
  }
}
```

行解析、索引构建和按位置读取分别封装为工具函数。

```ts
// 解析单行 JSON，并校验会话标识与事件字段。

    typeof value !== "object" ||

  return parseSessionEvent(value);
}

// length 包含行末换行，offset 和 length 均按字节计算。
interface EventLocation {
  offset: number;
  length: number;
}

// 分块扫描一次，按完整行建立索引；跨块的 UTF-8 字节合并后再解码。
async function buildFileSessionIndex(
  file: FileHandle,
  id: string,
): Promise<{ index: Map<string, EventLocation>; endOffset: number }> {
  const index = new Map<string, EventLocation>();
  let endOffset = 0;
  const { size } = await file.stat();
  let position = 0;
  let parts: Buffer[] = [];
  while (position < size) {
    const chunk = Buffer.alloc(Math.min(64 * 1024, size - position));
    const { bytesRead } = await file.read(chunk, 0, chunk.length, position);
    if (bytesRead === 0) throw new Error("会话文件读取不完整");
    let start = 0;
    for (let cursor = 0; cursor < bytesRead; cursor++) {
      if (chunk[cursor] !== 10) continue;
      parts.push(chunk.subarray(start, cursor));
      const event = parseFileSessionLine(
        id,
        Buffer.concat(parts).toString("utf8"),
      );
      const nextOffset = position + cursor + 1;
      if (index.has(event.eventId)) {
        throw new Error("会话文件中的事件标识重复");
      }
      index.set(event.eventId, {
        offset: endOffset,
        length: nextOffset - endOffset,
      });
      endOffset = nextOffset;
      parts = [];
      start = cursor + 1;
    }
    if (start < bytesRead) parts.push(chunk.subarray(start, bytesRead));
    position += bytesRead;
  }
  if (endOffset !== size) {
    throw new Error("会话文件末尾不完整，需核查后重新打开");
  }
  return { index, endOffset };
}

// 根据索引中的字节位置与长度读取单条事件。
async function readFileSessionEvent(
  file: FileHandle,
  id: string,
  location: EventLocation,
): Promise<SessionEvent> {
  const bytes = Buffer.alloc(location.length);
  let filled = 0;
  while (filled < bytes.length) {
    const { bytesRead } = await file.read(
      bytes,
      filled,
      bytes.length - filled,
      location.offset + filled,
    );
    if (bytesRead === 0) throw new Error("会话记录读取不完整");
    filled += bytesRead;
  }
  if (bytes[bytes.length - 1] !== 10) {
    throw new Error("会话记录末尾不完整");
  }
  return parseFileSessionLine(id, bytes.subarray(0, -1).toString("utf8"));
}
```

会话实现调用上述工具函数与追加事务，追加成功后才更新内存索引。

```ts
import { open } from "node:fs/promises";

function assertFileSessionUsable(closed: boolean, failed: boolean): void {
  if (closed) throw new Error("会话已关闭");
  if (failed) throw new Error("会话写入结果不确定，需核查文件后重新打开");
}

// path 所在目录已存在，文件只由当前实例写入。
async function createFileSession(
  id: string,
  path: string,
): Promise<SessionService> {
  // a+ 在文件不存在时创建文件，后续写入追加到末尾。
  const file = await open(path, "a+", 0o600);
  let loaded: Awaited<ReturnType<typeof buildFileSessionIndex>>;
  try {
    loaded = await buildFileSessionIndex(file, id);
  } catch (error) {
    try {
      await file.close();
    } catch (cleanupError) {
      throw new AggregateError([error, cleanupError], "初始化与关闭失败");
    }
    throw error;
  }

  // 只缓存定位信息，不缓存事件正文。
  const { index } = loaded;
  let { endOffset } = loaded;
  let closed = false;
  let failed = false;

  return createQueuedSession({
    id,
    async append(input) {
      assertFileSessionUsable(closed, failed);
      const submitted = parseSessionEvent(input);
      const location = index.get(submitted.eventId);
      const existing = location
        ? await readFileSessionEvent(file, id, location)
        : undefined;
      const event = prepareEvent(submitted, existing);
      if (existing) return existing;
      const line = Buffer.from(
        JSON.stringify({ sessionId: id, ...event }) + "\n",
        "utf8",
      );
      try {
        await appendFileTransaction(file, line);
      } catch (error) {
        if (error instanceof FileRollbackFailure) failed = true;
        throw error;
      }
      index.set(event.eventId, { offset: endOffset, length: line.length });
      endOffset += line.length;
      return event;
    },
    async read() {
      assertFileSessionUsable(closed, failed);
      const events: SessionEvent[] = [];
      // Map 按索引建立及新增的顺序迭代，保持文件追加顺序。
      for (const location of index.values()) {
        events.push(await readFileSessionEvent(file, id, location));
      }
      return events;
    },
    async dispose() {
      closed = true;
      await file.close();
      index.clear();
    },
  });
}
```

每次追加将新事件序列化为 1 行 JSON，写入文件末尾。

- 写入队列只协调当前文件，不阻止不同会话文件并行写入。

初始化时分块扫描 1 次文件，建立 `eventId` 到起始字节位置与长度的索引，不将事件正文常驻内存。

- 新事件提交只查询内存索引，重复提交才按字节位置读取原记录并比较内容，不再全量扫描历史。
- 文件追加成功后才更新索引，重启时从文件重新建立索引，不单独持久化索引。
- 调用 read() 时才读取并解析历史，公共包装层会先等待此前接纳的追加完成。

同 1 事实标识携带不同内容时，拒绝本次追加并向调用方报告冲突，后续提交仍可继续处理。

文件写入失败时回退本次追加，并向调用方报告失败，不自动重试。

- 回退成功后可继续提交，回退失败则停止当前实例的读写。
- 该回退机制只处理运行期间的写入失败，不包含进程崩溃后的恢复或断电持久性保证。

关闭时停止接纳新操作，等待已接纳的追加与读取结束，再关闭文件句柄。

文件方案适合主要按会话顺序追加、读取和重放的场景，但不支持多个实例同时写同 1 文件。

- 代价是启动扫描耗时和索引内存随事件数量增长，且运行期间不能由外部修改或替换文件。

#### 5.4.4 数据库会话

数据库方案复用数据库的事务能力，在同 1 个事务中完成查重与追加。

下面使用 SQLite 的同步 API，事务内部不穿插异步操作。

```ts
import { DatabaseSync } from "node:sqlite";

// path 所在目录已存在，不与 5.3 的数据库实例自动共享事务。
function createSqliteSession(id: string, path: string): SessionService {
  const db = new DatabaseSync(path);
  try {
    db.exec(`
      PRAGMA busy_timeout = 1000;
      CREATE TABLE IF NOT EXISTS session_events (
        session_id TEXT NOT NULL,
        eventId TEXT NOT NULL,
        type TEXT NOT NULL CHECK (type IN ('user', 'assistant', 'tool-result')),
        body TEXT NOT NULL,
        UNIQUE (session_id, eventId)
      ) STRICT;
    `);
  } catch (error) {
    try {
      db.close();
    } catch (cleanupError) {
      throw new AggregateError([error, cleanupError], "初始化与关闭失败");
    }
    throw error;
  }
  let closed = false;
  let failed = false;
  function assertOpen() {
    if (closed || failed) throw new Error("会话已关闭或事务状态不可信");
  }
  function transaction<T>(operation: () => T): T {
    assertOpen();
    db.exec("BEGIN IMMEDIATE");
    try {
      const result = operation();
      db.exec("COMMIT");
      return result;
    } catch (error) {
      try {
        db.exec("ROLLBACK");
      } catch (rollbackError) {
        failed = true;
        throw new AggregateError(
          [error, rollbackError],
          "会话追加与回退均失败",
        );
      }
      throw error;
    }
  }

  return {
    id,
    append(input) {
      return transaction(() => {
        const row = db
          .prepare(
            `
          SELECT eventId, type, body FROM session_events
          WHERE session_id = ? AND eventId = ?
        `,
          )
          .get(id, input.eventId);
        const existing = row ? parseSessionEvent(row) : undefined;
        const event = prepareEvent(input, existing);
        if (!existing) {
          db.prepare(
            `
            INSERT INTO session_events (session_id, eventId, type, body)
            VALUES (?, ?, ?, ?)
          `,
          ).run(id, event.eventId, event.type, event.body);
        }
        return event;
      });
    },
    read() {
      assertOpen();
      return db
        .prepare(
          `
        SELECT eventId, type, body FROM session_events
        WHERE session_id = ? ORDER BY rowid
      `,
        )
        .all(id)
        .map(parseSessionEvent);
    },
    dispose() {
      if (closed) return;
      closed = true;
      db.close();
    },
  };
}

const sqliteSession = createQueuedSession(
  createSqliteSession("session-a", "./sessions.sqlite"),
);
try {
  await sqliteSession.append({
    eventId: "input-1",
    type: "user",
    body: "查看项目状态",
  });
} finally {
  await sqliteSession.dispose();
}
```

`BEGIN IMMEDIATE` 串行协调同 1 数据库中的追加，并保证重复检查与写入发生在同 1 个事务中。

应用层查重让正常重试返回已有事件，表中的「唯 1 约束」兜底防止重复事件落库。

SQLite 实现按内部插入顺序读取记录，不向调用方暴露数据库行标识。

数据库方案适合需要条件查询、多连接并发访问或事务能力的场景。

- 需要整体提交多份权威记录时，应由上层操作组织事务。
- 数据库减少了自行实现查询与事务的成本，但仍需维护表结构、迁移与数据增长。

### 5.5 检索服务 - Harness 特化

检索服务根据查找条件，从已有事实中找到相关记录，供历史查找和上下文选取使用。

- 检索范围：根据可信的发起者身份确定有权访问的记录，再按会话、任务执行或事件类型限定查询。
- 返回内容：提供匹配片段及原记录标识，调用方可以读取完整事实，而不是只拿到脱离来源的文本。
- 数据归属：原记录仍是权威数据，全文或向量索引只是派生数据，可以从原记录重建。

这些查询范围与结果关联属于 Harness 特化，匹配、排序和索引维护可以复用通用检索机制。

「角色与授权规则」由权限服务维护，检索服务消费权限判断，在允许的范围内查找，不生成执行事实，也不决定结果如何整理并注入模型上下文。

- 后续读取原记录时，负责读取的服务仍需校验访问权限。

只按顺序查看完整会话时，可以直接读取会话记录；需要按内容查找相关事实时，才需要检索能力。

- 直接扫描适合记录量少、查询不频繁的场景，不需要维护额外索引。
- 全文索引适合按关键词、名称或错误信息查找，减少每次查询遍历全部记录的成本。
- 向量检索适合查询与原文用词不同、但含义相近的场景，需要额外生成向量并维护索引。

选择取决于查询方式、记录规模和维护成本，不是从扫描到全文再到向量的固定升级路线。

#### 5.5.1 对外接口与检索语义

查询包含查找文本、范围限制和结果数量，结果保留原记录标识与匹配片段。

```ts
interface RecordReference {
  readonly sessionId: string;
  readonly eventId: string;
}

// 从权威记录提取的检索材料，不替代原记录。
interface SearchRecord extends RecordReference {
  readonly executionId?: string;
  readonly eventType: string;
  readonly text: string;
}

interface SearchQuery {
  readonly text: string;
  readonly sessionId?: string;
  readonly executionId?: string;
  readonly eventTypes?: readonly string[];
  readonly limit: number;
}

interface SearchHit extends RecordReference {
  readonly executionId?: string;
  readonly eventType: string;
  readonly snippet: string;
}

// 由入口完成身份识别后传入，不能直接信任用户提交的身份字段。
interface SearchIdentity {
  readonly subjectId: string;
}

// 权限服务的占位接口，返回当前身份可检索的会话范围。
interface SearchPermissions {
  allowedSessions(identity: SearchIdentity): Promise<readonly string[]>;
}

interface AuthorizedSearch extends SearchQuery {
  readonly allowedSessionIds: readonly string[];
}

interface SearchBackend {
  // 范围过滤先于匹配、排序和 limit 截取，不能返回范围外的片段。
  search(query: AuthorizedSearch): Promise<readonly SearchHit[]>;
  dispose(): void | Promise<void>;
}

interface RetrievalService {
  search(
    identity: SearchIdentity,
    query: SearchQuery,
  ): Promise<readonly SearchHit[]>;
  dispose(): Promise<void>;
}

// 拥有 backend，借用 permissions；权限规则不在检索服务内维护。
function createRetrievalService(
  permissions: SearchPermissions,
  backend: SearchBackend,
): RetrievalService {
  let closed = false;
  const active = new Set<Promise<readonly SearchHit[]>>();
  let disposal: Promise<void> | undefined;

  async function search(
    identity: SearchIdentity,
    query: SearchQuery,
  ): Promise<readonly SearchHit[]> {
    const text = query.text.trim();
    if (!text || !Number.isSafeInteger(query.limit) || query.limit <= 0) {
      throw new Error("查找文本不能为空，结果数量必须是正整数");
    }
    const submitted = {
      ...query,
      text,
      eventTypes: query.eventTypes ? [...query.eventTypes] : undefined,
    };
    const allowed = await permissions.allowedSessions({ ...identity });
    const allowedSessionIds =
      submitted.sessionId === undefined
        ? [...allowed]
        : allowed.filter((id) => id === submitted.sessionId);
    if (!allowedSessionIds.length) return [];
    return backend.search({ ...submitted, allowedSessionIds });
  }

  return {
    search(identity, query) {
      if (closed) return Promise.reject(new Error("检索服务已关闭"));
      const result = search(identity, query);
      active.add(result);
      result.then(
        () => active.delete(result),
        () => active.delete(result),
      );
      return result;
    },
    dispose() {
      closed = true;
      return (disposal ??= Promise.allSettled([...active]).then(() =>
        backend.dispose(),
      ));
    },
  };
}
```

检索只在调用方指定且有权访问的范围内进行。

- 本例以会话为授权单位，更细的记录级权限需要相应扩展权限接口与过滤条件。
- 范围内没有匹配记录或没有可检索会话时返回空数组，权限查询或检索执行失败则向调用方报告错误。

直接扫描、全文索引和向量检索使用同 1 结果结构，但匹配规则与相关性排序由各实现决定。

- `snippet` 用于展示命中依据，不代表完整事实；
- 需要完整内容时，通过 `sessionId` 与 `eventId` 读取原记录。

全文和向量方案从 `SearchRecord` 建立索引，原记录保存成功后再更新索引，索引失败不回退已经保存的事实。

索引尚未更新时可能漏掉新记录，调用方不能把没有命中理解为事实不存在。

关闭时停止接纳新查询，等待已接纳的查询结束，再释放检索后端，不关闭借用的权限服务。

#### 5.5.2 直接扫描

直接扫描逐条读取检索材料，在授权与查询范围内进行文本匹配，不维护额外索引。

```ts
interface SearchScope {
  readonly allowedSessionIds: readonly string[];
  readonly sessionId?: string;
  readonly executionId?: string;
  readonly eventTypes?: readonly string[];
}

// 来源执行完整查询，只返回命中结果，不返回范围内的全部正文。
interface SearchSource {
  search(query: AuthorizedSearch): Promise<readonly SearchHit[]>;
}

function matchesSearchScope(record: SearchRecord, query: SearchScope): boolean {
  return (
    query.allowedSessionIds.includes(record.sessionId) &&
    (query.sessionId === undefined || record.sessionId === query.sessionId) &&
    (query.executionId === undefined ||
      record.executionId === query.executionId) &&
    (query.eventTypes === undefined ||
      query.eventTypes.includes(record.eventType))
  );
}

function searchHit(record: SearchRecord, snippet: string): SearchHit {
  return {
    sessionId: record.sessionId,
    eventId: record.eventId,
    executionId: record.executionId,
    eventType: record.eventType,
    snippet,
  };
}

// iterate 负责范围筛选和文本匹配，这里只整理命中结果。
function createStreamingScanSource(
  iterate: (query: AuthorizedSearch) => AsyncIterable<SearchRecord>,
): SearchSource {
  return {
    async search(query) {
      const hits: SearchHit[] = [];
      if (!query.allowedSessionIds.length || query.eventTypes?.length === 0) {
        return hits;
      }
      for await (const record of iterate(query)) {
        hits.push(searchHit(record, record.text.slice(0, 120)));
        if (hits.length >= query.limit) break;
      }
      return hits;
    },
  };
}

// 借用 source，不负责关闭权威记录服务。
function createScanBackend(source: SearchSource): SearchBackend {
  let closed = false;
  return {
    async search(query) {
      if (closed) throw new Error("扫描后端已关闭");
      return source.search(query);
    },
    dispose() {
      closed = true;
    },
  };
}

import { DatabaseSync as ScanDatabase } from "node:sqlite";

// 使用 5.4.4 的会话表，连接由调用方拥有。
const scanDb = new ScanDatabase("./sessions.sqlite");

async function* iterateSessionRecords(
  query: AuthorizedSearch,
): AsyncIterable<SearchRecord> {
  if (!query.allowedSessionIds.length || query.eventTypes?.length === 0) return;
  const clauses = [
    `session_id IN (${query.allowedSessionIds.map(() => "?").join(",")})`,
    "instr(lower(body), ?) > 0",
  ];
  const values: (string | number)[] = [
    ...query.allowedSessionIds,
    query.text.toLowerCase(),
  ];
  if (query.sessionId !== undefined) {
    clauses.push("session_id = ?");
    values.push(query.sessionId);
  }
  // 5.4 的简化表没有 executionId，不能忽略调用方的限制。
  if (query.executionId !== undefined) {
    throw new Error("当前会话表尚未保存任务执行标识");
  }
  if (query.eventTypes !== undefined) {
    clauses.push(`type IN (${query.eventTypes.map(() => "?").join(",")})`);
    values.push(...query.eventTypes);
  }
  const rows = scanDb
    .prepare(
      `
    SELECT session_id, eventId, type, body
    FROM session_events
    WHERE ${clauses.join(" AND ")}
    ORDER BY rowid LIMIT ?
  `,
    )
    .iterate(...values, query.limit);
  // 提前结束生成器时，finally 结束数据库游标，不关闭借用的连接。
  try {
    for (const row of rows) {
      if (typeof row.session_id !== "string") {
        throw new Error("会话标识格式无效");
      }
      const event = parseSessionEvent(row);
      yield {
        sessionId: row.session_id,
        eventId: event.eventId,
        eventType: event.type,
        text: event.body,
      };
    }
  } finally {
    rows.return?.();
  }
}

const scanBackend = createScanBackend(
  createStreamingScanSource(iterateSessionRecords),
);

// 由宿主注入权限服务与入口已确认的身份。
declare const searchPermissions: SearchPermissions;
declare const searchIdentity: SearchIdentity;
const scanRetrieval = createRetrievalService(searchPermissions, scanBackend);

try {
  console.log(
    await scanRetrieval.search(searchIdentity, {
      text: "项目",
      sessionId: "session-a",
      limit: 5,
    }),
  );
} finally {
  await scanRetrieval.dispose();
  scanDb.close();
}
```

直接扫描没有索引更新滞后，但匹配少或没有命中时，最坏仍需遍历整个有效范围。

- 直接扫描适合小规模历史查找、低频查询或验证检索规则，不适合大量记录上的频繁查询。

#### 5.5.3 全文索引

全文索引将词项与记录建立对应关系，查询时由搜索引擎匹配并排序，不必逐条匹配完整正文。

下面注入全文检索适配接口，由搜索引擎负责分词、索引和匹配，不手动维护关键词。

```ts
// 应用适配接口，具体搜索引擎由外部接入。
interface FullTextEngine {
  // 按 sessionId 与 eventId 更新索引，重复写入不产生重复条目。
  upsert(records: readonly SearchRecord[]): Promise<void>;
  // 在有效范围内匹配文本、排序并返回片段，结果数量不超过 limit。
  search(query: AuthorizedSearch): Promise<readonly SearchHit[]>;
  dispose(): Promise<void>;
}

interface FullTextSearchBackend extends SearchBackend {
  index(records: readonly SearchRecord[]): Promise<void>;
}

// 拥有搜索引擎适配器；权限判断仍由 createRetrievalService 完成。
function createFullTextBackend(engine: FullTextEngine): FullTextSearchBackend {
  let closed = false;
  const active = new Set<Promise<unknown>>();
  let disposal: Promise<void> | undefined;

  function run<T>(operation: () => Promise<T>): Promise<T> {
    if (closed) return Promise.reject(new Error("全文后端已关闭"));
    const result = Promise.resolve().then(operation);
    active.add(result);
    result.then(
      () => active.delete(result),
      () => active.delete(result),
    );
    return result;
  }

  return {
    index(records) {
      const snapshot = records.map((record) => ({ ...record }));
      return run(() => engine.upsert(snapshot));
    },
    search(query) {
      return run(() => engine.search(query));
    },
    dispose() {
      closed = true;
      return (disposal ??= Promise.allSettled([...active]).then(() =>
        engine.dispose(),
      ));
    },
  };
}
```

原记录保存后调用 `index` 更新派生索引，查询通过 `createRetrievalService` 获取授权范围后交给搜索引擎。

```ts
// 由宿主注入全文引擎；复用前例的权限服务与可信身份。
declare const fullTextEngine: FullTextEngine;
const fullTextBackend = createFullTextBackend(fullTextEngine);
const fullTextRetrieval = createRetrievalService(
  searchPermissions,
  fullTextBackend,
);

try {
  console.log(
    await fullTextRetrieval.search(searchIdentity, {
      text: "项目",
      sessionId: "session-a",
      limit: 5,
    }),
  );
} finally {
  await fullTextRetrieval.dispose();
}
```

全文索引适合关键词、名称和错误信息查找，但不能仅凭词义相近匹配完全不同的表达。

代价是维护派生索引、分词规则与更新链路。

#### 5.5.4 向量检索

向量检索将「记录文本」与「查找文本」转换为同 1 向量空间中的数值，按相似度寻找相关记录。

下面注入向量数据库适配接口，不在检索服务中维护向量或计算相似度。

```ts
// 应用适配接口，不是某个数据库 SDK；接入具体产品时实现这些方法。
interface VectorDatabase {
  // 按 sessionId 与 eventId 更新索引，重复写入不产生重复条目。
  upsert(records: readonly SearchRecord[]): Promise<void>;
  // 完成文本向量化、范围过滤与相似度检索，再按 limit 返回结果。
  search(query: AuthorizedSearch): Promise<readonly SearchHit[]>;
  dispose(): Promise<void>;
}

interface VectorSearchBackend extends SearchBackend {
  index(records: readonly SearchRecord[]): Promise<void>;
}

// 拥有数据库适配器；权限判断仍由 createRetrievalService 完成。
function createVectorBackend(database: VectorDatabase): VectorSearchBackend {
  let closed = false;
  const active = new Set<Promise<unknown>>();
  let disposal: Promise<void> | undefined;

  function run<T>(operation: () => Promise<T>): Promise<T> {
    if (closed) return Promise.reject(new Error("向量后端已关闭"));

    result.then(
      () => active.delete(result),
      () => active.delete(result),

    return result;
```

向量检索适合表达不同但语义相关的查找，代价是向量生成、存储和模型版本维护，精确名称查找未必比全文检索可靠。

直接扫描不维护索引，全文索引擅长词项匹配，向量检索侧重语义相似，可以按需求组合，而不是相互替代。

### 5.6 交互服务 - 通用

交互服务负责任务执行期间用户与 Agent 的双向交互，不包含最初提交任务的动作。

- **用户主动交互**：补充要求、调整方向，或请求暂停、终止任务。
- **Agent 主动交互**：请求用户补充信息或批准操作，并接收答复。
- **交互管理**：分发交互信息，将答复关联到对应请求，处理等待、取消、过期和无人应答。

「回调」与「消息通道」是可组合的通信机制：回调通过函数返回答复，消息通道通过独立消息传回答复，回调内部也可以使用消息通道。

如何选择方案取决于交互服务对接的下游提供什么接口：

- 下游通过函数返回答复 → 回调接入。
- 下游通过独立消息送回答复 → 消息通道接入。

#### 5.6.1 公共接口与交互语义

- 调用方通过 `send` 发送消息，不等待业务答复；
- 通过 `request` 发送请求并等待对应答复。

是否需要答复由调用方决定，不由消息类型决定。

`targetId` 用于定位交互对象；消息内容和答复可以是文本或结构化数据，由调用方与接收方约定。

```ts
import { randomUUID } from "node:crypto";

interface InteractionMessage {
  readonly targetId: string;
  readonly content: unknown;
}

type InteractionRequest = InteractionMessage;

interface PendingInteraction extends InteractionRequest {
  readonly requestId: string;
}

interface InteractionReply {
  readonly requestId: string;
  readonly value: unknown;
}

interface InteractionOptions {
  readonly timeoutMs: number;
  readonly signal?: AbortSignal;
}

interface InteractionBackend {
  send(message: InteractionMessage): Promise<void>;
  // signal 中止时必须结束等待、清理监听，并使 Promise 拒绝。
  request(
    request: PendingInteraction,
    signal: AbortSignal,
  ): Promise<InteractionReply>;
  dispose(): Promise<void>;
}

interface InteractionService {
  send(message: InteractionMessage): Promise<void>;
  request(
    request: InteractionRequest,
    options: InteractionOptions,
  ): Promise<InteractionReply>;
  dispose(): Promise<void>;
}

// 拥有 backend；关闭时取消等待，排空已接纳的操作，再关闭后端。
function createInteractionService(
  backend: InteractionBackend,
): InteractionService {
  const shutdown = new AbortController();
  const active = new Set<Promise<unknown>>();
  let closed = false;
  let disposal: Promise<void> | undefined;

  function run<T>(operation: () => Promise<T>): Promise<T> {
    if (closed) return Promise.reject(new Error("交互服务已关闭"));
    const result = Promise.resolve().then(operation);
    active.add(result);
    result.then(
      () => active.delete(result),
      () => active.delete(result),
    );
    return result;
  }

  return {
    send(message) {
      const snapshot = { ...message };
      return run(() => backend.send(snapshot));
    },
    request(request, options) {
      if (!Number.isInteger(options.timeoutMs) || options.timeoutMs <= 0) {
        return Promise.reject(new Error("交互等待时间必须为正整数"));
      }
      const snapshot = { ...request, requestId: randomUUID() };
      const timeoutMs = options.timeoutMs;
      const timeout = new AbortController();
      const signals = [shutdown.signal, timeout.signal];
      if (options.signal) signals.push(options.signal);
      const signal = AbortSignal.any(signals);

      return run(async () => {
        signal.throwIfAborted();
        const timer = setTimeout(
          () => timeout.abort(new Error("交互等待超时")),
          timeoutMs,
        );
        try {
          const reply = await backend.request(snapshot, signal);
          signal.throwIfAborted();
          if (reply.requestId !== snapshot.requestId) {
            throw new Error("交互答复与请求不对应");
          }
          return reply;
        } finally {
          clearTimeout(timer);
        }
      });
    },
    dispose() {
      closed = true;
      shutdown.abort(new Error("交互服务已关闭"));
      return (disposal ??= Promise.allSettled([...active]).then(() =>
        backend.dispose(),
      ));
    },
  };
}
```

- 无人应答时，由超时结束等待并报告错误；
- 取消、超时或关闭后，不再接受该请求的答复。

调用方决定是否重新询问、终止任务或采用其他处理方式。

#### 5.6.2 回调交互

宿主提供消息发送和请求处理回调，服务调用回调完成通信。

```ts
interface InteractionCallbacks {
  send(message: InteractionMessage): Promise<void>;
  // 宿主负责处理请求、返回答复，并在 signal 中止时结束等待。
  request(request: PendingInteraction, signal: AbortSignal): Promise<unknown>;
}

// 借用宿主回调，不负责关闭宿主界面。
function createCallbackInteractionBackend(
  callbacks: InteractionCallbacks,
): InteractionBackend {
  return {
    send: (message) => callbacks.send(message),
    async request(request, signal) {
      signal.throwIfAborted();
      const value = await callbacks.request(request, signal);
      signal.throwIfAborted();
      return { requestId: request.requestId, value };
    },
    async dispose() {},
  };
}

// 由宿主实现；send 分发消息，request 处理请求并返回答复。
declare const interactionCallbacks: InteractionCallbacks;
const callbackInteraction = createInteractionService(
  createCallbackInteractionBackend(interactionCallbacks),
);

try {
  console.log(
    await callbackInteraction.request(
      { targetId: "task-a", content: "请选择排查环境" },
      { timeoutMs: 30_000 },
    ),
  );
} finally {
  await callbackInteraction.dispose();
}
```

回调接入简单，但界面展示与取消等待由宿主实现；它也可以在内部使用消息通道。

#### 5.6.3 消息通道交互

请求与答复通过独立消息传递，后端用 `requestId` 找到对应的等待请求。
适合 Web、桌面应用或聊天机器人等分开发送请求与答复的场景。

```ts
type InteractionEnvelope =
  | { readonly type: "message"; readonly message: InteractionMessage }
  | { readonly type: "request"; readonly request: PendingInteraction }
  | { readonly type: "reply"; readonly reply: InteractionReply };

interface InteractionChannel {
  send(envelope: InteractionEnvelope): Promise<void>;
  // 通道负责验证外部消息，并向订阅者交付合法数据。
  subscribe(listener: (envelope: InteractionEnvelope) => void): () => void;
}

// 借用通道；拥有答复监听与本地等待表。
function createChannelInteractionBackend(
  channel: InteractionChannel,
): InteractionBackend {
  const waiting = new Map<
    string,
    { resolve(reply: InteractionReply): void; reject(error: unknown): void }
  >();
  const unsubscribe = channel.subscribe((envelope) => {
    if (envelope.type === "reply") {
      waiting.get(envelope.reply.requestId)?.resolve(envelope.reply);
    }
  });

  return {
    send: (message) => channel.send({ type: "message", message }),
    request(request, signal) {
      signal.throwIfAborted();
      return new Promise<InteractionReply>((resolve, reject) => {
        function finish(reply?: InteractionReply, error?: unknown) {
          if (!waiting.delete(request.requestId)) return;
          signal.removeEventListener("abort", onAbort);
          if (reply) resolve(reply);
          else reject(error);
        }
        function onAbort() {
          finish(undefined, signal.reason);
        }
        // 先登记等待，再发送，避免快速答复先于登记到达。
        waiting.set(request.requestId, {
          resolve: (reply) => finish(reply),
          reject: (error) => finish(undefined, error),
        });
        signal.addEventListener("abort", onAbort, { once: true });
        channel.send({ type: "request", request }).catch((error) => {
          finish(undefined, error);
        });
      });
    },
    async dispose() {
      unsubscribe();
      for (const pending of [...waiting.values()]) {
        pending.reject(new Error("交互通道后端已关闭"));
      }
    },
  };
}

// 由宿主提供已连接的通道；对端接收 request，返回同 requestId 的 reply。
declare const interactionChannel: InteractionChannel;
const channelInteraction = createInteractionService(
  createChannelInteractionBackend(interactionChannel),
);

try {
  await channelInteraction.send({
    targetId: "task-a",
    content: "暂停",
  });
  console.log(
    await channelInteraction.request(
      {
        targetId: "task-a",
        content: "暂停并确认处理结果",
      },
      { timeoutMs: 30_000 },
    ),
  );
} finally {
  await channelInteraction.dispose();
}
```

消息通道便于跨界面或进程通信，但需要维护消息协议、连接和对端处理器。宿主负责通道身份与权限校验，不以 `requestId` 代替授权。

### 5.7 权限服务 - 通用

权限服务根据可信身份、目标资源和操作，判断是否允许访问。

入口或认证机制负责确认身份，权限服务负责授权判断，调用方负责落实放行或拒绝。

- **授权内容**：哪个身份可以对哪些资源执行哪些操作，以及有效期等附加条件。
- **存在场景**：需要限制不同用户或执行主体的操作范围时，引入权限服务。
- **实现选择**：固定规则随代码发布；存储规则支持独立更新；已有统 1 权限系统时，通过接口接入。

在 Harness 中，模型与工具代某个身份执行，不能默认使用服务端全部权限。

启动任务不代表允许所有后续操作，应在具体操作和目标资源确定后检查权限；人工批准也不自动扩大原有授权范围。

重点检查场景包括：

- **上下文可见性**：是否允许指定内容进入模型请求，由上下文服务落实限制。
- **工具与目标资源**：是否允许调用指定工具、操作目标资源，由工具服务落实限制。
- **会话与记录**：是否允许查看历史、检索或导出记录，由会话与检索等服务落实限制。
- **任务控制**：是否允许发起任务、追加输入、暂停、终止或恢复指定任务，由执行服务落实限制。
- **Agent 管理**：是否允许创建、使用、修改或关闭指定 Agent，由 Agent 管理服务落实限制。
- **编排与委派**：是否允许创建后台任务、定时任务或委派其他执行主体，由编排服务落实限制；被委派主体不能自动获得委派方之外的权限。
- **配置与授权管理**：是否允许修改配置或调整指定身份的授权，由配置及授权管理的调用方落实限制。

#### 5.7.1 公共接口与权限语义

权限检查包含可信身份、资源类型、资源标识和操作。
资源标识应由资源所属服务确定，不能仅凭用户输入的路径或名称判断权限。

本例用明确授权表达规则：没有匹配授权或授权已经过期时拒绝；查询规则失败时报告错误，不按允许处理。
角色、资源归属等规则可以在内部扩展，不改变调用接口。

```ts
interface PermissionIdentity {
  readonly subjectId: string;
}

interface PermissionResource {
  readonly type: string;
  readonly id: string;
}

interface PermissionQuery {
  readonly resource: PermissionResource;
  readonly action: string;
}

interface PermissionScope {
  readonly resourceType: string;
  readonly resourceIds: readonly string[];
  readonly action: string;
}

interface PermissionDecision {
  readonly allowed: boolean;
}

interface PermissionBackend {
  // 只返回候选资源中有权执行指定操作的标识。
  allowedResourceIds(
    identity: PermissionIdentity,
    scope: PermissionScope,
  ): Promise<readonly string[]>;
}

interface PermissionService extends PermissionBackend {
  check(
    identity: PermissionIdentity,
    query: PermissionQuery,
  ): Promise<PermissionDecision>;
}

interface PermissionGrant {
  readonly subjectId: string;
  readonly resourceType: string;
  readonly resourceId: string;
  readonly action: string;
  // Unix 毫秒时间戳；省略表示没有时间限制。
  readonly expiresAt?: number;
}

interface PermissionRuleSource {
  // 按身份、资源类型、候选资源和操作查询，不读取该身份的全部授权。
  // 每次检查读取当前规则，不复用上次检查的结果。
  load(
    identity: PermissionIdentity,
    scope: PermissionScope,
  ): Promise<readonly PermissionGrant[]>;
}

// 固定规则和存储规则共用匹配逻辑，不支持隐含的通配授权。
function createRulePermissionBackend(
  source: PermissionRuleSource,
): PermissionBackend {
  return {
    async allowedResourceIds(identity, scope) {
      const grants = await source.load(identity, scope);
      const now = Date.now();
      const allowed = new Set(
        grants
          .filter(
            (grant) =>
              grant.subjectId === identity.subjectId &&
              grant.resourceType === scope.resourceType &&
              grant.action === scope.action &&
              (grant.expiresAt === undefined || grant.expiresAt > now),
          )
          .map((grant) => grant.resourceId),
      );
      return scope.resourceIds.filter((id) => allowed.has(id));
    },
  };
}

// 借用 backend，不拥有连接或监听，因此不提供资源关闭方法。
function createPermissionService(
  backend: PermissionBackend,
): PermissionService {
  async function allowedResourceIds(
    identity: PermissionIdentity,
    scope: PermissionScope,
  ): Promise<readonly string[]> {
    const snapshot = {
      ...scope,
      resourceIds: [...new Set(scope.resourceIds)],
    };
    if (!snapshot.resourceIds.length) return [];
    const allowed = new Set(
      await backend.allowedResourceIds({ ...identity }, snapshot),
    );
    // 结果不能扩大调用方指定的候选范围。
    return snapshot.resourceIds.filter((id) => allowed.has(id));
  }

  return {
    allowedResourceIds,
    async check(identity, query) {
      const ids = await allowedResourceIds(identity, {
        resourceType: query.resource.type,
        resourceIds: [query.resource.id],
        action: query.action,
      });
      return { allowed: ids.length > 0 };
    },
  };
}
```

`check` 判断单个资源，`allowedResourceIds` 筛选 1 组候选资源。
例如检索服务可以先取得候选会话标识，再获取允许检索的范围，之后才读取正文；它不是先读取全部正文再做权限过滤。

每次只查询本次判断所需的权限规则，不读取该身份的全部权限。
动态授权可能在 2 次检查之间变更，不适合做跨请求缓存；如需缓存，应明确有效期或授权变更时的失效机制，以及变更多久生效。

#### 5.7.2 固定规则

将授权关系写在代码中，初始化时保存独立副本，规则随应用发布更新。

```ts
function createFixedPermissions(
  grants: readonly PermissionGrant[],
): PermissionService {
  const saved = grants.map((grant) => ({ ...grant }));
  return createPermissionService(
    createRulePermissionBackend({
      async load(identity, scope) {
        return saved.filter(
          (grant) =>
            grant.subjectId === identity.subjectId &&
            grant.resourceType === scope.resourceType &&
            scope.resourceIds.includes(grant.resourceId) &&
            grant.action === scope.action,
        );
      },
    }),
  );
}

const fixedPermissions = createFixedPermissions([
  {
    subjectId: "user-a",
    resourceType: "session",
    resourceId: "session-a",
    action: "read",
  },
]);

// 由入口或认证机制提供可信身份，不直接采信请求中的 subjectId。
declare const permissionIdentity: PermissionIdentity;
const decision = await fixedPermissions.check(permissionIdentity, {
  resource: { type: "session", id: "session-a" },
  action: "read",
});
if (!decision.allowed) throw new Error("无权读取该会话");
// 由会话服务继续执行读取。
```

固定规则适合授权关系简单、变更不频繁的应用，接入成本低；修改规则需要重新发布或装配实例，不适合频繁管理授权。

#### 5.7.3 存储规则

规则保存在配置或数据库中，每次检查按身份、资源和操作读取当前相关授权；存储和规则写入由对应服务负责。

```ts
// 由配置或数据库适配器实现针对性查询，返回已解析、校验的当前授权。
// 这里只占位，不展开数据库查询、角色关联或缓存实现。
interface PermissionGrantStore extends PermissionRuleSource {}

function createStoredPermissions(
  store: PermissionGrantStore,
): PermissionService {
  return createPermissionService(createRulePermissionBackend(store));
}

// 宿主拥有存储实例及其连接，权限服务只借用读取能力。
declare const permissionGrantStore: PermissionGrantStore;
const storedPermissions = createStoredPermissions(permissionGrantStore);

const allowedSessions = await storedPermissions.allowedResourceIds(
  permissionIdentity,
  {
    resourceType: "session",
    resourceIds: ["session-a", "session-b"],
    action: "search",
  },
);
console.log(allowedSessions);
```

存储规则适合需要独立更新用户与资源授权的场景。
代价是每次检查依赖存储查询；引入缓存时，还需要明确授权变更何时生效。
这里不缓存规则，也不重新实现存储服务。

#### 5.7.4 外部权限服务

组织已有统 1 权限系统时，通过适配器调用它，不在本地重复维护授权规则。
外部系统可以内部采用角色或条件策略，只需转换为公共接口的结果。

```ts
// 应用适配接口，不是某个具体权限产品的 SDK。
interface ExternalPermissionClient {
  allowedResourceIds(
    identity: PermissionIdentity,
    scope: PermissionScope,
  ): Promise<readonly string[]>;
}

function createExternalPermissions(
  client: ExternalPermissionClient,
): PermissionService {
  return createPermissionService({
    allowedResourceIds: (identity, scope) =>
      client.allowedResourceIds(identity, scope),
  });
}

// 宿主负责连接、服务凭证、请求超时和响应校验。
declare const externalPermissionClient: ExternalPermissionClient;
const externalPermissions = createExternalPermissions(externalPermissionClient);

const toolDecision = await externalPermissions.check(permissionIdentity, {
  resource: { type: "tool", id: "readFile" },
  action: "invoke",
});
if (!toolDecision.allowed) throw new Error("无权调用该工具");
// 工具服务仍需检查具体目标文件的读取权限。
```

外部权限服务适合复用组织统 1 授权，减少重复规则维护；代价是网络延迟和服务可用性依赖。
请求失败应向调用方报告错误，不能降级为允许。

### 5.8 凭证服务 - 通用

凭证服务按标识提供访问外部服务所需的凭证，例如模型 API Key、访问令牌或数据库密码。
权限服务判断是否允许使用，凭证服务提供凭证，消费方负责将其用于实际请求。

- **存在场景**：只有少量固定凭证时，可以直接读取环境变量或受保护的配置文件；需要统 1 获取或接入集中管理时，再使用独立服务。
- **保护要求**：凭证不进入模型上下文、普通日志或工具返回内容，不与普通配置 1 起公开。
- **实现选择**：固定凭证从环境变量或配置文件读取；集中管理、刷新或轮换需求通过外部凭证系统接入。

#### 5.8.1 公共接口与使用规则

调用方携带可信身份和凭证标识获取凭证，服务先检查使用权限，再读取凭证。
凭证标识与实际来源的对应关系由宿主配置。

```ts
interface CredentialSource {
  // 未配置、已失效或读取失败时拒绝，不返回空值。
  get(credentialId: string): Promise<string>;
}

interface CredentialService {
  get(identity: PermissionIdentity, credentialId: string): Promise<string>;
}

// 借用权限服务和来源，不拥有需要关闭的资源。
function createCredentialService(
  permissions: PermissionService,
  source: CredentialSource,
): CredentialService {
  return {
    async get(identity, credentialId) {
      const decision = await permissions.check(
        { ...identity },
        {
          resource: { type: "credential", id: credentialId },
          action: "use",
        },
      );
      if (!decision.allowed) throw new Error("无权使用该凭证");
      const value = await source.get(credentialId);
      if (!value.trim()) throw new Error("凭证未配置有效值");
      return value;
    },
  };
}
```

消费方只将返回值用于目标服务的请求认证，不打印或向模型返回。
允许使用凭证不等于允许执行任意外部操作，具体操作仍需检查权限；读取失败也不应在错误信息中附带凭证正文。

#### 5.8.2 环境变量或配置文件

宿主将稳定的凭证标识映射到环境变量名或受保护的文件路径。
2 种来源共用获取接口，不将凭证文件混入普通配置的展示或导出。

```ts
import { readFile } from "node:fs/promises";

function createEnvironmentCredentials(
  names: Readonly<Record<string, string>>,
): CredentialSource {
  const mapping = new Map(Object.entries(names));
  return {
    async get(credentialId) {
      const name = mapping.get(credentialId);
      if (name === undefined) throw new Error("未配置该凭证来源");
      const value = process.env[name];
      if (value === undefined || !value.trim()) {
        throw new Error("环境变量中未配置有效凭证");
      }
      return value;
    },
  };
}

// 文件内容为 JSON 对象：键是凭证标识，值是凭证字符串。
function createFileCredentials(path: string): CredentialSource {
  return {
    async get(credentialId) {
      const text = await readFile(path, "utf8");
      let values: unknown;
      try {
        values = JSON.parse(text);
      } catch (error) {
        // 不转发解析器可能包含凭证正文的报错。
        throw new Error("凭证文件不是有效 JSON");
      }
      if (
        typeof values !== "object" ||
        values === null ||
        Array.isArray(values)
      ) {
        throw new Error("凭证文件必须为 JSON 对象");
      }
      if (!Object.hasOwn(values, credentialId)) {
        throw new Error("凭证文件未配置该凭证");
      }
      const value: unknown = Reflect.get(values, credentialId);
      if (typeof value !== "string" || !value.trim()) {
        throw new Error("凭证文件中未配置有效凭证");
      }
      return value;
    },
  };
}

const environmentCredentials = createEnvironmentCredentials({
  "model-api": "MODEL_API_KEY",
});
const fileCredentials = createFileCredentials("./private/credentials.json");

// 由宿主选择来源，并提供 5.7 的权限服务与可信身份。
declare const credentialPermissions: PermissionService;
declare const credentialIdentity: PermissionIdentity;
const credentials = createCredentialService(
  credentialPermissions,
  environmentCredentials, // 使用文件时替换为 fileCredentials。
);
const modelApiKey = await credentials.get(credentialIdentity, "model-api");
// 将 modelApiKey 交给模型客户端用于请求认证，不输出其值。
```

环境变量适合部署时注入，文件适合宿主维护固定凭证。
文件访问权限由宿主限制，不能提交到版本库；环境变量也不是自动安全的，不能随诊断信息 1 起输出。

本例每次获取都读取来源，不缓存凭证。
文件方案按需读取整个小文件，不支持自动刷新令牌；多份凭证的集中管理可交给外部系统。

#### 5.8.3 外部凭证系统

外部系统负责凭证存储、刷新或轮换，适配器按标识获取当前有效值；服务端连接、认证和请求超时由宿主维护。

```ts
// 应用适配接口，不是某个具体产品的 SDK。
interface ExternalCredentialClient {
  // 返回当前有效凭证；过期且无法刷新时拒绝。
  getCurrent(credentialId: string): Promise<string>;
}

function createExternalCredentials(
  client: ExternalCredentialClient,
): CredentialSource {
  return {
    get: (credentialId) => client.getCurrent(credentialId),
  };
}

// 宿主拥有客户端，负责响应校验及错误信息脱敏。
declare const externalCredentialClient: ExternalCredentialClient;
const managedCredentials = createCredentialService(
  credentialPermissions,
  createExternalCredentials(externalCredentialClient),
);
const managedApiKey = await managedCredentials.get(
  credentialIdentity,
  "model-api",
);
// 仅用于目标服务认证，不打印 managedApiKey。
```

外部系统适合已有集中管理或自动刷新、轮换需求的应用，代价是网络与服务可用性依赖。
获取失败直接报告错误，不自动改用其他身份或更高权限的凭证；消费方重新获取时才能拿到更新后的值，不会自动更新已经创建的客户端。

### 5.9 隔离服务 - 通用

隔离服务限制执行环境可访问的文件、网络和进程，以及可占用的计算资源，降低误操作或不可信代码对环境的影响。

- **存在场景**：执行不可信代码、允许执行 Agent 或用户提交的系统命令，或需要分隔不同任务的运行环境时，引入隔离机制。仅启动子进程不等于安全隔离。
- **限制范围**：明确可读写目录、网络访问、进程权限，以及 CPU、内存、GPU 等资源限制。具体能力取决于底层平台，不能默认所有平台都支持相同的限制；无法落实必要限制时，拒绝执行，不静默放宽。
- **实现选择**：本地沙箱限制当前设备上的执行；容器提供独立运行环境；已有远程执行平台时，通过外部服务接入。

隔离只覆盖受其管理的执行环境，不会自动约束绕过它运行的代码或同进程内的所有插件。

#### 5.9.1 公共接口与隔离语义

执行请求包含程序、参数和工作目录；隔离规则由应用装配方提供，不允许执行内容自行放宽限制。

本例明确指定文件、网络与资源范围，不继承宿主凭证或任意环境变量。

```ts
interface IsolatedRequest {
  readonly program: string;
  readonly args: readonly string[];
  readonly cwd: string;
}

interface IsolationPolicy {
  readonly files: {
    readonly readOnly: readonly string[];
    readonly readWrite: readonly string[];
  };
  readonly network: "deny" | "allow";
  readonly resources: {
    readonly cpuCores: number;
    readonly memoryMiB: number;
    readonly gpuDeviceIds: readonly string[];
  };
}

interface IsolatedResult {
  readonly exitCode: number;
  readonly stdout: string;
  readonly stderr: string;
}

interface IsolationBackend {
  // 先落实规则再启动；不支持必要限制时拒绝。
  // 隔离覆盖执行进程及其子进程；取消后终止执行并回收本次资源再拒绝。
  // 运行环境只保留基础运行依赖，不继承宿主秘密；输出大小由适配器限制。
  run(
    request: IsolatedRequest,
    policy: IsolationPolicy,
    signal: AbortSignal,
  ): Promise<IsolatedResult>;
}

interface IsolationService {
  run(request: IsolatedRequest, signal?: AbortSignal): Promise<IsolatedResult>;
  dispose(): Promise<void>;
}

// 借用后端；拥有本服务启动的执行，关闭时取消并等待它们结束。
function createIsolationService(
  backend: IsolationBackend,
  policy: IsolationPolicy,
): IsolationService {
  const saved: IsolationPolicy = {
    files: {
      readOnly: [...policy.files.readOnly],
      readWrite: [...policy.files.readWrite],
    },
    network: policy.network,
    resources: {
      ...policy.resources,
      gpuDeviceIds: [...policy.resources.gpuDeviceIds],
    },
  };
  const shutdown = new AbortController();
  const active = new Set<Promise<IsolatedResult>>();
  let closed = false;
  let disposal: Promise<void> | undefined;

  return {
    run(request, signal) {
      if (closed) return Promise.reject(new Error("隔离服务已关闭"));
      const snapshot = { ...request, args: [...request.args] };
      const combined = signal
        ? AbortSignal.any([signal, shutdown.signal])
        : shutdown.signal;
      const result = Promise.resolve().then(() => {
        combined.throwIfAborted();
        return backend.run(snapshot, saved, combined);
      });
      active.add(result);
      result.then(
        () => active.delete(result),
        () => active.delete(result),
      );
      return result;
    },
    dispose() {
      closed = true;
      shutdown.abort(new Error("隔离服务已关闭"));
      return (disposal ??= Promise.allSettled([...active]).then(() => {}));
    },
  };
}

// 示例规则由装配方确定；GPU 空列表表示禁止访问，不表示无限制。
const exampleIsolationPolicy: IsolationPolicy = {
  files: { readOnly: ["/workspace"], readWrite: ["/workspace/output"] },
  network: "deny",
  resources: { cpuCores: 2, memoryMiB: 512, gpuDeviceIds: [] },
};

// 三种接入机制共用同一调用示例。
async function demonstrateIsolation(service: IsolationService): Promise<void> {
  try {
    const result = await service.run({
      program: "python",
      args: ["script.py"],
      cwd: "/workspace",
    });
    console.log("退出码：", result.exitCode);
  } finally {
    await service.dispose();
  }
}
```

文件范围描述业务目录，基础运行依赖由后端单独提供；路径、挂载、规则值及程序可用性由适配器校验。
`network: "deny"` 表示禁止网络访问，`allow` 表示不施加网络访问限制。
GPU 列表只表达设备访问范围，不承诺算力比例或显存配额。

程序正常结束时返回退出码，非零退出码由调用方解释；隔离建立失败、取消或执行环境异常时拒绝 Promise。
超时可以由调用方通过取消信号触发。权限判断仍在执行前由调用方完成，隔离不是授权的替代。

#### 5.9.2 本地沙箱

本地沙箱适配器消费操作系统或成熟沙箱的限制能力，在当前设备启动受限执行，不用普通子进程冒充沙箱。

```ts
// 应用适配接口；具体沙箱实现负责满足 5.9.1 的执行要求。
interface LocalSandbox {
  execute(
    request: IsolatedRequest,
    policy: IsolationPolicy,
    signal: AbortSignal,
  ): Promise<IsolatedResult>;
}

function createLocalSandboxBackend(sandbox: LocalSandbox): IsolationBackend {
  return {
    run: (request, policy, signal) => sandbox.execute(request, policy, signal),
  };
}

// 由宿主提供已配置的沙箱；不在此处实现系统安全机制。
declare const localSandbox: LocalSandbox;
const localIsolation = createIsolationService(
  createLocalSandboxBackend(localSandbox),
  exampleIsolationPolicy,
);
await demonstrateIsolation(localIsolation);
```

适合任务需要在当前设备运行、使用指定本地资源的场景。
代价是不同平台的限制能力和配置方式可能不同，适配器必须确认所需规则可以落实，不能仅过滤命令字符串后直接执行。

#### 5.9.3 容器执行

容器适配器创建本次执行环境，将业务目录映射到容器路径，并落实网络与资源限制。
任务结束或取消后清理本次容器；是否保留写入目录中的结果由宿主决定。

```ts
interface ContainerExecutor {
  // image 由装配方选择；目录映射及容器创建、等待、清理由适配器负责。
  execute(
    image: string,
    request: IsolatedRequest,
    policy: IsolationPolicy,
    signal: AbortSignal,
  ): Promise<IsolatedResult>;
}

function createContainerBackend(
  executor: ContainerExecutor,
  image: string,
): IsolationBackend {
  return {
    run: (request, policy, signal) =>
      executor.execute(image, request, policy, signal),
  };
}

declare const containerExecutor: ContainerExecutor;
declare const executionImage: string;
const containerIsolation = createIsolationService(
  createContainerBackend(containerExecutor, executionImage),
  exampleIsolationPolicy,
);
await demonstrateIsolation(containerIsolation);
```

适合需要指定运行依赖、复用执行镜像或分隔多个任务环境的场景。
代价是镜像与容器运行设施的维护；不能默认容器启动后所有限制都已生效，也不能将宿主控制接口或无关敏感目录暴露给执行环境。

#### 5.9.4 外部隔离执行服务

通过外部平台启动隔离执行，适配器负责提交、等待结果，以及将取消通知转为远端终止操作。
只停止本地等待不等于取消远端执行。

```ts
// 应用适配接口，不是某个产品 SDK；远端可以使用沙箱或容器。
interface RemoteIsolationClient {
  // policy 中的目录是远端业务路径，材料传输与路径映射由适配器负责。
  // 取消时须确认远端执行终止；无法确认时报告未知状态，不声称已回收。
  execute(
    request: IsolatedRequest,
    policy: IsolationPolicy,
    signal: AbortSignal,
  ): Promise<IsolatedResult>;
}

function createRemoteIsolationBackend(
  client: RemoteIsolationClient,
): IsolationBackend {
  return {
    run: (request, policy, signal) => client.execute(request, policy, signal),
  };
}

// 宿主负责安全连接、服务认证、请求超时和响应校验。
declare const remoteIsolationClient: RemoteIsolationClient;
const remoteIsolation = createIsolationService(
  createRemoteIsolationBackend(remoteIsolationClient),
  exampleIsolationPolicy,
);
await demonstrateIsolation(remoteIsolation);
```

适合已有集中执行平台、需要远端运行环境的场景，代价是材料传输、网络延迟及平台可用性依赖。
连接中断不代表远端任务未执行，调用方不能直接重试有副作用的操作，应通过平台能力确认执行状态。

3 种示例只展示接入方式，真实限制由所注入的适配器落实。
服务借用这些适配器，不关闭宿主共享的沙箱设施、容器运行时或远端客户端；远端接入也不是独立于沙箱、容器之外的新隔离原理。

### 5.10 模型服务 - 通用

模型服务接收已经组装好的消息和调用参数，调用实际 Provider，将响应转换成统 1 的文本、工具调用及用量信息。
不负责选取上下文、执行工具或推进任务循环。

- **存在场景**：需要统 1 模型调用、流式输出或替换 Provider 时，使用独立服务；简单的 1 次性调用也可以直接消费 SDK。
- **统 1 内容**：消息、工具声明、调用参数、响应事件和错误分类。模型输出中的工具调用只是请求，不代表工具已执行。
- **接入方式**：网络传输与协议处理使用成熟 SDK，适配器处理 Provider 差异；不支持的参数或消息形式应明确报错，不静默忽略。

#### 5.10.1 公共接口与调用语义

调用方提供完整消息，模型服务不改写原始用户输入。
工具调用与工具结果通过调用标识关联；工具参数在接收完整响应后解析，具体参数校验由工具服务负责。

```ts
interface ModelToolCall {
  readonly id: string;
  readonly name: string;
  readonly arguments: unknown;
}

type ModelMessage =
  | { readonly role: "system" | "user"; readonly content: string }
  | {
      readonly role: "assistant";
      readonly content: string;
      readonly toolCalls?: readonly ModelToolCall[];
    }
  | {
      readonly role: "tool";
      readonly toolCallId: string;
      readonly content: string;
    };

interface ModelTool {
  readonly name: string;
  readonly description: string;
  readonly parameters: Readonly<Record<string, unknown>>;
}

interface ModelRequest {
  readonly model: string;
  readonly messages: readonly ModelMessage[];
  readonly tools?: readonly ModelTool[];
  readonly temperature?: number;
  readonly maxOutputTokens?: number;
}

interface ModelUsage {
  readonly inputTokens: number;
  readonly outputTokens: number;
}

type ModelFinishReason = "stop" | "tool-calls" | "length" | "other";

type ModelEvent =
  | { readonly type: "text"; readonly delta: string }
  | { readonly type: "tool-call"; readonly call: ModelToolCall }
  | {
      readonly type: "finish";
      readonly reason: ModelFinishReason;
      readonly usage?: ModelUsage;
    };

interface ModelResult {
  readonly text: string;
  readonly toolCalls: readonly ModelToolCall[];
  readonly finishReason: ModelFinishReason;
  readonly usage?: ModelUsage;
}

interface ModelProvider {
  // 正常结束恰好返回一个 finish；失败抛错，不用 finish 掩盖中断。
  // signal 取消或消费方提前退出迭代时，结束请求并清理响应流。
  // 工具参数碎片在适配器内部汇总，解析后才发出完整 tool-call。
  stream(
    request: ModelRequest,
    signal?: AbortSignal,
  ): AsyncIterable<ModelEvent>;
}

interface ModelService extends ModelProvider {
  complete(request: ModelRequest, signal?: AbortSignal): Promise<ModelResult>;
}

// Provider 适配器将 SDK 错误转换为此类型，不在消息中包含凭证。
class ModelCallFailure extends Error {
  constructor(
    message: string,
    readonly retryable: boolean,
    readonly retryAfterMs?: number,
  ) {
    super(message);
  }
}
```

用量信息取决于 Provider 是否提供，缺失时不编造；`length` 表示达到输出限制，不等于任务已经完成。
工具参数使用 `unknown`，避免将模型生成的数据当作已校验的业务参数。

#### 5.10.2 Provider 接入

每个 Provider 用适配器转换 SDK 请求、响应与错误。

本例只展示接入职责，不展开某个厂商的协议字段。

```ts
interface ModelSdkAdapter {
  // 适配器内部调用 SDK，并转换为 5.10.1 的统一事件。
  // 不支持的请求明确拒绝；工具参数解析失败作为调用失败报告。
  stream(
    request: ModelRequest,
    credential: string,
    signal?: AbortSignal,
  ): AsyncIterable<ModelEvent>;
}

// 借用凭证服务与 SDK 适配器，不拥有客户端连接。
function createSdkModelProvider(
  sdk: ModelSdkAdapter,
  credentials: CredentialService,
  identity: PermissionIdentity,
  credentialId: string,
): ModelProvider {
  const savedIdentity = { ...identity };
  return {
    async *stream(request, signal) {
      signal?.throwIfAborted();
      const credential = await credentials.get(savedIdentity, credentialId);
      signal?.throwIfAborted();
      yield* sdk.stream(request, credential, signal);
    },
  };
}
```

凭证复用 5.8，服务地址、客户端及其资源释放由应用装配方管理。
更换 Provider 时替换适配器，上游接口保持不变，但不承诺所有模型具有相同能力或参数范围。

#### 5.10.3 流式响应与取消

流式调用逐步返回事件，非流式调用收集同 1 组事件并返回完整结果。

工具参数可能分多段到达，但本例不向上游暴露尚未完整的调用。

```ts
// 借用 Provider；请求由调用方取消，客户端由宿主关闭。
function createModelService(provider: ModelProvider): ModelService {
  async function* stream(
    request: ModelRequest,
    signal?: AbortSignal,
  ): AsyncIterable<ModelEvent> {
    signal?.throwIfAborted();
    // 在开始迭代时复制请求，避免传输期间被调用方修改。
    const snapshot = structuredClone(request);
    let finished = false;
    for await (const event of provider.stream(snapshot, signal)) {
      signal?.throwIfAborted();
      if (finished) throw new ModelCallFailure("模型结束后仍返回事件", false);
      if (event.type === "finish") finished = true;
      yield event;
    }
    signal?.throwIfAborted();
    if (!finished) throw new ModelCallFailure("模型响应未完整结束", false);
  }

  return {
    stream,
    async complete(request, signal) {
      let text = "";
      const toolCalls: ModelToolCall[] = [];
      let finishReason: ModelFinishReason = "other";
      let usage: ModelUsage | undefined;
      for await (const event of stream(request, signal)) {
        switch (event.type) {
          case "text":
            text += event.delta;
            break;
          case "tool-call":
            toolCalls.push(event.call);
            break;
          case "finish":
            finishReason = event.reason;
            usage = event.usage;
            break;
        }
      }
      return { text, toolCalls, finishReason, usage };
    },
  };
}

// 由装配方提供 5.10.2 的 Provider。
declare const modelProvider: ModelProvider;
const modelService = createModelService(modelProvider);
const modelRequest: ModelRequest = {
  model: "configured-model",
  messages: [
    { role: "system", content: "根据用户要求回答，不编造已确认的事实。" },
    { role: "user", content: "解释什么是依赖注入。" },
  ],
};

const modelCancellation = new AbortController();
for await (const event of modelService.stream(
  modelRequest,
  modelCancellation.signal,
)) {
  if (event.type === "text") process.stdout.write(event.delta);
}
// 用户取消时调用 modelCancellation.abort()。
// 不需要流式展示时，改用 await modelService.complete(modelRequest)。
```

取消不是返回空结果或伪造正常结束，而是结束请求并报告中断。已经展示的文本不会自动撤回，调用方应明确标记未完成；会话记录和后续执行由对应服务维护。

#### 5.10.4 调用失败与重试

适配器根据实际 SDK 错误分类，决定是否允许重试；取消、无效参数和凭证错误不自动重试。重试次数与等待时间由装配方设置，不在调用逻辑中写死。

```ts
import { setTimeout as waitModelRetry } from "node:timers/promises";

interface ModelRetryOptions {
  readonly maxAttempts: number; // 包含首次请求。
  readonly delayMs: number;
}

function createRetryingModelProvider(
  provider: ModelProvider,
  options: ModelRetryOptions,
): ModelProvider {
  const { maxAttempts, delayMs } = options;
  if (
    !Number.isInteger(maxAttempts) ||
    maxAttempts < 1 ||
    !Number.isFinite(delayMs) ||
    delayMs < 0
  ) {
    throw new Error("模型重试配置无效");
  }
  return {
    async *stream(request, signal) {
      const snapshot = structuredClone(request);
      for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        signal?.throwIfAborted();
        let emitted = false;
        try {
          for await (const event of provider.stream(snapshot, signal)) {
            signal?.throwIfAborted();
            emitted = true;
            yield event;
          }
          return;
        } catch (error) {
          signal?.throwIfAborted();
          if (
            emitted ||
            !(error instanceof ModelCallFailure) ||
            !error.retryable ||
            attempt === maxAttempts
          ) {
            throw error;
          }
          await waitModelRetry(error.retryAfterMs ?? delayMs, undefined, {
            signal,
          });
        }
      }
    },
  };
}

declare const modelRetryOptions: ModelRetryOptions;
const retryingModelService = createModelService(
  createRetryingModelProvider(modelProvider, modelRetryOptions),
);
```

只有尚未向上游返回任何事件且错误允许重试时，才重新发起请求。一旦已有输出就交回调用方处理，不自动重放文本或工具调用。即使尚未收到事件，Provider 也可能已经处理或计费，重试不保证原请求没有发生。

超时由 SDK 或调用方的取消信号控制；失败不自动切换到其他模型或更高权限的凭证。上述示例验证服务的组织方式，实际网络调用、响应解析与连接清理由所注入的 SDK 适配器负责。

## 7、验证与评估

Harness 的行为正确，不等于 Agent 能稳定完成任务。

行为验证检查执行机制是否符合约定，效果评估衡量任务质量、成本和失败率。

### 7.1 模型输入与执行记录

固定会话记录，验证上下文组装后实际提交的模型输入。

裁剪、摘要、工具结果和用户交互都需要覆盖，检查必要信息是否保留、来源是否可重建。

重放可以验证记录解释和输入组装，不代表再次调用模型会得到相同结果。

### 7.2 执行控制与安全限制

通过真实入口触发输入、取消、超时和批准，检查各执行主体的状态变化。

验证取消后不再启动新的关联工作，并按约定终止或收敛已经启动的调用。

对拒绝、批准过期和越权请求，检查受限制的操作是否实际被阻止，而不只检查判断结果。

资源释放后，还要检查是否遗留进程、监听器或继续访问已释放资源的回调。

### 7.3 持久化、恢复与兼容性

在 Tool 完成、权威记录提交和派生索引更新等阶段注入失败，验证恢复行为。

检查已确认结果是否保留、派生数据能否重建，以及恢复是否误触发重复的外部副作用。

无法确认的操作结果，需要验证系统会标记未知并停止依赖它的后续工作。

配置、协议或持久格式变化时，用旧配置、旧调用方和已保存会话检查兼容范围内的正常处理，以及不兼容情况的明确拒绝。

### 7.4 执行预算与资源增长

在长会话、连续 Tool 调用、并发委派和大输出场景下，观察耗时、模型用量、内存与进程数量。

触发执行预算和输出限制，检查停止条件、返回信息与资源清理是否符合约定。

重复运行后，还要检查资源是否持续累积，而不只看单次执行峰值。

### 7.5 Agent Evaluation：任务质量与回归

Agent Evaluation 衡量任务结果、过程成本和失败类型，而不只比较最终文本。

评估集需要覆盖代表任务、风险场景和历史回归，并固定评分规则与运行条件。

模型存在随机性时，应报告分布、重复次数和置信范围，避免把单次结果当作稳定结论。

更换模型、调整指令、上下文策略或工具组合后，比较同一评估集上的质量、成本和失败率，再判断是否接受改动。
