• 开始这部分。先给主链路骨架。

一句话

> Agent 主链路就是 ReactLoopAgent 把 inbox 里的输入，推进成 turn / step，组装
> prompt，请求 LLM，执行 tool，把关键事实写进 SessionEvent log，然后决定结束 turn 还
> 是进入下一 step。

完整流程：

用户输入
-> agent.followup / steer / inject
-> inbox
-> wakeDriver
-> turn()
-> preStep()
-> step()
-> buildRequest()
-> LLM stream
-> assistant message
-> tool calls
-> tool results
-> next step or turn end

对应源码主入口：

packages/core/agent-loop/src/agent.ts

## 1. 用户输入 -> inbox

外部不会直接跑模型，而是先提交输入：

agent.followup(message)
agent.steer(message)
agent.inject(message)

区别：

followup
放入 next-turn，并唤醒 driver。

steer
放入 next-step，并唤醒 driver。

inject
放入 next-step，不唤醒 driver。

底层都走：

send(message, target, wakeup)

然后：

this.inbox.splice(...)

Inbox 会把变化写进 session：

agent/inbox/spliced

所以 pending 输入本身也是 durable 的。

## 2. inbox -> driver

如果 wakeup 是 true：

wakeDriver()

它会把 agent 状态从：

idle -> running

然后调用：

kick()

kick() 做的事很简单：

while (await this.turn()) {}

也就是：

> 只要还有 pending 输入，就继续跑 turn。

## 3. turn

turn() 表示一轮完整任务。

开始时写：

turn/start

结束时一定写：

turn/end

中间可能有：

0 个 step
1 个 step
多个 step

0 个 step 的情况：

pre-step 拒绝
第一批输入为空

## 4. preStep

preStep() 做三件事：

1. 从 inbox claim 输入
2. 组装 system prompt / tool schemas
3. 触发 agent/pre-step waterfall

关键点：

agent/pre-step 可以决定：
reject
enter(messages)

也就是说，模型真正能看到哪些 user messages，不是 inbox 原样进入，而是经过 pre-step 决
策。

## 5. step

step() 表示一次模型请求。

开始时写：

step/start

结束时写：

step/end

step 内部做：

1. render system prompt
2. session.deriveMessages()
3. buildRequest()
4. llm.stream()
5. 写 assistant/chunk
6. 汇总 assistant/message
7. 发现 tool-call 则执行工具

## 6. buildRequest

buildRequest() 负责构造最终 LLM 请求。

它会：

1. 从 agent options 得到 provider/model
2. 触发 agent/request waterfall
3. 调 ctx.llm.prepareCall()
4. 生成 request/header
5. 生成 request/context
6. 构造 GenerateOptions

重要：

request/header

会记录这次请求的：

config
system prompt
tool schemas
adapter defaults

这就是 model-visible means logged 的关键部分。

## 7. LLM stream

请求模型：

ctx.llm.stream(request)

模型流式返回 chunk。

每个 chunk 写：

assistant/chunk

流结束后汇总成：

assistant/message

assistant/chunk 用于 replay / UI fidelity。
assistant/message 用于 deriveMessages，进入后续模型历史。

## 8. tool execution

如果 assistant message 里有 tool-call block：

tool/call\*

交给：

executeToolCalls()

位置：

packages/core/agent-loop/src/tool-calls.ts

每个 tool call 会：

1. 写 tool/call
2. ctx.tools prepare / dispatch / finalize
3. 写 tool/result
4. additionalContexts 放进 next-step inbox

工具执行事件链：

tools/pre-execute
tools/execute
tools/post-execute

最后：

tool/result

会成为下一次模型请求可见的消息。

## 9. next step / turn end

工具执行后有两种：

没有 next-step 输入
-> agent/turn-stopping
-> turn/end

有 next-step 输入
-> 开下一 step

所以工具结果会触发下一次模型请求：

step 1: 模型请求 tool
step 1: tool/result 写入 next-step
step 2: 模型看到 tool result 后继续回答

## 10. session log -> UI / next request

所有关键事实都写进 SessionEvent log：

turn/start
agent/inbox/spliced
step/start
user/message
request/header
assistant/chunk
assistant/message
tool/call
tool/result
step/end
turn/end

后续用途：

UI
读 session/event 渲染聊天和工具卡片。

next request
session.deriveMessages() 推导下一次 LLM messages。

resume/fork/replay
都从 session log 还原。

最短总结：

inbox 管待处理输入
turn 管一轮任务
step 管一次模型请求
request/header 记录模型可见配置
assistant/chunk 记录流式过程
assistant/message 进入模型历史
tool/call 记录模型工具请求
tool/result 进入模型历史
SessionEvent log 是主链路事实源
