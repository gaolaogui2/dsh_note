# Harness 运行机制

[打开单张运行机制图](<-3. harness-architecture.html>)。顶部是用户交互，左侧是运行时控制循环，右侧展开上下文、模型、工具和子运行，底部是 Base。灰线表示控制流，蓝线表示能力调用或状态读写，虚线表示反馈、重试或可选路径；菱形标出分支条件。

图中采用常见的工具调用型 Agent 循环，具体字段用于说明数据如何传递。Harness 可以采用不同模型协议、状态存储和扩展机制；Workflow 可以替换部分决策步骤。此图关注运行主体、输入输出和状态变化。

## 核心运行路径

| 步骤 | 发起者及处理 | 产出与下一步 |
| --- | --- | --- |
| 接收输入 | 运行时创建或恢复一次运行，写入用户输入、目标、有效约束及交付要求 | 更新运行状态，检查本轮是否可运行 |
| 检查运行条件 | 检查取消、剩余预算及等待条件 | 可运行则继续；缺少输入则挂起；取消或预算耗尽则记录停止原因 |
| 构造请求 | 从运行状态读取历史、最新观察和任务信息，调用上下文构造能力 | 返回本轮模型输入；预算失败则阻塞本次调用并报告原因 |
| 调用模型 | 模型适配器转换请求及响应；运行时校验并解释响应 | 候选答案进入验收，工具调用意图进入行动准入；错误按策略有限重试或停止 |
| 行动准入 | 按工具名称解析实现，校验参数，检查权限、审批及执行预算 | 允许则分派；需审批则保存待执行行动并挂起；非法或拒绝的请求生成错误观察 |
| 行动执行 | 调度器调用工具实现，或创建带有目标、输入和预算的子运行 | 返回关联到原调用的观察、错误、产物引用或结果未知状态 |
| 记录观察 | 写入工具结果、子任务结果或验收发现的缺口，更新任务进度 | 确认更新后重新检查运行条件；下一轮请求读取这些新观察 |
| 验收与交付 | 按任务要求检查答案、证据和产物 | 满足要求则记录完成并交付；未满足则把缺口作为观察继续补充，或请求人工 |

运行策略决定循环的选择规则和停止条件。计划是可修订的任务状态，生命周期管理贯穿整个运行。模型输出表示候选答案或行动意图；实际权限判定、调用和资源释放由运行时及执行环境负责。

## 数据如何进入下一次模型请求

典型请求由指令、当前任务、相关历史、已保留观察和工具描述组成。典型模型输出可以包含答案，或 `tool_calls[{id, name, args}]`。运行时用 `name` 定位工具，用 `args` 发起操作，并保留调用 `id`。

工具返回 `{tool_call_id, status, content, artifactRefs}` 一类结果。运行时通过 ID 将结果关联到请求，区分成功、错误和外部结果未知，写入运行状态。下一轮请求构造时重新选择这些信息；大型产物可以只保留引用，并按需读取。不同模型协议对消息格式及工具调用配对有各自要求。

运行状态包含输入与事件、任务进度、有效约束、上下文视图、工具观察、产物引用、待审批行动和子任务关系。它与模型当前看到的输入有不同用途：完整运行记录用于追溯和恢复，本轮输入只包含被选中的部分。需要恢复的状态由 Base 中的存储实现承载。

## 上下文预算与长对话

上下文构造先选择有效信息，再检查输入和输出预留是否满足模型窗口约束。超限时可以检索替代全量资料、外置过长工具结果、摘要旧历史，并保留有效目标、约束、工具调用配对及必要证据引用。处理后重新估算；无进展或达到处理上限则返回阻塞原因，避免继续发送无法被接受的请求。

压缩产生的上下文视图及其来源应按任务追溯、恢复需求保留。摘要可能丢失信息，需要验证关键约束和证据是否仍可用。低于 token 上限也可能出现目标遗漏，因此每轮还要选择相关历史、处理过期信息并保留当前有效目标。

## 权限、审批与失败

准入检查发生在具体行动执行之前。工具名称不存在、参数非法或权限拒绝时，运行时生成可解释的错误观察，供后续决策使用。需人工审批时，保存准确的行动与参数并挂起；收到决定后重新检查，避免等待期间状态变化造成误执行。

模型调用失败可以按策略有限重试，并计入预算。工具执行失败要结合副作用判断：已执行、未执行和结果未知必须区分；结果未知时先确认外部状态，再决定重试、去重或补偿。恢复检查点不代表外部操作可以安全重放。

取消、超时和预算限制贯穿等待、模型调用、工具执行和子运行。运行时向仍在执行的工作传播取消并协调收尾；外部系统可能继续执行已经接收的操作，需要保留其状态并确认结果。

## 多 Agent 的实际执行

调度器创建子运行时，指定 `parentId / childId`、目标、输入、权限和预算。每个子运行拥有自己的上下文及控制循环，并分别调用模型与工具。父运行接收带有归属的结果和产物，再将其写入父任务的观察记录。

图中 Agent A 与 Agent B 是并列的执行主体。协作协议决定它们何时交换消息或产物、怎样交接，以及如何汇合结果。父任务负责子任务状态、失败处理和取消传播；共享资源的并发写入需要额外协调。

辩论可以采用独立作答、交换质疑、补充证据、修订和裁决的循环。图中的反馈线表示存在分歧且轮数允许时继续审查；裁决需要依据证据和任务验收标准，并保留未解决的分歧。达到轮数或预算上限时返回当前结果及其限制。是否提高准确性，应对照单 Agent 的准确性、共同错误、成本和时延验证。

## Base 与具体执行点

| 基础能力 | 实际使用位置 |
| --- | --- |
| 存储与产物 | 接收输入时写入事实；请求构造时读取；行动结束时记录观察；挂起与恢复时保存和读取待执行状态 |
| 运行时资源 | 每轮预算检查、模型和工具的超时、并发调度、子运行管理、取消传播及资源释放 |
| 身份、权限与隔离 | 行动准入点读取身份与策略，审批后重新检查，执行环境落实实际隔离 |
| 观测与评估 | 用运行、调用、子任务 ID 关联事件与消耗，记录状态变化，并按任务要求验证证据和产物 |

Skill 提供任务方法和资源，通过上下文加载和工具执行参与运行。MCP 的 Tools、Resources、Prompts 分别接入相应执行或上下文能力。插件、依赖注入和独立服务都是这些职责的实现选择。
