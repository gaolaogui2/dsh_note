# DeepSeek Harness 主链路

## 第 1 条链路：从启动配置到 Plugin Tree

这部分回答问题：执行 `dsh --profile web` 后，静态配置如何变成运行中的 Harness。下面从 2 个视角描述同 1 条启动链：

```text
配置关系视角
Static Profile + 外部 Patch Layers
→ Composed Profile

实际调用视角
创建 Cordis Runtime
→ 安装 Loader / Include
→ 在内存中组合 Composed Profile
→ Plugin Fibers
→ Runtime Plugin Tree
```

配置关系视角说明各配置概念如何形成最终结果，不表示代码调用顺序。
实际调用视角说明启动代码如何先建立加载基础设施，再组合配置并挂载 Plugins。

### 配置关系：从 Static Profile 到 Composed Profile

| 关键词              | 定义                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Plugin              | Runtime 中实际运行的功能单元。Session、Agent、LLM、Tool、Filesystem 和 Web Server 等能力都由 Plugin 提供。               |
| Plugin Entry        | 1 个 Plugin 在静态配置树中的装载声明，包含 `id`、`name`、`config`、`disabled` 和可选 `inject`。                          |
| Patch               | 对 Plugin Entry 的 1 条插入、修改或禁用指令。                                                                            |
| Patch Layer         | 来自同 1 配置来源、处于同 1 优先级的 1 组 Patches。                                                                      |
| Bundle              | 针对某类需求或能力的标准化 Plugin 组合。它通过依赖引入所需 Plugin 实现，并通过 `cordis.patch.yml` 提供预设 Patch Layer。 |
| Static Profile      | 针对某个运行场景的基础解决方案：选择并排序若干 Bundles，并提供 Profile 自身的自定义 Patch Layer。                        |
| Profile Patch Layer | 使用者针对单个 Static Profile 的自定义层，保存在该 Profile 的 `cordis.patch.yml`。                                       |
| Global Patch Layer  | 对本机所有 Profiles 生效的统一覆盖层，保存在 `$DSH_HOME/cordis.patch.yml`，优先级高于 Profile Patch Layer。              |
| CLI Patch Layer     | 通过 `--patch` 为本次启动临时追加的覆盖层，按命令行顺序应用。                                                            |
| Composed Profile    | Bundle、Profile、Global、CLI 和启动器等 Patch Layers 按优先级应用后形成的最终 Plugin Tree 配置。                         |
| Loader              | 消费 Composed Profile 的 Plugin Entries，导入并挂载 Plugins，最终构建 Harness Runtime Plugin Tree。                      |

**Plugin Entry**

Plugin Entry 是 1 个 Plugin 在配置树中的静态配置，常见字段包括：

```yaml
id: session
name: "@deepseek-ai/dsh-session"
config: {}
disabled: false
```

`id` 标识配置树中的条目，`name` 指定要加载的 Plugin，`config` 提供配置，`disabled` 决定是否启用。

Entry 还可以通过 `inject` 声明激活所需的 Service ：

| 写法                                                                            | 适用场景                                                                                                          |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Plugin 内：`export const inject`（函数/对象）或 `static inject`（类/`Service`） | Plugin 的固有依赖。2 种写法仅适配不同实现形式。                                                                   |
| Entry 中的 `inject: [webStartup]`                                               | 仅当前部署组合需要的附加依赖，例如要求某个场景启动信号出现后再激活。Loader 会将它与 Plugin 自带的 `inject` 合并。 |
| `ctx.inject(['fs'], callback)`                                                  | 一个 Plugin 内只有局部逻辑依赖某项 Service；依赖可用时运行 callback，依赖消失时卸载，恢复后重新运行。             |

```text
Plugin 自带 inject
+ Entry inject
→ 合并为 Fiber 的必需依赖
→ 全部可见后 Fiber 才能激活
```

数组形式只列出 Service 名。对象形式将 Service 名映射为该 Service 的 intercept 配置；
2 者声明的都是必需依赖，不表示“可选”。
如果 Plugin 可以在缺少某项能力时继续运行，就不要声明 `inject`，而是在使用处通过 `ctx.get('serviceName')` 检查该 Service 是否存在。

```ts
// 只声明依赖
export const inject = ["loader"];

// 声明依赖，并配置当前 Plugin 如何使用该 Service
export const inject = {
  loader: { await: true },
};
```

`await: true` 表示 Loader 的 Entries 仍在加载时，当前 Plugin 保持 Pending。
这是 Consumer 针对该 Service 的局部使用配置，不是 Service 的初始化配置；
只有 Service 定义了 intercept 配置时才使用对象形式。

**Patch**

Patch 是对 Plugin Tree 配置的 1 条修改指令，
可以插入新的 Plugin Entry，也可以按 `id` 修改或禁用已有 Entry。

```yaml
# 插入 Plugin Entry
- insert:
    - id: session
      name: "@deepseek-ai/dsh-session"

# 修改已有 Plugin Entry
- id: hmr
  disabled: true
```

**Bundle**

Bundle 是可发布、可复用的 Plugin 配置组合。
1 个 Bundle 通过 `cordis.patch.yml` 提供 Patch 列表，该列表在 Profile 组合过程中形成 1 个 Patch Layer。

```text
从发布单元看：Bundle 是 1 个 package
从配置组合看：Bundle 提供 1 个 Patch Layer
从文件内容看：cordis.patch.yml 是 Patch 列表
```

`base` 就是 1 个 Bundle，也是官方 Profile 使用的基础 Patch Layer。
它主要通过 `insert` 加入 Session、Agent、LLM、Tools、Filesystem、Shell 等共享 Plugin Entry。

`base` 不是 Profile，也不是 Cordis 强制加载的内置层。
官方 `web` 和 `headless` Profile 都选择它；自定义 Profile 可以不使用它，但需要自行组装所需的 Agent Runtime 插件。

**Static Profile**

Static Profile 是 Patch Layers 的基础组合声明，位于 `$DSH_HOME/profiles/<name>`。

```text
Static Profile
├── package.json
│   └── dsh.profile.bundles：声明并排序 Bundle Patch Layers
└── cordis.patch.yml
    └── 提供这个 Profile 自己的用户 Patch Layer
```

例如，静态 Web Profile 声明使用 `base` 和 `web-app` 2 个 Bundle，并可以通过自己的 `cordis.patch.yml` 覆盖它们。

Static Profile 不是若干 Patch Layer 已经合并后的结果；
它负责声明基础组合方案，并提供其中 1 个修改层。
全局用户 Patch、命令行 `--patch` 和启动器强制 Patch 位于 Static Profile 之外。

**配置链的最短关系**

```text
Plugin 实现
→ Bundle 将 1 组 Plugins 标准化为某类需求或能力方案
→ Static Profile 将若干 Bundles 组合为场景基础方案
→ 用户通过 Profile / Global / CLI Patch Layers 定制预设方案
→ 启动器强制 Patch 完成最终约束
→ 得到 Composed Profile
→ Loader 将 Plugin Entries 挂载为 Harness Runtime Plugin Tree
```

Profile Patch Layer 就是当前 Profile 的用户自定义层。
Global Patch Layer 用于本机统 1 覆盖，
CLI Patch Layer 用于本次启动的临时覆盖。
Patch 本身只修改静态配置；需要加入运行逻辑时，用户通过 Patch 插入自定义 Plugin，再由 Loader 挂载执行。

### 实际调用：从 Cordis Runtime 到 Plugin Tree

| 关键词        | 定义                                                                                |
| ------------- | ----------------------------------------------------------------------------------- |
| Context       | Plugin 访问当前 Services、Events 和运行元数据的作用域视图。                         |
| Root Context  | 1 套 Cordis Runtime 的根；持有共享基础设施并派生 Child Contexts。                   |
| Child Context | 从父 Context 派生的视图，可以继承能力，也可以通过 isolate 改变 Service 解析作用域。 |
| Service       | Plugin 通过 Context 提供和调用的具名能力。                                          |
| Provider      | 实现并注册某项 Service 的 Plugin 角色。                                             |
| Consumer      | 依赖并使用某项 Service 的 Plugin 角色。                                             |
| inject        | Plugin 的 Service 激活依赖；依赖未满足时 Fiber 保持 Pending。                       |
| Reflect       | 维护 Service 可见性，并在 Service 变化时重新判断相关 Fibers 能否激活。              |
| Event         | Context 间共享的通知或处理链扩展机制。                                              |
| Fiber         | 1 次 Plugin 挂载对应的生命周期节点，记录父子关系、状态和所拥有的 Effects。          |
| Effect        | 绑定到 Fiber 的可撤销注册或资源；Fiber 卸载时统 1 清理。                            |

#### Cordis Runtime 最小结构

理解 Loader 之前，需要先知道它将 Plugin Entry 加载到什么系统中。
Cordis 是 1 个插件运行内核，最小结构包括：

```text
Cordis Runtime
├── Context：插件访问当前运行时的视图
├── Plugin：被挂载的功能定义
├── Service：插件提供和依赖的能力
├── Event：通知、扩展点和处理链
├── Fiber：1 次 Plugin 挂载的生命周期节点
└── Effect：绑定到 Fiber 的可撤销副作用
```

##### Plugin、Fiber 与 Effect

Plugin 是功能定义，Fiber 是该 Plugin 在当前 Context 中 1 次实际挂载的生命周期实体。

Fiber 是 Plugin 的运行与生命周期宿主。
1 次 `ctx.plugin()` 挂载会创建 1 个 Fiber，并为其派生 Plugin Context。
直接调用 `ctx.extend()`、`ctx.isolate()` 或 `ctx.intercept()` 只会派生 Child Context，不会增加 Fiber；
这些 Context 仍归属于当前 Fiber，直到通过它们继续挂载 Plugin。

```text
ctx.extend() / isolate() / intercept()
→ 派生 Child Context
→ 仍指向当前 Fiber

childCtx.plugin(plugin)
→ 创建 Child Fiber
→ 派生该 Fiber 的 Plugin Context
```

`ctx.plugin(childPlugin)` 创建 Child Fiber，并把 Child 的销毁逻辑作为一个 Effect 注册到 Father Fiber。

Child Fiber 可以单独销毁并从 Father 的生命周期记录中移除，Father 继续运行。
Father Fiber 销毁时会执行自己的 Effects，调用 Child Fiber 的 disposer，进而级联清理整个子树。

Plugin 激活后产生的长期注册和外部资源，才需要通过 Effect 绑定到自身 Fiber。

```text
ctx.plugin()    → 创建并挂载 Child Fiber
ctx.effect()    → 将副作用和 disposer 交给当前 Fiber
ctx.on()        → 注册已经绑定当前 Fiber 生命周期的 Listener
fiber.dispose() → 反向执行清理并级联销毁 Child Fibers
```

因此，插件贡献的 Service、Listener、Registry Entry、Timer、Watcher 和 Child Plugin 都需要具备可撤销的生命周期归属。

##### Context

`new Context()` 创建 1 套独立的 Cordis Runtime、1 个 Root Context 和 1 棵 Root Fiber Tree。

Root Context 初始化 Cordis 的基础设施：

```text
Root Context
├── Reflect：Service 解析
├── Registry：Plugin 注册
├── Events：事件系统
└── Logger：日志系统
```

Plugin 挂载时会从父 Context 派生自己的 Child Context；
`extend()` 和 `isolate()` 也可以派生具有不同元数据或 Service 作用域的 Child Context。
多个 Child Context 最终继承同 1 个 Root Context，因此属于同 1 套 Cordis Runtime。

```text
Root Context
├── Child Context A
│   └── Plugin Fiber A
└── Child Context B
    └── Plugin Fiber B
```

Child Context 可以具有独立的 Service 解析作用域，但这不等于独立 Runtime。
只有再次执行 `new Context()`，才会创建另 1 套 Root Context 和 Fiber Tree。

- Context：当前节点能够看到哪些 Service、事件和元数据
- Fiber：当前 Plugin 由谁挂载、拥有哪些副作用、随谁 1 起销毁

##### Event

Event 是共享的事件订阅与处理链系统。

Root Context 创建 Events 基础设施，Child Context 继承并直接使用；
不会为每个 Child Context 创建独立 Event Bus。
监听器仍归属于注册它的 Context 和 Fiber，并随该 Fiber 卸载。

Event 可以承载流程型 IoC：调用方发出 1 个语义事件，由当前 Context 下注册的 Listener 决定谁观察或参与处理。
Waterfall Event 还允许 Listener 调用 `next()` 委托给下 1 层，或者不调用 `next()` 直接短路。

##### Include 与 Loader

Loader 不是 Cordis Core 的内置组成，而是建立在 Cordis Core 之上的独立 Plugin。
它把 Cordis 从“可以由代码挂载 Plugin”扩展为“可以依据静态配置挂载 Plugin Tree”。

Include 同样是 Plugin。
它依赖 Loader，负责读取基础 Plugin Entries，并通过 `applyEntryPatches()` 按顺序应用 Patch Layers，得到 Composed Profile。

```text
Cordis Loader Plugin
├── 提供 ctx.loader，根据 Plugin Entry 挂载 Plugin Tree
└── 挂载 Include Plugin
    ├── 读取基础 Plugin Entries
    └── 应用 Patch Layers，得到 Composed Profile
```

每个需要静态配置驱动的独立 Root Context 通常安装 1 次 Loader。
同 1 Root Context 下的 Plugin Context、`extend()` Context 和 `isolate()` Context 继承这套 Loader 基础设施，不需要重复安装。

Loader 必须由启动代码直接安装，不能依赖 Profile 加载自己，否则会形成“读取 Profile 需要 Loader，而加载 Loader 又需要先读取 Profile”的循环。
Composed Profile 直接存在于内存中，不要求先写成 1 个磁盘文件。

```text
new Context()
→ 启动代码固定挂载 Loader
→ Loader 挂载 Include
→ Include 读取 root cordis.yml
→ Include.applyEntryPatches() 在内存中应用 Patch Layers
→ 得到最终 EntryOptions[]，即 Composed Profile 的运行时表示
→ Include 将 EntryOptions[] 交给 Loader 的 EntryGroup
→ Loader 导入 Plugins 并创建 Fibers
→ 依赖满足的 Plugins 执行，依赖缺失的 Fibers 保持 Pending
```

运行结构的最短关系：

```text
Loader 创建 Plugin Fiber
→ Fiber 获得自己的 Context
→ inject 决定何时激活
→ Plugin 注册 Service / Event / Child Plugin
→ 注册形成归属于 Fiber 的 Effects
→ Fiber 卸载时撤销 Effects
```

Loader 遍历 Plugin Entries 并创建 Fibers，但 Plugin 不 1 定按 Entry 顺序立即执行。
缺少 `inject` 依赖的 Fiber 保持 Pending；依赖满足后才执行 Plugin，注册 Service、Event 和 Effect。
Entries 完成挂载、可激活的 Fibers 完成执行后，Harness 初始化完成。

#### Loader：从 Plugin Entry 到运行中的 Fiber

##### Plugin Entry 是 Loader 的输入

Plugin Entry 仍然是静态声明，不是运行中的 Plugin 实例。
`insert` 插入的也是 Plugin Entry；
Entry 的 `name` 可以指向业务 Plugin，也可以指向 `cordis:include`、`cordis:group` 等「配置树 Plugin」。

> 配置树 Plugin：以 1 组 Plugin Entries 为内容，并负责生成或组织 Plugin 子树的 Plugin。
>
> - include：读取配置并合并 Patches，生成最终 Entries。
> - group：将若干 Entries 包装成一个可统一管理、隔离的子树。
>
> 在定位上类似于 webpack-merge

```yaml
- id: gg
  name: "@example/gg"
  config:
    enabled: true
  inject:
    - fs
```

Loader 处理 1 个普通 Entry 的主干是：

```text
读取 Plugin Entry
→ EntryTree 根据 name 导入模块
→ Loader 解析模块导出的 Plugin 定义
→ ctx.plugin(plugin, entry.config)
→ Registry 创建该 Plugin 的 Fiber
→ 合并 Plugin 自带 inject 与 Entry inject
→ Fiber 根据 inject 决定是否执行 Plugin
```

`name` 是模块标识，Loader 的 EntryTree 负责导入该模块；
`config` 在创建 Fiber 时传入，Fiber 真正激活时解析配置并交给 Plugin 执行入口。

Plugin 可以是函数、类或带 `apply()` 的对象。
以对象形式的 `gg` 为例，`gg.apply(ctx, config)` 就是 `gg` Plugin 自己的主体内容：

```ts
const gg = {
  name: "gg",
  apply(ctx, config) {
    // Plugin 的注册和初始化逻辑
  },
};
```

##### inject 阻止尚未满足依赖的 Plugin 执行

`inject` 声明的是当前 Plugin Context 必须能够解析的 Service 名，不是 Plugin 名。

创建 Fiber 时会先检查 `inject`：

```text
存在缺失的必需 Service
→ Fiber 保持 PENDING
→ 不执行 apply()

必需 Service 全部可用
→ PENDING → LOADING
→ 执行 apply(ctx, config)
→ ACTIVE
```

`PENDING` 只阻止 Plugin 主体执行，不阻止 Loader 读取 Entry、导入 Plugin 或创建 Fiber。

Reflect 是每个 Root Context 初始化的 1 项 Cordis 内部 Service。
同 1 Root Context 下的 Child Context 和 Fibers 共享它；
另 1 次 `new Context()` 会创建 1 套相互独立的 Reflect、Registry、Events 和 Fiber Tree。

Service 注册、注销或可用性发生变化时，Reflect 执行：

```text
遍历 Registry 中所有 Plugin Runtime
→ 遍历其中所有 live Fibers
→ 读取每个 fiber.inject
→ 过滤 inject 包含该 Service 且 isolate scope 相同的 Fiber
→ 重新检查这些 Fiber 的 Service 实现
→ 局部刷新其生命周期状态
```

最准确的概括是：

> 全量扫描，条件过滤，局部刷新。

Reflect 没有维护 `Service → Consumer Fibers` 的反向索引，也没有为每个 Pending Fiber 单独建立监听器。
当前做法避免维护第 2 份容易随 Fiber 创建、销毁、inject 合并和 Service isolation 失真的派生关系；
Service 变化主要发生在启动、卸载和热更新等生命周期路径，通常不在请求热路径上。

Reflect 不只刷新 Pending Consumer。
Provider 消失时，正在使用该 Service 的 Active Consumer 也需要卸载：

```text
Service 出现：PENDING → LOADING → ACTIVE
Service 消失：ACTIVE → UNLOADING → PENDING
```

##### Plugin 如何提供 Service

假设 Loader 挂载名为 `gg` 的 Plugin，`gg.apply()` 内提供名为 `ggg` 的 Service：

```ts
const gg = {
  name: "gg",
  apply(ctx, config) {
    const ggg = createGgg(config);
    ctx.provide("ggg", ggg);
  },
};
```

`ggg` 的完整注册过程是：

```text
Loader 导入 gg
→ ctx.plugin(gg, config) 创建 gg Fiber
→ gg 的 inject 满足
→ gg Fiber：PENDING → LOADING
→ 执行 gg.apply(ctx, config)
→ ctx.provide('ggg', ggg)
→ 内部调用 ctx.reflect.provide(...)
→ Reflect Store 记录 ggg 的值和所属 gg Fiber
→ gg.apply() 完成
→ gg Fiber：LOADING → ACTIVE
→ Reflect.notify(['ggg'])
→ 刷新依赖 ggg 的 Consumer Fibers
```

`ctx.provide()` 在 `gg` 处于 Loading 时先登记 `ggg`，但严格的 Service 解析只接受 Active Provider。
`gg.apply()` 完成、`gg Fiber` 进入 Active 后，`ggg` 才正式对 Consumers 可用并触发通知。

`ggg` 是 Reflect Store 中的 1 条 Service 实现记录：

```ts
{
  name: 'ggg',
  value: ggg,
  fiber: ggFiber,
}
```

Loader 负责启动 `gg Plugin`；
`gg` 通过 `ctx.provide()` 提供 `ggg Service`；
Reflect 负责 Service 登记、解析和可用性通知。

##### Plugin 不等于 Service Provider

Plugin 激活后可以注册多种内容：

```text
ctx.provide() → 提供 Service
ctx.on()      → 注册 Event Listener
ctx.effect()  → 托管外部副作用
ctx.plugin()  → 挂载 Child Plugin/Fiber
```

Plugin 可以只监听事件、管理外部资源或挂载其他 Plugins，完全不提供 Service。
Plugin 是生命周期化的扩展单元；
Service 只是 Plugin 可以贡献的 1 种能力。

这些 API 调用发生在 Context 上，但生命周期所有权记录在 `ctx.fiber` 上：

##### Effect 为什么能自动撤销注册

Effect 是 Fiber 的通用生命周期清理机制。
`ctx.provide()`、`ctx.on()` 和 `ctx.plugin()` 内部已经把各自的 disposer 交给当前 Fiber，调用者不需要再手动套 1 层 `ctx.effect()`。

```text
ctx.provide() 内部 Effect → 卸载时注销 Service
ctx.on()      内部 Effect → 卸载时取消 Event Listener
ctx.plugin()  父级 Effect → 卸载时销毁 Child Fiber
```

显式 `ctx.effect()` 主要用于 Cordis 不知道如何清理的外部资源：

```ts
ctx.effect(() => {
  const timer = setInterval(work, 1000);
  return () => clearInterval(timer);
});
```

当 `gg Fiber` 卸载时，它持有的 Effects 被统 1 清理：

```text
gg Fiber 卸载
→ 执行 ctx.provide('ggg') 对应的 disposer
→ 从 Reflect Store 注销 ggg
→ Reflect.notify(['ggg'])
→ 依赖 ggg 的 Active Consumers 卸载并回到 PENDING
```

所以，`ctx.provide()` 本身已经完成 Service 的生命周期托管。
只有 Service 内部还持有 Socket、子进程、文件句柄等额外资源时，才需要为这些资源增加对应的清理逻辑。

## 第 2 条链路：从用户输入到 Agent 完成 1 轮请求

这部分回答问题：运行中的 Plugin Tree 如何接收 1 次用户输入，驱动 Agent Loop，并把结果记录、展示和持久化。

```text
用户输入
→ 场景入口
→ Agent Inbox
→ Turn / Step
→ Session Log
→ Model Request
→ LLM / Tools
→ Session Events
→ 场景输出
→ Persistence
```

### Harness 请求处理的统 1 入口：Controller

Controller 是请求入口和场景适配层，负责将不同场景的输入与控制意图转换为 `followup`、`steer`、`cancel` 等统 1 操作，再交给下游 Agent。
Agent 是统 1 执行主体，负责 Inbox、Agent Loop、Session Log、模型调用和 Tool 调用。
场景变化主要替换 Controller，不改变 Agent 的核心执行结构。
Controller 是架构角色，不 1 定对应单个 Plugin。

| 场景     | 主要 Controller                                                             |
| -------- | --------------------------------------------------------------------------- |
| Headless | `headless-runner`                                                           |
| Web      | 前端 `ConversationController`、Client Session 与后端 API Proxy Sessions API |
| ACP      | ACP Server                                                                  |
| SDK      | SDK JSON-RPC Server                                                         |

```text
场景输入 → Controller → Agent → Session Events → 场景输出
```

#### 示例 Controller ：Headless Runner

Headless 是 1 次性任务场景：1 次命令创建 1 组新的 Agent 和 Session，执行 1 个任务，输出最终结果，然后退出。
它在设计上没有「长期、跨连接、多会话的交互」这种重需求，逻辑相对简洁轻便。

```text
命令行 task
→ Headless 应用解析 task
→ Headless Runner 创建 Agent
→ Agent Runtime 为 Agent 准备并绑定 Session
→ 提交 task
→ 等待 Agent 完成
→ 输出最终回答并退出
```

`headless-runner` 只是 Headless 场景的 Controller：它驱动 1 次任务，但不涉及 Agent Loop、模型调用或 Tool 执行。

启动器（最外层的 dsh CLI 进程入口）和 Headless 应用之间通过 2 个内部 Service 接线：

```text
cmdlineArgs      = 启动器交给应用 Plugin 的剩余命令行参数
headlessStartup  = Headless 应用从参数中解析出的启动信息
```

这里出现 Service 是因为数据跨越了独立 Plugins 。

流程可以压缩为：

```text
外层 CLI 消费 --profile、--patch 等启动参数
→ 剩余参数通过 cmdlineArgs 交给 Headless 应用
→ Headless 应用解析出 task
→ headless-runner 接收 task
```

### Runtime、Agent 与 Session

Runtime 管理 Agent、Session 和其他运行时能力，不依赖上游的 Controller 。
需要支持长久会话的 Controller 会维护 Session ID，，并通过它定位后端会话。

- Web 服务通常让多个会话窗口共享 1 个 Root Runtime。
  - 多个用户、多个聊天窗口、SubAgent 和 Workflow 都可能在同 1 个 Runtime 中产生独立 Session 。
- Headless 通常是 1 进程、1 个 Agent、1 个 Session 。

1 个窗口通常持有 1 个 Session ID，但多个窗口也可以打开同 1 个 Session 。

同 1 Agent 收到的并发输入由自己的 Inbox 协调，不会启动两个独立 Agent Loop 同时修改同 1 个 Session。
不同 Agent 则可以在共享 Runtime 中并发运行。

| 关键词        | 定义                                                                                 |
| ------------- | ------------------------------------------------------------------------------------ |
| Agent Runtime | Root Context 下由 Agent、Session、Prompt、LLM、Tools 等 Plugins 共同组成的运行系统。 |
| Agent         | 接收输入并驱动 Agent Loop 的单个执行实例，通常绑定 1 个 Session。                    |
| Agent Loop    | 组织 Inbox、Turn、Step、模型请求和 Tool 执行的稳定控制循环。                         |
| Inbox         | Agent 尚未正式接受的输入队列，负责输入顺序、Follow-up 和 Steering 协调。             |
| Turn          | Agent 处理 1 次用户请求的完整周期，可以包含 1 个或多个 Steps。                       |
| Step          | Turn 内的 1 次模型调用及其输出处理；Tool Result 可能触发下 1 个 Step。               |
| Session       | 单个会话的运行时实例，负责追加 Events 并提供状态投影。                               |
| SessionStore  | Runtime 内活跃 Sessions 的创建入口和 `Session ID → Session` 索引。                   |
| Session Event | Session Log 中的 1 条已发生事实。                                                    |
| Session Log   | 单个 Session 的 append-only 有序事实序列，是会话恢复和模型上下文重建的依据。         |
| Projection    | 从 Session Events 计算 Messages、当前状态或 UI 数据，不独立拥有原始事实。            |
| Persistence   | 将 Session Log 保存到进程外，并在 Runtime 重启后加载它。                             |

> **Follow-up 与 Steering**：两者都是 Agent 运行期间接收新输入的调度方式。
> Follow-up 进入 `next-turn`，等待当前 Turn 完成后作为新 Turn 处理；
> Steering 进入 `next-step`，在当前 Turn 的下 1 个 Step 被模型接收。
> 它们是 Agent Runtime 的底层能力，具体交互入口可以只开放其中 1 种；
> 当前 Web 主 Session 支持两者，SubAgent continuation 与普通 SDK prompt 只使用 Follow-up。

#### Session、Session Log 与 SessionStore

三者的职责不同：

```text
Session       = 单个会话的运行时实例
Session Log   = 该会话按顺序追加的事实记录
SessionStore  = Runtime 内所有活跃 Session 的创建入口和内存索引
```

Session 负责追加 Events、维护序号并提供状态投影。
Session Log 是它管理的有序事件序列；使用 JSONL 持久化后端时，这些事件在磁盘上保存为 JSONL，但 Session Log 的概念不等于某 1 种文件格式。
SessionStore 负责：

- 创建新的 Session；
- 根据 Session ID 查找活跃 Session；
- 防止同 1 Runtime 中出现重复 Session ID；
- 在 Session 生命周期结束时移除实例。

之所以需要 Store，是因为 1 个 Runtime 可以同时容纳多个 Session，其他组件需要 1 个统 1 的关系：「Session ID → 活跃 Session 实例」。

在当前 Headless 链路中，Headless Runner 发起创建 Agent，Agent Runtime 组织 Agent 与 Session 的联合创建，SessionStore 负责构造和登记 Session。

Agent 与 Session 相互绑定，但职责不同：

```text
Agent
  ├── 执行任务
  ├── 驱动 Agent Loop
  ├── 持有执行配置与可用能力
  └── 绑定 1 个 Session

Session
  ├── 保存会话 Events
  ├── 保存会话元数据
  └── 从 Events 投影当前会话状态
```

Session 不保存 Agent Runtime 的全部配置和能力。
模型、Tools 等由 Agent 及其 Runtime Context 提供；Session 记录足以重建模型可见内容和会话状态的事实。

```text
Session Log
  ├── 对话事实：User / Assistant / Tool
  ├── 执行事实：Turn / Step / Inbox / Cancel
  ├── 上下文变换：Compaction
  ├── 请求事实：Header / Model Route / Usage
  └── 领域状态：Plan / Todo / Goal / Permission
```

> 领域状态：各功能 Plugin 持久化在 Session Log 中的业务状态。

它不保存 Plugin 实例、LLM Provider 实现或完整 Tool Runtime；这些由当前 Runtime 提供。

#### 新建、继续与恢复

同 1 个 Runtime 中的 Agent 仍然存活时，新输入直接交给现有 Agent：

```text
Session ID
→ 找到现有 Agent / Session
→ 追加新输入
→ 继续执行
```

此时不需要从磁盘重新加载 Session Log。

Runtime 重启或 Agent 已不在内存中时，才需要恢复：

```text
Session ID
→ Persistence 加载 Session Log
→ 创建新的 Session 实例
→ 从 Events 投影当前状态
→ 创建并绑定新的 Agent 实例
→ 继续对话
```

恢复不是让旧内存对象复活，也不是重新执行历史 Tool Call 或模型请求。它用持久化事实建立新的运行时实例。

因此：

> 内存中的 Agent 负责连续执行，Session Log 负责跨运行恢复。

#### Agent Inbox：尚未被正式接收的输入

用户输入不会直接变成 Model Request，而是先进入 Agent Inbox。

```text
Inbox       = 等待 Agent 协调和处理的输入
Session Log = Agent 已正式接收的会话事实
```

Inbox 的必要性来自运行时并发：Agent 可能仍在执行上 1 轮，多个输入也可能同时到达。
Inbox 先确定顺序和用途，再由 Agent Loop 接收输入。

```text
User Prompt
→ 进入 Inbox
→ Agent Loop 取出并接受
→ 写入 Session Log
→ 进入对应 Turn / Step
```

等待处理的输入还可能被取消或丢弃，不应提前成为 Session Log 中“已经发生”的事实。
输入还可分为下 1 轮的 Follow-up 与影响下 1 Step 的 Steering 。

#### Turn 与 Step

Turn 是 Agent 处理 1 次用户请求的完整过程，Step 是 Turn 内的 1 次模型调用。

```text
Turn
  ├── Step 1：模型决定调用 Tool
  ├── 执行 Tool
  ├── Step 2：模型读取 Tool Result 后继续
  └── 得到最终回答，Turn 结束
```

模型直接回答时，1 个 Turn 只有 1 个 Step；模型多次使用 Tools 时 1 个 Turn 包含多个 Steps 。

Agent Loop 接受 Inbox 中的输入后：

```text
记录 turn/start
→ 准备 Step
→ 记录 step/start
→ 将本 Step 接受的 User Message 写入 Session Log
→ 组装并发送 Model Request
→ 记录模型输出及 Tool 活动
→ 记录 step/end
→ 必要时进入下 1 Step
→ 记录 turn/end
```

#### Session Event 与 Session Log

Session Event 是 Session Log 中的 1 条事实，Session Log 是这些 Events 的追加式有序序列。

常见事件包括：

```text
turn/start         1 轮开始
step/start         1 次模型调用开始
user/message       用户消息被接受
assistant/chunk    模型返回 1 段流式内容
assistant/message  完整模型消息形成
tool/*             Tool 调用及结果
step/end           1 次模型调用结束
turn/end           1 轮结束
```

流式输出不会反复更新同 1 条 Event，而是持续追加新的 `assistant/chunk`，完成后再追加完整的 `assistant/message`：

```text
assistant/chunk：你好
assistant/chunk：，我来
assistant/chunk：帮你
assistant/message：你好，我来帮你
```

UI 可以订阅 Chunk Events 并实时拼接展示，最终 Message 则代表这次模型输出形成的完整消息。

#### 从 Session Log 组装 Model Request

Agent Loop 不会把整份 Session Log 原样发给模型。
Session Log 还包含 Turn、Step、错误和其他运行事实；Session 从其中投影出模型需要的 Messages。

```text
Session Log
→ 投影有效的 User / Assistant / Tool Messages
→ 得到对话历史 Messages
```

Agent Runtime 同时组装其他模型输入：

```text
Model Request
├── System Prompt
├── Messages
├── 当前可用 Tools
├── Provider / Model 配置
└── Session ID
```

现将已有的 User Prompt 写入 Session Log 再投影 Messages ，是为了让 Session Log 成为模型可见事实的 SSOT：

- 当前输入、历史消息、Assistant 回复和 Tool Result 使用同 1 套投影规则；
- 下 1 Step 能自然看到上 1 Step 新增的 Tool Result；
- Runtime 重启后可以从同 1 份 Log 重建请求上下文；
- 避免模型已经看到信息，但 Session Log 没有记录的状态分叉。

System Prompt、Tools 和请求配置由 Runtime 组装，不是普通对话 Messages；
Agent Loop 会在发出请求前记录重建它们所需的请求信息。核心约束是：

> Model-visible ⟺ logged：凡是进入模型请求的内容，都必须能够从 Session Log 重建。

#### Model Request 的 4 类输入

Agent Loop 不长期持有 Model Request 的内容。
每个 Step 开始时，它从独立能力取得 4 类输入：

```text
Model Request
  ├── System Prompt：模型应该如何工作
  ├── Messages：会话中已经发生了什么
  ├── Tools：模型当前被告知可以调用什么
  └── Model Config：由哪个 Provider / Model 处理请求
```

Agent Loop 负责组织这些输入和调用时机，各输入的内容与实现由对应 Plugins 提供。

##### System Prompt 是动态组装结果

System Prompt 不是 Runtime 启动时确定 1 次的固定字符串。
多个 Plugins 可以分别贡献 Prompt Sections 和运行时上下文：

```text
Harness 基础身份
+ Profile Persona
+ Tool 使用说明
+ Workspace / Runtime Context
+ 权限与安全规则
+ Skill、Plan 等 Plugin 提示
→ 当前 Step 的 System Prompt
```

System Prompt Service 是组装中心：

```text
各 Plugin 注册 Prompt Sections
→ 根据当前 Agent Context 收集可见内容
→ 排序、合并并完成变量解析
→ 生成当前 Step 使用的 System Prompt
```

每个 Step 重新组装，是因为 Tool 可见范围、运行模式、权限、Workspace Context 和 Agent 作用域都可能变化；
不同 Agent 和 SubAgent 也可以得到不同结果。

Tool Schemas 也在这次组装中确定。
System Prompt 与 Tool Schemas 在模型协议中通常是不同字段，但它们共同定义：

> 当前 Agent 被告知应该怎样工作，以及能够做什么。

##### Tool Schema 与 Tool Implementation

1 个 Tool 同时存在模型侧描述和 Runtime 侧实现：

```text
Tool Schema         = 给模型看的名称、描述和参数定义
Tool Implementation = Runtime 中真正执行该能力的实现
```

模型只能看到 Tool Schema，并据此生成结构化 Tool Call。
Runtime 接收 Tool Call 后，再根据名称找到实现并执行：

```text
模型读取 Tool Schema
→ 生成 Tool Call 与参数
→ Agent Loop 识别 Tool Call
→ Tool Runtime 查找对应实现
→ 执行校验、策略与权限流程
→ 调用具体实现
→ Tool Result 写入 Session Log
→ 下 1 Step 将结果投影给模型
```

模型不感知具体 Provider。
同 1 种文件能力可以由本地文件系统或 E2B 沙箱实现，只要它们满足同 1 能力定义；部署通过 Plugin 组合选择具体实现。

模型可见范围与 Runtime 可执行范围必须保持 1 致。

最短关系：

> Tool Schema 是模型侧接口，Tool Implementation 是 Runtime 能力，Tool Runtime 负责安全连接模型意图与实际执行。

#### LLM Service 与 Provider Adapter

Agent Loop 组装 Harness 内部统 1 格式的 Model Request，不直接依赖 DeepSeek 或其他厂商协议。

```text
Agent Loop
→ 生成统 1 Model Request
→ LLM Service 根据 Provider / Model 选择 Adapter
→ Adapter 转换为厂商请求协议
→ 调用模型 API
→ Adapter 将厂商响应转换为统 1 Stream
→ Agent Loop 继续处理
```

3 层职责是：

```text
Agent Loop       = 决定何时调用模型
LLM Service      = 根据 Provider / Model 路由到具体实现
Provider Adapter = 协议转换并完成真正的模型调用
```

Provider Adapter 同时统 1 输入和输出：

```text
Harness Model Request
→ 厂商请求格式
→ 厂商流式响应
→ Harness 统 1 Chunks
→ Session Events
```

因此替换 LLM Provider 时，Session、Agent Loop 和 Tool Runtime 不需要随厂商协议 1 起变化。
LLM 是 1 个典型的 Capability Seam：

```text
Service Definition = 统 1 LLM 调用能力
Service Provider   = 具体 Provider Adapter
Consumer           = Agent Loop
```

### Agent Loop 的稳定职责

Agent Loop 保持“纯粹”不等于它是空壳。它固定维护 Agent 执行循环的语义：

- 调度 Inbox；
- 建立 Turn / Step 生命周期；
- 决定何时组装和发送 Model Request；
- 消费模型 Stream 并记录 Session Events；
- 根据模型结果执行 Tool 或结束 Turn；
- 保证模型可见内容能够从 Session Log 重建。

Loop 外部的可替换能力包括：

```text
System Prompt 内容
Tool Schema 与 Tool Implementation
LLM Provider
Session Persistence
模型上下文投影
场景入口与输出方式
```

这形成清晰的稳定核与扩展能力：

> Cordis 提供 Plugin 与生命周期内核；Agent Runtime 将 Prompt、Tools、LLM、Session 和 Persistence 等横切能力拆分为独立 Plugins；Agent Loop 只保留稳定的 Turn / Step 编排语义。

1 次 Step 的完整输入和调用关系是：

```text
System Prompt Service → Prompt + Tool Schemas
Session               → Messages
Agent 配置             → Provider / Model
                         ↓
                     Agent Loop
                         ↓
                   Model Request
                         ↓
                     LLM Service
                         ↓
                  Provider Adapter
                         ↓
                       Model
```

| 关键词              | 定义                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------- |
| Model Request       | 1 个 Step 发给模型的完整请求，由 System Prompt、Messages、Tool Schemas 和模型配置组成。 |
| Messages            | 从 Session Log 投影出的模型对话历史，包括 User、Assistant 和 Tool 消息。                |
| System Prompt       | 当前 Step 动态组装的行为指令与 Runtime Context。                                        |
| Tool Schema         | 模型可见的 Tool 名称、描述和参数定义。                                                  |
| Tool Implementation | Runtime 收到 Tool Call 后实际执行的能力实现。                                           |
| Tool Runtime        | 管理 Tool 注册、可见性、策略、查找和执行的 Service。                                    |
| LLM Service         | 接收 Harness 统 1 Model Request，并根据 Provider 与 Model 路由到 Adapter。              |
| Provider Adapter    | 在 Harness 统 1 协议与具体模型厂商协议之间转换请求和流式响应。                          |

#### 模型输出、Tool 与下 1 Step

模型输出完成后，Agent Loop 根据完整 Assistant Message 判断当前 Turn 是否继续：

```text
没有 Tool Call
→ 当前 Step 结束
→ 当前 Turn 结束
→ Agent 回到 Idle

存在 Tool Call
→ Tool Runtime 执行 Tool
→ Tool Result 写入 Session Log
→ 开启下 1 Step
→ 从更新后的 Log 再次投影 Messages
→ 再次调用模型
```

Tool Result 不会绕过 Session 偷偷传给下 1 次模型调用。
Tool Call 和 Tool Result 都先成为 Session Log 中的事实，下 1 Step 再据此生成 Model Request。

#### 结果由场景入口呈现

Agent Loop 负责产生 Session Events，不直接负责某个具体界面的展示。不同场景以不同方式消费这些事件：

```text
Headless
→ 等 Agent 进入 Idle
→ 从 Session 取得最终 Assistant Message
→ 打印结果并退出

Web
→ 持续订阅 Session Events
→ 将 assistant/chunk 实时推送到窗口
→ turn/end 后结束本轮展示
→ Runtime、Agent 和 Session 继续存在
```

#### 持久化与状态恢复

Persistence Plugin 订阅 Session Events，并将新增记录写入持久化后端：

3 层职责是：

```text
Session             = 管理当前内存中的事件和投影
SessionStore        = 管理 Runtime 内的活跃 Sessions
Session Persistence = 保存和加载跨进程的 Session Log
```

从持久化 Log 恢复时，系统不会重新执行历史动作，而是按顺序读取 Events 并投影状态：

```text
User / Assistant / Tool Events
→ 对话 Messages

Turn / Step Events
→ 已完成的执行位置

Request Events
→ 模型请求相关状态

Session Header
→ Session ID、工作目录、父子会话关系等元数据
```

最短关系：

```text
Session Log = 可持久化的事实
Projection  = 从事实计算出的当前状态
Agent       = 根据当前状态继续执行
```
