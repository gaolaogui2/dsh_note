> Cordis 基础：Context、service、plugin、effect、event、waterfall、scope。

## Cordis

Cordis 是 1 个插件化运行时框架，用 Context 管理服务，用 Plugin 组合能力，用 Event 连接扩展点，并用可撤销的 Effect 管理生命周期。

「Cordis = plugin runtime + service container + event system + lifecycle manager」

它解决的问题是：当 1 个系统由很多可插拔模块组成时，如何让这些模块能按依赖关系加载、互相调用、互相拦截，并且在卸载或热更新时干净回收。

工作方式：

- Context 提供运行环境
- Service 暴露稳定能力
- Plugin 往环境里挂能力
- inject 声明依赖
- effect 保证注册可撤销
- event 提供扩展点
- waterfall 提供可短路的 middleware 链
- scope 让能力可以局部化到某个 agent 或子运行时

## 关键字

### 1. Context

Context 是 1 个运行时对象，暴露当前作用域可见的 service 能力入口，
并承载 event、middleware、effect lifecycle 等运行时机制；
具体业务状态由挂在 Context 上的 service 封装维护。
父 Context 派生出的 plugin/scoped Context 共享这套IoC、发布订阅、waterfall middleware 和生命周期系统，
但每个子 Context 的 effect 归属自己的 plugin/fiber。

可以把它理解成 1 个带生命周期的服务注册表：

ctx.tools
ctx.llm
ctx.sessions
ctx.systemPrompt
ctx.agents

插件不应该直接 import 某个具体实现来调用，而是通过 ctx.<serviceKey> 拿能力。这样 provider 可以替换，consumer 不需要改。

在 Harness 里，Context 是所有可插拔性的基础。比如 tool 插件只依赖 ctx.tools，不关心 agent-loop 是谁实现的。

### 2. Service

Service 是挂在 Context 上的能力对象。

例子：

- ctx.sessions：session log 服务
- ctx.tools：工具注册和执行服务
- ctx.llm：模型适配器服务
- ctx.agents：agent 注册和创建服务
- ctx.systemPrompt：prompt section / tool schema 组装服务

Service 的关键点不是“1 个类”，而是：它占据 1 个稳定的 ctx key，并定义其他插件可以依赖的接口。

所以 Harness 的设计会强调 Service Definition / Provider / Consumer：

- Definition：定义 ctx.xxx 接口
- Provider：实现这个接口
- Consumer：使用这个接口，比如 model-facing tool

### 3. Plugin

Plugin 是往 Cordis 树里贡献能力的单元。

1 个 plugin 可以：

- 提供一个 service
- 注册一个 tool
- 注册 prompt section
- 监听 event
- 修改 policy
- 挂 UI renderer
- 添加 LLM adapter
- 添加 sandbox provider

形式上可以是函数插件，也可以是 Service subclass。简化理解：

```js
export const inject = ['tools']

export function apply(ctx: Context) {
   ctx.tools.register(...);
}
```

inject 声明依赖。Cordis 会等依赖 service 存在后再激活插件，所以加载顺序不是手写的，而是由依赖关系驱动。

### 4. Effect

effect 是“带 disposer 的注册”。

Cordis 的核心纪律是：registrations are reversible effects。(插件往 runtime 里“注册”的任何东西，都必须能在插件卸载时撤回)

比如：

```js
ctx.effect(() => {
  const dispose = ctx.tools.register(tool);
  return dispose;
});
```

这意味着插件卸载、HMR、profile 切换、scope dispose 时，注册过的东西能按生命周期撤销。

在 Harness 里非常重要：tool、prompt section、adapter、event listener 都必须能卸载，否则插件树就不可热更新、不可组合、不可隔离。

### 5. Event

event 是插件之间的扩展点。

Service 提供能力，event 提供拦截、观察、改写、策略注入。

常见例子：

- agent/pre-step：模型请求前，决定哪些消息进入 step
- agent/request：模型请求前，允许改 provider/model/request
- llm/stream：模型流式调用
- tools/pre-execute：工具执行前的权限判断
- tools/execute：包住工具实际执行
- tools/post-execute：工具执行后可改结果
- session/event：session log 写入后通知 UI / persistence / telemetry

Harness 的设计原则是：新行为尽量挂到 event 上，而不是改 agent-loop。

### 6. Waterfall

waterfall 是 1 种 event dispatch mode，语义接近 middleware chain。

监听器会拿到 next：

```js
ctx.on("tools/pre-execute", async (exec, next) => {
  if (!allowed(exec)) {
    return { kind: "deny", reason: "Denied" };
  }
  return next();
});
```

关键规则：

- 调 next()：把控制权交给下一个 listener
- 不调 next()：短路，自己给最终结果
- 可以在 next() 前后包装、改写、观察结果

这就是为什么它适合：

- 权限 gate
- request middleware
- retry
- timeout
- tool result policy
- LLM stream wrapper

Harness 里很多关键点都是 waterfall：agent/pre-step、agent/request、llm/stream、tools/pre-execute、tools/execute、tools/post-execute。

### 7. Event Dispatch Modes

Cordis 事件不只有 waterfall。主要有四类：

- emit：同步通知，不等待，没有返回值
- parallel：并行等待所有 listener 完成
- serial：按顺序等待，有顺序语义
- waterfall：middleware 链，有 next() 和返回值

调度模式是事件契约的 1 部分。不能随便换，因为它决定 listener 是否能拦截、是否能短路、是否会被等待。

### 8. Scope

scope 是局部化注册能力。

全局 ctx 注册的东西对所有 agent 可见。agent 自己的 agent.ctx 注册的东西只对这个 agent 可见，并随 agent dispose 自动卸载。

例如：

- 某个 agent 有自己的 prompt persona
- 某个 agent 只暴露部分 tools
- subagent 有自己的 tool set
- workflow 子任务有自己的 system prompt 和 output policy

这就是 scoped registration 的意义：同 1 个进程里可以有多个 agent，每个 agent 的工具、prompt、策略不完全 1 样。

## 架构

Cordis 自身并没有创造性的提出 1 些新的概念或者解决方案，webpack Koa NestJS 里面都能找到部分类似的机制，
工程设计里的基础模式变化很慢，甚至可以说几十年级别稳定。

区别在于消费场景：

webpack 构建时系统：source files → module graph → transforms → chunks/assets 。

所以它的插件体系围绕：

- compiler
- compilation
- module graph
- loader pipeline
- asset emission
- build cache
- watch/rebuild

Cordis 是运行时系统：plugins → services → events → live capabilities → lifecycle 。

所以它围绕：

- runtime context
- services
- plugin activation
- effect disposal
- event dispatch
- scoped runtime views

agent runtime ：user input → session log → prompt → LLM → tool execution → session log → UI/API 。

所以它在 Cordis 上定义：

- agent
- session
- turn/step
- model-visible logging
- tool runtime
- LLM adapter
- subagent
- sandbox/permission
- runtime surfaces

Cordis 不是发明了插件化，而是把这些经典设计原则重新落到了 agent runtime 这个新消费场景。

## 实现

Cordis 架构本质是：以 Context 为访问入口，以 Fiber 为插件运行节点，组织成 1 棵可继承、可隔离、可卸载的运行时树。

除了 root fiber，其余生命周期节点都是 plugin fiber。

Fiber 是生命周期节点，Context 是这个节点访问运行时的视图。root context 初始化时直接挂载 4 个基础服务：Reflect、Registry、Events、Logger。普通插件 fiber 会通过 `parent.extend({ fiber: this })` 派生自己的 ctx。

- Reflect : 管动态 service 的注册、查找、隔离、扩展和变更通知；
  - 自定义 service 通过 `ctx.provide()` 或 `Service` 基类注册到 reflect 维护的服务表；
  - `ctx.xxx` 访问会被 Context Proxy 拦截，再交给 reflect 按当前 ctx 解析；
  - 父 Context 注册的 service 默认对子 Context 可见；
  - isolate / check / shadow 会影响 service 可见性和查找起点；
- Registry : 管 plugin 注册和生命周期；
  - `ctx.plugin()` 会创建新的 plugin fiber；
  - plugin 执行期间可以注册 service、事件回调、effect、子 plugin；
  - inject 声明依赖，依赖未满足时 fiber 会保持 pending，依赖满足后再激活；
- Events : 管事件监听和分发；
  - 支持框架内部事件，也支持业务层自定义事件；
  - 监听器注册绑定当前 fiber，fiber 卸载时自动移除；
  - 支持 emit / parallel / serial / bail / waterfall 等分发模式；
- Effect : 管当前 fiber 生命周期内“需要成对注册和清理”的运行时副作用；
  - setup 立即执行；
  - setup 返回的 disposer 在 fiber 卸载时执行；
  - 事件监听、service 注册、定时器、文件监听、子 plugin 挂载都适合放进 effect；
- Logger : 提供运行时日志能力；
  - 支持 logger 分组、日志级别、日志格式化和日志出口；
