> Harness core conventions 是 Harness 在 Cordis 上定义的 agent 执行链路协议和默认实现。

DeepSeek Harness 有 2 个 core：

- Cordis core：插件运行时底座，负责 Context / Plugin / Service / Event / Effect。
- Harness core：agent 执行链路核心，负责 Agent / Session / Message / Tool / Prompt / LLM / agent-loop。

Cordis core 管“插件怎么跑”；Harness core 管“agent 怎么跑”。

Harness core 的主线可以先抓成 3 块：

```
Agent 定义
  Agent interface、ctx.agents、agent/* events。

默认 Agent 实现
  agent-loop plugin、ReactLoopAgent、turn/step 主循环。

Session 事实源
  Session、SessionEvent、ctx.sessions、model-visible means logged。
```

整体关系：

```
用户输入
  -> Agent inbox
  -> agent-loop
  -> Turn
  -> Step
  -> Prompt assembly
  -> LLM stream
  -> Tool call / Tool result
  -> SessionEvent log
  -> UI / resume / fork / replay / next LLM request
```

## 1. Agent

Agent 是 Harness 对“1 个活的会话执行体”的抽象。

它分成 2 层：

- core/agent：定义 Agent interface、ctx.agents 注册表、agent/* 事件。
- core/agent-loop：实现默认 Agent class：ReactLoopAgent，并驱动 turn / step / LLM / tool / session log。

Agent interface 可以粗略理解成这个 JS class 形状：

```js
class Agent {
  id; // agent/session 共享身份
  options; // provider / model / maxTokens 等运行配置
  ctx; // 当前 agent 的 scoped Context
  session; // durable timeline，事实源
  inbox; // 待处理输入队列
  status; // idle / running

  send(message, target, wakeup) {} // 底层输入入口：指定 inbox 目标和是否唤醒
  followup(message) {} // 放入 next-turn，并唤醒 driver
  steer(message) {} // 放入 next-step，并唤醒 driver
  inject(message) {} // 放入 next-step，不唤醒 driver

  cancel(cause, options) {} // 取消当前执行，可选择保留 inbox
  whenIdle() {} // 返回 Promise，等待当前执行收敛到 idle
  runMaintenance(task) {} // 在 idle 阶段运行非 turn 维护任务

  // send / followup / steer / inject 不是 Promise。
  // 它们只提交输入，不代表 1 次完整执行。
}
```

标准交互模式：

```js
agent.followup(message); // 同步入队
await agent.whenIdle(); // 等待执行收敛
agent.session.deriveMessages(); // 从 session log 读取结果
```

为什么不是 `await agent.followup()`：

```
1 次输入可能触发多个 step。
1 个 step 可能触发多个 tool call。
模型可能流式输出。
执行可能被取消、重试、继续。
结果统一写入 session log，而不是挂在 submit 返回值上。
```

ctx.agents 是 live agent 注册表，负责创建、恢复、查找 agent。

agent-loop 作为 Cordis plugin，通过 ctx 消费这些 service：

```
ctx.sessions
ctx.systemPrompt
ctx.llm
ctx.tools
ctx.agents
```

位置：

```
packages/core/agent/src/runtime-types.ts
packages/core/agent-loop/src/agent.ts
```

## 2. Session

Session 是 Harness 对“1 次 agent 会话事实源”的抽象。

它不是消息数组，也不是状态快照，而是 durable timeline：按顺序追加 SessionEvent。

可以粗略理解成这个 JS class 形状：

```js
class Session {
  header; // session 元信息：id / cwd / parentSession / seedLength 等
  firstLiveSeq; // 本进程开始追加事件的位置

  get id() {} // session id
  get events() {} // 只读 SessionEvent timeline 快照
  get seq() {} // 下一个事件序号

  append(type, data, opts) {} // 写入 1 条事实事件

  requestHeader() {} // 从 request/header 事件折叠出当前请求配置
  requestContext() {} // 从 request/context 事件折叠出当前模型路由信息

  deriveMessages() {} // 从事件日志投影出下一次 LLM 请求需要的 messages
  deriveEventMessage(event) {} // 单条事件转 Message
}
```

Session 的写入方不是 Cordis logger，而是 agent-loop 和业务插件。

写入方式：

```js
session.append(type, data, opts);
```

ctx.sessions 是 SessionStore service，不是某个具体 Session。

```txt
Session      = 单个会话 timeline
ctx.sessions = 管理多个 Session 的 service
Agent.session = 当前 agent 正在使用的那一个 Session
```

为什么会有多个 Session：

```
多个聊天窗口
多个 agent
subagent
fork
resume
API 并发
```

## 3. SessionEvent

SessionEvent 是 session log 的基本单位。

可以粗略理解成：

```js
class SessionEvent {
  type; // 事件类型
  seq; // session 内递增序号
  time; // 发生时间
  data; // 事件数据
}
```

核心事件：

```
turn/start
turn/end
step/start
step/end
user/message
assistant/chunk
assistant/message
tool/call
tool/result
request/header
request/context
session/end-seed
```

事件分 2 类：

```
完整执行记录
  turn/start
  step/start
  request/header
  assistant/chunk
  tool/call
  step/end
  turn/end

模型可见消息
  user/message
  assistant/message
  tool/result
```

SessionEventMap 是可扩展的。插件可以追加自己的 durable event。

## 4. Turn

Turn 是 agent 对 1 次唤醒输入的完整处理周期。

它从：

```
turn/start
```

到：

```
turn/end
```

1 个 turn 里可以有：

```
0 个 step：输入被 agent/pre-step 拒绝，或没有进入模型请求。
1 个 step：请求 1 次模型后结束。
多个 step：模型调用工具，工具结果触发下一次模型请求。
```

所以：

```
Turn = 一轮任务
Step = 一次模型请求
```

## 5. Step

Step 是一次模型请求，以及这次请求产生的工具执行。

典型 step：

```
step/start
request/header
user/message
LLM stream
assistant/chunk*
assistant/message
tool/call*
tool/result*
step/end
```

如果模型没有 tool call，这个 step 后 turn 可能结束。

如果模型有 tool call，工具结果会写入 session，然后 agent-loop 判断是否进入下一 step。

## 6. Message

Message 是模型可见消息对象。

可以粗略理解成：

```js
class Message {
  id; // 稳定消息身份
  role; // system / user / assistant
  content; // 模型可见内容块
  source; // 来源信息
}
```

source 说明消息来源：

```
user    人类输入
plugin  插件注入上下文
model   模型输出
tool    工具结果
```

模型历史不是任务执行记录全集，而是下一次 LLM request 需要的 messages：

```
user/message       -> UserMessage
assistant/message  -> AssistantMessage
tool/result        -> ToolResultMessage
```

不会进入模型历史：

```
turn/start
step/start
assistant/chunk
tool/call
turn/end
```

`deriveMessages()` 有增量缓存。普通追加时只处理新增的 message surface；发生 replace / compaction 时才重建。

位置：

```
packages/llm/llm/src/message.ts
```

## 7. ToolCall / ToolResult

模型请求工具时写：

```
tool/call
```

工具完成后写：

```
tool/result
```

tool/call 保存模型原始工具请求：

```js
{
  callId,
  name,
  arguments,
}
```

tool/result 保存工具返回给模型看的结果：

```js
{
  message,
  error,
  meta,
}
```

callId 用来把 tool/call 和 tool/result 配对。

## 8. agent-loop

agent-loop 是默认 Agent 实现插件。

它做 4 件事：

```
1. 注册 ctx.agentLoop
2. 给 ctx.agents 注册 AgentFactory
3. 创建 ReactLoopAgent
4. 驱动 turn / step / prompt / LLM / tool / session log
```

执行链路：

```
followup 输入
  -> turn/start
  -> agent/pre-step
  -> step/start
  -> systemPrompt.assemble()
  -> request/header
  -> session.deriveMessages()
  -> agent/request
  -> llm/stream
  -> assistant/chunk*
  -> assistant/message
  -> tool/call*
  -> tools/pre-execute
  -> tools/execute
  -> tools/post-execute
  -> tool/result*
  -> step/end
  -> 如果工具结果需要继续，则进入下一 step
  -> turn/end
```

agent-loop 是主链路核心，但不是全部核心。

```
core/agent
core/session
core/tools
core/system-prompt
llm/llm
```

这些包提供稳定协议，agent-loop 消费它们并提供默认执行实现。

## 9. model-visible means logged

这是 Harness 最重要的纪律。

意思是：

> 任何会进入模型请求的内容，都必须能从 session log 重建。

所以这些必须进 log：

```
用户消息
插件注入给模型的上下文
assistant 最终消息
tool result
request/header 里的 system prompt / tools / config
```

否则这些能力会失真：

```
UI       渲染聊天记录、工具卡片、流式输出
resume   进程重启后恢复 session/agent
fork     从同一历史前缀开新会话分支
replay   调试、测试、审计时重放事件流
LLM      推导下一次请求的 messages
```

核心原则：

```
SessionEvent log = 唯一事实源
其他视图 = 从 log 派生
```

这就是 SSOT。
