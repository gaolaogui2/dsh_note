# DeepSeek Harness 领域定位地图

建立需求定位能力：看到 1 个问题时，先判断事实和职责属于哪个领域，再进入对应文档与 package。

```text
需求或现象
→ 判断属于哪个运行阶段
→ 找到拥有该事实的领域
→ 找到该领域的 Service Definition 或核心对象
→ 沿 Provider、Consumer 和扩展点定位相邻 packages
→ 最后才进入具体实现
```

建立地图，不要求掌握每个领域的内部实现。

## 定位时先问 5 个问题

遇到 1 个需求时，依次判断：

1. 这是启动配置、实时执行、持久事实、外部能力还是用户界面问题？
2. 哪个领域拥有这项状态或行为？
3. 它是 Service Definition、Service Provider 还是 Consumer？
4. 它通过 Service、Session Event、Live Event、Patch Layer 还是 RPC 与其他领域协作？
5. 最接近真实运行入口的 Profile、Bundle 或应用是什么？

最重要的原则：

> 先找职责与事实归属，再找调用路径；不要从 1 个看起来相关的文件开始全仓库漫游。

## 一级领域地图

### Agent 执行

```text
首要入口：packages/core/agent、packages/core/agent-loop
核心问题：Agent 生命周期、Inbox、Turn、Step、取消、实时状态
核心事实：进程内 live state
主要扩展：agent/* Events
```

`core/agent` 定义 Agent 接口、活跃 Agent 注册表和公共事件；`core/agent-loop` 提供默认执行驱动。使用 Agent 的扩展依赖 Agent Definition，不应直接耦合默认 Loop 实现。

### Session 与持久事实

```text
首要入口：packages/core/session、packages/session/*
核心问题：Session Events、Messages 投影、持久化、恢复、fork、查询
核心事实：append-only Session Log
主要扩展：SessionEventMap、session/event、projection、persistence
```

`core/session` 拥有 Session 与内存中的 SessionStore；`packages/session` 提供持久化、投影、统计、标题和遥测等独立能力；`packages/session-query` 提供跨 Session 的检索能力。

### System Prompt 与模型上下文

```text
首要入口：packages/core/system-prompt、packages/context/*
核心问题：Prompt Sections、动态 Context、变量、模型可见 Tool Schemas
核心事实：每个 Step 的 Prompt Assembly
主要扩展：Prompt Section、Context Provider、system-prompt/assemble
```

System Prompt Service 负责统一组装。Workspace 指令、时间、文件引用等内容由各自的 Context Plugin 提供，而不是写进 Agent Loop。

### Tool 注册与执行

```text
首要入口：packages/core/tools、具体 tool-* packages
核心问题：Tool Schema、可见范围、参数、策略、执行、结果、呈现
核心事实：Tool Registry 与 Tool Execution
主要扩展：Tool 注册、tools/* Events、Tool Presentation
```

Tool Schema 是模型看到的接口，Tool Implementation 是 Runtime 执行的能力。新增 Tool 时需要同时考虑模型呈现、执行路径、权限策略和 Session Log 结果。

### 整体 Runtime 与领域 Runtime

“Runtime”在 Harness 中有两个层次：

```text
整体 Agent Runtime
→ Root Context 下由全部 Plugins、Fibers 和 Services 组成的运行系统

领域 Runtime
→ 某个领域对外提供的长期运行 Service，例如 ToolRuntime、LlmRuntime
```

领域 Runtime 不是 Cordis 的统一特殊类型，而是领域 Service 的命名。`ToolRuntime`、`LlmRuntime`、`SubagentRuntime`、`CodeRuntime`、`SubprocessRuntime` 和 `WebRuntime` 原则上都可以由 Plugin 提供和替换。工程中更常替换 Provider 或 Adapter；整体替换领域 Runtime 会同时影响注册、调度、事件和 Consumers，改动范围更大。

默认组合通常让这些 Services 位于 Root Runtime 可见的共享 Context 作用域，供 Agent Loop 等 Consumers 使用。但每个 Service 的生命周期属于注册它的 Provider Plugin Fiber，不属于 Root Fiber，也不属于 Agent Loop。

#### ToolRuntime 的简要结构

`ToolRuntime` 是注册为 `ctx.tools` 的领域 Service，依赖 System Prompt，并把 Tool 从注册推进到模型呈现和实际执行：

```text
ToolRuntime
├─ Scoped Tool Layers：按 Context/Fiber 管理 Tool 注册与可见性
├─ Restrictions：限制当前作用域可见或可用的 Tools
├─ Presentation Mode：决定 Tool Schema 如何呈现给模型
├─ Guards / Policy：在执行前后实施策略
└─ Execution Pipeline：查找、调度并执行 Tool
```

主要能力可以概括为：

```text
register / get / schemas
→ 注册、查找并生成模型可见的 Tool Schemas

restrict / guard / presentAs
→ 控制可见性、执行策略和呈现方式

execute
→ 运行 pre-execute、Guard、Tool Implementation 和 post-execute 链路
```

Tool 注册仍是 Effect：注册 Plugin Fiber 卸载时，相应 Tool、限制与 Guard 一并清理。

### LLM 接入

```text
首要入口：packages/llm/llm、packages/llm/llm-*
核心问题：统一请求、Adapter 路由、厂商协议、Stream、Retry、Token Meter
核心事实：统一 LLM Request / Stream
主要扩展：LLM Adapter 注册与请求 Waterfall
```

`llm/llm` 定义统一能力，具体 `llm-*` package 提供 Provider Adapter。Agent Loop 只依赖统一 LLM Service。

### Filesystem、Shell 与执行环境

```text
首要入口：packages/fs、packages/shell、packages/subprocess、packages/terminal
相邻领域：packages/sandbox、packages/e2b、packages/lsp
核心问题：文件访问、命令执行、进程、PTY、隔离与远程执行环境
核心事实：各 Capability Service 的当前 Provider
主要扩展：Service Definition / Provider / Consumer，能力级 Policy Events
```

这些能力具有分层关系。模型调用 Tool，Tool 消费 Filesystem 或 Shell Service，具体 Provider 再选择本地、Sandbox 或 E2B 实现。替换底层 Provider 可以让多个上层 Consumers 一起迁移。

### SubAgent、Jobs 与 Workflow

```text
首要入口：packages/subagent、packages/jobs、packages/workflow
核心问题：委派、后台执行、所有权、并发、继续运行和清理
核心事实：子任务各自的 live state 与 Session Events
主要扩展：Provider Registry、控制 Tools、生命周期 Events
```

SubAgent 通常拥有独立 Agent 与 Session；Jobs 管理后台工作；Workflow 提供可替换的工作流执行能力。三者可能协作，但不共享同一个职责。

### Compaction 与上下文控制

```text
首要入口：packages/compaction、packages/spill、packages/context
核心问题：上下文窗口、历史压缩、大结果外置、模型可见上下文
核心事实：Session Log 与可重建的模型输入
主要扩展：Compaction Provider、Policy Plugin、Context Provider
```

这些能力调整模型最终看到的内容，但必须遵守 `Model-visible ⟺ logged`，不能建立无法从 Session Log 重建的隐藏上下文。

### Human Interaction

```text
首要入口：packages/interaction、packages/plan、packages/goal、packages/feedback
核心问题：审批、提问、命令、计划、目标和人工反馈
核心事实：按领域分别落在 live state 或 Session Events
主要扩展：Interaction Service、Commands、Tools、Agent Events
```

人工交互不等于普通模型 Tool Call。定位时先判断它是模型发起的交互、用户直接命令，还是需要持久化的会话状态。

### Web Host、API 与 Typert

```text
首要入口：packages/host、packages/api、packages/typert、apps/web
核心问题：服务端入口、RPC、类型图、对象解析、HTTP 与 WebSocket
核心事实：Runtime 对外暴露的类型化操作与事件
主要扩展：Remote、Typert Registry、Host Plugin
```

Host 和 API 将 Agent Runtime 暴露给远程客户端，但不拥有 Agent 与 Session 的核心语义。业务事实仍由对应 Runtime 领域维护。

### Web Client

```text
首要入口：packages/client/*、apps/web/src
核心问题：连接、客户端对象、Conversation Node、Slots、Renderer 和交互状态
核心事实：客户端投影与 UI state
主要扩展：Client Module、Slot Contribution、Conversation Node、Renderer
```

Web Client 消费 Session Events 和远程操作，将 Runtime 事实投影成界面。窗口不是 Agent Runtime 的领域对象。

### 外部自动化协议

```text
首要入口：packages/acp、packages/sdk、python/
核心问题：ACP、JSON-RPC、TypeScript SDK、Python SDK
核心事实：同一 Agent Runtime 的协议投影
主要扩展：Protocol、Server、Client
```

这些入口复用同一 Agent spine。定位问题时要区分 Runtime 语义错误和协议映射错误。

### 启动、组合与分发

```text
首要入口：apps/cli、packages/boot、packages/bundle
核心问题：Profile、Patch Layers、Loader、Bundle 和应用启动
核心事实：最终 Plugin Entry Tree
主要扩展：Bundle Patch、Profile Patch、CLI Overlay
```

如果需求只是改变某个部署装载哪些 Plugins 或使用哪个 Provider，优先考虑 Patch 与 Bundle，不要先修改能力实现。

### Settings、Credentials 与 Storage

```text
首要入口：packages/settings、packages/credentials、packages/storage
核心问题：用户设置、秘密值、授权和非 Session 数据保存
核心事实：分别由对应 Service 与 Provider 管理
主要扩展：文件 Provider、Credential Provider、Storage Backend
```

Settings 保存普通用户偏好；Credentials 管理秘密引用和授权；Storage 保存不属于 Session Log 的领域数据。三者不能因为都需要落盘而混成一个领域。

## 需求到入口的快速索引

| 需求或现象                         | 首要入口                                                               | 首先确认                                    |
| ---------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------- |
| Agent 卡在执行中或 Inbox 行为异常  | `packages/core/agent*`                                                 | live phase、Inbox、Turn/Step                |
| 重启后对话丢失或恢复错误           | `packages/core/session`、`packages/session`                            | Session Log、Persistence、Projection        |
| 模型看到了错误的指令或上下文       | `packages/core/system-prompt`、`packages/context`                      | Prompt Assembly、模型可见记录               |
| 模型看不到 Tool 或 Tool 无法执行   | `packages/core/tools`、具体 `tool-*`                                   | Schema 可见性与 Implementation 查找是否一致 |
| 接入或替换模型厂商                 | `packages/llm`                                                         | Definition、Adapter、Stream 转换            |
| 文件或命令需要切换本地与远程环境   | `packages/fs`、`packages/shell`、`packages/subprocess`、`packages/e2b` | Capability Provider 与共享执行世界          |
| SubAgent 无法继续、取消或清理      | `packages/subagent`、`packages/jobs`                                   | ownership、Session、后台生命周期            |
| API 请求失败但 Runtime 行为正常    | `packages/api`、`packages/typert`、`packages/host`                     | 协议验证、对象解析、远程分发                |
| UI 没有正确展示已有 Session Event  | `packages/client`                                                      | 客户端投影、Conversation Node、Renderer     |
| 某个 Profile 缺少或错误装载 Plugin | `apps/cli`、`packages/boot`、`packages/bundle`                         | Patch Layer 顺序与最终 Entry Tree           |
| 用户设置或密钥未生效               | `packages/settings`、`packages/credentials`                            | 普通设置与秘密值的职责分离                  |

## 跨领域需求的定位方法

一个真实需求通常跨越多个 packages，但仍应先确定一个事实拥有者。

```text
事实拥有者
→ 对外定义 Service / Event / 数据类型
→ Provider 提供具体实现
→ Consumer 在自己的职责内使用它
→ Bundle 决定部署时装载哪些实现
```

以“替换文件系统”为例，粗略关系是：

```text
Filesystem Definition
← Local 或 E2B Provider
← Tool、Shell、LSP 等 Consumers
← Bundle / Patch 选择部署实现
```

定位时避免两种误区：

- 从 Consumer 看到具体行为，就把能力实现写进 Consumer；
- 因为最终需要修改多个 packages，就认为多个领域共同拥有同一事实。

跨领域不等于职责不清。多数情况下仍然只有一个事实拥有者，其他部分只是 Provider、Consumer、协议投影或部署组合。

## 本阶段的三个推演任务

每个任务回答：事实归谁、从哪里开始读、会经过哪些扩展机制、最终由哪个 Profile 或场景装载。

### 任务一：新增一个 Model-facing Tool

Model-facing Tool 是直接暴露给模型、允许模型主动调用的 Runtime 接口。模型主动使用外部能力时只能发出 Tool Call；Service、Provider 和 Plugin 内部 API 对模型不可见。

```text
System Prompt / Messages / Runtime Context
→ Runtime 主动提供给模型的信息

Model-facing Tool
→ 模型主动请求 Runtime 执行能力的入口

Service
→ Plugins 之间调用的内部能力
```

Tool 与 Capability 的关系通常是：

```text
Model
→ Model-facing Tool
→ Capability Service
→ Provider
→ 外部系统
```

例如文件读取：

```text
Model
→ read Tool
→ Filesystem Definition：ctx.fs
→ Local / Sandbox / E2B Provider
→ 实际文件系统
```

新增 Tool 时先判断它调用的真实能力是否已经存在：

```text
已有底层 Capability
→ 新增 Tool Consumer

没有底层 Capability，但能力需要复用或替换
→ 设计 Definition + Provider + Consumer

只服务模型且逻辑简单，不需要复用或替换
→ Tool 可以直接实现，不必为了形式额外建立 Seam
```

Capability 适合独立抽象的信号包括：多个 Tools 或 Plugins 需要调用、存在本地与远程等多种实现、Provider 需要独立演化，或者非模型入口也需要复用。

一个完整 Model-facing Tool 横跨四个职责面：

```text
模型呈现
→ Tool Schema：名称、描述、参数和返回语义

执行
→ 参数验证、调用领域 Service、形成结构化结果

权限与策略
→ tools/pre-execute → tools/execute → tools/post-execute

持久事实
→ Tool Call 与 Tool Result 进入 Session Log
```

Tool Plugin 负责模型交互层，不应重新实现已有 Capability，也不应拥有具体厂商协议、连接池、凭证存储或底层重试策略。

任务一的定位结果：

```text
事实拥有者：Tool 背后的领域 Capability；仅模型内部状态 Tool 可由自身拥有
首要入口：对应领域 Definition + 同类 tool-* Consumer
相邻领域：core/tools、相关 Policy / Approval / Sandbox、core/session
扩展机制：Service inject + Tool 注册 + tools/* Live Events + Session Events
运行入口：Bundle Patch 或 Profile Patch
```

完成判断：

```text
模型能正确发现和调用
Runtime 能找到并执行
Policy 能限制危险操作
Session Log 能重建 Tool Call 与 Tool Result
```

### 任务二：替换 LLM 或 Filesystem Provider

Capability Seam 不是 Cordis 的独立运行时实体，而是 Definition、Provider 和 Consumer 之间的架构关系：

```text
Provider ──实现并注册──▶ Definition
Consumer ──依赖并使用──▶ Definition
```

Runtime 中实际存在的是 Plugin、Fiber、Service 与 inject 关系，不存在一个单独的 Seam 实例。以 Filesystem 为例：

```text
fs-local / fs-e2b Provider Plugin
→ 实现 FileSystem Definition
→ 注册 ctx.fs

tool-fs Consumer Plugin
→ inject fs
→ 通过 ctx.fs 使用当前 Provider
```

Definition 通常不是 Patch 单独加载的 Plugin。Provider 与 Consumer 在代码层共同依赖 Definition package；Loader 导入这些 Plugins 时，模块系统自然加载 Definition。Provider 激活后才在 Runtime 中注册 Service 实例。

```text
代码层：
a-provider ──dependency──▶ a Definition
tool-a     ──dependency──▶ a Definition

Runtime 层：
a-provider → ctx.a ← tool-a
```

Consumer 在自己的 Plugin 定义中声明 `inject`：

```ts
export const name = "tool-a";
export const inject = ["a"];

export function apply(ctx: Context) {
  // ctx.a 可用后才会执行
}
```

永久依赖写在 Consumer Plugin 的 `inject` 中；仅某个部署额外要求的依赖可以写在 Entry 的 `inject` 中。Plugin 自带依赖与 Entry 依赖最终合并到 Fiber。

架构关系、物理目录、Runtime 和部署配置是四个不同层次：

```text
架构层：Capability Seam
→ Definition / Provider / Consumer 的职责关系

代码层：Capability Family
→ 在一个 package group 中收敛主要 Definition、Providers、Consumers 和 Policies

Runtime 层：Service + Fiber + inject
→ Provider 注册 Service，Consumer 等待并调用

部署层：Bundle / Patch Layer
→ 选择本次运行装载哪个 Provider 和 Consumer
```

Capability Family 可以在物理目录中收敛维护，但不要求把所有间接 Consumer 强行移动到同一个目录。一个 Plugin 对 Harness 都只是 Plugin；Provider、Consumer、Tool 和 Policy 是它在架构关系中承担的角色。一个 Plugin 也可以同时承担多个角色。

#### Patch Layer 如何组装 Capability A

假设 Capability A 包含三个 packages：

```text
@demo/a           Definition
@demo/a-provider  Provider Plugin，提供 ctx.a
@demo/tool-a      Consumer Plugin，inject a 并注册 Model-facing Tool
```

Patch Layer 只装载两个运行时 Plugins：

```yaml
- insert:
    - id: a-provider
      name: "@demo/a-provider"
      config: {}

    - id: tool-a
      name: "@demo/tool-a"
      config: {}
```

Definition 由两个 Plugins 的代码依赖加载，不需要额外添加 `a-definition` Entry。即使 Consumer Entry 排在 Provider 前面，缺少 `a` 时 Fiber 也只会保持 Pending；Provider 注册 `ctx.a` 后，Reflect 刷新并激活 Consumer。

#### Patch Layer 如何替换 Provider

Patch 不需要声明 `seam: filesystem`。Provider 与 Seam 的关联已经由代码中的 Definition 实现和 `ctx.fs` 注册建立；Patch 只选择装载哪个 Plugin。

最小替换模式：

```yaml
- id: old-provider
  disabled: true

- insert:
    - id: new-provider
      name: "@demo/new-provider"
```

例如将 Filesystem 从 Local Provider 切换为 E2B：

```yaml
- id: fs-local
  disabled: true

- insert:
    - id: e2b
      name: "@deepseek-ai/dsh-e2b"
      config:
        cwd: !!js process.cwd()

    - id: fs-e2b
      name: "@deepseek-ai/dsh-fs-e2b"
```

旧 Provider 必须禁用，因为 `fs-local` 与 `fs-e2b` 在同一作用域都会注册 `ctx.fs`；同时激活会因重复 Service 直接失败。

Provider 是否公用没有 `public` 或 `shared` 字段，而由 Service 注册位置与 Context isolate scope 决定：

```text
同一个 Service key
+ 同一个 isolate scope
+ 多个 Consumers
= 共用一个 Provider
```

Provider 默认也不知道有哪些 Consumers。Cordis 不维护 `Service → Consumer Fibers` 反向表；Provider 只会观察到实际调用，以及 Capability API 显式传入的调用上下文。需要调用方身份时，必须把身份或 Context 设计进 Capability 的调用协议。

#### 共享执行世界

接口相同不保证外部环境一致。Filesystem、Subprocess、Shell、Terminal 与 LSP 等能力可能需要指向同一个执行世界。切换到 E2B 时通常至少同步替换 Filesystem 与 Subprocess Providers：

```yaml
- id: subprocess
  disabled: true

- id: fs-local
  disabled: true

- insert:
    - id: e2b
      name: "@deepseek-ai/dsh-e2b"

    - id: subprocess-e2b
      name: "@deepseek-ai/dsh-subprocess-e2b"

    - id: fs-e2b
      name: "@deepseek-ai/dsh-fs-e2b"
```

这样 File Tools 与 Shell 等 Consumers 才会通过各自的 Capability 看到同一个 E2B 工作区。共享执行世界也没有通用配置字段，需要从 Capability 文档、Provider 职责和 Bundle 组合判断。

任务二的定位与验证结果：

```text
Service Definition：稳定接口与 Service key
Service Provider：可替换实现，注册该 Service
Consumers：只依赖 Definition，不感知具体 Provider
组合入口：Bundle / Profile Patch 选择 Provider Plugin
验证路径：从真实 Consumer 行为验证接口、作用域与外部世界一致
```

Provider 替换的成功标准不是“新 Service 已注册”，而是所有相关 Consumers 通过同一 Definition 观察到正确且一致的外部世界。

### 任务三：新增 UI Surface 或拦截 Tool Call

这其实是两类需求：UI Surface 投影 Runtime 事实；Tool Call Interceptor 参与 Tool 执行。先判断需求是否改变事实，再决定修改客户端、服务端扩展点或 Session Log。

#### 新增 UI Surface

UI 负责展示 Runtime 已有事实和发起操作，不拥有 Agent、Session 或 Tool 的领域事实。

```text
只改变已有数据的展示
→ Client Renderer / Slot / Conversation Node

浏览器还拿不到所需数据或操作
→ Host / API / Typert 暴露类型化查询、命令或事件

产生需要重启后恢复的新事实
→ 由事实拥有者定义 Session Event，再由服务端与客户端投影
```

例如，为已有 Tool Result 增加专用卡片，只需要客户端 Renderer；为界面增加“批准本次执行”操作，则需要 Interaction 或 Tool Policy 领域拥有操作语义，并通过 API/Typert 暴露给客户端。

#### 拦截 Tool Call

Tool 执行的扩展链可以概括为：

```text
Tool Call
→ tools/pre-execute
→ Tool Guard
→ Tool Implementation
→ tools/post-execute
→ Tool Result
→ Session Log
```

不同需求对应不同入口：

```text
执行前检查、审批或拒绝
→ tools/pre-execute 或 Guard

执行后观察、统计或临时反馈
→ tools/post-execute Live Event

改变真正的 Tool 能力
→ Tool Implementation 或其依赖的 Capability Provider

需要恢复、回放或进入后续模型上下文
→ 新增或扩展 Session Event
```

Live Event 表示当前进程中的通知和协调；Session Event 表示持久事实。一次状态既需要实时推送又需要重启后恢复时，应先由 Session Event 建立事实，再由服务端将其投影给客户端，不能只依赖 WebSocket 通知。

定位顺序：

```text
1. 所需数据是否已经存在？
2. 它是临时 live state，还是需要恢复的 durable fact？
3. 浏览器是否已经能通过现有 API、事件或投影访问？
4. 最后才选择 Renderer、RPC、Tool Event、Guard 或 Session Event。
```

任务三的定位结果：

```text
事实拥有者：Agent、Session、Tool 或 Interaction 等对应 Runtime 领域；UI 只拥有界面状态
服务端入口：事实拥有者的 Service/Event；需要远程访问时经过 Host、API 与 Typert
客户端入口：Client Module、Slot、Conversation Node 或 Renderer
Live Event 或 Session Event：临时协调使用 Live Event；可恢复事实使用 Session Event
呈现与执行的关系：Renderer 解释执行结果；Interceptor 通过 Tool Runtime 扩展点参与执行
```

## 完成标准

第三阶段完成时，应该能够：

1. 面对一个需求，先指出主要领域和事实拥有者；
2. 区分 Definition、Provider、Consumer 和部署组合；
3. 判断应使用 Session Event、Live Event、Service、Patch 还是 RPC；
4. 说明首要阅读入口和两个以内的相邻领域；
5. 完成上面三个推演任务，不要求函数级调用栈。

本阶段的目标不是记住所有目录，而是形成一条稳定的定位路径：

> 需求 → 事实拥有者 → 扩展机制 → 相邻领域 → 运行组合。
