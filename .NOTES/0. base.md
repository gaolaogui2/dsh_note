# DeepSeek Harness 学习基线

> Cordis + Harness conventions + Plugins + Distribution/Composition + runtime surface = DeepSeek Harness

分别表示：

- Cordis：插件、Service、Context、Fiber 和生命周期内核。
- Harness Conventions：Agent、Session、Tool、LLM、Capability Seam 等稳定约定。
- Plugins：这些约定的具体实现。
- Distribution / Composition：通过 Package、Bundle、Profile、Patch 交付并组装 Plugins。
- Runtime Surfaces：通过 Web、Headless、ACP、SDK 等 Controller 对外提供能力。

## 价值

模型本身是黑箱，而真正决定 Agent 能否稳定工作的是模型外围的 harness engineering：上下文如何进入模型、工具如何执行、状态如何持久化、权限如何约束、失败如何恢复，以及不同交互入口如何复用同一套 runtime。
过去这层能力通常隐藏在 Claude Code、Codex 等具体产品内部；DeepSeek Harness 将它作为完整的开源工程对象暴露出来。

它的关键价值不只是“支持插件”，而是用同 1 种组合模型组织 Agent runtime：

- Cordis 管理插件、服务、事件、作用域和生命周期。
- Session Log 统一模型上下文、恢复、回放、fork、审计和 UI 投影所依赖的持久事实。
- Capability Seam 将能力定义、Provider 和 Consumer 分开，使 LLM、Tool、Filesystem、Sandbox、Subagent 等实现可以替换。
- Web、Headless、ACP 和 SDK 复用同一条 Agent spine，而不是各自实现一套 Agent。

它与 webpack 的相似点不是二者都有 plugin，而是都把变化频繁的实现组织在稳定的组合机制之后：webpack 组合构建能力，DeepSeek Harness 组合 Agent runtime 能力。因此，它更像一个可以持续改造的 runtime substrate，而不是功能固定的 Agent 应用。

DeepSeek Harness 的高价值已经成立：

1. **学习价值**：它提供了少见的、可以完整研究的现代 Agent runtime 实现。
2. **工程价值**：它能承载模型、工具、sandbox、权限、subagent、workflow 和交互入口的定制。
3. **行业参考价值**：它把 session event sourcing、capability seam、插件生命周期和多运行形态投影变成了可讨论、可验证的公共设计。

尚未确定的是它能否成为行业事实标准。这个结果取决于稳定 API、插件开发体验、组合可预测性、分发与兼容机制、真实使用规模和刚需场景，而不只取决于架构是否先进。

> 技术、学习和工程价值已经成立；平台与生态价值正在验证；行业标准地位仍需时间决定。

## 学习目标

先粗读并建立全局概念，再沿主链路和具体问题逐层深入。第一轮不追求理解所有实现细节，也不遍历全部 package；先知道项目由哪些部分组成、各部分为什么存在、彼此如何连接。

最终需要形成 3 层掌握：

1. 架构级掌握：能说清楚 Harness 为什么是插件树，session log 为什么是事实源，agent-loop 为什么要瘦，能力为什么拆成 seam。
2. 链路级掌握：能跟踪一次请求：用户输入 → agent inbox → turn/step → prompt assembly → LLM stream → tool execution → session event → UI/下一步。
3. 定位级掌握：遇到需求时知道该先看哪里，并能继续找到事实所有者、扩展点和验证证据。

学习顺序遵循一个原则：

> 先建立地图，再走通主路，随后认识区域，最后研究局部机制。

## 第一阶段：全景概念

预期时间：2～3 小时。

目标：只理解 5 个全局关键词，形成 DeepSeek Harness 最小架构认知，不进入源码、运行链路或工程细节。

### 五个关键词

1. **Cordis**：底层插件框架，提供 Context、Service、Event 和生命周期管理。
2. **Harness**：围绕模型组织上下文、工具、状态、执行和交互的 Agent runtime。
3. **Plugin**：Harness 的基本组成单元；核心能力和外围功能都通过插件装配。
4. **Session Log**：Agent 经历的持久事实源，支撑上下文重建、恢复、回放和投影。
5. **Capability Seam**：一项可替换能力的完整拆分，由 Service Definition、Provider 和 Consumer 组成。

五个概念的关系：

```text
Cordis
└── 运行和管理 Plugin
    └── 组合成 Harness
        ├── 用 Session Log 保存持久事实
        └── 用 Capability Seam 组织可替换能力
```

### 阅读入口

只读以下文档的概念性部分：

- [项目 README](../README.md)
- [架构总览](../docs/architecture.md)
- [Cordis primer](../docs/cordis-primer.md)

只关注这五个关键词的含义与关系。暂时跳过 Agent、Session、Turn、Step 等领域对象细节，以及目录结构、源码、并发、取消、错误恢复、测试和 Agent Note。

### 阶段产物

能用自己的话解释五个关键词，并复述它们的关系图即可进入下一阶段，不要求源码证据。

## 第二阶段：走通主链路

目标：把第一阶段的静态地图连成一次完整运行过程，理解数据和控制权如何流动。

1. `dsh web` 如何变成一棵运行中的插件树。

### 阶段产物

任选三个假设需求，写出初步定位：

- 新增一个 model-facing tool。
- 替换一个 LLM 或 filesystem provider。
- 新增一个 UI surface 或拦截一次 tool call。

每个需求只需说明可能涉及的 package、扩展机制和运行入口。

## 第四阶段：专题精读

预期时间：每个专题 6～12 小时；Agent runtime、Session architecture 和 Web architecture 通常需要 8～16 小时。

目标：围绕实际兴趣或真实任务深入一个领域，不按目录顺序遍历仓库。

推荐专题：

1. Cordis 生命周期：Context、Service、Plugin、Inject、Effect、Event、Waterfall、Fiber、Scope。
2. Agent runtime：Inbox、Turn、Step、pre-step、request、stream、tool scheduling、turn closure。
3. Session architecture：event vocabulary、deriveMessages、persistence、projection、fork、compaction。
4. Tool runtime：schema、scoping、execution mode、policy、guard、result context、presentation、Code Mode。
5. Capability seam：选择 LLM、filesystem、shell、subagent 或 workflow，研究完整 Definition / Provider / Consumer。
6. Web architecture：Connection、Typert Remote、API Proxy、Client runtime、Conversation Node 和 slots。
7. Distribution：profile、bundle、settings、credentials、Harness home、ACP 和 SDK。

每次只选择一个专题，先读 subsystem reference 和 package README，再进入源码。相关 Agent Note 用于理解设计理由和被放弃的方案，不代替当前实现。

### 阶段产物

对选定专题完成一份结构化总结：

```text
职责：它拥有哪个问题？
核心对象：有哪些稳定概念？
协作关系：上游、下游和扩展点是什么？
事实存放：状态属于 session log、live state、service state 还是 sidecar？
关键取舍：获得了什么，承担了什么代价？
```

## 第五阶段：源码验证与实践

预期时间：持续进行，按单项实践估算。

目标：把专题理解落实到函数、事件、生命周期和测试证据，形成可以修改代码的工程能力。

每个结论使用同一条证据闭环：

```text
概念
→ 找到声明者
→ 找到生产者
→ 找到消费者
→ 跟踪一次真实运行
→ 确认事实存放位置
→ 确认生命周期与失败语义
→ 找到测试、snapshot 或 invariant
→ 总结收益、代价与替代方案
```

源码验证模板：

```text
问题与约束：它解决什么问题，受什么限制？
事实所有权：谁拥有状态，谁只能消费或投影？
实现机制：Service、Event、Plugin、SessionEvent 或配置如何协作？
验证证据：哪个源码位置和哪类测试证明该结论？
收益与代价：获得了什么，又牺牲了什么？
```

实践任务从小到大推进：

1. 追踪一个事件或 tool 的声明、注册、调用、日志和测试：2～4 小时。
2. 修改一个局部配置，通过 `--dump-config` 验证 composition 结果：1～2 小时。
3. 编写一个最小插件或 tool，理解注册和卸载：4～8 小时。
4. 替换一个 provider，验证 Consumer 不依赖具体实现：8～16 小时。
5. 完成一个真实小改动，并按 testing policy 选择最小充分证据：通常 1～3 天。

这一阶段再深入以下细节：

- `followup`、`steer` 和 `inject` 的调度差异。
- Waterfall 的 `next()`、短路和 listener 顺序。
- cancellation、error recovery、parallel/exclusive tool scheduling 和 teardown。
- source plane、artifact plane、real composition、snapshot 与 real-API e2e。
- README/JSDoc、Agent Note、doc-sync、typecheck 和 relevant checks。

## 总体完成标准

学习没有固定时间期限。前 3 个阶段通常需要约 10～16 小时有效专注时间；每个阶段达到对应产物后再进入下一阶段，也可以因为真实任务暂时跳到某个专题，之后再补齐前置理解。

最终应能独立回答：

- DeepSeek Harness 的核心架构由哪些部分组成？
- 一次请求如何从输入流经 Agent、LLM、Tool、Session log 和 UI？
- 为什么 model-visible input 必须进入 session log？
- 为什么扩展通常不应修改 agent-loop？
- 为什么 capability seam 包含 Definition、Provider 和 Consumer？
- 新增能力、替换 provider、添加 tool 或 UI surface 时应该从哪里开始？
- 应使用哪些代码、运行结果、测试、snapshot 或 invariant 验证结论？

## 评价框架

粗读阶段使用简化版本：

> 当前实现 = 解决的问题 + 核心机制 + 获得的能力

精读阶段使用完整版本：

> 当前实现 = 问题与约束 + 事实所有权 + 实现机制 + 验证证据 + 收益与代价

判断 Harness 能否成为 Agent 基座，重点看以下六项。

### 1. 领域对象

Agent、Session、Turn、Step、Tool、LLM adapter 和 SessionEvent 等抽象能否表达恢复、取消、并发、fork、compaction 与多种运行入口。

### 2. 事实源

`model-visible means logged` 是关键。如果 session log 能一致支撑 replay、audit、fork、compaction、SDK 和 UI projection，它就是基座级设计。还要检查哪些事实有意留在 live state 或 sidecar，以及这种分离是否清晰。

### 3. 扩展点

新需求应主要通过 service、event、plugin 和 composition 接入。频繁修改 agent-loop 意味着扩展点没有吸收变化。

### 4. 能力拆分

LLM、tools、fs、subprocess、sandbox、subagent、workflow、credentials 和 settings 应有明确所有权，并能在稳定接口后独立替换。

### 5. 分发形态

Web、Headless、ACP、SDK、profiles、bundles、settings 和 credentials 应覆盖真实开发者工作流，并共享同一套核心语义。

### 6. 生态治理

文档、兼容性、插件开发体验、版本迁移、测试工具和调试体验，决定项目能否从好架构发展为可持续生态。

## 生态判断

能否从高价值的 Agent runtime 发展为行业基座，取决于以下条件：

1. Service、event 和 schema 是否逐渐形成稳定 API。Developer preview 阶段的破坏性变化是主要生态风险。
2. 插件模板、示例、本地调试、typed API、发布规范、兼容性检查和发现机制是否足够低摩擦。
3. 插件安装、声明、启用、配置和升级是否形成清晰的默认分发路径。
4. 开发者是否形成持续扩展 Agent runtime 的真实需求。
5. 插件自由度是否受事实所有权、service/event 纪律、安全策略和兼容性验证约束。

> 自由扩展 + 严格边界 + 可验证兼容

Harness 的 service、event 和 session-log 纪律正在建立这组边界。
