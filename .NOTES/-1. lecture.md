## 表述标准

以下标准用于本文各章节的整理与审阅。

**1. 固定内容边界**

以指定目录及其层级为范围，先明确本节的主题、要解决的问题，以及与相邻章节的分工。正文围绕本节主题展开，细节深度与所在层级匹配。其他章节负责的内容，只保留理解当前主题所需的衔接，并引用其已有说明。

**2. 精炼**

在保留关键信息、表达精度和可读性的前提下，减少表述体积。优先删除重复、赘述和无助于理解的铺垫；保留必要的定义、关系、条件、限制和例子。精炼以读者更容易准确理解为标准，字数只是辅助指标。

**3. SSOT**

同一项内容保留一处完整说明，其他位置按需引用。去重同时覆盖指定目录内部的重复，以及当前目录与前面已经整理并固定内容之间的重复。沿用已有定义、机制和结论，当前章节只补充自身主题所需的新信息。

引用处保留必要的定位或衔接，让当前段落独立可读；完整定义、机制和论证由原位置维护。发现前文需要修正时，修改其所属位置，再同步引用。

**4. 可读性**

按读者理解所需的顺序引入概念：先交代具体对象及其用途，再解释关系和机制。术语首次出现时给出必要定义；句子明确主体、动作和对象，指代能直接找到对应内容。抽象关系难以理解时，用一个最小例子说明。可读性是独立的验收要求，文字准确、简短，也需要让读者容易理解。

**5. 事实与判断**

明确区分通用概念、具体实现、分析判断和演进建议。描述实现时给出依据；评价优劣时说明适用条件与比较标准；尚未验证的内容标明不确定性。前文已固定的结论，沿用相同术语和成立范围。

**执行顺序**：明确主题与分工 → 确认已有内容及其所属位置 → 补齐本节必要信息 → 去重与精炼 → 检查可读性、精度和完整性。

**冲突处理原则**：精炼以信息完整、表达准确和阅读顺畅为前提；SSOT 通过集中维护完整说明、保留必要衔接来实现。

## 一、总览

Agent = **Model + Harness** ：

- Model 提供推理与决策能力，
- Harness 负责组织上下文、调用模型、执行工具，并管理状态、权限与运行过程，

2 者共同构成可执行任务的 Agent 系统。

**定位与需求**

DSH 是 1 个开源、插件化的 Agent Runtime，为模型执行任务提供上下文、工具、交互、会话与安全控制。
这里关注它的跨场景组合与复用：在满足行为、安全和恢复要求的前提下，通过局部替换适配不同模型、执行环境和交互入口，控制接入与维护的成本。

**架构设计**

**Pattern**：针对不同的业务场景，社区有相应的成熟方案：

- 构成稳定的应用适合直接代码写入实现；
- 需要任务步骤明确可控的场景适合显式流程编排；
- 能力与入口持续变化的系统适合插件化与接口分离。

这些方案可以组合，分别处理系统组装与任务执行中的变化。
它们在 Harness 出现之前已有广泛实践：业务需求随时代变化，但底层的架构原则与设计模式相对稳定。

**DeepSeek Mapping**：DSH 以 Cordis 为插件运行基础，用 Capability Seam 组织可替换能力，用配置组合场景，并由 Agent、Workflow 等插件承载执行策略。
核心与扩展采用同 1 插件模型，使用方通过能力接口复用不同实现。

**主要取舍**

- **组合复用**：相较直接代码组装，可减少替换实现对使用方的影响；代价是需要理解依赖、作用域和生命周期。
  收益取决于能力划分是否合理，以及替换与组合的实际频率。
- **开放实现**：开源支持审计、定制、私有部署和自行维护，也需要部署方承担相应维护责任。
- **会话连续性**：DSH 要求模型可见内容能从 Session Log 重建，为上下文、输出和恢复提供共同事实来源。
  这是独立于插件化的日志约束，代价是记录、存储与敏感数据管理。

**风险与处理原则**

组合与替换需要验证行为和生命周期；扩展执行需要授权与隔离；故障恢复需要区分日志持久化与外部操作结果。
日志完整性还需兼顾敏感信息保护与数据保留要求。

**依据与演进**

设计依据见 [项目架构说明](../docs/architecture.md)。
上述取舍属于定性分析，实际成本与性能收益需在明确场景下对照验证。

**Roadmap（本文建议）**：持续关注跨场景复用、组合诊断、协议与数据迁移，以及扩展分发和开发体验。
以实际接入障碍和维护成本确定改进优先级。

## 二、宏观架构

本章以图定位能力，以表查阅 Seam 的职责与实现，建立 DSH 的整体结构认识。
具体时序、状态变化与异常处理由 [链路](#三链路) 章节展开。

**Cordis 扩展机制**

Cordis 通过 Plugin 装配功能，并以 Context、Service、Event、Fiber 和 Effect 提供统一的访问、扩展与卸载机制。
预设 Service 与自定义 Service 在 Cordis 中定位相同；区别只在于预设 Service 已有默认装配和 Consumer。

```text
Cordis Runtime
├─ Context：提供作用域与 Service 访问
├─ Plugin：装配功能
│  └─ Fiber：承载 Plugin 实例与生命周期
├─ Service：提供稳定能力入口
│  ├─ Method：供 Consumer 直接调用
│  └─ Registry：注册与发现可扩展内容
├─ Event：在运行阶段观察、追加、修改或拦截行为
└─ Effect：登记清理函数，在 Plugin 卸载时撤销注册或释放资源
```

Registry 是 Service 组织可扩展内容的方式，不是独立的 Cordis 原语。
Registry 扩展系统具有什么能力，Event 扩展运行到特定阶段时允许发生什么行为；自定义扩展还需要 Consumer，才能进入实际业务流程。
Effect 不保存资源本身，而是保存如何撤销 Plugin 创建的注册关系或释放运行资源。

**能力构成与主要调用路径**

图以默认 Agent Loop 的执行方式为主，展示从启动装配到 Controller 返回结果的主要路径。

## 三、链路

**启动装配、请求执行、控制与恢复，是快速理解 Runtime 运行过程的通用划分。**
可将其作为分析不同 Harness 的通用框架：它不与任何 Harness 强绑定，也不代表具体实现中的模块划分或固定执行顺序。

这里以 DSH 的默认插件组合为例。

**运行主线**

- 启动装配：Profile / Bundle / Patch → Cordis 插件树 → 依赖解析与生命周期激活 → Runtime 就绪。
- 请求执行：输入 → Agent Inbox → Turn / Step → 上下文装配 → 模型决策与工具执行循环 → 场景输出。
- 控制与恢复：运行中处理引导、取消、失败与超时，退出时等待进行中工作结束并释放资源；恢复时加载会话事实、重建状态并创建执行实例。

请求链描述默认 `ReactLoopAgent` 的执行方式，可随 Agent Plugin 替换。

启动装配、控制与恢复的职责及生命周期约束相对稳定；输入接纳后的 Turn、Step、模型请求与工具调用流程，由 Agent Driver 及相关服务共同实现。

会话日志贯穿执行过程，支撑模型上下文、输出投影和状态恢复；安全策略在相关能力调用处执行。

**场景与拆分**

以下是不同 Harness 场景常见的链路拆分需求，各场景可在主线内部按职责、并发和生命周期进 1 步拆分：

- 单次任务：输入、处理与输出；配合超时和退出清理。
- 持续交互：输入排队、多轮执行；配合引导、取消和会话续接。
- 长周期任务：分阶段推进、等待唤醒；配合检查点恢复、重试与补偿。
- 多 Agent 协作：任务分派、并行执行与结果集成；配合实例及依赖管理。
- 事件响应与批处理：接入、排队、调度与处理；配合失败重投和中断续行。

DSH 是可组合的通用 Agent Runtime：Controller 决定交互与存续方式，Agent Plugin 决定执行策略，Workflow、Subagent 等插件扩展任务组织方式。
场景差异体现在主线内部结构，效率与可靠性取决于调度、状态管理和资源控制的具体实现。

### 3.1 启动主链

**需求与约束**

启动负责将配置和环境中的选择转为可运行系统，确定实际组成、依赖状态与资源归属。
不同入口应能复用装配过程，并区分运行就绪、启动失败和启动期间的受控退出。
失败时需要保留定位依据，并释放已登记到运行树的资源。

本节以 Profile 启动为场景，只说明配置组织、自举、插件装配及结果交接。
配置算法与 Cordis 内部机制归入[实现](#五实现)，运行期控制归入[控制与恢复主链](#33-控制与恢复主链)。

**方案与选择**

系统可以由入口代码直接组装，也可以由框架管理组件，或根据声明生成运行实例。
DSH 组合框架管理与声明驱动：配置声明目标组成，Loader 将声明转为插件树，Cordis 管理依赖与生命周期。
这套设计支持入口复用和场景换装，同时引入配置优先级、作用域和生命周期的理解成本。

#### 3.1.1 宏观流程

```text
Launcher 接收启动参数
→ 配置组织：解析 Profile，形成有序 Patch 列表
→ 运行基础：创建 Cordis，挂载 Loader
→ 插件装配：Include 生成 Entry 声明，Loader 建立配置树，Cordis 建立运行树
→ 结果交接：启动逻辑等待插件装载和依赖解析完成，再判断运行就绪、失败或受控退出
```

配置树描述目标组成，Fiber 运行树承载插件实例、依赖与资源。
这些阶段表示职责交接；插件装载与依赖激活可以并发交织。

#### 3.1.2 Launcher：入口与自举协调

Launcher 是应用入口中的启动逻辑，由普通程序代码承担，该名称描述职责。
它选择启动输入，建立最小装配能力，提供公共启动信息与退出入口，并汇总启动结果。

> 启动自举：先创建 Cordis、挂载 Loader，再利用这组最小运行能力装配其余插件。

终端、IDE 或服务管理器可以启动承载 Harness 的进程，由 Node.js 执行入口文件；宿主也可在已有进程中调用启动函数。
`pnpm dsh --profile …` 是其中 1 种源码启动方式。

#### 3.1.3 配置来源与 Patch 组织

Profile 选择场景所需的 Bundle，并与用户配置、命令行参数和启动环境共同构成启动输入。
Launcher 按以下优先级从低到高汇集 Patch Layer：

1. Bundle 默认组合。
2. Profile 场景配置。
3. 所选 `$DSH_HOME` 内跨 Profile 的用户配置。
4. 命令行中按参数顺序提供的 1 个或多个 `--patch`。
5. Launcher 根据组合结果与环境生成的 Patch。

> Launcher 只对各层排序并保留层内顺序，根 Include 才按顺序应用 Patch。

最终产物是根配置路径与有序 Patch 列表。

#### 3.1.4 Cordis 与 Loader 自举

Launcher 创建根 Context 和根 Fiber，并设置模块解析基准与本次 `DSH_HOME`。
随后直接挂载 Loader Plugin，使根 Context 获得配置树管理、模块解析与插件装载能力。

Loader 就绪后，Launcher 向根 Context 注入启动环境快照、场景参数和受控退出能力。
这些信息独立于配置树，可供随后装配的插件使用。

本阶段产出具备基础路径、公共启动信息和 Loader 的根 Context。

#### 3.1.5 从配置树到运行树

Launcher 创建固定 `id: include` 的根 Include Entry，并向它传入根配置文件路径与有序 Patch 列表。
Include 读取基础 Entry、逐项应用 Patch 并生成 Entry 声明列表，Loader 据此建立 Entry 配置树。
Loader 解析各 Entry，并通过 Cordis 挂载 Plugin；Cordis 根据 Service 依赖推进激活，以 Fiber 承载实例和资源生命周期。
Entry 顺序决定配置位置，不直接决定激活顺序；需要先后约束的插件通过 Service 依赖表达。

交接结果是由 Entry 配置树对应到 Fiber 运行树。

#### 3.1.6 装配结果、诊断与退出

启动辅助逻辑等待 Loader 与生命周期任务收敛，再检查仍存活的运行树：

- **运行就绪**：应启用的 Entry 已激活，根 Context 交给宿主管理请求和进程存续。
- **启动失败**：配置、模块、依赖或插件执行无法形成有效运行树，启动终止。
- **受控退出**：场景或信号已在启动期间释放运行树，启动结束且不再执行就绪检查。

错误由最先掌握有效上下文的阶段发现，并携带配置来源、Patch 目标、Entry、模块、缺失 Service 或原始异常等定位信息向上传递。
Patch 目标不匹配等可跳过问题产生告警；阻止有效运行树形成的问题终止启动。
CLI 负责展示错误并决定进程退出，嵌入式宿主处理启动函数的拒绝结果。

根 Context 建立后的不可恢复错误会触发根 Fiber 释放。
该过程只清理登记在运行树上的资源；外部副作用仍需对应插件提供幂等、补偿或独立清理。
正常退出等待运行树释放，重复中断或等待超时可以升级为强制退出。

#### 3.1.7 设计评价与演进

分层配置、自举装配、声明与实例分离、依赖激活和树形释放，使不同场景复用同 1 启动链。
代价是故障可能跨配置来源、模块装载与生命周期传播，需要结合配置结果、阶段诊断和运行树定位。

配置机制见 [Entry、Patch 与 Loader](#54-entrypatch-与-loader)；公共启动检查与释放路径的实现依据见 [App Boot](../packages/boot/app-boot/src/index.ts)，对应行为用例见 [启动测试](../packages/boot/app-boot/tests/app-boot.spec.ts)。
这些依据支持对应路径的行为判断，目标 Profile 的装配结果仍需通过实际入口验证；测试分层见[验证与交付保障](#七验证与交付保障)。

**Roadmap（本文建议）**：当覆盖来源、启动耗时或依赖等待难以定位时，补充字段来源、阶段耗时和 `PENDING` 依赖链等诊断信息。

### 3.2 请求主链

**预期解决**

在不同交互场景中定位或建立入口 Agent，将外部输入交给 Agent 执行，并持续向调用方反馈可观察、可持久、可恢复的执行过程与结果。

**方案与选择**

独立短任务适合直接请求与响应；持续交互中，输入可能在执行期间到达，适合通过队列分离提交与执行，并独立反馈进度。
DSH 的默认组合采用后者，也允许 Controller 等待执行结束，为单次任务提供请求响应式入口。

Controller 将外部协议映射为稳定的 Agent 操作，并负责入口 Agent 的生命周期和场景输出。
Agent Provider 决定请求执行方式；默认 `ReactLoopAgent` 以 Inbox 接收输入，以 Turn / Step 推进模型与 Tool 循环，并将执行事实写入 Session。

#### 3.2.1 宏观流程与边界

```text
用户或程序输入
→ Controller 关联外部会话、Session 与入口 Agent
→ Agent Registry 查找、创建或恢复入口 Agent
→ Controller 将意图映射为 Agent 操作
→ Inbox 排队，Agent Loop 在执行边界认领并接纳输入
→ 组装上下文并请求模型
├─ 最终回答 → 结束本次执行
└─ Tool Call → 执行能力 → 记录 Tool Result → 进入后续 Step
→ Session 事实投影为场景输出
→ Controller 返回回执、完成结果或持续输出
```

Controller、Agent API 与 Session 构成稳定外层。

Agent Provider 必须实现 Agent Seam Definition 定义的约定。

Agent Seam Definition 定义不包含 Turn / Step ，它们是默认 `ReactLoopAgent` 为执行观察、控制和恢复提供的生命周期坐标，属于可选能力，Agent Seam Definition 只定义最小公共约定。

#### 3.2.2 Controller 与入口 Agent

Controller 是面向具体交互场景的应用层协调器。
它管理协议与连接，根据外部会话标识查找、创建或恢复入口 Agent，并持有新建实例的 `AgentHandle`。
连接断开是否释放 Agent 取决于具体场景；Controller 的调度止于入口 Agent，多 Agent 协作由下游 Subagent 或 Workflow 能力负责。

Controller 将外部意图映射为以下最小交互集合：

| 操作       | Inbox 位置  | 是否唤醒 | 语义与时机                                                                      |
| ---------- | ----------- | -------- | ------------------------------------------------------------------------------- |
| `followup` | `next-turn` | 是       | 提交普通后续任务，由独立 Turn 处理。                                            |
| `steer`    | `next-step` | 是       | 调整最近 1 次可接纳的 Step；Agent 空闲时启动新 Turn。                           |
| `inject`   | `next-step` | 否       | 为下 1 次可接纳的模型请求补充上下文；Agent 空闲时保持等待。                     |
| `cancel`   | 不适用      | 不适用   | 请求停止当前活动；输入保留与收敛规则见[运行中控制](#332-运行中控制与状态收敛)。 |

Agent 执行需要外部决定时，通过 Interaction 能力发起提问、审批或计划确认。
Controller 展示请求并交回响应，使原执行继续。

> Interaction 是执行过程与用户交换信息或决定的领域统称，包括提问、批准、命令与反馈。
> 它们按发起方、返回语义、权限作用和记录方式拆分实现，避免将信息答复误作操作授权，或将用户主动控制混入 Agent 的等待流程。

不同 Controller 按各自协议定义返回时机与输出方式：

- SDK 可以只等待 Agent 接受并写入 Inbox，拿到 MessageId 即返回，
- 自动化协议可以等待执行结束，
- Web 场景可以先确认提交再持续推送 Session 事实和 Agent 状态。

回执与完成结果的含义见[完成、失败与结果归属](#326-完成失败与结果归属)，失败反馈见[错误传播与结果归属](#3322-错误传播与结果归属)。

#### 3.2.3 Agent 输入投递与 Inbox

每个 Agent 实例持有 1 个独立的 Inbox。
`followup`、`steer` 和 `inject` 将消息分别投递到 2 个有序区域：

| 队列        | 内容与执行时机                             |
| ----------- | ------------------------------------------ |
| `next-turn` | 保存等待独立 Turn 处理的普通任务。         |
| `next-step` | 保存等待最近 Step 处理的干预或补充上下文。 |

```text
输入进入 Inbox
→ 唤醒或等待已有 Driver
→ Agent Loop 在 Step 边界认领候选消息
→ pre-step 决定拒绝或给出最终接纳消息
→ 接纳消息写入 Session
→ 后续模型输入从 Session 事实投影
```

Inbox 将输入到达与执行解耦，但不会修改已经组装或发出的模型请求。
同 1 Agent 可以接收并发投递，但默认由 1 个 Driver 串行执行；不同 Agent 可以并行运行。
Inbox 变更先形成 Session 事件，再更新队列；事件写入内存中的 Session Log 后，当前进程已经可见；只有持久化刷新完成后，进程重启才能重新加载这些事件。

> - Session append → 进程内生效
> - Persistence flush → 获得跨进程恢复保证

被认领的消息只有通过 `pre-step` 接纳并写入 Session 后才成为模型可见事实。

#### 3.2.4 默认 Agent Loop：请求执行

DSH 默认使用 `dsh-agent-loop` Agent Plugin。
它创建 `ReactLoopAgent`，由 Driver 串行推进 Turn，以 Step 组织每次模型请求及其 Tool 调用。

| 层级   | 定位                                               |
| ------ | -------------------------------------------------- |
| Driver | Agent 的 1 次持续工作期。                          |
| Turn   | 1 个独立任务的连续处理周期，在认领首批输入前开启。 |
| Step   | 1 次模型请求及该次响应产生的 Tool 调用。           |

```text
接纳输入并写入 Session
→ 从 Session 历史、System Prompt、Tool Schema 和模型配置组装请求
→ LLM 返回流式响应
├─ 最终回答 → 写入 Assistant Message → 结束 Turn
└─ Tool Call → Tools 校验并调用能力 → Tool Result 写入 Session
                                          ↓
                                  投影到后续模型请求
```

Tool Call 是模型自主调用能力的入口。
Controller、Workflow 或其他 Plugin 的确定性调度可以直接消费 Capability Seam，无需经过 Tools Service。
Tool Result 只是本次能力调用的观察结果；模型需要继续判断时，同 1 Turn 进入后续 Step。
运行中 `next-step` 输入也可以在后续接纳边界加入当前 Turn，`next-turn` 任务留待后续 Turn。

#### 3.2.5 Session 事实与场景输出

已接纳输入、模型输出、Tool Call 和 Tool Result 都先写入 Session，再投影为后续模型历史和场景输出。
模型生成的 Chunk 仅用于实时展示；最终提交到 Session 的 Assistant Message 才是可恢复、可重建的执行事实。
Controller 订阅 Session 事件和 Agent 状态，并按协议转换为响应、通知或 UI 更新。

同 1 Session 的输出需要保持顺序。
连接断开时停止订阅；是否同时取消或释放 Agent 由 Controller 的生命周期策略决定。

#### 3.2.6 完成、失败与结果归属

模型停止生成、Step 结束、Turn 结束、Agent 空闲、任务成功和用户验收是不同状态：

```text
Model Stop
≠ Step End
≠ Turn End
≠ Agent Idle
≠ Task Success
≠ User Acceptance
```

`MessageId` 回执只证明输入已提交；执行结束由 Agent 状态与 Session 事实证明，任务成功由目标对应的结果证据证明，用户验收由外部确认或业务规则证明。
Agent idle 表示当前整体活动已停止，单条输入对应哪个结果仍需因果关联。
任何单层状态都不能替代后续层次的完成证据。

#### 3.2.7 设计评价与演进

Controller 与 Agent API 隔离场景协议和执行策略，Inbox 解耦输入到达与执行时机，Session 统 1 模型历史、场景输出和恢复依据。
相较每次输入独立执行并返回结果，这种组合支持运行中补充输入，
运行期间到达的 steer、inject 或后续任务，可能与原始输入共同影响模型结果。因此，Agent 进入 Idle 只能证明当前所有工作已经停止，不能说明某条输出由哪条输入产生。
若 Controller 需要按请求返回准确结果，就必须额外记录每条输入对应的执行区间和输出。

这些依据限定于默认 Provider；替换实现后需重新验证输入接纳、事实记录和输出语义。

**Roadmap（本文建议）**：输入持续积压时完善背压，多个任务争用资源时评估公平调度，调用方需要逐条验收时补充消息与结果关联。
演进需保持同 1 Session 的事实顺序与模型可见内容可重建。

### 3.3 控制与恢复主链

**预期解决**

控制与恢复主链需要处理 3 类问题：

- 运行中发生取消、超时或失败时，明确哪些工作可以继续，哪些需要停止，并反馈处理结果。
- 释放 Agent 或退出 Runtime 时，等待受管工作结束，清理相关资源。
- 恢复会话时，根据持久日志重建状态。
  外部操作的结果无法确认时，明确标记为未知，供后续核查和处理。

**解决方式**

**Pattern**：按所有权管理运行中的工作与资源，按持久事实恢复会话。

**DeepSeek Mapping**：Agent 与 Cordis 承担进程内控制和资源管理。
Session Log 保存执行事实，Session Persistence 负责日志加载与修复协调。

#### 3.3.1 宏观流程与职责边界

控制与恢复包含 4 个场景：

| 场景         | 触发条件                                          | 完成标准                                                 |
| ------------ | ------------------------------------------------- | -------------------------------------------------------- |
| 运行中控制   | 取消、局部超时或执行失败                          | 局部问题交回执行方判断；需要终止时收敛当前活动并表达结果 |
| 生命周期释放 | Controller、AgentHandle、Provider 或父 Fiber 释放 | Agent 及其受管子资源停止，实例注销，作用域撤销           |
| 正常会话恢复 | 调用方显式恢复已持久化的 Session                  | 从事实重建状态，创建并发布新的 Agent 实例                |
| 崩溃恢复     | Runtime 非预期中断后重新加载 Session              | 修复日志尾部，显式标记无法确定的执行结果                 |

实时状态与连接错误由所属组件处理。
影响模型上下文、恢复或审计的执行事实需要记入 Session。

#### 3.3.2 运行中控制与状态收敛

```text
运行中发生控制请求或调用异常
├─ 局部失败或超时 → 调用结果交回执行方 → 判断继续执行或结束 Turn
└─ 主动取消或无法继续的执行错误
   → 停止受影响活动的后续调度
   → 向尚在执行的受管工作传播取消
   → 等待这些工作结束
   → 记录相关事实，结束受影响的 Turn
   → Driver 无后续活动时回到 idle
```

##### 3.3.2.1 Cancellation、Timeout 与 Deadline

取消是协作式请求，依赖下游响应 Signal；仅发出信号不能证明工作已停止。
默认取消同时清理待处理输入。
调用方可以通过 `keepInbox` 保留输入，后续执行仍遵循 Agent 的唤醒规则。

Tool、模型适配器和进程调用可以各自设置局部超时。
发生超时时，对应执行器将其转换为本次调用的失败或取消结果。

DSH 尚未提供覆盖 Controller、Agent Loop 与全部下游能力的统 1 端到端 Deadline。

##### 3.3.2.2 错误传播与结果归属

错误由能够解释其语义的层级处理：

- **Tool 调用失败**：通常形成 Tool Result，供模型在后续 Step 判断。
  如果通过其他途径直接调用能力，则由调用方处理错误。
- **模型请求或执行循环无法继续**：Agent Loop 结束当前 Turn，并将相关执行结果记入 Session。
- **协议、连接或响应转换出错**：由 Controller 反馈。
  Controller 再按场景决定是否取消或释放入口 Agent。

#### 3.3.3 生命周期释放

```text
所有者释放 AgentHandle / Provider / 父 Fiber
→ 调用方停止向目标实例投递工作
→ 如果释放的是 Provider，同时拒绝后续新的创建与恢复行为
→ 取消 Agent 活动并等待其完全停稳
→ Cordis 撤销 Agent 作用域内的受管资源
→ 注销 Agent 并分离 Session
```

Provider 卸载还需等待尚未完成的创建与恢复任务退出，防止卸载后仍有新实例发布。

Fiber 只负责已登记的资源。
未登记资源需要另行清理，已经发生的外部副作用也不会随 Fiber 释放而自动撤销。

#### 3.3.4 正常会话恢复

```text
调用方提交 Session ID → Agent Registry 委托 AgentFactory 恢复
→ Session Persistence 加载持久事实
   ├─ 正常日志 → 校验并重建状态
   └─ 可修复的中断尾部 → 崩溃修复 → 校验并重建状态
→ 创建 Agent 并完成作用域装配
→ 发布实例并将 AgentHandle 交回调用方
→ 继续接收输入
```

恢复保留 Session 身份，进程内句柄、连接和作用域资源需要重新建立。
历史模型请求和 Tool Call 用于重建上下文，不会因此再次执行。

以下情况会使恢复请求向调用方报错：

- 未配置 Persistence。
- 日志加载或校验失败。
- Agent 实例装配失败。

恢复流程负责释放本次申请的临时资源，并回滚未成功交付的实例。
调用方负责决定重试还是提示用户。
普通 Agent 创建属于请求进入前的准备。

#### 3.3.5 崩溃恢复与未决工作

Runtime 非预期中断时，Session 中可能还有未结束的 Step、Turn 或 Tool Call。
DSH 冷加载 Session 时，会保留已经完整写入的事实，并修复日志尾部：

- 为中断的 Step 与 Turn 补齐结束记录。
- 为尚未开始的 Tool Call 补充相应失败结果。
- 为已经开始但没有记录结果的 Tool Call，补充结果未知的失败记录。

修复后的日志交回[恢复主流程](#334-正常会话恢复)。
具体修复依据见 [Session 尾部修复](../packages/core/session/src/repair.ts)。

当前进程内后台 Job 和 Goal continuation 也不会在 Runtime 重启后自动续行。
`jobs-local` 只维护查询、等待和取消所需的进程内状态，不记录通用执行过程；Job Producer 可以另行记录过程，交给 Agent 的完成结果或通知进入 Session。

##### 3.3.5.1 副作用交付、幂等、去重与补偿

外部副作用需要区分接收、执行、提交、确认和记录：

```text
接收请求
→ 开始执行
→ 外部状态提交
→ Harness 获得确认
→ Session 记录结果
```

进程可能在任意两个阶段之间中断。
缺少 Session 结果只能证明 Harness 未记录确认，不能证明外部操作没有发生。

具体能力需要根据外部系统的行为决定恢复方式。
例如，通过幂等键或去重机制防止重复执行，通过状态复查确认操作结果，必要时进行补偿或请求人工确认。

任意外部操作的安全重试，仍需要对应能力提供支持。

#### 3.3.6 设计评价与演进

这套设计的主要收益与代价是：

- **协作式停止**：相较直接终止进程，可以在停止过程中完成资源清理和事实记录。
  代价是需要等待下游响应取消信号。
- **日志恢复**：相较只保留内存状态，可以在进程重启后延续会话。
  代价是需要持久化执行事实，并维护日志校验与修复机制。

**验证依据**

取消的实现见 [ReactLoopAgent](../packages/core/agent-loop/src/agent.ts)。
释放与恢复回滚的实现见 [Agent Provider](../packages/core/agent-loop/src/index.ts)。
对应行为用例见[取消测试](../packages/core/agent-loop/tests/cancel.spec.ts)、[恢复测试](../packages/core/agent-loop/tests/resume.spec.ts)和[尾部修复测试](../packages/core/session/tests/repair.spec.ts)。
这些用例只覆盖各自声明的条件。
具体外部系统的副作用仍需集成验证。

**Roadmap（本文建议）**

- 跨能力任务需要统 1 时限时，引入端到端 Deadline。
- 后台工作需要跨进程存续时，引入持久任务状态与恢复调度。
- 外部操作需要自动恢复时，为对应能力补充幂等、状态复查与补偿协议。

## 四、领域

**预期解决**

明确每类问题由哪个领域拥有，避免运行内核、业务能力、会话事实和交互入口相互侵入。

**解决方式**

按基础机制、单个 Agent、交互与协作、运行保障的顺序展开，各领域维护自身职责、状态和接口约定。
模型访问、工具执行和执行环境归入能力领域，身份与凭证归入安全领域，Memory 属于跨会话派生数据；各领域通过稳定能力、事实事件和组合声明协作。

**阅读顺序**

```text
基础机制
├── 插件运行时
├── 能力
├── 组合
└── 配置与设置

单个 Agent
├── Agent
├── 数据管理
├── 模型上下文
└── 执行控制

交互与协作
├── 用户交互
├── 执行安全
├── 任务编排
└── Controller

运行保障
├── 运行可靠性
└── 运行观测与诊断
```

### 4.1 插件运行时：依赖与生命周期

**需求与约束**

插件运行时负责按依赖激活插件，并在依赖失效或所有者退出时撤销注册、释放资源。它使不同场景的插件组合共用 1 套装载与清理机制。

##### 4.1.1 职责划分：可见性、可用性与所有权

| 职责       | 决定的行为                                   | DSH 对应机制                 |
| ---------- | -------------------------------------------- | ---------------------------- |
| 依赖可见性 | 插件通过当前 Context 能访问哪个 Service 实例 | Context 与 Service isolation |
| 依赖声明   | 插件必须具备哪些 Service 才能激活            | `inject` 与依赖刷新          |
| 资源所有权 | 哪个 Fiber 负责撤销注册、释放资源和子插件    | Fiber 与 Effect              |

派生 Context 可以改变局部属性或 Service 的查找范围，仍归属原 Fiber；挂载子插件才会创建新的 Fiber。
Context 层级与 Fiber 父子关系因此需要分别理解。

#### 4.1.2 方案与选择

**Pattern**：根据依赖是否动态变化，以及资源管理需求选择组装方式。

| 方案                       | 方案经典示例                                                        | 适用条件                             | 收益与代价                                         |
| -------------------------- | ------------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------- |
| 显式创建与注册插件         | Webpack：配置中创建 Plugin，初始化时通过`apply(compiler)` 注册 Hook | 插件集合在初始化时确定               | 组装直观；插件间依赖与额外资源清理由插件或应用负责 |
| 依赖注入容器与生命周期钩子 | NestJS：注入 Service，通过初始化与销毁钩子管理模块                  | 需要集中管理依赖和实例范围           | 减少手工组装；动态依赖失效的处理仍需另行设计       |
| 动态服务注册与依赖驱动激活 | OSGi Declarative Services：必需服务满足时激活组件，失效时停用       | Service 会在运行期间出现、消失或替换 | 自动响应依赖变化；需要处理级联卸载与状态重建       |

**DeepSeek Mapping**：DSH 使用 Cordis 的动态依赖与资源管理机制，适合按场景组合、装卸和替换插件。其代价是 Provider 变化可能引起多个 Consumer 重新激活，插件需自行处理业务状态的延续。

#### 4.1.3 依赖：从启动条件到运行期可用性

插件通过 `inject` 声明必需的 Service 名称，具体 Provider 由组合与作用域决定。
Cordis 持续检查这些 Service 是否可用：

```text
必需 Service 尚不可用 → 插件等待
全部必需 Service 可用 → 插件加载并激活
必需 Service 消失     → 使用方插件卸载并清理资源，回到等待
必需 Service 恢复     → 使用方插件重新加载并激活
```

模块导入成功不代表依赖已满足。缺少 Provider、作用域不匹配或循环等待，都可能使插件无法激活；DSH 启动时检查应启用 Entry 的激活结果，见[装配结果、诊断与退出](#316-装配结果诊断与退出)。

可选 Service 可以在使用点查询，并明确缺失时的行为；也可以将相关功能放入声明该依赖的子插件，使其单独装卸。

#### 4.1.4 生命周期：登记、撤销与释放完成

Cordis 通过 Effect 登记清理函数（disposer）。
已自动登记清理的 API 直接调用；通过原生或第 3 方 API 创建的未受管资源，需要使用 ctx.effect() 登记清理函数。

父 Fiber 释放时会级联释放子 Fiber，子 Fiber 也可独立释放。

Effect 按登记逆序触发清理，但异步清理可能并发执行，不保证完成顺序。
若资源要求“停止接收 → 等待在途工作结束 → 关闭连接”，应在同 1 个异步 disposer 中明确等待顺序，并返回代表完整清理过程的 Promise，见[释放必须等待工作停稳](../docs/defensive-patterns.md#dispose-must-reach-quiescence-not-just-request-it)。

释放只覆盖已登记资源，不会撤销已发生的文件修改或外部操作；结果核查、重试和补偿由对应能力负责，见[副作用交付](#3351-副作用交付幂等去重与补偿)。

#### 4.1.5 风险与处理

| 易混淆的保证                 | 实际范围                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| 插件重新激活即业务恢复       | 重新激活只重建插件运行资源；业务状态需由对应服务恢复，见[控制与恢复主链](#33-控制与恢复主链)         |
| Service isolation 即安全隔离 | 它只改变 Service 的查找范围；不可信代码需要执行隔离与权限控制，见[执行安全](#410-执行安全策略与隔离) |

#### 4.1.6 验证依据与演进

机制依据见 [Service 教程](../docs/cordis-tutorial/03-services.md)、[Context API](../docs/cordis-api/context.md)和[生命周期教程](../docs/cordis-tutorial/02-lifecycle-and-effects.md)。[生命周期用例](../packages/extensions/tool-cordis/tests/cordis-lifecycle.spec.ts)覆盖初始化失败回滚、异步清理等待和父子释放；各插件仍需验证自身的依赖变化、在途工作停止与状态恢复。

**Roadmap（本文建议）**：完善缺失依赖与作用域诊断，记录资源所有者及清理耗时；出现可测性能问题时，再优化依赖刷新。

### 4.2 能力：语义与实现解耦

**需求与约束**

Agent Loop 需要调用模型，文件工具需要读写文件。
这些需求可以保持不变，具体模型供应商和文件所在环境却可能变化。
本节讨论如何分开能力的使用与实现，使调用逻辑可以复用，并明确替换实现需要满足的条件。

#### 4.2.1 职责分工与拆分价值

沿用[宏观架构](#二宏观架构)中的 Capability Seam，以 DSH 的模型调用为例：

| 角色                         | 在模型调用中的职责                                  |
| ---------------------------- | --------------------------------------------------- |
| Consumer：使用方             | Agent Loop 组织请求，消费模型响应，决定如何继续执行 |
| Service Definition：能力接口 | 定义请求参数、响应流、错误与取消等调用约定          |
| Provider：实现方             | 模型适配器转换供应商协议，发送请求并转换响应        |

更换模型供应商时，只要新适配器满足 Agent Loop 所依赖的约定，Loop 就能复用原有调用逻辑。
压缩和标题生成也可以使用同 1 LLM 接口，集中复用协议适配。
文件、命令和网络能力可以采用相同分工。

代价是需要设计公共接口、表达实现差异，并验证替换后的行为。
只有1 个调用点、实现长期稳定时，直接调用 SDK 可能更简单；出现重复适配或独立替换需求时，拆分更有价值。
3 种角色可以位于同 1 包中，只有需要独立演进时才拆包。

#### 4.2.2 接口约定：以使用方的实际需要为依据

公共接口需要说明输入如何解释、返回值代表什么、失败如何表达，以及取消后执行会停到什么程度。
例如，读文件接口需要明确路径与工作目录的关系，模型接口需要明确响应结束时是成功、失败还是取消。

接口过宽，会要求 Provider 实现无人使用的功能；接口过窄，会迫使 Consumer 反复判断供应商和平台。
因此，应先明确真实调用方需要的行为，再决定统 1 哪些差异、显式保留哪些差异。

替换 Provider 时，输入、结果、错误、取消和外部副作用都需要重新核对。
“能力未知”与“明确不支持”应分别表达；已知不支持的请求应在可判定时拒绝。
相同的方法和参数，只能证明调用形式兼容。

#### 4.2.3 模型适配：统 1 调用，保留能力差异

DSH 的 LLM Service 通过适配器提供统 1 响应流，但每次调用仍需按具体 Provider／Model 确认输入模态、上下文容量和参数支持情况。
例如，图片模型接收图片，纯文本路由接收图片占位信息；调用形式 1 致，模型实际获得的信息仍有差别。

DSH 在准备请求时解析模型能力与默认参数，并将解析结果与实际执行请求的适配器绑定，避免动态更新时混用不同实现的信息。
模型目录用于发现候选，具体模型是否可调用由适配器判断；显式指定但不支持的推理参数在请求前拒绝。
具体规则见 [LLM](../packages/llm/llm/README.md)。

适配器返回统 1 的内容块、用量和结束信息。
模型请求失败以终止 failure 表达，Consumer 丢弃未完成输出；中间件或 Consumer 自身异常仍按所属组件处理。
重试由独立策略执行，并保留请求与日志的关联；网络中断不证明此前未产生输出或费用。
请求与恢复流程见 [Model Request 与 LLM](#57-model-request-与-llm)。

#### 4.2.4 工具接入：使用能力并呈现结果

Tool 可以作为能力的 Consumer。
例如，文件工具把模型提出的读文件请求转换为 FS 调用，再把结果提供给模型。
参数描述、JSON 校验和面向模型的结果呈现由工具及 Tool Runtime 负责，底层文件操作由 FS Provider 实现。

工具返回的结构化数据供调用程序继续处理，模型通过整理后的内容读取结果，界面则按展示规则呈现。
缩短模型可见文本时，应保留完整的工具返回值。
模型可以直接调用工具，也可以通过 Code Mode 程序调用工具。
2 种方式都通过同 1 Tool Runtime 使用已注册的工具，并接受参数校验与权限检查。
结果分工见 [Tool Presentation](#583-tool-presentation-与结果投影)。

工具策略决定允许、拒绝或请求审批；Guard 的拒绝不能被后续处理改回允许。
并发安全按具体参数判断，明确安全的调用才进入有界并发池，其余独占执行；结果按模型顺序提交，也不保证外部操作按该顺序发生。
具体执行机制见 [Tool Runtime](#58-tool-runtime)与 [Tools](../packages/core/tools/README.md)。

工具报错或取消不能自动撤销已经发生的文件修改或外部操作。
是否可以重试，需要具体能力提供依据；幂等、结果核查和补偿见[副作用交付](#3351-副作用交付幂等去重与补偿)。

#### 4.2.5 执行环境：相关 Provider 配套使用

文件工具修改的文件，必须与命令执行、终端访问和 LSP 分析的文件属于同 1 目标环境。
例如，将命令切换到远端执行时，也需要让文件操作指向同 1 远端目录，避免修改本地副本却在远端运行测试。

DSH 分别提供 FS、Subprocess、Shell、Terminal 与 LSP 能力，通过配置选择配套 Provider。
路径解释、工作目录、权限和进程生命周期需要 1 起验证；各能力职责与调用关系见[执行能力与运行环境](#59-执行能力与运行环境)。

本地、沙箱和远端实现具有不同的平台限制。
「隔离」是否覆盖「文件、网络、进程或凭证」，以具体执行机制为准，见[执行安全](#410-执行安全策略与隔离)。

#### 4.2.6 验证依据与演进

验证从真实 Consumer 发起调用：模型适配使用真实 API 检查响应与失败；工具覆盖参数、结果、并发和取消；执行环境通过读写文件并运行命令检查组合是否 1 致。
接口单元测试不能独立证明 Provider 可替换，服务清单与依赖关系见[能力地图](../docs/capability-seams.md)。

**Roadmap（本文建议）**：多个 Consumer 重复处理同 1 实现差异时，完善公共接口；新增 Provider 时补充替换与组合验证；实际任务需要新的能力差异时，再扩展能力描述。

### 4.3 组合：进程级与 Agent 级组装

**需求与约束**

组合决定 Runtime 装载哪些插件，以及各 Agent 使用哪些工具、指令和策略。
它负责选择与共享范围，插件运行时负责装配，具体插件实现业务行为。

**方案与选择**

**Pattern**：组合固定时可直接编写初始化代码；多个场景需要复用能力时，可通过声明式配置选择插件；Agent 之间存在能力差异时，可进一步使用 Preset 与作用域。

**DeepSeek Mapping**：DSH 通过 Profile、Bundle 和 Patch 组织进程级组合，通过 Agent Preset 组织实例可用的能力。

#### 4.3.1 进程级组合：产品组装

进程级组合选择 Controller、共享服务和能力 Provider。例如 Headless 与 Web 复用基础能力，装配不同入口。

| 组合单元 | 职责                       | 生效方式                                     |
| -------- | -------------------------- | -------------------------------------------- |
| Bundle   | 分发插件代码及默认配置贡献 | 作为 Profile 指定的有序 Patch Layer 加入组合 |
| Profile  | 选择产品场景及 Bundle 列表 | 形成该次启动的场景组合                       |
| Patch    | 修改或插入指定 Entry       | 按层次和层内顺序作用于配置声明               |
| Entry    | 声明 1 项插件及配置        | 由 Loader 建立对应运行实例                   |

Patch 按层次和层内顺序生成最终 Entry 声明；插件激活需满足声明的 Service 依赖。修改 `config` 会替换整个字段，需要保留的配置必须一并写出。优先级见[配置来源与 Patch 组织](#313-配置来源与-patch-组织)，算法见 [Entry、Patch 与 Loader](#54-entrypatch-与-loader)。

分层组合减少重复配置，但排查问题时需确认字段来自哪一层。配置预览只反映声明结果，运行就绪仍需验证插件激活与实际能力。

#### 4.3.2 Agent 级组合：实例组装

Agent Preset 的 `agent.cordis.yml` 描述该组 Agent 使用的插件。DSH 将同一版本的 Preset 插件共享挂载一次；AgentFactory 在实例发布前的 `setup` 阶段，将 Agent 作用域关联到该 Preset。下图表示能力查找关系：

```text
进程级共享设施
└─ Preset 常驻组合：共享插件与贡献
   ├─ Agent A：独立 Session、执行状态与局部贡献
   └─ Agent B：独立 Session、执行状态与局部贡献

贡献查找：Agent 局部 → Preset → Global
```

支持作用域的工具、提示词等注册按近层优先查找；Preset 监听器可接收关联 Agent 的对应事件。共享插件需按 Agent 或 Session 分开保存实例状态，避免多个 Agent 相互影响。

Agent 自有资源随实例释放，Preset 插件由 Preset 服务持有，不随单个 Agent 退出而卸载。

这套贡献查找规则不自动隔离任意 Service。Preset 自有 Service 必须使用 Cordis `isolate`，否则挂载检查会拒绝其向全局发布；机制见 [dsh-scope](../packages/core/scope/README.md)。

#### 4.3.3 组合变化：新实例、运行实例与恢复

| 变化                                | DSH 的处理方式                                                                     |
| ----------------------------------- | ---------------------------------------------------------------------------------- |
| 进程级用户 Patch 更新               | 重新组合插件树；候选失败时保留最后可用树，成功后按插件生命周期更新                 |
| Preset 组合文件更新                 | 按文件时间戳与大小识别新版本；后续加入的 Agent 使用新版本，已运行 Agent 保留原版本 |
| 子 Agent 通过`composeFrom` 加入组合 | 复用父 Agent 正在使用的版本，不重新按 Preset id 装载                               |
| 空白会话切换 Preset                 | 调用方检查切换资格；新组合可用后再切换作用域关联，失败时保留原组合                 |
| 跨进程恢复会话                      | 按会话记录的 Preset id 解析组合；该 id 不锁定旧配置文件版本                        |

Preset 更新可能使多个版本同时驻留。当前旧版本不会在最后一个 Agent 退出时回收，而是随 Preset 服务释放；频繁修改会增加资源占用。

#### 4.3.4 风险与处理

Preset 挂载需检查必需依赖是否满足，避免发布无法使用的 Agent。用户 Preset 的 `trust` 标签只描述来源信任，不限制插件代码权限；执行限制见[执行安全](#410-执行安全策略与隔离)。

#### 4.3.5 验证依据与演进

机制依据见 [App Boot](../packages/boot/app-boot/README.md)和 [Agent Presets](../packages/preset/agent-presets/README.md)，对应用例见 [Profile](../packages/boot/app-boot/tests/profile.spec.ts)与 [Preset 挂载](../packages/preset/agent-presets/tests/mount.spec.ts)。具体组合仍需验证实际激活、并发实例隔离和更新失败后的行为。

**Roadmap（本文建议）**：完善配置来源追踪、旧 Preset 版本回收，以及跨进程恢复所需的版本保留。

### 4.4 配置与设置：系统结构与运行参数

**需求与约束**

Harness 的组成配置与 Provider 的运行设置：装载哪些插件、使用哪些 Provider、采用哪些运行参数，以及配置从哪里来、如何覆盖、校验和生效。

每项配置由使用它的服务负责解析和校验。
配置提供默认值，会话采用的模型与权限选择由 Session 相关机制保存和恢复；这里只说明配置变更对会话的影响。

插件装配见[组合](#43-组合进程级与-agent-级组装)，具体 Provider 的配置项由对应服务说明。
API Key、访问令牌等凭证的存储、读取与授权流程，见[凭证、授权与身份](#4101-凭证授权与身份)。

#### 4.4.1 配置内容：系统组成、运行参数与会话选择

配置既包含 Harness 自身的选项，也包含 Provider 的选项；按作用和生效方式区分，便于判断 1 次修改会影响什么。

| 配置内容         | 示例                                              | DSH 中的管理方式                                         |
| ---------------- | ------------------------------------------------- | -------------------------------------------------------- |
| 系统组成         | 装载哪个模型适配器，选择本地还是远端执行 Provider | Entry／Patch 声明组合，由插件装载过程应用                |
| 运行参数与默认值 | 工具并发上限、Provider 参数、新会话默认权限       | 插件配置提供初始值；接入 Settings 的选项可由用户设置覆盖 |
| 会话自己的选择   | 当前会话使用的模型与权限模式                      | 由所属服务管理，需回放的选择及实际模型请求写入 Session   |

例如，修改新会话默认权限，影响的是后续创建的会话；已有会话保留自己的权限选择。各配置项的作用范围由使用它的服务定义。

#### 4.4.2 有效值：默认配置与用户覆盖

DSH 的 Settings 按命名空间管理设置，即每个注册方拥有 1 组设置项。
注册方提供 Schema（字段类型、默认值与校验规则）及来自插件配置的基础值，Settings 再应用用户覆盖：

```text
字段默认值 → 插件配置提供的基础值 → 用户设置
                                      后者覆盖前者
```

这是 Settings 的解析顺序；会话是否采用解析后的值，由上 1 节所述的服务规则决定。
未配置 Settings Provider 时，各插件仍可解析自己的 Entry 配置。

“恢复默认”应删除用户覆盖，让后续基础配置变化仍能生效。
例如，把当前默认并发数复制到用户设置，会将它变成固定覆盖值，失去继续采用默认值的效果。

Settings 的对象 patch 递归合并用户层中的字段；Entry Patch 则替换目标 `config`。
2 种更新方式分别见 [Settings](../packages/settings/settings/README.md)和 [Entry、Patch 与 Loader](#54-entrypatch-与-loader)。

#### 4.4.3 保存设置：校验、冲突与失败处理

Settings 服务先校验候选设置，再交由存储 Provider 持久化；保存成功后，更新内存中的有效值并通知订阅方。
各插件负责按自身的生效规则应用新值。
只读 Provider 拒绝写入；非 JSON 值或不满足字段规则的结果，在提交前拒绝。
服务退出时等待已接纳的写入和已开始的通知处理完成。

并发编辑需要分别处理写入顺序和版本冲突。
Settings 在同 1 进程内按命名空间排队写入，并允许调用方携带 `expectedRevision`，拒绝基于旧版本的修改。
文件 Provider 在写锁内重读文件并原子替换，保留其他设置组的修改；多个进程修改同 1 设置组时仍由后写覆盖，不能依靠进程内版本检查防止冲突。

启动时已有设置文档非法，会导致装配失败。
运行中外部编辑无效，则保留最后有效值并告警；某一设置组校验失败可单独处理。
文件更新、监听与失败规则见[文件 Provider](../packages/settings/settings-file/README.md)。

#### 4.4.4 应用设置：何时生效、影响哪些实例

保存设置、计算有效值和实际应用是不同步骤。
Settings 提供不可变的有效值快照，并按提交顺序通知；使用设置的服务决定何时读取新值，以及是否需要重连或重建资源。

例如，DSH 的工具并发设置可在下 1 组调用时读取；正在进行的模型请求使用已经准备并记录的参数，后续修改只在相应读取时点影响新的请求。
需要重连或重建的设置，还需由使用方报告应用结果，并明确失败时保留旧资源还是拒绝后续调用。

模型请求需要记录实际采用的配置，不能仅根据当前设置文件推断过去的请求。
请求记录规则见 [Model Request 与 LLM](#57-model-request-与-llm)。

#### 4.4.5 验证依据与演进

配置界面应区分默认值、用户覆盖和生效范围。
界面隐藏了敏感字段时，只修改用户选定的字段，避免用不完整数据覆盖整组设置；Settings 的脱敏范围与限制见[凭证、授权与身份](#4101-凭证授权与身份)。

验证应覆盖默认值继承、清除覆盖、非法输入、并发冲突、外部编辑失败，以及新值是否在声明的时点生效。
实现依据见本节链接，对应并发场景见[写入用例](../packages/settings/settings-file/tests/concurrency.spec.ts)。

**Roadmap（本文建议）**：用户难以解释有效值时补充来源与生效范围；跨进程编辑频繁时引入真正的条件写入；资源切换失败难以判断时增加应用状态与回滚反馈。

### 4.5 Agent：执行主体与生命周期

**需求与约束**

交互入口、自动化客户端和编排器需要定位执行主体、提交输入、干预活动并管理其存续，同时允许内部执行策略变化。Agent 领域负责这些稳定操作及其生命周期语义；模型如何选择行动、流程如何推进归入[执行控制](#48-执行控制自治度与确定性)。

成功标准是调用方能区分实例身份、输入提交、执行状态与资源释放；创建失败不会发布半成品，释放完成后不再遗留该实例承诺管理的工作。任务成功仍由目标对应的结果证据判断。

**方案与选择**

**Pattern**：独立短任务可以通过函数或单次 Run 返回结果；持续交互适合保留执行实例，通过消息投递与状态观察分离提交和执行；跨进程长期任务还需要持久调度与恢复协议。几种方案可组合，但各自的完成、取消与恢复语义需要明确。

**DeepSeek Mapping**：DSH 以 Agent 接口承接输入和控制，以 AgentRegistry 定位活跃实例，以 AgentFactory 创建或恢复实例，以 AgentHandle 交付访问与释放责任。默认实现为 ReactLoopAgent，Controller 与其他 Consumer 通过公共接口使用它。

Agent 实例经历以下生命周期：

| 阶段  | 行为                                                     |
| ----- | -------------------------------------------------------- |
| 准备  | Factory 创建 Session、Agent 与作用域，实例尚未对外可见   |
| setup | 关联 Preset，并注册 Agent 局部能力                       |
| 发布  | 将 Session 与 Agent 加入 Registry，并向调用方交付 Handle |
| 活动  | 在`idle`、`running` 和 `maintenance` 状态间切换          |
| 释放  | 取消活动、等待停稳、注销实例并释放 Agent 作用域          |

插件的 mount／unmount 属于 Fiber 生命周期，不是 Agent 生命周期。

#### 4.5.1 对象划分：实例、事实、工厂与句柄

| 对象          | 职责与存续范围                                     |
| ------------- | -------------------------------------------------- |
| Agent         | 活跃执行实例，持有输入、执行状态、Session 与作用域 |
| Session       | 会话事实及其内存投影，持久化后可用于恢复与回放     |
| AgentRegistry | 当前 Runtime 内活跃 Agent 的发现与身份登记         |
| AgentFactory  | 创建或恢复具体实现，协调准备、发布和失败回滚       |
| AgentHandle   | 创建调用方持有的访问与释放句柄，绑定确切实例       |

DSH 的 Agent 与其 Session 共享 SessionId，同一 Registry 中该 id 只对应 1 个活跃实例。
恢复可以沿用 Session 身份，同时创建新的 Agent 对象与运行资源；保留 id 不等于保留旧对象。

Registry 查询返回 Agent，创建或恢复返回 AgentHandle。
前者允许输入与控制，后者额外承担实例释放。

历史中的父子会话关系也不同于当前 Runtime 的实例所有权：带有历史父会话的 Session 恢复后，可以直接作为新的入口 Agent 运行。

#### 4.5.2 输入与状态：提交、唤醒与完成

持续交互允许新输入在已有活动期间到达。
输入接口需要声明何时接纳、是否唤醒、能否影响已经发出的模型请求，以及拒绝或取消后如何处理待执行内容。

DSH 通过 Inbox 接收输入：followup 提交后续任务，steer 在后续执行边界进行引导，inject 补充上下文而不主动唤醒。
队列与 Turn／Step 的具体关系见[Agent 输入投递与 Inbox](#323-agent-输入投递与-inbox)，本节保留调用方需要区分的状态：

| 可观察量                   | 能够说明的事实                   | 仍需另外判断的事实                             |
| -------------------------- | -------------------------------- | ---------------------------------------------- |
| 输入已提交                 | 输入已进入对应投递路径           | 是否被接纳、执行及产生目标结果                 |
| running                    | Driver 正在推进或收尾活动        | 当前是否仍有模型请求、某条输入是否完成         |
| idle                       | 当前没有运行中的 Driver          | Inbox 是否为空、是否存在维护工作、任务是否成功 |
| whenIdle() 完成            | 所观察的整体活动与维护工作已停稳 | 某条消息的结果归属，以及未来是否会被再次唤醒   |
| AgentHandle.dispose() 完成 | 该句柄所拥有的实例完成释放       | 外部副作用是否满足业务目标                     |

例如，空闲 Agent 接收 inject 后可以保留待处理上下文；维护任务也可以占用实例而保持公开状态为 idle。
需要等待停稳时使用相应等待操作，不能仅依据状态字段推断。
多条输入共同影响执行时，逐条结果需要额外的因果关联，见[完成、失败与结果归属](#326-完成失败与结果归属)。

#### 4.5.3 创建与发布：先完成组合，再交付实例

**Invariant（可被发现的执行实例）**：实例进入公共发现范围时，应已满足该接口承诺的初始化条件。否则调用方可能在工具、上下文或依赖尚未准备好时开始执行。

DSH 的创建与恢复共用未发布准备阶段：Factory 建立 Session、Agent 与作用域，执行可信的组合 setup，再发布 Session 和 Agent，并将句柄交给调用方。
setup 负责在 Agent 对外可用前完成能力组装；组装完成后，调用方才能取得实例并启动执行。

准备或发布失败时，由 Factory 回滚本次私有资源。
同 id 并发创建可以同时开始准备，最终只允许 1 个进入 Registry，其余创建失败并清理。
该机制处理当前 Runtime 内的身份冲突，不提供跨进程分布式互斥。

创建期间的取消信号只约束本次创建事务，成功交付后由 Agent 控制和句柄释放管理实例。具体事务与事件时序见 [Agent 接口、Registry 与所有权](#55-agent-接口registry-与所有权)。

#### 4.5.4 取消、释放与恢复：不同的生命周期操作

取消用于停止当前活动，实例可以继续存在并接受后续输入；释放用于结束实例的存续。
恢复则以持久事实建立新的执行实例，既需要重建会话状态，也需要重新取得当前可用能力。

DSH 的默认取消请求向下传播 Signal，通常同时清理待执行输入，调用方可选择保留 Inbox。
调用方 Fiber 和 Factory Provider 共同持有程序化 Agent 的生命周期；任 1 所有者卸载或句柄主动释放，都汇合到同 1 次释放过程，等待执行停稳并清理作用域、注册关系与 Session 关联。

释放操作必须由资源实现完成实际停止与等待，协作式取消信号只表达请求。
持久 Session 用于重建事实，进程内连接与句柄需要重新建立，未记录的外部操作结果需要另行核查；取消、退出与恢复路径见[控制与恢复主链](#33-控制与恢复主链)。

#### 4.5.5 Provider 替换与多实现路由

上层通过 Agent Seam 定义的接口与公开事件操作 Agent。替代 Provider 必须实现相同的输入、状态、事件和释放语义。

AgentRegistry 只有 1 个 AgentFactory 注册槽。
Runtime 可以在启动组合中替换 Provider，但不能同时注册多个 Factory，再为每次创建直接选择其中 1 个。

多种 Agent 实现需要在同 1 Runtime 中共存时，可以将唯 1 注册的 Factory 实现为路由器。
路由 Factory 根据创建请求选择下游实现；各下游实现仍需满足 Agent Seam 的公共约定。

#### 4.5.6 验证依据与演进

公共语义见 [Agent 运行类型](../packages/core/agent/src/runtime-types.ts)，创建与释放实现见 [AgentLoop Factory](../packages/core/agent-loop/src/index.ts)。[作用域生命周期用例](../packages/core/agent-loop/tests/scope-lifecycle.spec.ts)覆盖未发布 setup、冲突回滚、所有者卸载和释放等待；[取消用例](../packages/core/agent-loop/tests/cancel.spec.ts)与[恢复用例](../packages/core/agent-loop/tests/resume.spec.ts)限定各自的行为范围。接口声明本身不能证明替代 Provider 已满足这些语义。

**Roadmap（本文建议）**：调用方需要逐条验收时补充输入与结果关联；多种执行模型需要同进程共存时设计 Factory 路由；需要跨进程接管时明确持久身份、实例租约和重复执行处理。

### 4.6 数据管理：记录、保存与复用

**需求与约束**

Agent 执行任务时，会产生对话、工具调用和执行结果，也可能接收图片等附件。
系统需要保存这些内容，供后续对话、历史查询和会话恢复使用。
工作区名称、显示顺序等可修改信息，也需要单独管理。

本节说明这些数据由谁保存、如何修改，以及如何供后续任务使用。
模型请求中的信息选择与组织见[模型上下文](#47-模型上下文组装与压缩)，服务之间的具体调用关系见[数据与资源服务](#510-数据与资源服务)。

#### 4.6.1 会话日志：保存执行过程

用户提出了什么要求、模型调用了什么工具、工具返回了什么结果，都属于会话执行过程。
按顺序追加这些记录，可以核查历史并恢复对话；代价是需要持续保存日志，并在恢复时读取和处理历史记录。

DSH 用 Session Log 保存执行记录，Session Persistence 负责持久化。
后续模型输入和场景输出由日志生成，见[Session 事实与场景输出](#325-session-事实与场景输出)。
修改后续可见历史时，追加替换或遮蔽记录，保留原始事件，见[消息投影与上下文压缩](#472-消息投影与上下文压缩)。

跨进程恢复要求记录已完成持久化；恢复会话不会重新执行历史工具调用。
具体恢复过程与外部操作结果未知时的处理，见[控制与恢复主链](#33-控制与恢复主链)。

#### 4.6.2 可编辑状态：由所属服务管理

工作区名称和显示顺序需要随用户操作更新。
工作区服务负责定义可修改的字段、校验修改并保存当前值；如需追溯修改过程，还需保留变更记录。

DSH 的 Storage 提供存储支持，Workspace 管理工作区登记及其会话归属。
删除工作区登记只移除管理记录，保留目录、用户文件和会话日志；归档会话也保留历史。
路径识别、归属校验及更新失败的处理见 [Workspace](../packages/workspace/workspace/README.md)。

#### 4.6.3 附件与长结果：单独保存内容

图片和很长的工具输出可以单独保存，会话中只保留引用或预览。
例如，完整测试报告保存为文件，工具结果保留报告预览和读取位置，后续需要时再取回全文。

DSH 使用 2 种机制处理这些内容：

- [Attachment](../packages/attachment/attachment/README.md)：校验并持久化图片，再返回可写入会话的稳定引用。
- [Spill Policy](../packages/spill/spill-policy/README.md)：为适用的工具文本保存完整格式化结果，再返回预览和读取位置；保存失败时保留原结果。上游已丢弃的内容无法在此恢复。

单独保存可以减少直接写入会话的内容，但 Spill 不提供全链路内存或上下文硬上限。
引用指向的内容必须保持可读取；恢复或 fork 后的会话可能共享附件，删除内容前需要检查所有引用者。

#### 4.6.4 历史查询：查找记录与核对来源

查找某次工具调用，可以直接读取会话记录；搜索大量历史内容，可以使用索引。
搜索片段、统计和界面视图由已有记录生成，属于派生数据；它们需要保留与原记录的对应关系，便于核查。
索引和缓存还需在来源变化或自身失效时更新、重建。

DSH 的 [Session Query](../packages/session-query/session-query/README.md) 提供会话与事件读取、父子关系追踪和全文搜索，调用方无需直接读取存储文件。
同一会话同时存在于内存与持久存储时，优先读取内存记录；这不代表两处数据已同步，也不提供跨来源的一致快照。
读取未运行的会话也不会启动 Agent。

Session Query 本身不鉴权，调用方负责限制可见数据。
模型工具按工作区授权，API／Web 等入口需校验调用者身份与会话权限。
查询工具采用精确 cwd 匹配，与 Workspace 的路径识别规则不同，见[查询工具限制](../packages/session-query/tool-session-query/README.md#known-limitations-and-deferred-work)。

会话投影、缓存、统计、标题与遥测的实现见 [Session 派生服务](#5101-session-派生服务)。

#### 4.6.5 记忆：保留可复用信息

Memory 从历史中选择和提炼值得后续任务使用的信息，例如用户偏好、经验、项目约定或有效的处理方法。
记忆需保留来源、适用范围和时效，支持纠正与遗忘；再次提供给 Agent 前，还需检查访问权限及其与当前任务的相关性。

记忆可能概括错误或随时间过期，因此需要能回到原记录核查。
与重建搜索索引相比，重新生成记忆还必须尊重已有的纠正和遗忘要求。

DSH 的 Session、Query、Storage、Skill 和上下文扩展可用于实现记忆能力，但尚未形成覆盖写入、召回、纠正和遗忘的完整 Memory 服务。

#### 4.6.6 风险、依据与演进

一次操作可能同时写入内容、会话记录和索引。
DSH 的 Storage Hub 不提供跨领域事务保证；各写入方需要约定提交顺序，并处理只完成部分写入的情况。
例如，报告文件已经保存，但会话引用写入失败，就需要处理未被引用的文件。

验证应覆盖写入中断、引用内容缺失、共享附件误删、索引或缓存过期，以及越权查询。
实现依据见各小节链接与 [Session](../packages/core/session/README.md)，验证分层见[验证与交付保障](#七验证与交付保障)。

**Roadmap（本文建议）**：完善外置资源回收、跨存储修复流程，以及可纠正的 Memory 生命周期。

### 4.7 模型上下文：组装与压缩

**需求与约束**

每次请求模型，都需要把指令、工具描述、运行环境和会话历史组织为输入。
会话历史增长后，需要通过裁剪或摘要控制输入量，避免超过模型的上下文上限，也减少了延迟与费用；同时保留任务目标、约束和继续执行所需的信息。

本节讨论输入的选择、组装与压缩。
数据保存与历史查询见[数据管理](#46-数据管理记录保存与复用)，模型及请求参数的配置见[配置与设置](#44-配置与设置系统结构与运行参数)。

#### 4.7.1 上下文组装：选择内容并组织输入

模型上下文包含以下内容，工具描述可能通过独立请求字段传递。

| 内容               | 用途                             | 组装要求                                  |
| ------------------ | -------------------------------- | ----------------------------------------- |
| 提示词             | 说明职责、行为要求与调用协议     | 按当前 Agent 的作用域解析指令、顺序和变量 |
| 工具描述           | 告知模型可调用的工具及参数       | 与当前实际可调用的能力一致                |
| 运行环境           | 提供当前目录、权限、时间等信息   | 使用本次请求有效的值，标明来源            |
| 会话历史与引用内容 | 提供用户任务、工具结果和相关资料 | 选择当前有效消息，解析所需引用，保留来源  |

外部文件、工具结果和检索资料作为任务信息进入请求，其文本不因此获得指令权限。
引用解析需遵守当前访问权限；只有路径或 URL 无法确定当时读到的内容，还需保存实际内容或可确定读取同 1 版本的引用。
记录要求见 [Session 事实与场景输出](#325-session-事实与场景输出)。

**DeepSeek Mapping**：DSH 每个 Step 重新组装上下文。SystemPrompt 汇集当前 Agent 作用域内的提示词与运行环境，Tools 提供可见工具描述，Session Projection 从日志生成本次使用的会话消息。稳定指令保留在请求前缀，动态环境在首次出现或有效变化时形成带来源的日志消息。

替换提示词的扩展需保留启用中的 Tool／Code Mode 等调用协议。
提示词负责告知模型规则，执行限制由能力与策略组件实施，见[能力](#42-能力语义与实现解耦)。

#### 4.7.2 消息投影与上下文压缩

消息投影是从 Session 日志生成当前有效消息的过程；上下文压缩则缩减后续请求使用的历史内容，保留原始日志。

**Pattern**：短会话可保留完整历史；内容增多后可组合以下方式：

- **按需读取**：请求中只放当前需要的资料，减少无关输入，但可能漏取信息；查询与长结果外置见[数据管理](#46-数据管理记录保存与复用)。
- **裁剪工具结果**：缩短已进入历史的长输出，降低占用，但可能丢失细节。
- **摘要较早历史，保留近期原文**：维持最近操作的完整信息，但摘要会增加模型调用成本，也可能遗漏约束或误写结论。

**DeepSeek Mapping**：DSH 的 Basic Compaction 使用 Token Meter 估算上下文占用，并按当前 Provider／Model 的容量判断是否需要压缩。

```text
估算上下文占用
├─ 可容纳 → 继续请求模型
└─ 需要压缩 → 可选：裁剪工具结果 → 重新估算
                                  ├─ 可容纳 → 继续请求模型
                                  └─ 仍过大 → 摘要较早历史，保留近期原文
                                             → 记录摘要与替换范围，再检查占用
```

摘要由单独的模型请求生成。
选择压缩范围时保持工具调用与结果配对，避免只留下其中 1 方；摘要提交后，后续消息投影使用摘要替换对应历史。
例如，较早的排查过程可以概括为已验证的结论、约束和待办，最近 1 轮工具调用与结果仍保留原文。

#### 4.7.3 容量、失败与缓存

**容量估算**

上下文预算需计入提示词、工具描述和历史消息，并为模型输出预留空间。
DSH 在满足复用条件时，以 Provider 返回的 token 用量为依据，结合历史内容的变化估算当前占用；否则，根据字符数和消息结构进行粗略估算。
因此，估算结果在预算内，也不保证实际请求符合 Provider 的容量限制。
用量数据的复用条件见 [Token Meter](../packages/llm/token-meter/README.md)。

如果提示词、工具描述或无法拆分的近期消息本身就超过容量，仅压缩较早历史仍无法使请求满足限制。

**压缩失败**

DSH 会检查摘要是否比原文短，以及压缩后的上下文是否回到预算内。
失败后的处理取决于触发场景：

- **常规自动压缩**：失败时可告警，并使用最后已持久化的有效历史继续请求模型。
- **Provider 已报告上下文溢出**：只有历史确实缩减且替换结果已持久化，才允许重试模型请求。

工具结果裁剪和摘要可能先后提交。
如果裁剪已保存、后续摘要失败，已生效的裁剪仍然保留，后续使用裁剪后的历史。
自动压缩、手动压缩及溢出恢复的完整规则见 [Basic Compaction](../packages/compaction/compaction-basic/README.md)。

**缓存复用**

当请求前缀相同且满足 Provider 的缓存条件时，KV Cache 可以复用这部分内容已有的计算结果。DSH 生成摘要时，会尝试沿用原会话的请求前缀以利用缓存。摘要替换历史后，后续请求的前缀可能变化；切换模型或 Provider 也可能使缓存无法复用。实际收益需根据 Provider 返回的缓存用量确认。

#### 4.7.4 验证依据与演进

验证需分别检查输入构造和压缩质量：

- **输入构造**：请求能否重建、作用域是否隔离、引用是否对应当时内容、工具调用与结果是否配对，以及超大消息和压缩失败时的行为。
- **压缩质量**：是否保留目标、约束、未完成事项和可核查证据；token 减少量只能说明缩减效果。

通用策略见 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（查阅于 2026-09-21）。
DSH 实现依据见 [SystemPrompt](../packages/core/system-prompt/README.md)、[Basic Compaction](../packages/compaction/compaction-basic/README.md)，验证依据见[请求重建用例](../packages/core/agent-loop/tests/request-reconstruction.spec.ts)及[压缩用例](../packages/compaction/compaction-basic/tests/compaction-basic.spec.ts)；组件调用关系见[上下文装配与压缩](#571-上下文装配与压缩)。

**Roadmap（本文建议）**：按失败原因改进：无关资料过多时优化内容选择，摘要遗漏时加强质量评估与原文取回，容量判断偏差持续出现时完善计量，缓存损失明显时优化前缀组织。

### 4.8 执行控制：自治度与确定性

**需求与约束**

单 Agent 的内部执行架构：哪些行动和路径由模型选择，哪些步骤、状态转换与停止条件由程序控制。
选择方式取决于任务路径的不确定性、失败成本、预算和恢复要求；不同实现仍需满足 Agent 接口约定的输入、状态、取消与生命周期语义。

**方案与选择**

**Pattern**：以执行路径的主要决策者为两端，可以形成 ReAct 主导、混合设计与 Workflow 主导的连续选择。

| 内部执行架构  | 控制权分配                                               | 适用场景与主要代价                                         |
| ------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| ReAct 主导    | 模型根据观察选择下一行动，程序维护调用、执行与反馈循环   | 路径难以预先确定；调用次数与执行路径较难预测               |
| 混合架构      | 程序规定阶段和转换条件，模型在阶段内自主选择行动         | 部分过程固定、部分需要探索；需要维护阶段状态和局部自治规则 |
| Workflow 主导 | 程序规定步骤、分支与结束条件，模型完成指定节点的推理任务 | 路径与检查要求相对稳定；流程覆盖和异常分支的维护成本较高   |

权限、预算和执行隔离适用于所有架构。
这里的自由度主要指模型对执行路径的选择范围；程序控制流程，也不意味着模型输出和外部操作结果具有确定性。

**DeepSeek Mapping**：DSH 默认的 `ReactLoopAgent` 采用 ReAct／工具调用循环，公共 Agent 接口与具体循环实现分离。
以下混合架构与 Workflow 型 Agent 描述可选设计；接入 DSH 时需由具体 Agent Provider 实现并验证相应语义。

#### 4.8.1 ReAct 主导：模型选择执行路径

模型根据上下文提出回答或工具调用；Runtime 校验并执行工具，将结果记录为下 1 次决策的观察。

```text
当前上下文与可用工具
→ 模型提出行动
├─ 回答 → Runtime 判断本轮是否可以结束
└─ Tool Call → 策略校验与执行 → 记录观察 → 后续模型请求
```

模型持续根据新观察调整路径，适合调查、诊断等难以预先列全步骤的任务。
程序负责调用合法性、执行策略和结果记录；若任务有明确验收标准，还需在结束前检查结果证据。
模型可能重复尝试或过早回答，因此需要预算与进展控制。

DSH 的 `ReactLoopAgent` 以 Turn／Step 承载循环，Tools Service 执行工具，Session 保存可重建事实。
具体时序见[默认 Agent Loop](#324-默认-agent-loop请求执行)和 [Turn／Step 实现](#563-turn--stepreact-执行循环)；Turn 结束与任务成功的区别见[完成、失败与结果归属](#326-完成失败与结果归属)。

#### 4.8.2 混合架构：程序控制阶段，模型选择局部路径

混合架构在同 1 个 Agent 内组合显式状态转换与局部 ReAct 循环。
程序规定阶段目标、允许的行动和进入下 1 阶段的条件；模型在当前阶段内选择具体路径。
也可以由模型提出计划，程序校验后按计划执行，并在指定条件下允许重新规划。

```text
Agent 接纳任务
→ 调查阶段：模型自主检索和验证线索
→ 程序检查证据是否满足阶段要求
→ 修改阶段：模型在允许范围内选择修改与工具调用
→ 程序运行验收
   ├─ 未通过且预算允许 → 返回对应阶段继续处理
   └─ 通过 → 记录结果并结束执行
```

该方式保留局部探索能力，同时明确关键步骤的先后与验收要求。
代价是程序需要维护阶段状态、回退规则和阶段间信息；阶段划分不合理时，模型可能缺少完成任务所需的行动空间。

提示词中的步骤建议属于行为引导；需要保证的阶段转换必须由执行器检查。
「工具可见性」缩小模型的选择范围，实际权限由执行策略落实，见[执行安全](#410-执行安全策略与隔离)。
仅增加权限限制，并不改变 ReAct 的路径决策方式。

DSH 可通过作用域贡献、`agent/pre-step`、工具策略与 `agent/turn-stopping` 等扩展点调整默认循环。
设计需要的阶段转换和调度语义超出现有扩展点时，应由专用 Agent Provider 实现；Provider 替换约定见 [Agent](#45-agent执行主体与生命周期)。

#### 4.8.3 Workflow 主导：Agent 内部的显式流程

Workflow 型 Agent 以脚本、状态机或图定义内部执行过程。
执行器维护当前节点、节点结果与转换条件，按程序规则调用模型或工具；模型负责指定节点的分类、提取、生成等推理任务。

```text
Agent 接纳输入
→ 程序读取并校验资料
→ 模型提取结构化信息
→ 程序校验字段与业务规则
   ├─ 校验失败且可重试 → 带错误信息返回提取节点
   ├─ 无法继续 → 记录原因，等待补充输入或结束
   └─ 校验通过 → 程序生成产物并检查结果
→ 记录结果，结束执行
```

步骤与分支明确时，这种实现便于检查路径覆盖、控制重试范围并定位失败节点。
确定性步骤可以直接调用能力，无需每 1 步都请求模型；若某个节点需要多轮探索，也可以嵌入局部 ReAct 循环，形成混合设计。

显式流程需要为预期的异常、缺失输入和失败结果设计处理分支。
流程走到结束节点，只证明满足了已编码的结束条件；业务成功仍取决于这些条件能否充分检查目标。
脚本或图本身也不提供持久恢复，跨进程续行需要保存节点状态、有效输入与结果，并处理外部副作用的幂等和未决状态。

在 DSH 中将这种设计实现为 Agent Provider 时，需要维持统 1 的输入、状态、取消、等待与释放语义，并让模型实际使用的输入与输出可以从 Session 事实重建。
流程节点可以使用自己的内部状态表示，接入规则见 [Agent 接口、Registry 与所有权](#55-agent-接口registry-与所有权)。

#### 4.8.4 共同控制：预算、取消、进展与完成

3 类架构都需要控制「消耗、等待和无效执行」。
ReAct 在循环中检查，混合架构在局部循环和阶段转换处检查，Workflow 在节点准入与重试路径检查；持续耗时的调用还需要独立的超时与取消机制。

| 控制项                    | 要约束的量                         | DSH 当前覆盖与限制                                              |
| ------------------------- | ---------------------------------- | --------------------------------------------------------------- |
| 单次模型输出上限          | 1 次对话模型请求的输出 token       | AgentOptions.maxTokens 随请求记录；不累计整个 Turn 的成本       |
| 工具并发上限              | 同 1 Agent 执行组中的并行调用数    | maxParallelToolCalls 约束并行安全调用；不代表进程级总配额       |
| 单次工具超时              | 1 次已声明时限的工具调用           | Timeout Policy 传递取消信号；终止依赖工具及下游响应             |
| 重复调用提醒              | 单个 Agent 连续同名、同参数调用    | Repeat Tool Reminder 按阈值提供建议，不阻止调用                 |
| 单次任务总预算与 Deadline | 本次执行的累计成本、步骤数或总耗时 | 默认循环没有内建 Turn 总预算，也没有覆盖全部下游的统一 Deadline |

DSH 默认循环的单次请求上限不能限制整个任务；工具超时只发出取消信号，下游忽略信号时仍可能继续。
执行器需要等待已启动工作停稳，再确认取消或释放完成。
取消语义见[运行中控制](#332-运行中控制与状态收敛)，策略实现见 [Guard](#564-guard超时与循环卫生)。

进展判断应关联已获得的证据、已完成的目标或已消除的缺口。
重复调用可能是合法轮询，执行了新步骤也不必然有进展。
DSH 的重复调用提醒只识别当前进程内连续同名、同参数的调用；`agent/turn-stopping` 只在循环准备结束时触发，不能单独限制持续工具调用。

完成判定需要区分候选答案、执行结束与目标达成。
具有可执行验收规则的任务，应检查产物或外部状态；开放任务需要声明评价标准和人工介入条件。
选择哪种内部架构，都不能以模型自述或流程结束代替结果证据。

#### 4.8.5 验证依据与演进

DSH 的接口依据见 [Agent 运行类型](../packages/core/agent/src/runtime-types.ts)，默认循环实现见 [Agent Loop](../packages/core/agent-loop/src/agent.ts)，现有拦截行为见[循环拦截用例](../packages/core/agent-loop/tests/interception.spec.ts)。
这些依据支持公共接口与默认循环的行为判断；混合或 Workflow 型 Provider 需要分别验证自己的阶段转换、输入接纳、错误处理、取消收敛与请求重建。

架构比较应在相同「任务、可用能力与资源预算」下进行，观察成功率、总成本、延迟和人工介入，并检查失败路径和验收依据，见 [Agent Evaluation](#76-agent-evaluation质量度量与回归决策)。
更少的模型决策不自动意味着更高的任务成功率。

**Roadmap（本文建议）**：任务探索成本过高时，评估将稳定步骤固化为阶段或流程节点；固定流程频繁遇到未覆盖情况时，评估在对应节点增加局部自治。按实际失败补充累计预算、进展信号和完成检查；确有跨进程续行需求时，再设计内部执行状态的持久化与副作用恢复。

### 4.9 用户交互：命令、询问、批准与反馈

**需求与约束**

用户可以控制 Agent 运行、补充信息、批准操作或评价结果。
本节说明这些交互分别表达什么意图、产生什么效果，以及答复失效、等待取消和处理失败时如何处理。

普通任务输入与运行中引导见 [Controller 与入口 Agent](#322-controller-与入口-agent)，权限策略与实际隔离见[执行安全](#410-执行安全策略与隔离)，界面和协议接入见[场景协调](#412-controller场景协调与入口适配)。

**Pattern**：按意图区分交互，避免同 1 个“确认”被解释为不同决定。

| 交互       | 用户表达的意图                       | 处理结果                       |
| ---------- | ------------------------------------ | ------------------------------ |
| 命令       | 执行明确的控制操作，例如切换模式     | 对应处理函数执行操作并返回结果 |
| 询问与答复 | 补充任务所需的信息，例如选择目标目录 | 发起询问的工具或插件取得答复   |
| 批准与拒绝 | 决定某项具体操作是否获得许可         | 执行方据此放行或拒绝该操作     |
| 反馈与评价 | 对已有过程或结果提供意见             | 保存意见，供后续分析           |

每次交互需明确关联的 Agent、请求或评价对象，并区分等待中、已完成、已取消和不可用等状态。
DSH 通过 Commands、User Questions、User Approval 和 Feedback 分别承接这些职责。

#### 4.9.1 命令与询问：控制和信息输入

**命令由用户主动发起。** DSH 直接解析并分发给注册的处理函数，无需模型判断命令含义。处理函数可以修改设置、取消执行或向 Agent 提交引导信息。命令输入、直接返回的文本和调用记录不会自动进入模型上下文；需要模型参与时，由处理函数显式提交输入。具体规则见 [Commands](../packages/interaction/commands/README.md)。

**询问由执行中的工具或插件发起。** 答复应交回对应的请求，再由发起方决定如何继续；例如，询问工具将用户选择作为工具结果提供给模型。计划确认可以使用专门的表单，但改变展示方式不会改变答复含义，也不会自动授予工具执行权限。

DSH 对携带 Agent 的询问，只接受当前存活且未被其他 Agent 管理的入口 Agent；活跃子 Agent 需将未解决的问题交回父 Agent。恢复后的提问资格按当前运行身份判断。
缺少交互 Provider、请求失效或等待取消时，需明确返回失败；保存过问题并不意味着重启后能继续原来的等待。
调用资格与答复格式见 [User Questions](../packages/interaction/user-questions/README.md)。

#### 4.9.2 批准：有限许可与失败处理

**Invariant（需要审批的操作）**：只有收到与当前请求对应的明确许可，操作才能执行。拒绝、取消、无人答复或处理失败均不能视为允许。批准只表示获得许可，操作是否成功仍需查看执行结果；取消等待也不能撤销已经提交到外部系统的动作。

**DeepSeek Mapping**：DSH 的审批请求必须属于尚未结束的 Turn，结果为单次允许、拒绝、取消或不可用。策略 `ask` 允许向已配置的答复方请求决定，`never` 表示需要审批时自动拒绝。当前许可只用于本次操作，不提供长期授权及其撤销存储。审批请求与决定记入日志，模型通过发起方提交的工具结果获知处理情况，审批记录本身不进入模型上下文。

用户作出决定前，需要看到足以判断操作影响的信息。
DSH 当前审批请求包含工具名称、原因和可选调用标识，不包含完整工具参数；如果需要核对完整命令、目标资源或修改内容，就需补齐请求与展示数据。审批结果、记录与失败规则见 [User Approval](../packages/interaction/user-approval/README.md)。

#### 4.9.3 反馈：不可变备注与可编辑评价

DSH 提供 2 类反馈，当前均用于评价与分析，不进入模型上下文，也不直接引导后续执行。

| 类型     | 评价对象与修改方式                                           | 提交后的含义                                     |
| -------- | ------------------------------------------------------------ | ------------------------------------------------ |
| 会话备注 | `/feedback` 追加意见，重复提交分别保留，不能修改或撤回旧备注 | 确认表示已追加到内存日志，不保证已写入磁盘       |
| 消息评价 | 对指定模型回复给出正负评价和备注，支持修改与删除             | 保存前确认目标消息已持久化；版本不匹配时返回冲突 |

会话备注可按部署策略触发会话遥测共享，确认信息需说明当前共享行为；进入发送队列不代表接收端已收到。
消息评价不触发该共享，fork 会话也不复制原有评价。
消息评价的版本检查只协调同 1 服务实例内的写入，不保证跨进程修改互不覆盖。

记录与存储分工见 [Feedback：会话备注与消息评价](#5131-feedback会话备注与消息评价)，具体提交规则见[会话反馈](../packages/feedback/command-feedback/README.md)与[消息评价](../packages/feedback/message-feedback/README.md)。
若让模型使用反馈，需要明确选择哪些内容，并通过可记录的输入路径提交。

#### 4.9.4 验证依据与演进

验证应覆盖答复是否交给正确请求，以及重复答复、过期请求、缺少 Provider、取消等待和审批拒绝时的结果；命令还需验证实际控制效果，反馈需验证保存确认与并发冲突。
每个入口都需验证请求展示、答复返回和执行继续的完整过程，注册了服务不等于入口已经支持交互。

实现依据见各小节的服务文档，服务关系见[人机交互服务](#513-人机交互服务)。

**Roadmap（本文建议）**：审批信息不足时补齐行动预览；入口行为不一致时建立共享交互用例；确需跨重启等待时保存交互状态并重新关联执行者；反馈需影响后续任务时，再设计明确的模型输入规则。

### 4.10 执行安全：策略与隔离

**需求与约束**

Agent 可以读写文件、启动进程和访问外部服务。
执行安全负责确定并落实访问限制，本节涵盖凭证与身份、权限策略和执行隔离。

**Pattern**：提示词告知规则，执行组件检查权限，操作系统或远程环境实施隔离。文件、网络、进程和凭证需分别确定保护范围，保证只适用于已接入限制的调用路径。

#### 4.10.1 凭证、授权与身份

API Key、访问令牌等凭证用于访问外部服务。
DSH 的 Credentials Provider 负责存取，Authorization Flow 通过登录、验证码等交互取得凭证。
身份认证确认调用者是谁；DSH 的 Anonymous User ID 只关联遥测、反馈与请求，不能作为认证依据。
服务分工见[身份、凭证与授权服务](#512-身份凭证与授权服务)。

配置应通过凭证引用或记录键关联凭证，使用方在需要时读取实际值，界面只展示是否配置及来源等描述。
产品 CLI 下，本地凭证来源依次为：启动时继承的环境、受管凭证文件、项目 `.env`、Harness Home 的 `.env`，前者优先。
来自继承环境的值不可通过凭证服务修改，写入会被拒绝；具体规则见 [Credentials Local](../packages/credentials/credentials-local/README.md)。

Authorization Flow 在本次尝试中通过 Credentials 提交凭证，Authorization 服务观察到提交后才确认完成，避免将已有凭证误作本次授权结果。
同 1 凭证键只允许 1 个授权流程运行；当前流程不能跨重启恢复，删除本地凭证也不等于向签发方撤销授权。
流程与失败处理见 [Authorization](../packages/credentials/authorization/README.md)。

凭证保护还需覆盖存储和输出：

- **存储访问**：本地凭证文件在 POSIX 上采用文件 `0600`、目录 `0700`，阻止其他操作系统用户访问。同用户运行的工具仍可能读取；默认 `workspace-write` 主要限制写入。若需向工具隐藏凭证，应将凭证存取与工具执行环境隔离。
- **输出脱敏**：配置返回、错误、日志和传输内容都可能泄露凭证。当前 Settings 只遍历 Object／Dict／Array，不能完整处理 Union、Intersection、Transform 中的敏感字段，序列化 Schema 中的默认值也可能泄露。远程可见的设置需遵守这些限制，见 [Settings 已知限制](../packages/settings/settings/README.md#known-limitations-and-deferred-work)。

#### 4.10.2 策略解析与执行点

DSH 按职责管理权限，没有统 1 包办所有权限的策略服务。

| 规则         | 管理与执行职责                                                         |
| ------------ | ---------------------------------------------------------------------- |
| 沙箱策略     | Sandbox Policy 解析本次模式与工作区，FS／Shell 等组件按策略执行        |
| 审批策略     | Approval 管理`ask`／`never`，语义见[批准](#492-批准有限许可与失败处理) |
| 工具调用规则 | 插件注册允许、拒绝或请求审批的规则，由 Tool Runtime 执行               |

Permission Presets 组合沙箱模式与审批策略。
工具可见范围由 [Tool Runtime](../packages/core/tools/README.md) 另行管理，隐藏工具本身不构成权限隔离。

**SandboxMode 是沙箱执行策略的 1 部分**，表达文件操作的限制类别：

| 模式                 | 受该策略约束的文件操作               |
| -------------------- | ------------------------------------ |
| `read-only`          | 禁止修改文件，保留后端声明的必要例外 |
| `workspace-write`    | 允许写入工作区及后端声明的临时目录   |
| `danger-full-access` | 跳过 DSH 沙箱隔离，仍受宿主权限约束  |

Sandbox Policy 按“本次显式批准的模式 → Session 最近 1 次模式 → 部署默认值”的优先级取值；工作区使用 Session Header 中的固定 `cwd`，缺失时采用部署回退目录。
Consumer 将解析后的策略交给执行 Provider，而不是自行读取配置推断权限。

```text
操作请求 → 解析有效策略 → 检查本次操作
                       ├─ 拒绝 → 返回原因
                       ├─ 允许 → 按策略执行 → 返回结果
                       └─ 需要审批 → 取得许可后按批准范围执行
```

模式变更写入 Session，供恢复和后续模型请求使用；默认值与变更生效规则见[配置与设置](#44-配置与设置系统结构与运行参数)。
当前模式不包含网络、进程或凭证的独立权限策略，也不保证敏感文件不可读取。

#### 4.10.3 平台机制与隔离强度

**DeepSeek Mapping**：Sandbox Seam 定义进程沙箱接口，Provider 提供隔离机制，Consumer 在启动进程时调用。DSH 的受限 Bash／PowerShell 命令及持久终端使用这条路径，限制覆盖进程及其子进程；文件服务等能力按各自实现落实策略。

本地 Provider 在 Linux 优先使用 Bubblewrap，再尝试 Landlock；macOS 使用 Seatbelt；Windows 使用 ACL Restricted Token。Windows ACL 与部分旧 Linux Kernel 上的 Landlock 标记为 `partial`（部分限制），调用方需保留这一事实。平台例外与运行器检查见 [Sandbox Local](../packages/sandbox/sandbox-local/README.md)。

**Invariant（声明受限的执行路径）**：需要隔离时，必须使用能落实本次策略的执行机制。沙箱不可用时返回 `SANDBOX_UNAVAILABLE`，不能自动改为无限制执行。裁决与执行结果需分别记录，并区分权限拒绝、沙箱故障与程序自身错误。

DSH 将进程内插件和部署配置视为受信任代码。
插件直接调用宿主 API，或能力没有接入策略检查时，不会自动受到工具沙箱限制。
Cordis Scope 的服务可见性、Worker Thread 的执行与终止机制，以及 `node:vm` 的代码上下文，都不能替代不受信任代码所需的权限隔离。

#### 4.10.4 验证依据与演进

验证需从真实执行点检查允许与拒绝、路径别名、跨工作区写入、部分隔离、沙箱不可用和审批后失败。
凭证检查覆盖文件读取、配置返回与诊断输出，包括同用户工具的访问。

补充实现依据： [Sandbox Policy](../packages/sandbox/sandbox-policy/README.md)、[Sandbox](../packages/sandbox/sandbox/README.md)和 [Permission Presets](../packages/interaction/permission-presets/README.md)。

**Roadmap（本文建议）**：按实际缺口补齐遗漏的策略检查和凭证脱敏；需要限制网络或读取时增加对应策略；需要运行不受信任插件时引入进程与权限隔离；远程执行还需明确权限如何传递、验证与撤销。

### 4.11 编排：任务与多 Agent 协作

**需求与约束**

任务是要达成的目标，Turn 是 1 次执行轮次。
1 轮内可以多次请求模型、调用工具；该轮结束后，用户后续输入、Goal 续行或 Schedule 到期都可以触发新1 轮。
因此，同 1 任务可以跨多个 Turn，中间不 1 定有用户交互。

本节讨论任务如何持续推进、何时执行、交给谁执行，以及如何收回结果。
单个 Agent 内部的执行方式见[执行控制](#48-执行控制自治度与确定性)，输入接纳规则见 [Controller 与入口 Agent](#322-controller-与入口-agent)。

**Pattern**：按任务需要选择机制，可以组合使用；增加并发前，先确认工作能独立推进。

| 任务需要                   | 对应机制              |
| -------------------------- | --------------------- |
| 记录目标、协作方式和待办   | Goal／Plan Mode／Todo |
| 1 轮结束后继续未完成目标   | Goal Round Driver     |
| 管理已启动的耗时工作       | Jobs                  |
| 在未来时间继续任务         | Schedule              |
| 按步骤、分支和并发关系执行 | Workflow              |
| 将独立任务交给其他 Agent   | Subagent              |

每项工作都需明确由谁启动、停止和释放资源，结果交给谁，以及重启后如何处理。
调用返回、工作完成和目标达成分别需要对应依据。

#### 4.11.1 会话内协作状态

Goal 保存持续目标及推进状态，Plan Mode 表达协作方式，Todo 保存短期事项清单。
DSH 没有强制 Goal → Plan → Todo 的固定关系；更新 Todo 不会自动启动任务，Plan Mode 也不提供权限隔离。

**DeepSeek Mapping**：DSH 每个 Agent 只保留 1 个当前目标，以带修订号的快照记录变化，通过版本比较拒绝过期修改。Goal Round Driver 在 Agent 空闲、目标处于 active、续行已启用且预算有余量时投递下 1 轮输入。例如，第 1 轮完成实现，目标仍未完成，Driver 可以触发下 1 轮，由 Agent 继续验证，无需用户再次发送消息。

`maxGoalRounds` 只限制已接纳的目标轮次，不计普通用户轮次，也不限制 token、时间或费用。
目标状态可以恢复，自动续行许可只在当前进程有效；恢复会话、fork 或替换 Driver 后，需要显式重新启用。
具体机制见 [Goal：跨轮目标续行](#5141-goal跨轮目标续行)。

**Invariant（目标完成判定）**：记录完成状态只表示调用方声明目标已达成。DSH 不提供独立的成功认证器，仍需用产物、测试或外部结果证明完成。

#### 4.11.2 异步任务与调度

**Jobs 管理已经启动的后台工作，Schedule 决定未来何时提交任务。**
2 者的停止、等待和恢复规则不同。

DSH Jobs Local 将工作绑定到具体 Agent 实例及后台执行方。
请求停止后，任务仍处于 Stopping，继续占用并发容量，直到执行方确认结束；取消等待只结束本次等待，不会停止任务。Agent 释放时会取消所属任务并等待结束，启动任务的插件或 Controller 重载则不终止任务。
当前任务记录只在进程内存在，
重启后不恢复。接口与释放规则见 [Jobs Local](../packages/jobs/jobs-local/README.md)。

DSH Schedule 支持延迟、指定时间和固定周期，周期最短为 5 分钟。它保存触发条件与派发记录，到期后等待 Agent 空闲，再通过 Follow-up 提交任务，不打断当前 Turn。

```text
保存定时任务 → 会话运行期间计时 → 到期并等待 Agent 空闲
→ 提交 Follow-up → 保存派发记录 → 后续 Turn 处理任务
```

未运行的会话没有活动计时器，恢复为运行中的会话后才处理过期任务；周期任务只处理最新到期项，不补跑全部错过的次数。
Fork 不继承父会话提醒。
当前插件只接入装载后创建的根 Agent，不接管已有实例或子 Agent，详见 [Schedule](../packages/schedule/schedule/README.md)。

创建和实际删除需保存成功后才确认。
派发时，若 Follow-up 已入队而派发记录尚未持久化就崩溃，恢复后可能重复提交。
派发也不证明模型已完成任务或用户已读；离线准时执行、外部通知和避免重复副作用，需要额外机制。

#### 4.11.3 Workflow：流程主导的编排

本节的 Workflow 在任务层组织步骤、分支和并发，并在指定节点调用 Agent。
单个 Agent 内部采用显式流程的设计见 [Workflow 主导](#483-workflow-主导agent-内部的显式流程)。

DSH Workflow 由独立 Engine 接收脚本并返回运行对象，接口独立于 Agent Driver。
调用方负责收集结果、取消和释放；卸载 Engine 只阻止新运行，已接纳的运行仍由调用方管理。

Worker Provider 限制并发数与总子任务数，在取消或 Worker 失败时清理启动中和已启动的子任务。Worker Thread 避免脚本计算阻塞 Host Event Loop，并支持强制终止；它的隔离范围见[平台机制与隔离强度](#4103-平台机制与隔离强度)。

显式脚本固定控制顺序，但模型生成的脚本仍需校验，模型节点和外部调用的结果也可能变化。
取消不能撤销已经发生的外部操作，恢复业务状态需另行设计幂等与补偿。

当前实现没有持久检查点、跨重启恢复或统 1 的跨 Agent token 预算；并发上限不能代替总成本限制。
接口与执行规则见 [Workflow](../packages/workflow/workflow/README.md)和 [Worker Provider](../packages/workflow/workflow-worker-thread/README.md)。

#### 4.11.4 子 Agent：执行主体委派

子 Agent 适合输入、职责和交付结果明确的独立任务。
父 Agent 提供任务、约束、必要上下文和验收标准，收集回报并核查证据后继续推进。

| 模式                  | 使用方式                   | 结束与后续交互                                      |
| --------------------- | -------------------------- | --------------------------------------------------- |
| One-shot（1 次性）    | 启动 1 次子任务，等待结果  | 通过请求的取消信号停止，调用方收集结果并释放资源    |
| Continuable（可续行） | 保留子会话，可继续发送任务 | 当前轮中断与整体释放分开处理，后续消息经 Inbox 排队 |

DSH 的可续行子 Agent 可以根据已保存的会话重新创建执行实例，这称为冷恢复。
续行管理器负责当前实例的存续，后续任务直接进入子 Agent 的 Inbox，无需另建 Job。
消息入队不代表已经开始或完成，详细结果保存在子会话中。

父子消息按当前活跃实例及父子关系校验权限。
回报要求父 Agent 在线；通知已接收不代表父级已消费，父级消失或释放时也没有持久信箱保证送达。
不能只凭相同 Session ID 接管旧实例的权限。

各 Provider 的上下文、恢复和权限能力需分别确认。
`inheritsParentContext` 只表示继承已完成对话；进程内子 Agent 的权限固定于委派时，不能自行扩大。
当前可续行管理依赖本地 Agent 生命周期，不能推断远程 Provider 同样支持。
实现与限制见 [Subagent](../packages/subagent/subagent/README.md)。
Agent Team 仍属实验方向，尚非稳定产品接口。

#### 4.11.5 验证依据与演进

验证重点是任务能否正确继续和结束：目标恢复后需重新启用、后台停止需等待执行方结束、定时派发可能重复、Workflow 启动中取消需清理子任务，以及子 Agent 冷恢复和父级释放时的回报处理。
并发任务还需检查重复工作、文件冲突、结果遗漏和总资源消耗。

实现依据见各小节链接及 [Goal](../packages/goal/goal/README.md)、[Goal Round Driver](../packages/goal/goal-round-driver/README.md)，组件关系见[编排服务](#514-编排服务)。

**Roadmap（本文建议）**：按需求补齐目标完成评估与资源预算、后台任务持久化、Workflow 检查点与幂等处理；扩大跨 Provider 协作前，明确结果交付、授权和取消保证。

### 4.12 Controller：场景协调与入口适配

**需求与约束**

Controller 将用户或程序的操作交给对应的 Agent 或业务服务，并向调用方返回结果。
本节讨论不同入口如何选择调用方式、输出形式和连接结束后的处理规则；会话定位与输入投递见 [Controller 与入口 Agent](#322-controller-与入口-agent)。

例如，同样提交“修复 BUG”，命令行可以等待执行结束后输出答案，浏览器可以先确认接收，再持续展示进度。
两者复用 Agent 能力，但需要各自定义何时返回、返回什么，以及用户断开连接后是否继续执行。

**Pattern**：单次任务适合直接调用 Runtime 并等待结果；长期交互需要管理会话、订阅事件；外部程序通过协议调用，SDK 再将协议操作封装为语言接口。选择入口时需同时考虑交互需求、连接寿命和结果交付方式。

#### 4.12.1 使用方与交互方式

**DeepSeek Mapping**：DSH 为不同使用方提供以下入口。

| 入口                         | 使用方                                 | 交互方式                                       |
| ---------------------------- | -------------------------------------- | ---------------------------------------------- |
| Headless                     | 在命令行执行任务的用户                 | 提交 1 次任务，等待答案后退出                  |
| Web                          | 在浏览器中使用 Agent 的用户            | 持续对话、查看进度、管理多个会话               |
| ACP（Agent Client Protocol） | 支持 ACP 协议的其他程序                | 通过协议创建会话、提交任务、接收答案或取消执行 |
| SDK                          | 用 TypeScript／Python 开发应用的开发者 | 在代码中调用接口，操作 Agent 并获取结果与状态  |

这些入口复用 Harness 能力，由各自的 Controller 适配操作和结果。入口选择取决于使用方及其交互需求。

#### 4.12.2 业务分发、传输与客户端投影

Headless 直接调用 Runtime，不启动服务端口。ACP 与 SDK 都通过标准输入／输出传输 JSON-RPC 消息，但使用不同协议；ACP 的 stdout 专用于协议帧。

「通过协议调用 Harness 的入口」需要分别处理业务操作、协议调用和客户端展示。
以 DSH Web 为例：

| 组件                            | 职责                                                   |
| ------------------------------- | ------------------------------------------------------ |
| API Remotes                     | 提供业务操作，解析操作对应的 Agent、Session 等对象     |
| Typert Gateway                  | 按生成的类型描述校验参数和返回值，分发调用             |
| Connection                      | 传输请求与事件，关联请求和响应，检查请求来源并封装响应 |
| Client Projection（客户端投影） | 将事件与查询结果组织成界面状态                         |

参数校验通过只表示输入符合接口要求。
是否允许操作目标 Agent，仍需在对象解析和业务操作处检查；浏览器传入 Session ID 不会自动获得控制权。

业务调用通过请求与响应返回结果，任务进度和新增会话消息通过事件流持续推送。
组件调用关系见 [Remote API 与 Client Projection](#515-remote-api-与-client-projection)。

客户端恢复连接后，需要按数据来源补齐状态。
DSH 的 Remote 转发事件不在重连后重放，客户端需重新查询对应领域状态；Session 记录的恢复规则见[输出、持久化与恢复](#516-输出持久化与恢复)。

#### 4.12.3 结果返回与连接清理

**结果返回**：入口需要明确何时结束响应，以及响应包含哪些输出。DSH 的两种等待式入口分别采用以下规则：

- **Headless**：等待 Agent 停稳、Session 写入存储后，输出本次执行区间内最后一条非空 Assistant 文本；以最终 Turn 的完成状态决定退出码。
- **ACP**：每会话同时最多处理 1 个 Prompt 请求，等待输入接纳、Agent 整体空闲和输出发送完成后结束响应。期间补充的引导（Steering）也可能贡献结果，因此返回内容（`end_turn`）不 1 定只对应最初提交的 Prompt。

退出码和协议结束原因不证明业务目标达成，判定依据见[完成、失败与结果归属](#326-完成失败与结果归属)。

ACP 只发送已提交的 Assistant 文本与图片，避免将未提交的模型增量和重试内容作为答案，代价是无法逐 Token 输出。
图片读取失败也会使响应失败。
实时展示与可恢复记录的区别见 [Session 事实与场景输出](#325-session-事实与场景输出)。

**连接清理**：每项已接纳操作都应明确由谁负责停止和清理。Controller 只能控制有权操作的 Agent 实例，并按入口约定决定断连后继续执行还是取消释放。发出取消请求不表示工作已经结束，等待与释放规则见[运行中控制与状态收敛](#332-运行中控制与状态收敛)；外部副作用和后台任务分别遵守所属服务的约定。

DSH ACP 将 Agent 的生命周期绑定到连接。
断连时先停止接纳新请求，取消并等待本连接的输入接纳、Agent 活动和输出结束，再清理所属 Agent 的可续行子 Agent，释放所持有的 AgentHandle。
同 1 Context 中其他入口管理的 Agent 不受这次清理影响。
当前 ACP 只创建新会话，不支持会话恢复或完整交互界面，具体限制见 [ACP](../packages/acp/acp/README.md)。

#### 4.12.4 风险、依据与演进

验证重点是操作发给正确会话、返回时机符合协议，以及取消、断连和输出失败后资源能正确清理。
还需覆盖重连补齐状态与冷会话恢复。
协议客户端应通过真实序列化与进程入口验证 stdout 只包含约定输出、错误映射及客户端状态更新；同进程方法调用不能替代这些检查。

### 5.1 Context、Fiber 与 Effect

**预期解决**

确定作用域、Plugin 挂载实例和资源清理之间的所有权关系。

**解决方式**

Context 表示可见性，Fiber 表示一次挂载，Effect 将注册和资源绑定到 Fiber。

**底层设计**

| 概念          | 定位                                                           |
| ------------- | -------------------------------------------------------------- |
| Cordis        | 插件运行时框架，核心包为`@deepseek-ai/cordis`                  |
| Context / ctx | Context 是承载服务访问与作用域信息的类，ctx 是其对象           |
| Service       | 按名称提供和解析的能力，可由插件注册并被其他插件依赖           |
| Fiber         | 根运行时或单次插件应用的生命周期单元，记录状态、依赖与清理动作 |
| Effect        | 登记到 Fiber 的生命周期操作，关联执行逻辑与清理函数            |

`new Context()` 创建根 ctx 与根 Fiber，建立 `ctx.fiber` 和 `fiber.ctx` 的双向引用。
`ctx.plugin()` 先创建插件 Fiber，再派生绑定该 Fiber 的插件 ctx；插件 Fiber 纳入父 Fiber 的生命周期。
`extend()`、`isolate()` 和 `intercept()` 只派生普通子 ctx，继承当前 Fiber。
Context 链描述环境继承与服务作用域，Fiber 树描述插件实例及其生命周期。

下面合并展示 Context 字段与内置服务方法，是概念模型，不是可编译的源码声明：

```text
class Context {
  root: Context;
  fiber: Fiber;
  baseUrl?: string;

  registry: RegistryService;
  reflect: ReflectService;
  events: EventsService;
  logger: LoggerService;

  constructor() {
    const ctx = new Proxy(this, ReflectService.handler);
    ctx.root = ctx;
    ctx.fiber = new Fiber(ctx);
    ctx.reflect = new ReflectService(ctx);
    ctx.registry = new RegistryService(ctx);
    ctx.events = new EventsService(ctx);
    ctx.logger = new LoggerService(ctx);
    return ctx;
  }

  plugin(plugin, config?);
  effect(setup);
  provide(name, service): Dispose;
  get(name): Service | undefined;
  on(event, listener): Dispose;
  emit(event, ...args): void;
  extend(meta?): Context;
  isolate(service, label?): Context;
  intercept(service, config): Context;
}
```

Context Proxy 将固定成员访问交给 Context，将动态 Service 名称交给 Reflect 按当前作用域解析。
Registry 管理插件与依赖注入，Reflect 管理服务提供与解析，Events 管理事件分发，Logger 提供具名日志。
`plugin()` 创建可等待的 Fiber，`effect()` 登记同步或异步生命周期操作，`get()` 读取服务，`emit()` 分发事件。
派生方法中，`extend()` 附加局部属性，`isolate()` 隔离指定 Service 的解析域，`intercept()` 附加指定 Service 的局部配置。

```text
ctx.extend() / ctx.isolate() / ctx.intercept() → Child Context，仍属当前 Fiber
ctx.plugin()                                    → Child Fiber + Plugin Context
ctx.provide()                                   → Service disposer
ctx.on()                                        → Listener disposer
ctx.effect()                                    → 外部资源 disposer
```

父 Fiber 卸载时反向执行 Effects，并级联销毁 Child Fibers。子 Fiber 可以独立卸载。

**坑与对策**

- 将 Context 层级当成 Fiber 层级：派生 Context 不自动创建生命周期节点。
- 手工重复包装 `ctx.provide()`、`ctx.on()` 或 `ctx.plugin()`：这些 API 已绑定 disposer。
- Socket、子进程等资源无清理归属：显式使用 `ctx.effect()` 或 Service disposer。

**相似方案**

React Effect、依赖注入 Scope 和结构化并发都强调资源随拥有者退出；Fiber 将该原则应用于 Plugin Tree。

### 5.2 Service、Reflect 与 Event

**预期解决**

让 Plugins 在作用域内发现能力，并随 Service 可用性变化安全激活或卸载。

**解决方式**

`inject` 声明必需 Service；Reflect 维护 Service 实现和可见性；Event 提供通知与处理链。

**底层设计**

```text
缺少必需 Service → Fiber 保持 PENDING
依赖全部可用     → PENDING → LOADING → ACTIVE
必需 Service 消失 → ACTIVE → UNLOADING → PENDING
```

Plugin 自带 `inject` 表示固有依赖，Entry `inject` 表示部署附加依赖。局部依赖使用 `ctx.inject()`；可选能力在使用点通过 `ctx.get()` 检查。

Reflect 在 Service 变化时扫描存活 Fibers，按 Service 名和 isolate scope 过滤，再局部刷新生命周期。Provider 在 `LOADING` 阶段注册的 Service，进入 `ACTIVE` 后才可用。

Event 由同一 Root Runtime 共享，Listener 随所属 Fiber 卸载。Waterfall Listener 调用 `next()` 继续处理，不调用则短路。

**坑与对策**

- 把 `inject` 写成 Plugin 名：它声明的是 Service 名。
- 把对象形式 `inject` 当成可选依赖：数组和对象形式都表示必需依赖。
- Provider 消失后保留 Consumer：Reflect 会卸载 Consumer 并使其回到 `PENDING`。

**长期演进**

在不复制易失反向索引的前提下，提高大规模 Fiber 扫描和依赖诊断能力。

### 5.3 Event 与 Interception Pipeline

**预期解决**

让持久事实、运行中协调和能力策略使用不同事件类型，并允许外部 Hook 协议复用原生扩展点。

**解决方式**

Session Events 记录可恢复事实；Agent Events 协调活跃 Agent；Capability Events 承载领域策略和 Provider 接入；Cordis Dispatch Mode 定义通知、串行和瀑布处理；Hook Bridge 将外部协议映射到这些事件。

**底层设计**

```text
Event Taxonomy
├── Session Event：append-only durable fact
├── Agent Event：live Agent coordination
└── Capability Event：policy / provider interception

Dispatch Mode
├── emit：通知所有 Listeners
├── serial：按序执行所有 Listeners
└── waterfall：当前 Listener 通过 next() 委托后续处理

External Hook Protocol
→ Claude Code / Codex Bridge
→ Native Agent / Tool Extension Points
```

**坑与对策**

- 用实时 Event 保存恢复所需事实：需要重放的数据必须成为 Session Event。
- Waterfall Listener 忘记 `next()`：不调用即主动短路后续处理。
- Hook Bridge 建立第二套生命周期：Bridge 只转换协议，原生事件仍是唯一扩展入口。
- Listener 资源脱离 Fiber：通过 `ctx.on()` 或 Effect 绑定卸载。

**相似方案**

Event Sourcing、Middleware Chain 和 Protocol Adapter 分别对应持久事实、控制链与外部协议转换。

**长期演进**

稳定事件分类、Scope 过滤、错误隔离和 Hook 兼容矩阵，并保持每类事实只有一个权威事件源。

### 5.4 Entry、Patch 与 Loader

**预期解决**

把分层配置转换为真实 Plugin 挂载。

**解决方式**

Entry 描述单个 Plugin，Patch Layers 生成最终 Entries，Include 负责组合，Loader 负责导入和挂载。

**底层设计**

| 概念        | 定位                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| Entry       | 1 个 Plugin 装配项；`id` 供 Patch 定位，`name` 指定模块，`config` 提供参数，`disabled` 控制启用状态。 |
| Patch       | 对 Entry 执行新增、字段覆盖或启用状态调整。                                                           |
| Patch Layer | 来自同 1 配置来源、内部顺序稳定的 1 组 Patch。                                                        |
| Bundle      | 提供 Plugin 与默认组合，向 Profile 贡献 Patch Layer。                                                 |
| Profile     | 组合有序 Bundle，并提供场景级用户配置。                                                               |
| Group       | 组织嵌套 Entry，并可为指定 Service 建立共同隔离域。                                                   |

```yaml
id: session
name: "@deepseek-ai/dsh-session"
config: {}
disabled: false
```

```text
Bundle Patch Layers
→ Profile Patch Layer
→ Home Patch Layer
→ CLI Patch Layers
→ Launcher-enforced Patch
→ Composed Profile
```

`DSH_HOME` 默认指向 `~/.dsh`，用于定位 Profile、跨 Profile 的 Home Patch 和运行数据；每次启动可以选择其他 Home。
同 1 层保留声明顺序，多个 CLI Patch 按参数顺序应用。
Launcher 生成层为已有 `agent-presets` Entry 补充内置预设目录，并在禁用遥测时修改已有 `session-telemetry-otel` Entry；它不会凭空新增这两个 Entry。

Launcher 只形成有序 Patch 列表。
根 Include 读取基础 Entry 并依次应用 Patch，再把结果交给 Loader 建立 Entry 配置树；Patch 来源文件保持不变。

- 普通 Patch 按 `id` 定位 Entry，并替换指定的顶层字段；未指定字段保留，`config` 不递归合并。
- `insert` 向根列表或目标 Group 追加 Entry，后续 Patch 可以继续修改。
- `disabled` 保留 Entry 声明并改变启用状态；Group 的禁用状态由子 Entry 继承。
- 目标不存在、向非 Group 插入子项或 `name` 不匹配时产生告警并跳过当前 Patch；同一 Group 内重复 `id` 会拒绝配置树更新。

```text
读取 Entry
→ 根据 name 导入模块
→ 解析 Plugin 定义
→ ctx.plugin(plugin, config)
→ Registry 创建 Fiber
→ 合并 inject
→ Fiber 进入 PENDING 或 ACTIVE
```

**坑与对策**

- 将 Entry 当成运行实例：Entry 只是 Loader 输入，Fiber 才是挂载实例。
- 将 Patch Layer 顺序与 Fiber 激活顺序混为一谈：前者决定最终配置，后者由依赖决定。
- 在配置中使用 `!js`：Plugin `config` 和 Entry `disabled` 中的表达式使用 `!!js`。
- 将配置预览当成运行结果：`--dump-config` 不包含 Launcher 生成 Patch 和 `!!js` 求值结果，也不验证 Plugin 激活或外部服务健康。

**相似方案**

Webpack 配置合并、Kubernetes overlays 和应用模块清单都采用声明与运行分离；Loader 增加了 Plugin 生命周期语义。

**长期演进**

强化配置来源追踪、覆盖冲突提示和 `--dump-config` 可解释性。

### 5.5 Agent 接口、Registry 与所有权

**预期解决**

让调用方创建、恢复和控制 Agent，同时隔离具体驱动器并明确实例的生命周期所有权。

**解决方式**

`packages/core/agent` 定义公共接口和 Registry；AgentFactory 提供创建与恢复；AgentHandle 将程序化实例绑定到调用方 Fiber；具体 Agent 实现只通过 Registry 发布。

**底层设计**

```text
Consumer
→ ctx.agents.create() / resume()
→ AgentFactory
→ 创建 Session、Agent Scope 与具体 Agent
→ setup
→ SessionRegistry + AgentRegistry 发布
→ AgentHandle 返回调用方
```

Agent 创建与发布是受回滚保护的事务。调用方 Fiber、AgentHandle 和 Provider 卸载共同汇合到同一个完全停稳点；销毁按停止驱动器、撤销作用域、移除 Agent、分离 Session 的顺序完成。

**坑与对策**

- Consumer 构造具体 Agent：统一经 `ctx.agents` 访问，避免依赖私有驱动器。
- Setup 驱动尚未发布的 Agent：Setup 只负责受信任的组合，不触发执行。
- 创建失败后残留 Session 或 Scope：发布前失败必须回滚全部私有资源。
- Provider 卸载后仍发布 continuation：卸载等待 create、resume 和驱动器全部收敛。

**相似方案**

资源句柄、事务式发布和 Actor Registry 都提供类似的身份与所有权管理。

**长期演进**

保持 Agent 公共接口与具体驱动器解耦，强化跨 Scope 创建、恢复和 teardown 的一致语义。

### 5.6 AgentLoop Service 与 ReactLoopAgent

**预期解决**

将 Agent 的创建管理与单实例执行分离，使 Factory 生命周期和 ReAct 状态机能够独立理解与演进。

**解决方式**

`AgentLoop` Service 管理创建与恢复；`ReactLoopAgent` 管理单实例状态；Turn / Step 循环管理模型与 Tool 的交替执行。

**底层设计**

```text
AgentLoop Service：Factory 与生命周期
└── ReactLoopAgent：单 Agent 实例与运行状态
    └── Turn / Step：ReAct 执行循环
```

**坑与对策**

- 把 Service、实例和循环算法视为同一层：分别判断依赖所有权、运行状态和步骤控制。
- 用具体类作为公共扩展接口：Consumer 依赖 Agent 接口，`ReactLoopAgent` 保持包内实现。

**相似方案**

Factory、Actor Instance 和 Message Loop 也按创建管理、实例状态和消息处理分层。

**长期演进**

保持三层接口单向依赖，使新 Driver 可以复用 Agent Registry，而不继承 ReactLoopAgent 的内部算法。

#### 5.6.1 AgentLoop Service：Factory 与生命周期

**预期解决**

创建或恢复 Agent，并保证 Session、Scope、Registry 和驱动器作为一个事务发布和释放。

**解决方式**

`packages/core/agent-loop/src/index.ts` 中的 `AgentLoop` 实现 AgentFactory，持有 `agents`、`sessions`、`llm`、`tools` 和 `systemPrompt` 依赖，构造 `ReactLoopAgent` 并将其发布到两个 Registries。

**底层设计**

```text
ctx.agents.create() / resume()
→ AgentLoop Service
→ 创建或加载 Session
→ 创建 Agent Scope
→ 构造 ReactLoopAgent
→ 执行 setup
→ 发布 Session + Agent
→ 返回 AgentHandle
```

调用方 Fiber 与 AgentLoop Provider 共同拥有实例。创建失败或任一所有者释放时，统一进入停止驱动器、撤销 Scope、移除 Agent、分离 Session 的收口路径。

**坑与对策**

- 把 `AgentLoop` 当成每个 Agent 的运行对象：它是共享 Factory Service，运行状态属于 `ReactLoopAgent`。
- 发布一半后失败：Session 与 Agent 的发布处于同一回滚事务。
- 调用方只注入 `agents` 导致驱动器依赖缩减：Factory 保留自身依赖 Context，调用方 Context 只提供所有权。

**相似方案**

Transactional Factory 和结构化资源所有权都要求对象只在完整初始化后可见。

**长期演进**

稳定 Factory 与 AgentHandle 语义，使新的 Driver Provider 能复用创建、恢复和 teardown 约定。

#### 5.6.2 ReactLoopAgent：实例状态与控制

**预期解决**

串行管理单个 Agent 的输入、活动状态、唤醒、取消和完全停稳。

**解决方式**

`packages/core/agent-loop/src/agent.ts` 中的 `ReactLoopAgent` 实现 Agent，以 Inbox 保存待处理输入，以显式 Phase 管理当前活动，以单一 Driver Promise 表示 drain interval。

**底层设计**

```text
Phase
├── idle：无活动驱动器
├── maintenance：维护操作占用实例
└── running：持有 AbortController、Turn、Step 与 wakeRequested

send()
→ Inbox splice
→ wakeDriver()
→ kick()
→ 连续执行 Turn
→ idle
```

`followup()` 写入 `next-turn` 并唤醒；`steer()` 写入 `next-step` 并唤醒；`inject()` 写入 `next-step` 但不唤醒。Inbox 的插入、编辑、删除和领取均先记录规范化 splice 事件。

首次 Step 领取全部 `next-step` 和最前面的 1 条 `next-turn`；同 1 Turn 的后续 Step 只领取新增的 `next-step`。
领取只把消息关联到当前 Turn；`pre-step` 接纳后才写入模型可见的 `user/message`，拒绝或移除的消息不会自动返回 Inbox。
有效变更先追加 `agent/inbox/spliced`，再更新队列；只有持久化写入或 `session/flush` 完成后，变更才具备跨进程恢复保证。

**坑与对策**

- 同时启动两个 Driver Promise：只有 `idle` 可以创建新 Driver；运行中输入由现有循环领取。
- abort 后到达的唤醒丢失：`wakeRequested` 在收敛点重放有效唤醒。
- 将 `whenIdle()` 绑定到单条消息：它观察完整 drain interval，可能跨多个连续 Turns。
- 发出取消即释放实例：teardown 等待忽略信号的工作完成。

**相似方案**

Actor mailbox 串行输入，结构化并发等待子工作，事件循环用显式状态控制唤醒。

**长期演进**

强化取消竞态、维护任务与后台工作的统一状态表达，并保持单实例串行语义。

#### 5.6.3 Turn / Step：ReAct 执行循环

**预期解决**

在一个用户请求中重复调用模型和工具，直至得到最终回答或终止结果。

**解决方式**

`kick()` 驱动连续 Turns；`turn()` 原子领取输入并驱动连续 Steps；`preStep()` 组装上下文并开放扩展；`step()` 调用模型、提交输出并决定结束或执行 Tool Calls。

**底层设计**

```text
turn/start + claim Inbox
→ preStep()
→ step/start
→ buildRequest()
→ LLM Stream
├── Final Answer → assistant/message → step/end → turn/end
└── Tool Calls → executeToolCalls() → Tool Results → step/end → 下一 Step
```

流式输出以 `assistant/chunk` 展示，以 `assistant/message` 形成完成锚点。Tool Scheduler 可并行执行安全调用，以独占调用形成屏障；结果仍按模型顺序提交。

**坑与对策**

- 把 Turn 当成一次模型调用：一个 Turn 可以包含多个 Steps。
- 把 Inbox Event 当成模型消息：只有被领取并接纳的输入形成 `user/message`。
- 用 Chunk 代替完整消息：Chunk 服务实时展示，Message 才是后续投影的完成事实。
- 取消后继续分发 Tool Call：停止新分发，等待已启动调用完成，并记录未分发调用的中止结果。
- 插件失败终止整个 Agent：失败收口当前 Turn，Driver 回到可继续接收输入的状态。

**相似方案**

ReAct Loop 根据观察选择下一行动；事务日志为每个 Turn 和 Step 提供持久边界。

**长期演进**

增强并行调度、请求恢复和 Runtime Invariant，同时保持“模型决策—工具执行—结果观察”的最小循环。

#### 5.6.4 Guard：超时与循环卫生

**预期解决**

在不扩张 Agent Loop 内核的前提下，限制单次 Tool 时长并提示无进展的重复调用。

**解决方式**

`dsh-tool-call-timeout-policy` 包装 `tools/execute`，只执行 Tool Definition 声明的 `timeoutMs`；`dsh-repeat-tool-reminder` 按 Agent 追踪连续同名同参调用，在阈值处注入建议性上下文。

**底层设计**

```text
Tool Call
├── Declared timeoutMs → Derived AbortSignal → Tool Pipeline → TOOL_TIMEOUT
└── Post-execute Fingerprint → Consecutive Count → Advisory Context
```

Timeout 是协作式取消，真正终止由 Tool 和下游 Capability 响应 Signal；重复检测是进程内启发式提醒，不否决调用。提醒作为有来源的模型可见消息写入日志，原 Tool Result 保持不变。

**坑与对策**

- 将 Deadline 当成硬杀：只有向下转发 Signal 并能终止工作的 Tool 才声明超时。
- 为未声明 Tool 设置隐式默认值：预算由资源所有者显式定义。
- 将重复调用一律阻断：完全相同的轮询可能合法，默认只提醒并允许配置排除。
- 多个执行 Wrapper 顺序不明：注册顺序必须明确超时覆盖整次重试还是单次尝试。

**长期演进**

增加基于进展信号的循环检测、分层 Deadline 和统一取消诊断，同时保留 Guard 的插件化。

### 5.7 Model Request 与 LLM

**预期解决**

为每个 Step 生成可重建的模型请求，并隔离具体模型厂商协议。

**解决方式**

System Prompt Service、Session Projection、Tool Runtime 和 Agent Config 分别提供请求输入；LLM Service 将统一请求路由到 Provider Adapter。

**底层设计**

```text
Model Request
├── System Prompt：当前指令与 Runtime Context
├── Messages：从 Session Log 投影的对话历史
├── Tool Schemas：当前模型可见能力
└── Model Config：Provider 与 Model
```

System Prompt 每个 Step 动态组装，以反映 Agent Scope、权限、Workspace Context 和 Tool 可见性。

```text
ReactLoopAgent
→ Harness Model Request
→ LLM Service
→ Provider Adapter
→ Model API
→ Harness Chunks
→ Session Events
```

**坑与对策**

- 把整份 Session Log 发给模型：只投影有效 Messages。
- 绕过日志传递当前输入或 Tool Result：所有模型可见内容先形成可重建事实。
- 让 ReactLoopAgent 依赖厂商协议：协议转换归 Provider Adapter。

**相似方案**

统一数据库 Driver 和 HTTP Adapter 都通过稳定内部接口隔离外部协议；LLM Service 还需要统一流式输出。

**长期演进**

在稳定 Model Request 和 Stream 语义的前提下扩展模型路由、能力协商、重试和遥测。

#### 5.7.1 上下文装配与压缩

**预期解决**

把提示词、会话消息、工具描述和动态引用装配为可重建且受 Token 预算约束的模型请求。

**解决方式**

`dsh-system-prompt` 按 Agent Scope 汇集 Prompt Sections；`dsh-session-projection` 从 Session Log 派生 Messages；`context/*` Plugins 注入 Workspace Instructions、时间、文件和 Session 引用；`dsh-token-meter` 测量压力；`dsh-compaction` 与 Tool Result Pruner 改写后续投影。

**底层设计**

```text
Session Log → Session Projection → Messages
Prompt Sections + Runtime Context + Tool Schemas
→ Token Meter
├── Within Budget → Model Request
└── Over Budget → Compaction / Tool Result Pruning → New Projection
```

压缩追加 `compaction/*` 事实并遮蔽旧投影，不删除原始事件。文件和会话引用在当前 Agent 的工作区与授权范围内解析。

**坑与对策**

- 缓存完整 System Prompt：每个 Step 按当前 Scope 和 Tool 可见性重新装配。
- 将引用内容旁路写入请求：模型可见内容必须进入日志或从日志事实重建。
- 将 Session Query 与 Compaction 混用：前者检索其他事实，后者控制当前历史投影。

**长期演进**

提高 Token 估算、引用来源标注、增量摘要、压缩质量和 KV Cache 稳定性。

### 5.8 Tool Runtime

**预期解决**

安全连接模型生成的结构化调用与 Runtime 中的真实执行能力。

**解决方式**

Tool Schema 描述模型接口，Tool Implementation 执行能力，Tool Runtime 管理注册、可见性、参数校验、策略、权限和调度。

**底层设计**

```text
模型读取 Tool Schema
→ 生成 Tool Call
→ ReactLoopAgent 识别调用
→ Tool Runtime 查找 Implementation
→ 参数校验 / Policy / Approval
→ 执行 Implementation
→ Tool Result 写入 Session Log
→ 下一 Step 投影结果
```

模型输出不含 Tool Call 时结束 Turn；包含 Tool Call 时执行工具并开启下一 Step。

**坑与对策**

- Schema 可见但 Implementation 不可执行：模型可见集合与运行时可执行集合必须一致。
- Tool 复制底层能力：Tool 通过 Capability Service 调用 Provider。
- 危险操作直接执行：在 Tool 执行链加入 Policy、Permission 或 Approval。

**相似方案**

RPC Dispatcher 也负责 Schema、路由和调用；Tool Runtime 还需要面向模型呈现、会话记录和多 Step 反馈。

**长期演进**

扩展并行与独占调度、结果呈现、错误分类和跨执行环境的一致行为。

#### 5.8.1 Native Tool Calling

**预期解决**

让模型直接选择并调用单个 Tool，保留最清晰的调用、批准和结果链路。

**解决方式**

`ToolRuntime` 将当前 Scope 可见的 Schemas 直接交给模型；模型产生 Tool Call 后，调用依次经过校验、策略、执行、结果定稿和会话记录。

**坑与对策**

- 将不可见 Tool 保留在提示词：Schema 可见性和可执行集合必须来自同一 Scope。
- 将多个相互依赖的调用全部并行：仅明确声明并发安全的连续调用可以重叠，独占调用形成顺序屏障。

#### 5.8.2 Code Mode 与 Code Runtime

**预期解决**

让模型用一个临时程序组合多次 Tool 调用、控制中间数据和表达分支，而不把全部中间结果写入模型上下文。

**解决方式**

`ToolRuntime` 在 `code` 或 `both` 模式下生成当前 Tool 集合的类型化 SDK，并暴露保留入口 `run_code`；`CodeRuntime` 在隔离载体中执行模型程序，异步 bindings 将子调用重新送入完整 Tool Pipeline。

**底层设计**

```text
Visible Tool Schemas
→ Generated TypeScript / Python SDK
→ run_code(program)
→ CodeRuntime Provider
→ tools.<name>(args)
→ Native Tool Pipeline
→ Program Logs + Return Value
→ Outer Tool Result
```

当前实现提供 Worker Thread TypeScript Provider 与 CPython subprocess Provider。每次运行使用新执行环境；中间 binding 值仅在执行期存在，外层日志与返回值才进入模型上下文。Worker Thread 提供资源隔离和强制终止，但不构成安全边界。

**坑与对策**

- 把 Code Mode 当成 Workflow：前者由模型即时编程，后者由显式流程拥有控制权。
- 子调用绕过 Tool Policy：bindings 必须重新经过完整 Tool Pipeline。
- 运行结束后遗留子调用：外层运行结束前必须取消并 drain 已启动工作。
- 依赖跨运行内存状态：每次运行使用新环境，可恢复事实只存在于 Session Log。

**长期演进**

扩充 Runtime Provider、流式进度和安全隔离，同时保持语言 SDK、Tool Schema 与执行结果一致。

#### 5.8.3 Tool Presentation 与结果投影

**预期解决**

让同一 Tool 在 Native、Code Mode、日志回放和不同 UI 中保持一致语义，并按场景呈现合适视图。

**解决方式**

Tool Definition 同时声明规范输出和纯函数式 render intent；Session Event 保存调用、最终模型内容及必要 presentation metadata；客户端按 `generic`、`terminal`、`diff`、`search`、`read` 或 `web` 等意图渲染。

**坑与对策**

- UI 按 Tool 名硬编码：展示意图由 Tool 所有，UI 只实现通用卡片类型。
- 将 UI 文本作为规范结果：Canonical Value 服务程序调用，Model Content 与 Presentation 分别投影。
- 回放依赖执行期对象：展示只能依赖持久参数、结果和 metadata。

**长期演进**

统一 Native 与 Code 子调用的可视化、增量状态、资源引用和降级渲染。

#### 5.8.4 Output Retention：有界输出与可恢复原文

**预期解决**

限制 Tool 输出占用的内存和模型上下文，同时区分预算截断、上游不完整和历史压缩。

**解决方式**

`dsh-output-retention` 为 Tool 提供按条目或字节保留的纯库；Tool 自行保留业务语义并可配合 Spill 保存全文；`dsh-compaction-tool-result-pruner` 在上下文压力下追加替换事件，缩减未来模型投影。

**底层设计**

```text
Execution Output
├── Tool-time Retention → Bounded Preview + Omission Metadata
│                         └── Optional Spill → Full Result Locator
└── History-time Pruner → Replacement Event → Bounded Future Projection
                          └── Original Session Event Retained
```

Retention 只回答保留与省略范围；退出码、权限错误和 Provider 部分失败仍由 Tool 表达。Pruner 改写模型表面，不删除追加日志中的原始结果。

**坑与对策**

- 将 `truncated` 当成执行不完整：预算省略与上游失败使用不同字段。
- 按字符限制进程或网络流：资源保护按 UTF-8 字节计量，模型压力仍由 Token Meter 判断。
- 截断后不给恢复路径：可取回的完整结果进入 Spill，并返回定位信息。
- 原地覆盖历史 Tool Result：使用追加式 Surface Replacement，保留审计原文。

**长期演进**

统一各 Tool 的保留元数据、Spill 生命周期和 Token 感知预算，并增加语义化内容选择。

### 5.9 执行能力与运行环境

**预期解决**

把文件、进程、命令、终端、语言服务和 Sandbox 的架构关系落实为同一执行世界。

**解决方式**

`dsh-fs`、`dsh-subprocess`、`dsh-shell`、`dsh-terminal`、`dsh-lsp` 和 `dsh-sandbox` 分别定义职责；本地、Sandbox 与 E2B Providers 由 Composition 成套选择；对应 Tool Consumers 只依赖 Service Definitions。

**底层设计**

```text
Tool Consumers
├── File Tools → ctx.fs
├── Bash / PowerShell Tools → ctx.shell → ctx.subprocess
├── Terminal Tools → ctx.terminals → ctx.subprocess.spawnTerminal
└── LSP Tool → ctx.lsp → ctx.fs + ctx.subprocess

Process Request → Sandbox Policy → ctx.sandbox → Wrapped Process
Remote World → fs-e2b + subprocess-e2b
```

`subprocess` 持有进程树和终止语义；Shell 持有命令默认值与结果语义；Terminal 持有跨调用 PTY Session；LSP Provider 持有协议连接和代码导航语义。

**坑与对策**

- Tool 直接生成本地进程：经 Shell、Terminal 或 LSP Service 进入共享 Subprocess。
- 混搭本地文件系统与远程进程：Composition 必须选择同一执行世界的 Providers。
- 将 Worker Thread 或 E2B 标签直接当成安全保证：以具体 Sandbox 和 Provider 契约判断隔离强度。
- 终止单个进程但遗漏后代：Subprocess Provider 持有并清理完整进程树。

**长期演进**

统一远程执行世界、Windows 与 POSIX 语义、资源限额、终止结果和环境能力探测。

### 5.10 数据与资源服务

**预期解决**

**解决方式**

`dsh-session` 持有追加式会话日志；`dsh-workspace` 持有工作区实体；`dsh-storage` 连接类型化 Data Forms 与具名 Backends；`dsh-attachment` 保存不可变图片内容；`dsh-spill` 外置超大工具结果；`dsh-session-query` 提供查询与检索，调用方负责授权，见[历史查询](#464-历史查询查找记录与核对来源)。

**底层设计**

统一标识、Schema 迁移、保留和回收策略，同时保持各数据服务的事实所有权。

#### 5.10.1 Session 派生服务

**预期解决**

从完整 Session Log 提供客户端读模型、统计、标题和遥测，而不让每个 Consumer 重复扫描日志或创建第二事实源。

**解决方式**

`dsh-session-projection` 注册增量 Fold 单元；Projection Cache 保存可丢弃的计算检查点；Stats、Title 和 Telemetry 分别消费会话事实，输出各自的派生结果。

**底层设计**

```text
Session Log：唯一事实源
├── Projection Registry → Client Read Models
│   ├── Projection Cache：版本化 Fold 检查点
│   └── Session Stats：Turn / Step / Timing
├── Session Title：确定性回退或单一模型 Provider
└── Session Telemetry：脱敏投影 → Reporting Backend
```

Projection Cache 只缩短回放，不拥有事实；版本、Schema 或 Session 生命周期身份不匹配时丢弃并重算。Telemetry 只负责捕获和投递，批处理、重试与丢失策略归 Reporting Backend。

**坑与对策**

- 将缓存当成权威状态：日志领先，缓存只允许落后，不允许领先。
- 用分页窗口计算全会话统计：Stats 从完整事件流 Fold，避免分页和 Compaction 改变结果。
- 同时注册多个标题 Provider：Title Service 只接受一个生成策略，并保留确定性回退。
- 将遥测发送结果写回会话事实：Telemetry 是外发投影，不反向改变 Session Log。

**长期演进**

扩充可复用 Projection Units、冷读恢复和反馈门控遥测，同时保持派生状态可删除、可重建。

#### 5.13.1 Feedback：会话备注与消息评价

**预期解决**

同时支持不可变的会话级意见和可编辑的消息级评价，并避免反馈意外进入模型历史。

**解决方式**

`dsh-command-feedback` 将会话意见追加为 `feedback/record`；`dsh-message-feedback` 将评分与备注保存为 Storage Sidecar，并通过 Host Remote 提供查询、写入和删除。

**底层设计**

```text
Session Feedback
└── /feedback → feedback/record → Session Log → Optional Telemetry Trigger

Message Feedback
└── UI / Host Remote → messageFeedback Service → Storage Sidecar
```

两类反馈都不进入模型历史。前者是不可变 Session Event，可触发反馈门控遥测；后者是带版本控制的可编辑业务状态，不是 Session Event，也不触发遥测释放。

**坑与对策**

- 用同一记录承载两种语义：按不可变审计与可编辑产品状态分治。
- 把反馈作为下一轮模型输入：反馈默认仅供产品改进和人工分析。
- 覆盖并发消息反馈：写入和删除使用版本比较，冲突返回当前权威值。

**长期演进**

增加结构化分类、聚合分析和明确授权的模型消费入口，不改变两类事实的所有权。

### 5.14 编排服务

**预期解决**

落实会话内计划、后台任务、Workflow 和子 Agent 的状态、所有权与释放规则。

**解决方式**

`dsh-plan-mode` 和 `dsh-tool-todo` 保存会话协作状态；Goal、Jobs 与 Schedule 分别承载持续目标、后台工作和定时提醒；Workflow Service Definition、Worker Provider 与 Tool Consumer 执行显式流程；Subagent Registry 连接进程内、ACP、Codex、Claude Code 和 DSH SDK Providers，并通过 Tool Consumers 暴露委派与控制。

**底层设计**

```text
Session → Plan / Todo Events
Session → Goal Events → Goal Round Driver → Later Turns
Producer → Jobs Registry → Background Work → Completion Notice
Session → Schedule Events → Live Owner Timer → Follow-up Turn
Tool Request → WorkflowEngine → Worker Thread → Agent Tasks
Tool Request → ctx.subagents → Selected Provider → Child Agent
Child Result / Report → Parent Session
```

Worker Thread 只隔离 Workflow 对 Host Event Loop 的占用，不构成安全边界。Workflow Run 和 Subagent Run 均由调用方持有取消与释放责任。

**坑与对策**

- 把 Workflow 接到 AgentFactory：Workflow 通过独立 Engine 调用普通 Agent。
- 将 Goal、Job 和 Schedule 合为一种任务：按持续决策、后台执行和时间触发分别建模。
- 多个 Subagent Provider 隐式竞争：调用请求显式选择 Provider。
- 父子 Agent 共享可变内存：通过 Session、消息和报告通道交换事实。

**长期演进**

补齐持久检查点、恢复、取消传播、跨 Agent 预算和后台结果收集。

#### 5.14.1 Goal：跨轮目标续行

**预期解决**

让同一 Session 围绕一个长期目标自动续行，同时保留暂停、恢复、完成和阻塞的显式状态。

**解决方式**

`dsh-goal` 以 `goal/change` 保存目标快照和修订号；`dsh-goal-round-driver` 在 Agent 空闲时按轮次预算投递后续输入；Tool 与 Command Consumers 管理目标。

**底层设计**

```text
Goal Mutation → goal/change → Durable Goal State
                                 + Process-local Activation
                                 → Round Driver → Follow-up Turn
```

目标阶段、修订和已开始轮数可恢复；继续执行的 activation 只存在于当前进程。恢复、Fork 或 Driver 替换后默认不自动续行，必须显式 Resume。

**坑与对策**

- 持久化自动执行权限：只持久化目标事实，续行授权保持进程内。
- 用 Goal 表达并行任务：当前模型每个 Agent 只保留一个目标；独立工作交给 Jobs 或 Subagents。
- 只靠自然语言判断结束：完成、阻塞和暂停必须提交显式状态。

**长期演进**

增加独立评估器和 Token、时间、成本预算，同时保持目标状态与调度策略分离。

#### 5.14.2 Jobs：进程内后台工作

**预期解决**

统一管理跨 Tool Call 持续运行的后台任务，使其可查询、等待、取消和回收。

**解决方式**

`dsh-jobs` 定义 Registry；`dsh-jobs-local` 按 Owner 保存运行记录并限制并发；Producer 注册任务，`dsh-tool-jobs` 提供控制和完成通知。

**底层设计**

```text
Producer → ctx.jobs.start(owner) → Running / Stopping / Terminal
Controller → list / wait / cancel
Settlement → Snapshot + Owner-scoped Notice
```

Job 生命周期绑定准确的 Agent Owner；Registry Service 或 Owner 释放时取消并等待任务收口。当前 Registry 是进程内实现，重启后不恢复。

**坑与对策**

- 将后台进程等同于持久 Job：当前状态只在进程内，持久执行需要新 Backend。
- 取消返回即释放容量：只有 Producer 的完成信号才能终结记录。
- 用 Session ID 代替对象所有权：清理由准确 Agent 生命周期触发，避免复用标识误伤新实例。

**长期演进**

按实际需求增加持久 Backend、租约、跨进程 Worker 和可恢复结果。

#### 5.14.3 Schedule：会话内定时续行

**预期解决**

在指定时间或固定间隔向原 Session 投递后续轮次，并让调度状态可恢复和审计。

**解决方式**

`dsh-schedule` 将创建、删除和派发记录追加到 Session Log；当前根 Agent 的进程内 Owner 折叠状态、维护 Timer，并在 Agent 空闲后排入 Follow-up。

**底层设计**

```text
Schedule Tool → Schedule Events → Durable Fold
                                  → Live Owner Timer
                                  → Idle Admission
                                  → Follow-up Turn
                                  → Dispatch Event
```

Schedule 保存触发意图，不提供外部通知。冷 Session 不运行 Timer；恢复为 Live Session 后处理到期记录。周期任务按锚点计算最新到期项，不补放全部错过的次数。

**坑与对策**

- 把持久计划等同于常驻调度器：执行依赖原 Session 的 Live Owner。
- 到点中断当前 Turn：等待 Agent Idle，再投递普通后续轮次。
- 将派发等同于模型成功或用户已读：Dispatch 只证明 Follow-up 已入队并记录。

**长期演进**

如需离线准时执行或外部送达，引入独立 Scheduler 与 Notification Capability，并定义幂等和回执语义。

### 5.15 Remote API 与 Client Projection

**预期解决**

让浏览器和外部客户端通过稳定协议访问 Host Runtime，同时保持业务身份解析、传输和 UI 投影彼此分离。

**解决方式**

API Remotes 定义面向应用的业务操作和 Agent/Session 查找策略；Typert 提供类型图、运行时 Registry 与 RPC Gateway；Connection 和 WebServer 承载传输；Client Runtime 将远程对象与 Session Events 投影给 UI Plugins。

**底层设计**

```text
Web Client / SDK Client
→ Client Runtime / Remote
→ Connection：RPC 与 Event Transport
→ WebServer / JSON-RPC Server
→ Typert Gateway：Schema 与 Dispatch
→ API Remotes：业务策略与对象解析
→ Agent / Session / Runtime Service
→ Session Events
→ Client Projection / UI Slots / Renderers
```

Typert 将源码类型生成物、运行时 Schema Registry 和 Loader 发现分开。Host 负责业务执行和事件来源；Client 负责连接、对象服务、Slot 组合与呈现，不重新拥有 Agent 或 Session 事实。

**坑与对策**

- 将 BFF 策略写入 Transport：业务路由归 API Remotes，Connection 只承载通信。
- Browser 与 Host 各自定义一套对象语义：使用同一类型图和远程接口。
- UI 直接维护会话事实：UI 从 Session Events 和 Remote Objects 投影。
- 只测试源码内调用：协议和 SDK 还需验证真实进程与构建产物入口。

**相似方案**

BFF、Typed RPC 和前端状态投影采用相同分层；这里还要求远端投影与 Session Log 事实保持一致。

**长期演进**

完成 Remote API 收敛、减少旧 API Proxy 路径，并保持 Host、Web Client、TypeScript SDK 和 Python SDK 的协议同步。

### 5.16 输出、持久化与恢复

**预期解决**

让实时输出和跨进程恢复共享同一事实来源。

**解决方式**

Controller 消费 Session Events 形成场景输出；Persistence Plugin 保存新增 Events；恢复时从日志构造新的 Session 和 Agent。

**底层设计**

```text
Session ID
→ Persistence 加载 Session Log
→ SessionStore 创建 Session
→ Projection 重建 Messages 和领域状态
→ 创建并绑定新的 Agent
→ 继续对话
```

Headless 在 Agent Idle 后读取最终 Assistant Message；Web 持续订阅 `assistant/chunk` 等 Events。恢复不会重新执行历史模型请求或 Tool Call。

**坑与对策**

- 把恢复理解为复活旧对象：恢复会创建新的运行时实例。
- 让 UI 状态成为恢复依据：恢复依据是 Session Log，UI 是投影。
- Persistence 改变事实语义：存储后端只负责保存和加载 Events。

**相似方案**

Event Sourcing 的恢复过程同样是加载事件并重建投影；Snapshot 可以加速恢复，但不能成为不可解释的第二事实源。

**长期演进**

控制日志规模、提升恢复速度，并保持 JSONL、SQLite、SDK 和 UI 对事件语义的一致投影。

#### 6.5.1 Tool 扩展

```text
→ Capability Service
→ Provider
→ External System
```

**坑与对策**

- 为简单 Tool 强行建立 Seam：只有存在复用、替换或独立演进需求时才抽象 Capability。
- Tool 持有连接池、凭证或厂商重试：这些职责归 Provider。

**相似方案**

函数调用、Command Bus 和 RPC Method 都提供结构化执行入口；Tool 额外面向模型描述能力。

**长期演进**

改善工具发现、组合、权限表达和结果呈现。

#### 6.5.2 Skill 扩展

**预期解决**

让 Agent 稳定执行一类复杂任务，而不把完整 SOP 固化进核心 Prompt 或代码。

**解决方式**

Skill 作为面向特定任务的最小可复用执行单元，提供步骤、判断标准、约束、参考资料和可复用脚本。`@deepseek-ai/dsh-skill` 维护独立的 `ctx.skills` Registry；Provider 负责发现与加载；`@deepseek-ai/dsh-tool-skill` 将目录和 `skill` Tool 发布到 `ctx.tools`，供模型按需加载正文。

**底层设计**

```text
Filesystem / Bundled / Runtime Provider
→ ctx.skills：list / snapshot / get
→ dsh-tool-skill
├── Catalog：名称与描述进入模型上下文
└── skill Tool：按名称加载正文与资源基址
→ Instructions / References / Scripts
→ Existing Tools
→ Verified Result
```

**坑与对策**

- 将 Skill 写成知识堆积：保留执行路径和判断标准，细节按需加载。
- 将 Skill 当成 Tool：Skill 规定方法，Tool 提供执行能力。
- 将 Skill Registry 与 Tool Registry 合并：前者管理任务方法及来源，后者只暴露模型可调用入口。
- 只描述步骤而缺少验证：Skill 应定义可观察的完成证据。

**相似方案**

Runbook、SOP 和局部 Harness 都封装任务方法；Skill 还参与 Agent 的动态选择和上下文装载。

**长期演进**

提升触发准确性、渐进披露、组合复用和结果评估。

#### 6.5.3 MCP 接入

**预期解决**

通过标准协议连接外部 MCP Server，并将其工具接入 Harness Tool Runtime。当前实现只桥接 MCP Tools，不提供 MCP Resources 或 Prompts Consumer。

**解决方式**

`@deepseek-ai/dsh-mcp-client` 通过 `stdio` 或 `streamable-http` 连接 MCP Server，发现远端 Tools，并以 `mcp__<serverName>__<rawName>` 注册到 `ctx.tools`。

**底层设计**

```text
External System
→ MCP Server
→ dsh-mcp-client：stdio / streamable-http
→ tools/list + tools/call
→ ctx.tools：mcp__<serverName>__<rawName>
→ Agent
```

**坑与对策**

- 将 MCP 当成 Tool 或 Skill：MCP 解决接入协议，Tool 和 Skill 解决 Agent 消费形式。
- 把协议能力等同于当前实现能力：Server 即使提供 Resources 或 Prompts，当前 Harness 也不会发现或注册它们。
- 信任外部 Server 的全部能力：接入后仍执行 Runtime 的作用域、权限和日志规则。

**相似方案**

OpenAPI、RPC 和 Plugin Protocol 都能连接外部系统；MCP 专门面向模型上下文与工具生态。

**长期演进**

增强 Tool 发现、权限协商、连接生命周期和跨 Server 兼容性；若引入 Resources 或 Prompts，应先定义独立 Consumer、模型可见投影和持久化语义。

#### 6.5.4 领域扩展示例：知识库

**预期解决**

让 Agent 检索外部知识，并保证进入模型的资料可追踪、可引用、可恢复。

**解决方式**

按复用范围选择直接 Tool 实现或完整 Capability Seam，并通过 Tool、Context Plugin、API 或 UI 提供给 Consumers。

**底层设计**

```text
知识库能力
├── Service Definition：查询、检索、读取和引用语义
├── Provider：向量库、文档平台、搜索服务或本地索引
├── Consumer
│   ├── Retrieval Tool：模型主动检索
│   ├── Context Plugin：Runtime 主动注入资料
│   └── API / UI：供程序或用户直接查询
└── Session Events：记录实际进入模型的检索结果和引用
```

**坑与对策**

- 只有一个简单 Tool 仍拆完整 Seam：没有复用或替换需求时直接实现。
- 只记录查询参数，不记录模型实际看到的结果：模型可见结果必须可重建。
- 将索引、连接配置和凭证复制进日志：它们归 Provider、Settings 或 Credentials。

**相似方案**

数据库、企业搜索、工单系统和代码索引都可采用相同的 Definition、Provider、Consumer 和 Session Event 分工。

**长期演进**

关注引用质量、权限继承、增量索引、多 Provider 路由和检索结果评估。

### 6.6 Runtime 自省与自修改

**预期解决**

让 Agent 检查当前 Plugin Tree 和 Service API，并在受控环境中定义、挂载、执行和撤销动态 Plugins。

**解决方式**

模型通过 `tool-cordis` 访问只读运行时信息和动态包操作；Host 与 Browser 各自由受限 Runner 执行对应半边；UI 提供定义状态和运行入口。

**底层设计**

```text
Agent
→ tool-cordis
├── Inspect：Plugin / Service Inventory
└── Dynamic Package
    ├── Definition
    ├── Host Runner：node:vm
    ├── Client Runner：Browser Plugin
    ├── Run Request / Result
    └── Dispose：撤销动态 Fiber 与 Effects
```

动态 Plugin 仍使用 Cordis Context、Service、Event、Fiber 和 Effect，不获得独立于核心生命周期的旁路。Browser 与 Host 分别编译和执行各自代码面，通过显式协议协调。

**坑与对策**

- 把运行时自省变成无限制宿主访问：Runner 限制可见 API 和执行环境。
- 动态代码绕过 Fiber 生命周期：挂载和撤销仍由 Cordis 管理。
- Host 与 Browser 代码面混合：使用双半边定义与显式请求往返。
- 将动态状态默认视为持久事实：只有需要恢复或进入模型上下文的结果写入 Session Log。

**相似方案**

浏览器 DevTools、REPL、插件热加载和 Notebook 都支持运行时检查或动态执行；自修改 Harness 还要求能力作用域、资源清理和模型可见记录可控。

**长期演进**

增强动态包验证、权限隔离、资源配额、可审计性和安全的持久化策略。

## 七、验证与交付保障

**预期解决**

证明单个 Package、完整 Plugin 组合、协议投影和发布产物在真实使用路径上保持一致，并判断 Agent 在开放任务中的结果质量与执行代价。

**解决方式**

软件验证按风险选择 Unit、Coverage、Snapshot、Browser、Real-API E2E、Built Smoke 和静态 Gates，并以 Runtime Invariant 和可观测数据验证跨模块关系。Agent Evaluation 使用版本化任务集、运行证据、外部结果和人工反馈评价开放任务。

**底层设计**

```text
工程保障
├── 行为验证：Unit / Contract Regression
├── 组合验证：Loader Smoke / Snapshot / Browser
├── 外部验证：Real-API E2E
├── 产物验证：Build / Built Smoke / Publint
├── 静态验证：Typecheck / Lint / Hygiene / Doc Sync
├── 运行验证：Runtime Invariant / Telemetry / Diagnostics
├── Agent Evaluation：任务结果 / 执行轨迹 / 安全 / 成本 / 时延
└── 治理：Agent Note / Compatibility / Release
```

**坑与对策**

- 用覆盖率代替行为证据：Coverage 证明代码被执行，不证明产品按预期工作。
- 只测试手工组装：产品可见 Plugin 需要通过 Loader 和真实 Composition 验证。
- 断言 Agent 自述成功：重新读取文件、运行命令或检查外部状态。
- 混用源码与构建产物：测试默认走 Source Plane，发布入口显式走 Artifact Plane。
- 全量测试成为默认动作：按改动面选择最小充分证据，CI 负责完整矩阵。

**长期演进**

让每类新能力在设计阶段声明验证层级，并使本地、CI、SDK、浏览器和发布流程共享一致的证据标准。

### 7.1 测试分层与真实入口

**预期解决**

用成本与真实性不同的测试层覆盖局部逻辑、组合行为、用户输出和真实 Provider。

**解决方式**

Unit 覆盖局部行为与错误路径；Coverage 执行逐文件门禁；Snapshot 固定协议和用户输出；Browser 验证 Web 投影；Real-API E2E 验证真实模型；Built Smoke 验证发布产物。

**底层设计**

```text
Unit
→ Package 行为、边界条件、事件顺序、生命周期清理
Coverage
→ packages/*/*/src 逐文件覆盖门禁
Snapshot
→ Headless / ACP / SDK 的关键输出与持久日志

Real-API E2E
→ 真实模型与 Provider 行为

→ plain Node 执行发布后的 lib 入口
```

- 改变模型、协议或用户输出却不更新 Snapshot：同一改动同步更新对应场景。

**相似方案**

测试金字塔按成本分层；DeepSeek Harness 额外强调真实 Composition、Session Transcript 和发布产物。

**长期演进**

增加能力 Seam、生命周期和协议场景的可表达性，缩短高价值真实入口测试的反馈时间。

### 7.2 Runtime Invariant、可观测性与诊断

**预期解决**

发现类型系统和单元测试无法覆盖的运行时关系错误，并定位失败发生在哪个 Plugin、Session、Agent 或外部能力。

**解决方式**

Invariant 检查权威事件流或可变关系；Telemetry 记录运行指标与用量；Diagnostics 暴露具体失败对象、路径和违反的规则。

**底层设计**

```text
Runtime Evidence
├── Session Events：持久执行事实
├── Agent / Capability Events：实时生命周期
├── Invariants：跨对象关系检查
├── Telemetry：Usage、Timing、Outcome
└── Diagnostics：Subject、Path、Violation、Correction
```

Harness 的证据链连接输入来源、执行过程、结果主张与外部结果：

```text
Input Provenance
→ Decision / Action
→ Observation
→ Claim
→ Verification
→ External Outcome
```

执行路径可以随场景和模型调整，但每个结果主张必须持续满足同一证据标准。Session 事实证明 Harness 内发生了什么，外部状态验证证明目标系统实际发生了什么，二者不能相互替代。

Invariant 检查拥有关系的权威数据，不检查方法是否存在、Plugin metadata 或固定示例。没有可观察关系时，应明确该能力没有对应 Invariant。

**坑与对策**

- 检查 Service 是否存在就宣称行为正确：从真实 Consumer 观察结果。
- 将相关结果压成一个状态：超时、Signal 和 Exit Code 等正交结果分别报告。
- 回调异常破坏 Dispatcher：隔离单个 Listener 异常，继续服务其他订阅者。
- Diagnostic 只写“失败”：指出对象、路径、违反的规则和修正方式。

**相似方案**

数据库约束、Design by Contract 和生产监控都验证运行关系；Harness Invariant 直接连接 Plugin、Event 和 Session 的权威状态。

**长期演进**

将更多跨 Package 关系转为低噪声 Invariants，并统一日志、Trace、Metrics 与 Session 诊断视图。

### 7.3 Source Plane 与 Artifact Plane

**预期解决**

防止源码测试因路径映射通过，但发布后的 `lib/`、Worker、CLI 或协议入口实际不可用。

**解决方式**

静态 Gates 和普通测试通过 TypeScript paths 解析 `src`；只有明确验证发布行为的 Built Smoke 和配置子进程消费 `lib/`。

**底层设计**

```text
Source Plane
├── Typecheck
├── Lint
├── Unit Tests
└── Static Generators

Artifact Plane
├── Package Exports
├── CLI bin
├── Worker Entry
├── Config Subprocess
└── SDK / Protocol Distribution
```

**坑与对策**

- 测试意外加载旧 `lib/`：普通测试统一使用 Source Plane。
- 只在 `tsx` 下运行 CLI：发布入口用 plain Node 执行构建产物。
- Worker 或非 index 入口未验证：为每个独立产物入口增加 Built Smoke。
- 同一模块从 `src` 与 `lib` 各加载一次：保持 Compiler Face 和解析路径明确。

**相似方案**

源码测试与安装包测试、开发服务器与生产 Bundle 验证解决同类问题；这里还需覆盖 Worker、配置 Loader 和多 SDK。

**长期演进**

减少源码与产物之间的隐式差异，并让发布前检查自动识别需要验证的 Artifact 入口。

### 7.5 文档、决策与兼容性验证

**预期解决**

让公开行为、设计理由、代码实现和发布兼容性长期保持一致。

**解决方式**

README 与 JSDoc 记录当前接口和行为；Subsystem 文档记录领域语义；Agent Note 记录非平凡决策与取舍；生成目录和文档 Gates 防止结构漂移。

**底层设计**

```text
Current Contract
├── Source Types / JSDoc

Decision Rationale
└── Agent Note

Derived Evidence
├── Generated Catalogs
├── Snapshot Fixtures
```

### 7.6 Agent Evaluation：质量度量与回归决策

**预期解决**

判断 Agent 是否完成任务、是否安全高效，以及 Prompt、Model、Tool、Skill 或策略变更是否产生真实改进。

**解决方式**

以版本化任务集驱动离线评估，以生产结果和人工反馈驱动在线评估；将结果质量、轨迹质量、安全、成本和时延组合为发布依据。

**底层设计**

```text
Versioned Task Set + Runtime Variant
→ Isolated Execution
→ Transcript + Artifacts + External State
→ Evaluators
   ├── Deterministic Checks：状态、文件、协议与业务规则
   ├── Rule-based Scores：成本、时延、步骤与违规
   ├── Model Judge：开放式语义质量
   └── Human Review：高风险与争议样本
→ Comparable Metrics
→ Regression Gate / Experiment Decision
```

评估对象必须绑定任务集版本、Harness 版本、模型版本、Prompt、工具集合、配置和随机参数。成功证据优先取自外部结果与可重放事实，而不是 Agent 自述。

**坑与对策**

- 将软件测试等同于 Agent Evaluation：测试验证确定性契约，评估衡量开放任务的效果与代价。
- 只比较最终答案：同时检查执行轨迹、副作用、引用、权限、成本和时延。
- 用 Model Judge 作为唯一裁判：确定性结果优先使用规则验证，并以人工样本校准 Judge。
- 在固定题集上持续调参：隔离开发集、回归集和保留集，监测数据污染与评测过拟合。
- 只优化单一成功率：设置安全、成本和时延硬约束，防止 Reward Hacking。

**相似方案**

软件回归测试、机器学习 Benchmark、在线实验和质量抽检共同构成 Agent 评估体系。

**长期演进**

建立按场景分层的 Golden Set、失败分类、轨迹评分、Judge 校准、线上采样和自动回归门禁。

## 八、生产运行与治理

**预期解决**

让 Harness 在多模型、多用户、持续变更和生产流量下保持推理供给可治理、信任关系可审计、服务运行可恢复。

**解决方式**

在运行时机制之外建立三个平台级闭环：模型治理管理推理供给，安全与合规控制跨主体信任，生产运营保障持续交付。Evaluation 为策略和发布提供质量证据，Memory 作为数据领域向运行时提供经过授权的跨会话信息。

**底层设计**

```text
Runtime Facts + Product Outcomes
├── Model Governance：模型选择、容错与版本控制
├── Trust Governance：身份、数据、扩展与审计
└── Production Operations：发布、容量、韧性与灾备

Observed Results → Evidence → Policy Change → Controlled Release → New Results
```

三个治理领域使用 Runtime 事实与 Evaluation 结果，但不反向侵占 Agent、Session、Tool 和 Capability 的运行时所有权。

**坑与对策**

- 将功能齐全等同于可规模化：必须补齐质量决策、风险控制和运营反馈。
- 将平台策略散落在业务 Plugin：跨场景规则由独立治理服务拥有。
- 用单一指标驱动所有优化：同时约束质量、安全、成本、时延和稳定性。

**长期演进**

形成从离线验证、在线观测、策略调整到受控发布的持续改进系统。

### 8.1 模型治理：路由、容错与版本控制

**预期解决**

在多个模型、Provider 和能力版本之间稳定选择推理资源，并控制可用性、成本、时延和行为漂移。

**解决方式**

为模型声明上下文、Tool Calling、Structured Output、多模态和流式能力；Router 根据任务与策略选择候选；执行层实施限流、重试、Fallback 和熔断；版本系统记录完整请求配置。

**底层设计**

```text
Task Requirements + Policy + Budget
→ Capability Matching
→ Model Router
→ Provider Adapter
→ Rate Limit / Retry / Circuit Breaker / Fallback
→ Normalized Stream and Usage
→ Versioned Evidence + Evaluation
```

模型名称不足以定义行为版本；可复现实验还需绑定 Provider、模型修订、System Prompt、采样参数、Tool Schema 和路由策略。Fallback 必须满足调用所需能力，不得只按可用性盲切。

**坑与对策**

- 将不同模型视为完全可互换：路由前验证上下文、协议和输出能力。
- 对所有错误统一重试：只重试暂态且可安全重放的请求，并限制退避与总预算。
- Fallback 改变安全或数据策略：候选模型必须满足相同的数据、地域和权限约束。
- 只记录最终模型名：同时记录路由理由、尝试链、配置版本和用量。
- 直接全量切换新版本：通过离线评估、Canary、A/B Test 和可回滚发布逐步放量。

**相似方案**

API Gateway、服务发现、负载均衡和 Feature Flag 提供相似控制机制；模型治理还需处理能力差异与非确定性输出。

**长期演进**

实现质量—成本—时延联合路由、动态容量感知、Provider 健康评分和自动回退，并以评估结果约束策略更新。

### 8.2 安全与合规：端到端信任治理

**预期解决**

控制不可信输入、模型输出、扩展代码和外部服务带来的越权、数据泄露、供应链与合规风险。

**解决方式**

建立主体、数据、能力和执行环境四类信任关系；在输入、上下文装配、Tool 调用、外部传输和持久化各阶段执行分层策略，并生成可查询审计记录。

**底层设计**

```text
Identity + Workspace + Data Classification
→ Authorization Policy
→ Context and Capability Filtering
→ Approval for High-risk Effects
→ Sandbox / Egress / Secret Enforcement
→ Audit + Retention + Deletion

Extension Trust
├── Tool / Skill / MCP / Plugin Provenance
├── Version Lock + Integrity Verification
└── Allow / Revoke / Quarantine
```

Prompt Injection 被视为不可信数据影响决策的问题；防护同时依赖来源标注、指令优先级、最小权限、参数策略、批准和执行隔离。批准只授予一次明确操作，不替代 Sandbox、数据策略或审计。

**坑与对策**

- 只在 Prompt 中要求模型安全：关键约束必须由确定性执行点强制。
- 将 Sandbox 当成完整安全系统：还需身份、授权、网络出口、秘密和数据治理。
- 默认信任安装的 Skill、MCP 或 Plugin：记录来源与版本，限制能力，并支持撤销和隔离。
- 先检索或发送数据再鉴权：权限过滤必须发生在数据暴露与外部传输之前。
- 审计日志无限保存敏感内容：按数据类别执行最小记录、脱敏、保留和删除策略。

**相似方案**

Zero Trust、Policy Enforcement Point、软件供应链安全和数据治理提供相同的职责分离。

**长期演进**

完善多租户隔离、策略即代码、内容来源追踪、扩展签名、数据驻留、合规导出和自动风险响应。

### 8.3 生产运营：部署、发布、韧性与灾备

**预期解决**

让 Harness 在持续变更、流量波动和局部故障下维持明确的服务目标，并能够降级、恢复和回滚。

**解决方式**

以 SLI/SLO 定义用户可感知目标；按资源瓶颈规划容量和背压；通过分阶段发布、健康检查、故障隔离、幂等执行、备份与恢复演练控制变更和事故。

**底层设计**

```text
Build + Evaluation + Security Gates
→ Versioned Artifact
→ Canary / Staged Rollout
→ SLI / SLO Observation
├── Healthy → Continue Rollout
└── Regression → Degrade / Roll Back

Runtime Resilience
├── Admission Control + Queue + Backpressure
├── Timeout + Retry Budget + Circuit Breaker
├── Lease + Heartbeat + Idempotency + Deduplication
└── Backup + Restore + Disaster-recovery Drill
```

服务目标覆盖成功率、端到端时延、首 Token 时延、取消收口、成本和数据持久性。降级策略可减少并发、切换合格模型、关闭非关键能力或转入确定性流程，但不得降低安全和证据标准。

**坑与对策**

- 只监控进程存活：同时观测任务成功、模型质量、队列、依赖和用户结果。
- 无限重试放大故障：使用总重试预算、退避、熔断和幂等键。
- 将进程内 Job 当成分布式任务：跨进程执行需要持久队列、租约、心跳和重复投递处理。
- 发布只验证服务启动：Canary 比较质量、安全、成本和时延，并预先定义回滚条件。
- 有备份但不演练恢复：定期验证恢复点、恢复时间和事件、索引、资源之间的一致性。

**相似方案**

SRE、分布式任务系统和渐进式交付提供通用机制；Agent 服务额外需要把非确定性质量纳入 SLO 与发布决策。

**长期演进**

建立多区域容灾、自动扩缩、故障注入、容量预测、按租户成本归因和质量感知的自动发布控制。

#### 8.3.4 容量、配额与资源治理

**预期解决**

控制模型、工具、进程、存储和后台任务的资源消耗，使吞吐、时延、成本和可靠性可预测。

**解决方式**

各资源所有者执行局部限制，Settings 和 Plugin Config 提供可调参数，Telemetry 与 Diagnostics 汇总 Usage、Timing、Outcome 和容量信号。

**底层设计**

```text
Resource Governance
├── Model：Context Window / Output Tokens / Retry
├── Agent：Turn / Step / Cancellation
├── Tool：Parallelism / Exclusivity / Timeout
├── Process：CPU / Memory / Sandbox Limits
├── Data：Spill Threshold / Retention / Storage Quota
└── Orchestration：Agent Count / Job Count / Schedule / Workflow Limits

Config / Settings → Local Enforcement → Telemetry → Capacity Decision
```

限制在拥有资源的模块执行：Agent Loop 控制 Tool 并发，Capability Provider 控制外部资源，Compaction 控制上下文压力，Storage Policy 控制持久数据。

**坑与对策**

- 在 Plugin 内硬编码部署参数：变化的上限进入经校验的 Config 或 Settings。
- 只设置全局超时：模型、Tool、子进程和 Workflow 分别在真实异步边界处理取消与收口。
- 用截断掩盖容量问题：超大 Tool 输出使用 Spill，历史压力使用 Compaction。
- 只统计平均时延：同时观察分位数、取消、重试、失败、Token 和资源峰值。
- 限制已触发但执行仍继续：限制必须连接 AbortSignal、Provider 终止能力和最终 drain。

**相似方案**

操作系统配额、服务端 Rate Limit、数据库 Retention 和分布式系统 Backpressure 都在资源所有点执行限制。

**长期演进**

建立跨 Agent 的统一预算分配、Backpressure、成本归因、容量预测和自适应并发。
