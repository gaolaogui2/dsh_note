# Harness Engineering：以 DeepSeek Harness 为解剖标本

## 1、总览

Agent 由 Model 和 Harness 共同构成。

- Model 提供推理、生成和决策能力。
- Harness 为 Model 准备输入、提供行动能力，管理执行过程、状态和风险，压制 Model 产出质量波动。

Harness 需要回答 4 类问题。

- 系统由哪些职责组成，各部分如何连接。
- 程序和模型分别控制哪些执行步骤。
- 权限、取消、失败和资源释放由谁处理。
- 执行事实如何记录，进程退出后能够恢复什么。

这些问题不会有「脱离现实业务场景」限定的唯 1 最优解。

- 直接组装强调简单和低开销，
- 插件化强调替换和组合，
- Workflow 可以增强可预期，
- Agent Loop 强调动态决策。
- 持久化增强连续性和恢复能力，
- 「隔离与审批」可以降级错误操作的影响。

每项收益都会增加对应的实现、运行或维护成本。

具体系统设计实现通常组合多种上述方案。

评价 harness 架构时，需要先圈定现实业务场景：任务类型、变化频率、性能预算、安全要求、恢复范围和团队成本。

Harness 的许多架构思想并非为 Agent 专门创造，而是既有软件架构经验在新场景中的应用与调整。
相比快速变化的业务需求，这些思想相对稳定，可以为不同实现提供共同基础。
社区因此不必从零建立全部设计原则，有条件更快形成共识与规范。
模型决策的不确定性和外部行动的风险，仍需要在 Agent 场景中重新验证和补充。

举例：DSH 是当前社区中少有的「完全开源&高度插件化」且正在高速迭代的 Harness ，
「完全开源」可以提高社区信任程度与参与热情，
「插件化」架构提供的可替代性可以在最大程度扩展针对真实业务场景的兼容范围，
「运行时生命周期」进 1 步提高了插拔性，实现了插件的运行时替换。

DSH 尚在早期内测阶段，若可以保持接口的稳定性，有概率成为社区认可的通用 Harness Base 基建。
即使最终社区没有选择 DSH ，也会是与其相似的「开源&高度插件化&接口稳定&基础能力完整&开箱即用」的 Harness 。

## 2、宏观架构

不同取舍的 Harness 在实现上差异很大，
这里忽略细节，从更宏观的角度来划分稳定职责：「宿主与入口、场景协调、Agent 执行、上下文与模型、能力执行、数据管理、运行控制和运行保障」。

这些职责是逻辑分工，不等同于固定的目录结构、进程或服务：

- 这些职责可以在 1 个进程中直接组装，也可以按资源、风险或团队边界拆成多个服务。

宏观划分的收益是识别稳定关系和真实变化点：

- 模型供应商、工具集合、执行环境、存储方式、交互入口和 Agent 策略都是常见变化点。

只有变化足够频繁，或者存在独立责任主体时，抽象接口和独立生命周期才会产生足够收益。

组件可以直接组装，也可以通过依赖注入或插件 Runtime 管理。
直接组装简单，依赖注入集中管理实例和依赖，插件 Runtime 进 1 步支持动态组合与生命周期管理。
动态程度越高，依赖、作用域、生命周期、诊断和兼容成本通常也越高。

语义稳定但实现需要替换的能力，可以用稳定接口分开调用方和实现方，例如 DSH 的 Capability Seam 隔离。

1 个完整的 Capability Seam 包含 Definition、Provider 和 Consumer。

- Definition 定义调用约定，Provider 实现能力，Consumer 使用结果并决定后续行为。

接口应由 Consumer 的真实需要驱动，而不是复制某个 Provider 的完整 API。

还需要明确运行资源和可变状态的所有者。

- 由其管理生命周期、维护有效状态，并处理失败后的清理或恢复

## 3、链路

一次工作会跨多个职责推进，状态、控制和所有权也会随阶段交接。

Harness 的运行过程通常包含启动、请求、控制与恢复，具体系统可以合并、拆分或省略部分阶段。

每个阶段都需要明确输入、产出、完成条件、失败责任和外部副作用。

### 3.1 启动主链

启动主链把代码、配置和运行环境中的选择转换为可接收工作的 Runtime。

它通常经过输入解析、运行基础创建、组件装配、依赖解析、就绪检查和结果交接。

静态组装适合组成稳定的系统，依赖注入适合集中管理模块，声明式或插件装配适合按场景替换组件。

配置来源需要明确优先级、合并顺序和最终有效值。

配置顺序决定覆盖结果，显式依赖决定组件何时可以提供能力。

启动函数返回或模块导入成功都不等于 Runtime 已经就绪。

启动成功表示必需能力可用，启动失败需要报告失败阶段和清理结果，受控退出则不再执行就绪交接。

生命周期只能释放已经登记的资源，已经提交的外部副作用仍由所属能力核查或补偿。

DSH 用 Profile、Bundle 和 Patch 形成配置输入，再由 Loader、Entry、Cordis 和 Fiber 完成插件装配与生命周期管理。

### 3.2 请求主链

请求主链把外部输入转换为 Agent 工作，并把执行事实和结果交回调用方。

入口先关联身份、会话和执行主体，再决定直接执行还是排队等待。

直接执行路径短，适合独立请求；Inbox 将输入到达与处理时机解耦，适合持续交互和运行中干预。

并发投递不等于并发执行，新输入也不能改写已经发出的模型请求。

Workflow 由程序决定阶段和分支，Agent Loop 由模型根据中间结果选择下一步，混合架构在程序控制的阶段内开放局部决策。

模型发起能力调用时，执行器需要校验请求、调用能力、记录结果，再决定继续或结束。

程序也可以直接调用能力，不需要把所有操作都转换为 Tool Call。

影响后续执行、恢复或审计的输入和结果需要形成持久事实。

实时生成的临时片段可以用于展示，只有正式提交的结果才应成为恢复依据。

输入已接收、执行已结束、Agent 已空闲、任务已成功和用户已验收是不同状态。

多条输入共同影响执行时，逐条返回准确结果还需要记录输入与输出之间的因果关系。

DSH Controller 将外部意图映射为稳定的 Agent 操作，默认 ReactLoopAgent 通过 Inbox、Driver、Turn 和 Step 推进模型与 Tool 循环。

这些对象属于 DSH 默认执行实现，不是所有 Agent Provider 的必需结构。

### 3.3 控制与恢复主链

控制与恢复主链处理运行中的失败和停止，并在释放或重启后重新建立可信状态。

取消是协作式停止请求，发送信号不表示工作已经停止。

停止完成要求受影响工作已经退出、资源已经清理，并且迟到回调不会再修改释放后的状态。

局部超时限制单项操作的等待时间，多个局部超时不会自动形成覆盖整个任务的 Deadline。

错误应由能够解释其语义的执行方处理，无法继续的工作才结束更大范围的活动。

恢复通常包括加载事实、校验或修复记录、重建状态和创建新的运行对象。

恢复保留身份和已记录事实，不会复活旧连接、句柄、计时器或进程。

历史模型请求和能力调用用于重建上下文时，不应自动再次执行。

缺少结果记录只能证明 Harness 没有记录确认，不能证明外部操作没有发生。

外部副作用需要具体能力提供幂等、去重、状态复查、补偿或人工确认。

会话恢复与任务恢复是不同能力，后台任务跨进程续行还需要持久任务状态和重新接管规则。

DSH 使用 AbortSignal 协作取消，通过 Fiber 释放登记资源，并通过 Session Persistence 加载、校验和修复 Session Log。

DSH 可以恢复会话事实，但进程内 Job 和 Goal continuation 不会因此自动续行。

## 4、领域

### 4.1 运行时组成：依赖与生命周期

运行时组成决定组件如何取得依赖，以及资源由谁创建和释放。

直接组装最简单，依赖注入集中管理实例，插件 Runtime 还能响应组件出现、消失和替换。

动态性越强，越需要明确作用域、级联失效和重新激活后的状态恢复。

### 4.2 能力：语义与实现解耦

能力领域把稳定调用语义与具体实现分开。

拆分可以复用 Consumer 并替换 Provider，但需要维护公共接口和实现差异。

只有存在复用、替换或独立演进需求时，Capability Seam 才比直接调用更有价值。

### 4.3 组合：进程级与 Agent 级组装

进程级组合决定一个产品启动哪些系统能力，Agent 级组合决定单个执行实例取得哪些模型、工具和策略。

静态组合便于理解，声明式组合便于换装，动态组合需要处理运行实例与新配置之间的关系。

恢复旧会话时，还需要明确沿用历史选择还是采用当前配置。

### 4.4 配置与设置：系统结构与运行参数

配置描述系统组成和启动选择，设置维护用户或运行时可以修改的参数。

动态修改只有在拥有参数的组件能够安全应用时才成立。

更新过程需要先校验候选值，持久化成功后再替换内存有效值，并通知使用方。

模型请求还需要记录实际采用的配置，不能用当前设置推断过去的请求。

### 4.5 Agent：执行主体与生命周期

Agent 是接收输入并推进任务的执行主体。

实例、持久事实、创建工厂和控制句柄承担不同职责，不应由一个对象隐式包办。

创建完成后才能发布实例，取消、释放和恢复也需要分别定义。

Agent 空闲只表示当前没有活动，不代表业务目标已经达成。

### 4.6 数据管理：记录、保存与复用

追加日志适合保存执行过程，可编辑领域存储适合维护当前值，大内容适合通过稳定引用关联。

查询、索引和记忆是根据用途从原始事实派生的能力。

同一份内容可以被日志引用、被索引检索，再被选入记忆，但每份权威数据仍需要唯一所有者。

### 4.7 模型上下文：组装与压缩

模型上下文由提示词、工具描述、历史消息、当前输入和输出预留共同占用容量。

组装过程需要选择模型真正需要的信息，并保证模型可见内容可以重建。

压缩、裁剪和外置引用分别牺牲精度、即时可用性或读取成本。

准确摘要加外置原文可以显著扩大有效会话范围，但不能把有限上下文变成无限容量。

### 4.8 执行控制：自治度与确定性

ReAct 让模型选择执行路径，Workflow 让程序控制路径，混合架构在两者之间分配决定权。

ReAct 适合开放问题，Workflow 适合步骤稳定和高风险流程，混合架构适合程序控制阶段而模型处理局部判断。

无论采用哪种方式，都需要管理预算、取消、进展和完成条件。

### 4.9 用户交互：命令、询问、批准与反馈

命令由用户主动控制系统，询问由执行过程请求信息，批准授予有限操作许可，反馈记录用户评价。

这些交互的发起方、返回语义、权限作用和记录方式不同，不应合并成一种通用消息。

批准服务可以被不同 Runtime 接入，反馈则需要独立消费链路才能帮助研发发现问题。

### 4.10 执行安全：策略与隔离

安全领域决定谁可以执行什么操作，以及操作实际被限制到什么程度。

身份、授权、凭证、审批、执行策略和隔离机制承担不同职责。

策略需要在真实能力调用点执行，沙箱强度则取决于文件、网络、进程和凭证的具体隔离机制。

### 4.11 编排：任务与多 Agent 协作

编排负责把一个目标拆成阶段、后台工作、定时续行或多个执行主体。

Workflow 强调显式流程，Job 强调异步工作，Schedule 强调时间触发，子 Agent 强调执行主体委派。

并行和后台执行最终由 Harness 调度机制落实，模型只能提出或触发相应请求。

### 4.12 Controller：场景协调与入口适配

Controller 将 CLI、GUI、API 或自动化协议转换为稳定的 Agent 操作。

它负责关联外部身份、会话和入口 Agent，并决定回执、流式输出、最终结果和断连清理方式。

Controller 管理入口场景，不负责替代下游 Workflow 或多 Agent 编排。

### 4.13 运行可靠性：故障、取消与恢复

可靠性领域要求系统明确成功、失败、取消和未知结果，并停止依赖不可信状态的后续工作。

恢复、重试、幂等和补偿解决不同问题，不能相互替代。

捕获异常和记录日志都不表示系统已经恢复，状态所有者仍需重新建立约束。

### 4.14 运行观测与诊断

Session 事实、运行事件、日志、指标和 Trace 服务于不同观察目的。

关联标识需要把请求、模型调用、能力执行和后台工作连接起来。

观测数据帮助定位问题，Invariant 则定义哪些状态必须成立，并为诊断提供判断标准。

## 7、验证与交付保障

验证需要证明架构承诺在真实入口和失败条件下成立，而不只是单个函数返回预期值。

### 7.1 测试分层与真实入口

单元测试验证局部语义，集成测试验证组件协作，端到端测试验证真实入口和外部行为。

模型可见内容、用户输出和持久格式还需要稳定快照或重放用例。

测试范围应与改动风险匹配，完整平台矩阵通常由 CI 承担。

### 7.2 Runtime Invariant、可观测性与诊断

Invariant 定义运行期间必须成立的状态关系，例如资源释放后不能继续接收回调。

事件、日志、指标和 Trace 提供观察证据，诊断过程再用这些证据定位违反约束的位置。

可观测不等于正确，缺少可观测信息也不等于行为没有发生。

### 7.3 Source Plane 与 Artifact Plane

源码检查和构建产物检查验证不同对象，不能混用隐式路径掩盖问题。

源码层测试应在干净工作树上解析源码，发布路径和运行冒烟则应验证真实构建产物。

### 7.4 性能与资源限制验证

性能结论需要明确负载、数据规模、机器环境、指标和对照基准。

长会话、并发任务、流式输出和进程清理都需要观察时间与资源增长。

预算、超时和输出上限还需要验证超限后的结果与清理行为。

### 7.5 文档、决策与兼容性验证

文档需要与当前行为、公开接口和配置保持一致。

架构决策保留稳定理由和放弃的方案，升级说明负责外部可感知变化。

持久数据、协议和 SDK 变化需要验证旧记录或旧调用方会得到什么结果。

### 7.6 Agent Evaluation：质量度量与回归决策

Agent Evaluation 衡量任务结果、过程成本和失败类型，而不只比较最终文本。

评估集需要覆盖代表任务、风险场景和历史回归，并固定评分规则与运行条件。

模型存在随机性时，应报告分布、重复次数和置信范围，避免把单次结果当作稳定结论。

## 8、生产运行与治理

生产治理处理单次执行之外的长期运行问题，包括模型变化、安全合规、发布、容量和灾备。

### 8.1 模型治理：路由、容错与版本控制

模型路由需要根据任务、能力、成本、延迟和可用性选择 Provider。

降级与重试不能假设不同模型行为完全等价，实际请求需要记录采用的模型和配置。

模型升级需要通过固定评估集和生产指标观察效果与回归。

### 8.2 安全与合规：端到端信任治理

安全治理覆盖身份、授权、凭证、数据访问、执行隔离和审计。

多租户系统还需要隔离会话、存储、进程、缓存和观测数据。

数据需要明确收集、保留、删除、脱敏和导出规则，扩展还需要供应链和版本信任。

### 8.3 生产运营：部署、发布、韧性与灾备

部署拓扑需要匹配执行资源、隔离强度、延迟和扩缩需求。

发布与升级需要处理配置、协议、持久数据和运行任务的兼容关系。

在线运行需要 SLO、容量与配额、故障响应、备份恢复和灾难演练。

生产系统最终关注的是可持续交付和可恢复运行，而不是单次演示成功。
