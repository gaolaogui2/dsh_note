## 表述标准

以下标准用于本文各章节的整理与审阅。

**1. 固定内容边界**

以指定目录及其层级为范围，先明确本节的主题、要解决的问题，以及与相邻章节的分工。正文围绕本节主题展开，细节深度与所在层级匹配。其他章节负责的内容，只保留理解当前主题所需的衔接，并引用其已有说明。

**2. 精炼**

在保留关键信息、表达精度和可读性的前提下，减少表述体积。优先删除重复、赘述和无助于理解的铺垫；保留必要的定义、关系、条件、限制和例子。精炼以读者更容易准确理解为标准，字数只是辅助指标。

**3. SSOT**

同一项内容保留一处完整说明，其他位置按需引用。去重同时覆盖指定目录内部的重复，以及当前目录与前面已经整理并固定内容之间的重复。沿用已有定义、机制和结论，当前章节只补充自身主题所需的新信息。

引用处保留必要的定位或衔接，让当前段落独立可读；完整定义、机制和论证由原位置维护。发现前文需要修正时，修改其所属位置，再同步引用。

**4. 可读性**

按读者理解所需的顺序引入概念：先交代具体对象及其用途，再解释关系和机制。术语首次出现时给出必要定义；句子明确主体、动作和对象，指代能直接找到对应内容。抽象关系难以理解时，用一个最小例子说明。可读性是独立的验收要求，文字准确、简短，也需要让读者容易理解。

**5. 事实与判断**

明确区分通用概念、具体实现、分析判断和演进建议。描述实现时给出依据；评价优劣时说明适用条件与比较标准；尚未验证的内容标明不确定性。前文已固定的结论，沿用相同术语和成立范围。

**执行顺序**：明确主题与分工 → 确认已有内容及其所属位置 → 补齐本节必要信息 → 去重与精炼 → 检查可读性、精度和完整性。

**冲突处理原则**：精炼以信息完整、表达准确和阅读顺畅为前提；SSOT 通过集中维护完整说明、保留必要衔接来实现。

## 一、总览

Agent = **Model + Harness**：

- Model 提供推理、生成与决策能力。
- Harness 为模型准备输入、提供行动能力，并管理执行过程、状态和风险。

Model 决定系统能否理解和推理，Harness 决定这些能力如何进入可运行、可控制、可恢复的工程系统。

### 1.1 研究对象

Harness 架构需要回答 4 类问题：

1. **系统如何组成**：入口、Agent Runtime、模型、能力、数据与外部资源如何分工和连接。
2. **任务如何执行**：程序与模型分别控制哪些步骤，输入如何进入，结果如何返回。
3. **运行如何受控**：权限、隔离、取消、超时、失败和资源释放由谁负责。
4. **状态如何延续**：执行事实如何记录，上下文如何生成，进程退出后能够恢复什么。

这些问题相互关联，但不要求使用相同的实现方式。
一个 Harness 可以直接组装固定模块，也可以使用依赖注入、插件或独立服务；任务执行可以由 Workflow、Agent Loop 或两者共同控制。

### 1.2 方案选择

Harness 没有脱离场景的最优架构。
每种方案都在确定性、自治度、扩展性、隔离性、性能和维护成本之间作出选择。

| 设计侧重点 | 常见选择 | 主要收益 | 主要代价 |
| ---------- | -------- | -------- | -------- |
| 简单与低开销 | 直接调用和静态组装 | 路径短，行为容易追踪 | 替换、复用和独立演进成本较高 |
| 可替换与可组合 | 接口分离、依赖注入或插件化 | 局部实现可替换，能力可跨场景复用 | 需要管理依赖、作用域和生命周期 |
| 确定性与可审计 | Workflow 主导执行 | 步骤和分支明确，容易限制行为 | 难以覆盖开放任务中的未知路径 |
| 自治与适应性 | Agent Loop 主导执行 | 模型可根据中间结果动态选择路径 | 成本、时延和结果波动更难控制 |
| 连续性与恢复 | 持久事实与检查点 | 支持长会话、审计和中断恢复 | 增加存储、一致性和数据治理成本 |
| 安全与故障隔离 | 权限策略、审批和执行隔离 | 限制错误或不可信操作的影响 | 增加交互、资源消耗和平台复杂度 |

具体系统通常组合这些方案，而不是只选择其中一种。
例如，应用可以使用静态模块组成稳定外壳，在局部能力上使用可替换 Provider，并在确定性 Workflow 中嵌入需要模型判断的 Agent Step。

### 1.3 评价方法

架构评价从目标场景和约束开始，而不是从技术名称开始。
同一方案在高频交互、批处理、开发工具和高风险自动化中的价值可能完全不同。

比较候选方案时，需要明确：

- 需要支持哪些任务、入口和外部能力；
- 哪些组成会变化，变化频率和责任主体是什么；
- 延迟、吞吐、费用和上下文容量限制是什么；
- 哪些操作需要授权、隔离、审计或人工确认；
- 哪些状态必须持久化，故障后需要恢复到什么程度；
- 团队愿意承担多少实现、运维和兼容成本。

方案只有在这些条件下才有可比较的收益与代价。
实现完整不代表适合所有场景，机制更多也不代表架构更成熟。

### 1.4 DeepSeek Mapping

DSH 面向能力、入口和执行方式持续变化的场景，选择 Cordis 插件 Runtime、Capability Seam、声明式组合和持久 Session Log。
这套选择强调局部替换、跨场景复用和生命周期管理，代价是需要理解插件依赖、作用域、配置覆盖和事实记录。

DSH 还允许 Agent、Workflow、Controller 和能力 Provider 分别替换，因此适合观察同一组通用问题如何由多个可组合实现共同解决。
后续章节先分析通用架构，再用 DSH 检查这些分析能否映射到真实代码和运行行为。

## 二、宏观架构

宏观架构从静态视角说明 Harness 由哪些职责组成，以及这些职责如何依赖、替换和共同演进。
这里描述的是分析框架，不要求每个 Harness 都采用相同模块、进程或部署边界。
具体运行顺序见[链路](#三链路)，各领域的设计选择见[领域](#四领域)，DSH 组件和接口见[实现](#五实现)。

### 2.1 通用组成

一个完整 Harness 通常包含以下职责：

```text
使用方或外部系统
        ↓
入口与场景协调
        ↓
Agent 执行策略
        ├─ 上下文组装 → 模型调用
        └─ 能力调用   → 外部资源
        ↓
执行事实与场景输出

运行控制贯穿各层：配置、权限、取消、生命周期、观测与恢复
```

| 职责 | 解决的问题 | 常见实现方式 |
| ---- | ---------- | ------------ |
| 宿主与入口 | 谁启动系统，谁接收请求，何时返回结果 | CLI、GUI、服务端 API、IDE 或自动化入口 |
| 场景协调 | 如何关联用户、会话和执行实例 | Controller、应用服务或协议适配层 |
| Agent 执行 | 如何接纳输入并推进任务 | 请求处理器、Workflow、Agent Loop 或混合状态机 |
| 上下文与模型 | 模型看到什么，如何调用和切换模型 | Prompt 组装、历史投影、压缩和模型适配器 |
| 能力执行 | 模型或程序如何操作外部世界 | 函数、工具、能力接口、远程服务或子 Agent |
| 数据管理 | 哪些事实需要记录、查询和恢复 | 会话日志、领域存储、对象存储、索引和记忆 |
| 运行控制 | 如何限制行为并处理生命周期 | 设置、权限、审批、隔离、取消和资源所有权 |
| 运行保障 | 如何发现问题并安全继续 | 日志、事件、指标、追踪、重试、幂等和补偿 |

这些职责是逻辑分工，不等同于代码包或进程数量。
小型 Harness 可以在一个函数中完成多项职责，大型 Harness 可以把同一职责拆到多个进程或服务。

### 2.2 稳定骨架与变化点

宏观设计的核心不是拆出最多模块，而是识别哪些关系需要稳定，哪些实现需要变化。

通常相对稳定的是：

- 外部输入如何转换为执行请求；
- Agent 如何取得模型、能力和状态；
- 执行事实如何形成上下文和输出；
- 权限、取消、失败和生命周期如何沿调用关系传递。

常见变化点包括模型供应商、工具集合、执行环境、存储方式、交互入口和 Agent 执行策略。
只有当变化具有实际频率或独立责任主体时，抽象接口和独立生命周期才会产生足够收益。

### 2.3 组成方式与取舍

| 组成方式 | 侧重点 | 收益 | 代价与适用条件 |
| -------- | ------ | ---- | -------------- |
| 直接组装 | 清晰、低开销 | 调用关系直观，调试路径短 | 适合组成稳定的小型系统；变化增多后容易形成耦合 |
| 模块与依赖注入 | 职责分离 | 便于测试、替换和集中管理实例 | 需要维护接口、实例范围和初始化顺序 |
| 插件 Runtime | 动态组合与生命周期 | 能按场景装卸能力并响应依赖变化 | 需要处理作用域、级联激活、卸载和诊断 |
| 独立服务 | 隔离与独立扩缩 | 故障、资源和发布可以分开管理 | 引入网络协议、一致性、部署和观测成本 |

这些方式可以分层组合。
例如，单进程内使用插件组织能力，同时把高风险执行或高负载模型代理放到独立服务。

### 2.4 能力接口

当能力语义相对稳定而实现需要替换时，可以在使用方和实现方之间建立能力接口。
一个完整的 Capability Seam 包含 3 个角色：

- **Definition** 定义输入、结果、失败、取消和生命周期约定；
- **Provider** 实现能力，并处理具体外部系统或运行环境；
- **Consumer** 调用能力，并根据结果决定后续行为。

接口应由 Consumer 的实际需要驱动，不应简单复制某个 Provider 的完整 API。
拆分的收益是复用和替换，代价是公共语义可能无法覆盖所有实现差异，因此接口还需要表达能力发现、限制或降级条件。

### 2.5 状态、控制与所有权

数据流和控制关系共同决定系统能否正确运行。
输入、模型响应、能力结果和用户决定形成数据流；权限、取消、超时、生命周期和背压控制这些数据何时可以继续流动。

每项运行资源和可变状态都需要明确所有者。
所有者决定创建、修改、持久化、释放和失败恢复；跨层共享状态如果没有唯一所有者，容易产生并发覆盖、重复执行和无法确认的结果。

记录事实与保存当前值是不同职责。
事实日志适合重建过程和审计，可编辑领域存储适合维护当前状态，大内容和索引可以由稳定引用关联。
具体选择见[数据管理](#46-数据管理记录保存与复用)。

### 2.6 DeepSeek Mapping

DSH 采用单进程 Cordis 插件 Runtime 作为主要组成方式，以 Context 提供作用域和 Service 访问，以 Fiber 和 Effect 管理插件资源。
Controller 适配入口，Agent Seam 承载可替换执行策略，Capability Seam 连接模型、文件、命令、网络、交互和编排等能力，Session 保存模型可见和可恢复的执行事实。

这套映射体现了“稳定职责 + 可替换实现 + 统一生命周期”的选择。
它不是 Harness 的必需结构：组成稳定的应用可以直接组装，高隔离或独立扩缩的能力也可以采用进程或服务边界。

## 三、链路

链路从动态视角说明一次工作如何跨职责推进，以及控制、事实和所有权在阶段之间如何交接。
启动、请求、控制与恢复是常见分析视角，不代表固定模块或唯一执行顺序。

不同 Harness 可以合并、拆分或省略部分阶段。
判断链路是否成立，需要关注每个阶段接收什么、产出什么、何时完成、失败由谁处理，以及外部副作用能否确认。

### 3.1 启动主链

启动主链把代码、配置和运行环境中的选择转换为可接收工作的 Runtime。

#### 3.1.1 宏观流程

```text
接收启动输入
→ 解析组成与参数
→ 创建运行基础
→ 装配组件并解析依赖
→ 建立资源所有权和运行状态
→ 检查就绪、失败或受控退出
→ 将 Runtime 交给宿主
```

这些阶段表示职责交接，不要求严格串行。
组件加载、依赖解析和资源初始化可以并发，但 Runtime 只能在必需能力可用后对外宣告就绪。

#### 3.1.2 组成方式

静态组装在代码中直接创建对象，适合组成稳定、启动路径固定的系统。
依赖注入容器集中创建实例并解析依赖，适合模块较多但组合仍由应用控制的系统。
插件或声明式装配把目标组成与实例创建分开，适合需要按场景替换、增删和重新激活能力的系统。

动态程度越高，越需要明确配置优先级、依赖等待、作用域、初始化失败回滚和卸载行为。

#### 3.1.3 配置来源与覆盖顺序

配置可以来自默认值、部署环境、场景预设、用户设置和本次启动参数。
系统需要定义来源优先级、同层顺序、合并方式和最终有效值，并在诊断中保留关键来源。

配置既可能选择系统组成，也可能只改变运行参数。
组成变化通常需要重新装配，运行参数是否可以动态修改则由拥有该参数的组件决定。

#### 3.1.4 运行基础与组件装配

启动入口先建立其余组件共同依赖的最小运行基础，例如模块解析、依赖管理、资源登记和退出控制。
随后，组装逻辑根据目标组成创建组件，并把实例、注册关系和清理操作交给对应生命周期所有者。

初始化产生外部副作用时，组件还需要定义失败后的核查或补偿方式。
释放内存对象不能自动撤销已经提交到文件、进程或远程系统的操作。

#### 3.1.5 依赖、并发与就绪

组件只有在必需依赖可用且初始化完成后才能提供能力。
独立组件可以并发启动；存在先后要求时，应通过显式依赖或阶段约定表达，不能依靠偶然的配置顺序。

就绪条件应面向宿主能够使用的能力，而不是“启动函数已经返回”或“模块已经导入”。
系统还需要区分仍在等待、已经失败和启动期间收到退出请求。

#### 3.1.6 装配结果、诊断与退出

启动成功表示必需能力可用，Runtime 可以接收工作。
启动失败应指出失败阶段、相关配置或组件、原始原因和已经完成的清理。
受控退出表示系统按请求停止装配并释放已登记资源，不应继续执行就绪交接。

宿主负责展示或传播最终结果，并决定进程是否退出。
资源所有者负责清理自己创建的资源；无法回滚的外部副作用需要单独报告。

#### 3.1.7 DeepSeek Mapping 与取舍

DSH 的 Launcher 汇集 Profile、Bundle、用户配置和有序 Patch，创建 Cordis 并挂载 Loader。
Include 生成 Entry 配置树，Cordis 根据 Service 依赖激活插件，Fiber 承载实例及其资源生命周期；启动辅助逻辑等待装配收敛后检查就绪状态。

该实现强调跨入口复用和动态组合，代价是启动问题可能跨配置来源、模块解析、依赖和生命周期传播。
具体配置算法和组件机制见[实现](#五实现)。

### 3.2 请求主链

请求主链把外部输入转换为 Agent 工作，并把执行事实和结果交回调用方。

#### 3.2.1 宏观流程与边界

```text
接收外部输入
→ 关联会话与执行主体
→ 接纳或排队输入
→ 选择并推进执行策略
→ 组装模型上下文或调用确定性能力
→ 记录执行事实
→ 投影进度、结果和状态
→ 返回回执、完成结果或持续输出
```

入口提交、执行开始、模型停止、能力完成和任务成功是不同时间点。
协议需要明确自己在哪个时间点返回，以及返回值证明了什么。

#### 3.2.2 Controller 与入口 Agent

入口协调器把 CLI、GUI、API 或事件协议转换为稳定的执行操作。
它负责关联外部身份、会话和入口 Agent，并决定连接结束后继续、取消还是释放执行实例。

入口 Agent 是场景首先控制的执行主体，不代表整个任务只能有一个 Agent。
Workflow、子 Agent 或其他执行器可以在入口之后组织更多工作；这些下游对象的生命周期仍需有明确所有者。

#### 3.2.3 Agent 输入投递与 Inbox

输入可以直接触发一次执行，也可以先进入 Inbox，再由执行器在明确边界接纳。
直接执行路径短，适合独立请求；队列将输入到达与处理时机解耦，适合持续交互、运行中干预和背压控制。

并发投递不等于并发执行。
同一 Agent 是否串行、哪些消息可以合并、运行中的输入何时生效，都由接纳规则决定；已经组装或发出的模型请求通常不会被新输入改写。

#### 3.2.4 执行策略与模型循环

确定性 Workflow 由程序选择阶段和分支，适合步骤稳定、审批严格或需要重复执行的任务。
Agent Loop 让模型根据上下文和中间结果选择下一步，适合路径难以预先枚举的任务。
混合架构由程序控制阶段、预算和关键决策点，在局部开放模型选择。

模型发起能力调用时，执行器校验请求、调用能力、记录结果，再决定继续模型循环或结束。
程序也可以直接调用能力接口，不需要把所有操作都转换为模型 Tool Call。
详细取舍见[执行控制](#48-执行控制自治度与确定性)。

#### 3.2.5 Session 事实与场景输出

输入、模型输出、能力调用和结果中，影响后续执行、恢复或审计的内容需要形成持久事实。
模型历史和场景输出可以从这些事实投影，但实时生成的临时片段不应自动成为最终结果。

事实写入当前内存与持久化完成是不同保证。
需要跨进程恢复时，系统必须明确何时刷新完成，以及刷新失败后调用方可以相信哪些内容。

#### 3.2.6 完成、失败与结果归属

```text
输入已接收
≠ 执行已结束
≠ Agent 已空闲
≠ 任务已成功
≠ 用户已验收
```

回执证明输入已被接收，执行状态证明当前活动是否结束，任务证据证明目标是否达成，用户或业务规则决定是否验收。
多条输入共同影响一次执行时，按请求返回准确结果还需要记录输入、执行区间与输出之间的因果关系。

#### 3.2.7 DeepSeek Mapping 与取舍

DSH Controller 将外部意图映射为 `followup`、`steer`、`inject` 和 `cancel`，入口 Agent 通过 Inbox 接收输入。
默认 `ReactLoopAgent` 以 Driver、Turn 和 Step 串行推进模型与 Tool 循环，Session 记录已接纳输入和执行结果，并投影为模型历史与场景输出。

这套实现强调持续交互、运行中补充输入和会话重建，代价是“消息已提交”“Agent 空闲”和“某条输入已取得结果”不能相互替代。
Turn 和 Step 属于默认 Provider 的内部结构，不是所有 Agent 实现的必需概念。

### 3.3 控制与恢复主链

控制与恢复主链处理运行中的失败和停止，并在资源释放或进程重启后建立可信状态。
核心问题不是让流程继续，而是明确哪些工作已经停止、哪些事实仍然有效、哪些结果无法确认。

#### 3.3.1 宏观流程与职责边界

| 场景 | 触发条件 | 完成标准 |
| ---- | -------- | -------- |
| 运行中控制 | 取消、超时或执行失败 | 受影响工作停止继续调度，结果由能解释其语义的组件处理 |
| 生命周期释放 | 所有者退出、实例释放或系统关闭 | 受管工作停稳，登记资源释放，迟到回调不能再修改已释放状态 |
| 正常恢复 | 调用方重新打开持久会话或任务 | 从已确认事实重建状态，并创建新的运行对象 |
| 崩溃恢复 | 进程在执行中意外中断 | 修复或拒绝不完整记录，显式标记无法确认的结果 |

实时连接、执行实例、持久事实和外部副作用具有不同生命周期。
恢复其中一项不代表其他项也已恢复。

#### 3.3.2 运行中控制与状态收敛

取消是协作式停止请求。
发送取消信号只表示请求已经传播；受影响工作结束、清理完成并记录结果后，停止才算完成。

局部超时限制单次模型、能力、进程或入口操作的等待时间。
多个局部超时不会自动形成覆盖整个任务的 Deadline；端到端时限还需要统一剩余预算、传播方式和到期结果。

##### 3.3.2.1 Cancellation、Timeout 与 Deadline

取消、超时和强制终止解决不同问题。
取消允许执行方协作清理，超时决定调用方不再等待，强制终止在下游不响应时限制继续运行，但可能留下未提交或未知状态。

系统需要分别记录停止原因、实际结束状态和部分结果。
任何一项都不能由另一项推断。

##### 3.3.2.2 错误传播与结果归属

局部失败由能够解释其语义的执行方处理。
能力调用失败可以成为上层可处理的结构化结果；依赖该结果的执行无法继续时，执行器结束受影响活动；协议或展示失败则由入口协调器反馈。

捕获异常不会撤销已经发生的状态修改。
只有状态所有者重新建立约束，或丢弃不可信状态并停止依赖它的工作，系统才能安全继续。

#### 3.3.3 生命周期释放

释放遵循资源所有权：所有者先停止接收新工作，再取消并等待在途工作，最后撤销注册、关闭连接和释放子资源。
“调用了取消接口”不等于释放完成；完成状态要求受管工作已经停稳，迟到回调不会继续修改已释放对象。

生命周期机制只能清理已经登记的资源。
文件修改、远程提交和其他外部副作用需要对应能力核查或补偿。

#### 3.3.4 正常会话恢复

恢复通常包含 4 个步骤：加载持久事实、校验或修复记录、重建领域状态、创建新的运行对象。
恢复保留的是身份和已记录事实，不是旧进程中的对象、连接、句柄、计时器或进程。

历史模型请求和能力调用用于重建上下文时，不应自动再次执行。
恢复失败需要释放本次创建的临时资源，并把错误交给调用方决定重试、降级或提示用户。

#### 3.3.5 崩溃恢复与未决工作

进程可能在操作开始、外部提交、获得确认或记录结果之间中断。
恢复逻辑需要区分尚未开始、明确失败、已经成功和结果未知，不能把缺少结果记录解释为外部操作没有发生。

会话恢复与任务恢复是不同能力。
会话日志可以重建历史和上下文；后台任务要在重启后继续，还需要持久任务状态、调度条件、租约或重新接管规则。

##### 3.3.5.1 副作用交付、幂等、去重与补偿

```text
接收请求
→ 开始执行
→ 外部状态提交
→ Harness 获得确认
→ 记录结果
```

中断可能发生在任意两个阶段之间。
安全处理依赖具体能力提供幂等键、去重、状态复查、补偿或人工确认；通用 Runtime 无法替外部系统推断真实结果。
详细原则见[重试、幂等与补偿](#4134-重试幂等与补偿)。

#### 3.3.6 DeepSeek Mapping 与取舍

DSH 通过 AbortSignal 协作取消受管工作，通过 Fiber 生命周期释放登记资源，并由 Session Persistence 加载、校验和修复 Session Log。
冷加载会为中断的 Step 和 Turn 补齐结束事实，区分尚未开始和结果未知的 Tool Call；恢复时创建新的 Agent，不复活旧运行对象。

该实现能够恢复会话事实，但进程内 Job 和 Goal continuation 不会因此自动续行。
它说明持久日志可以扩大恢复范围，同时也说明任务接管和外部副作用确认仍需所属能力单独设计。

## 四、领域

**预期解决**

明确每类问题由哪个领域拥有，避免运行内核、业务能力、会话事实和交互入口相互侵入。

**解决方式**

按基础机制、单个 Agent、交互与协作、运行保障的顺序展开，各领域维护自身职责、状态和接口约定。
模型访问、工具执行和执行环境归入能力领域，身份与凭证归入安全领域，Memory 属于跨会话派生数据；各领域通过稳定能力、事实事件和组合声明协作。

**阅读顺序**

```text
基础机制
├── 插件运行时
├── 能力
├── 组合
└── 配置与设置

单个 Agent
├── Agent
├── 数据管理
├── 模型上下文
└── 执行控制

交互与协作
├── 用户交互
├── 执行安全
├── 任务编排
└── Controller

运行保障
├── 运行可靠性
└── 运行观测与诊断
```

### 4.1 插件运行时：依赖与生命周期

**需求与约束**

插件运行时负责按依赖激活插件，并在依赖失效或所有者退出时撤销注册、释放资源。它使不同场景的插件组合共用 1 套装载与清理机制。

##### 4.1.1 职责划分：可见性、可用性与所有权

| 职责       | 决定的行为                                   | DSH 对应机制                 |
| ---------- | -------------------------------------------- | ---------------------------- |
| 依赖可见性 | 插件通过当前 Context 能访问哪个 Service 实例 | Context 与 Service isolation |
| 依赖声明   | 插件必须具备哪些 Service 才能激活            | `inject` 与依赖刷新          |
| 资源所有权 | 哪个 Fiber 负责撤销注册、释放资源和子插件    | Fiber 与 Effect              |

派生 Context 可以改变局部属性或 Service 的查找范围，仍归属原 Fiber；挂载子插件才会创建新的 Fiber。
Context 层级与 Fiber 父子关系因此需要分别理解。

#### 4.1.2 方案与选择

**Pattern**：根据依赖是否动态变化，以及资源管理需求选择组装方式。

| 方案                       | 方案经典示例                                                        | 适用条件                             | 收益与代价                                         |
| -------------------------- | ------------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------- |
| 显式创建与注册插件         | Webpack：配置中创建 Plugin，初始化时通过`apply(compiler)` 注册 Hook | 插件集合在初始化时确定               | 组装直观；插件间依赖与额外资源清理由插件或应用负责 |
| 依赖注入容器与生命周期钩子 | NestJS：注入 Service，通过初始化与销毁钩子管理模块                  | 需要集中管理依赖和实例范围           | 减少手工组装；动态依赖失效的处理仍需另行设计       |
| 动态服务注册与依赖驱动激活 | OSGi Declarative Services：必需服务满足时激活组件，失效时停用       | Service 会在运行期间出现、消失或替换 | 自动响应依赖变化；需要处理级联卸载与状态重建       |

**DeepSeek Mapping**：DSH 使用 Cordis 的动态依赖与资源管理机制，适合按场景组合、装卸和替换插件。其代价是 Provider 变化可能引起多个 Consumer 重新激活，插件需自行处理业务状态的延续。

#### 4.1.3 依赖：从启动条件到运行期可用性

插件通过 `inject` 声明必需的 Service 名称，具体 Provider 由组合与作用域决定。
Cordis 持续检查这些 Service 是否可用：

```text
必需 Service 尚不可用 → 插件等待
全部必需 Service 可用 → 插件加载并激活
必需 Service 消失     → 使用方插件卸载并清理资源，回到等待
必需 Service 恢复     → 使用方插件重新加载并激活
```

模块导入成功不代表依赖已满足。缺少 Provider、作用域不匹配或循环等待，都可能使插件无法激活；DSH 启动时检查应启用 Entry 的激活结果，见[装配结果、诊断与退出](#316-装配结果诊断与退出)。

可选 Service 可以在使用点查询，并明确缺失时的行为；也可以将相关功能放入声明该依赖的子插件，使其单独装卸。

#### 4.1.4 生命周期：登记、撤销与释放完成

Cordis 通过 Effect 登记清理函数（disposer）。
已自动登记清理的 API 直接调用；通过原生或第 3 方 API 创建的未受管资源，需要使用 ctx.effect() 登记清理函数。

父 Fiber 释放时会级联释放子 Fiber，子 Fiber 也可独立释放。

Effect 按登记逆序触发清理，但异步清理可能并发执行，不保证完成顺序。
若资源要求“停止接收 → 等待在途工作结束 → 关闭连接”，应在同 1 个异步 disposer 中明确等待顺序，并返回代表完整清理过程的 Promise，见[释放必须等待工作停稳](../docs/defensive-patterns.md#dispose-must-reach-quiescence-not-just-request-it)。

释放只覆盖已登记资源，不会撤销已发生的文件修改或外部操作；结果核查、重试和补偿由对应能力负责，见[副作用交付](#3351-副作用交付幂等去重与补偿)。

#### 4.1.5 风险与处理

| 易混淆的保证                 | 实际范围                                                                                             |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| 插件重新激活即业务恢复       | 重新激活只重建插件运行资源；业务状态需由对应服务恢复，见[控制与恢复主链](#33-控制与恢复主链)         |
| Service isolation 即安全隔离 | 它只改变 Service 的查找范围；不可信代码需要执行隔离与权限控制，见[执行安全](#410-执行安全策略与隔离) |

#### 4.1.6 验证依据与演进

机制依据见 [Service 教程](../docs/cordis-tutorial/03-services.md)、[Context API](../docs/cordis-api/context.md)和[生命周期教程](../docs/cordis-tutorial/02-lifecycle-and-effects.md)。[生命周期用例](../packages/extensions/tool-cordis/tests/cordis-lifecycle.spec.ts)覆盖初始化失败回滚、异步清理等待和父子释放；各插件仍需验证自身的依赖变化、在途工作停止与状态恢复。

**Roadmap（本文建议）**：完善缺失依赖与作用域诊断，记录资源所有者及清理耗时；出现可测性能问题时，再优化依赖刷新。

### 4.2 能力：语义与实现解耦

**需求与约束**

Agent Loop 需要调用模型，文件工具需要读写文件。
这些需求可以保持不变，具体模型供应商和文件所在环境却可能变化。
本节讨论如何分开能力的使用与实现，使调用逻辑可以复用，并明确替换实现需要满足的条件。

#### 4.2.1 职责分工与拆分价值

沿用[宏观架构](#二宏观架构)中的 Capability Seam，以 DSH 的模型调用为例：

| 角色                         | 在模型调用中的职责                                  |
| ---------------------------- | --------------------------------------------------- |
| Consumer：使用方             | Agent Loop 组织请求，消费模型响应，决定如何继续执行 |
| Service Definition：能力接口 | 定义请求参数、响应流、错误与取消等调用约定          |
| Provider：实现方             | 模型适配器转换供应商协议，发送请求并转换响应        |

更换模型供应商时，只要新适配器满足 Agent Loop 所依赖的约定，Loop 就能复用原有调用逻辑。
压缩和标题生成也可以使用同 1 LLM 接口，集中复用协议适配。
文件、命令和网络能力可以采用相同分工。

代价是需要设计公共接口、表达实现差异，并验证替换后的行为。
只有1 个调用点、实现长期稳定时，直接调用 SDK 可能更简单；出现重复适配或独立替换需求时，拆分更有价值。
3 种角色可以位于同 1 包中，只有需要独立演进时才拆包。

#### 4.2.2 接口约定：以使用方的实际需要为依据

公共接口需要说明输入如何解释、返回值代表什么、失败如何表达，以及取消后执行会停到什么程度。
例如，读文件接口需要明确路径与工作目录的关系，模型接口需要明确响应结束时是成功、失败还是取消。

接口过宽，会要求 Provider 实现无人使用的功能；接口过窄，会迫使 Consumer 反复判断供应商和平台。
因此，应先明确真实调用方需要的行为，再决定统 1 哪些差异、显式保留哪些差异。

替换 Provider 时，输入、结果、错误、取消和外部副作用都需要重新核对。
“能力未知”与“明确不支持”应分别表达；已知不支持的请求应在可判定时拒绝。
相同的方法和参数，只能证明调用形式兼容。

#### 4.2.3 模型适配：统 1 调用，保留能力差异

DSH 的 LLM Service 通过适配器提供统 1 响应流，但每次调用仍需按具体 Provider／Model 确认输入模态、上下文容量和参数支持情况。
例如，图片模型接收图片，纯文本路由接收图片占位信息；调用形式 1 致，模型实际获得的信息仍有差别。

DSH 在准备请求时解析模型能力与默认参数，并将解析结果与实际执行请求的适配器绑定，避免动态更新时混用不同实现的信息。
模型目录用于发现候选，具体模型是否可调用由适配器判断；显式指定但不支持的推理参数在请求前拒绝。
具体规则见 [LLM](../packages/llm/llm/README.md)。

适配器返回统 1 的内容块、用量和结束信息。
模型请求失败以终止 failure 表达，Consumer 丢弃未完成输出；中间件或 Consumer 自身异常仍按所属组件处理。
重试由独立策略执行，并保留请求与日志的关联；网络中断不证明此前未产生输出或费用。
请求与恢复流程见[组织调用](#55-组织调用适配器注册表与执行分发)。

#### 4.2.4 工具接入：使用能力并呈现结果

Tool 可以作为能力的 Consumer。
例如，文件工具把模型提出的读文件请求转换为 FS 调用，再把结果提供给模型。
参数描述、JSON 校验和面向模型的结果呈现由工具及 Tool Runtime 负责，底层文件操作由 FS Provider 实现。

工具返回的结构化数据供调用程序继续处理，模型通过整理后的内容读取结果，界面则按展示规则呈现。
缩短模型可见文本时，应保留完整的工具返回值。
模型可以直接调用工具，也可以通过 Code Mode 程序调用工具。
2 种方式都通过同 1 Tool Runtime 使用已注册的工具，并接受参数校验与权限检查。
结果分工见[建立事实系统](#57-建立事实系统日志持久化与投影)。

工具策略决定允许、拒绝或请求审批；Guard 的拒绝不能被后续处理改回允许。
并发安全按具体参数判断，明确安全的调用才进入有界并发池，其余独占执行；结果按模型顺序提交，也不保证外部操作按该顺序发生。
具体执行机制见[组织调用](#55-组织调用适配器注册表与执行分发)与 [Tools](../packages/core/tools/README.md)。

工具报错或取消不能自动撤销已经发生的文件修改或外部操作。
是否可以重试，需要具体能力提供依据；幂等、结果核查和补偿见[副作用交付](#3351-副作用交付幂等去重与补偿)。

#### 4.2.5 执行环境：相关 Provider 配套使用

文件工具修改的文件，必须与命令执行、终端访问和 LSP 分析的文件属于同 1 目标环境。
例如，将命令切换到远端执行时，也需要让文件操作指向同 1 远端目录，避免修改本地副本却在远端运行测试。

DSH 分别提供 FS、Subprocess、Shell、Terminal 与 LSP 能力，通过配置选择配套 Provider。
路径解释、工作目录、权限和进程生命周期需要 1 起验证；调用分发见[组织调用](#55-组织调用适配器注册表与执行分发)，执行限制见[落实安全](#59-落实安全策略解析执行点与隔离机制)。

本地、沙箱和远端实现具有不同的平台限制。
「隔离」是否覆盖「文件、网络、进程或凭证」，以具体执行机制为准，见[执行安全](#410-执行安全策略与隔离)。

#### 4.2.6 验证依据与演进

验证从真实 Consumer 发起调用：模型适配使用真实 API 检查响应与失败；工具覆盖参数、结果、并发和取消；执行环境通过读写文件并运行命令检查组合是否 1 致。
接口单元测试不能独立证明 Provider 可替换，服务清单与依赖关系见[能力地图](../docs/capability-seams.md)。

**Roadmap（本文建议）**：多个 Consumer 重复处理同 1 实现差异时，完善公共接口；新增 Provider 时补充替换与组合验证；实际任务需要新的能力差异时，再扩展能力描述。

### 4.3 组合：进程级与 Agent 级组装

**需求与约束**

组合决定 Runtime 装载哪些插件，以及各 Agent 使用哪些工具、指令和策略。
它负责选择与共享范围，插件运行时负责装配，具体插件实现业务行为。

**方案与选择**

**Pattern**：组合固定时可直接编写初始化代码；多个场景需要复用能力时，可通过声明式配置选择插件；Agent 之间存在能力差异时，可进一步使用 Preset 与作用域。

**DeepSeek Mapping**：DSH 通过 Profile、Bundle 和 Patch 组织进程级组合，通过 Agent Preset 组织实例可用的能力。

#### 4.3.1 进程级组合：产品组装

进程级组合选择 Controller、共享服务和能力 Provider。例如 Headless 与 Web 复用基础能力，装配不同入口。

| 组合单元 | 职责                       | 生效方式                                     |
| -------- | -------------------------- | -------------------------------------------- |
| Bundle   | 分发插件代码及默认配置贡献 | 作为 Profile 指定的有序 Patch Layer 加入组合 |
| Profile  | 选择产品场景及 Bundle 列表 | 形成该次启动的场景组合                       |
| Patch    | 修改或插入指定 Entry       | 按层次和层内顺序作用于配置声明               |
| Entry    | 声明 1 项插件及配置        | 由 Loader 建立对应运行实例                   |

Patch 按层次和层内顺序生成最终 Entry 声明；插件激活需满足声明的 Service 依赖。修改 `config` 会替换整个字段，需要保留的配置必须一并写出。优先级见[配置来源与覆盖顺序](#313-配置来源与覆盖顺序)，通用装配机制见[建立运行骨架](#52-建立运行骨架组件图依赖与作用域)。

分层组合减少重复配置，但排查问题时需确认字段来自哪一层。配置预览只反映声明结果，运行就绪仍需验证插件激活与实际能力。

#### 4.3.2 Agent 级组合：实例组装

Agent Preset 的 `agent.cordis.yml` 描述该组 Agent 使用的插件。DSH 将同一版本的 Preset 插件共享挂载一次；AgentFactory 在实例发布前的 `setup` 阶段，将 Agent 作用域关联到该 Preset。下图表示能力查找关系：

```text
进程级共享设施
└─ Preset 常驻组合：共享插件与贡献
   ├─ Agent A：独立 Session、执行状态与局部贡献
   └─ Agent B：独立 Session、执行状态与局部贡献

贡献查找：Agent 局部 → Preset → Global
```

支持作用域的工具、提示词等注册按近层优先查找；Preset 监听器可接收关联 Agent 的对应事件。共享插件需按 Agent 或 Session 分开保存实例状态，避免多个 Agent 相互影响。

Agent 自有资源随实例释放，Preset 插件由 Preset 服务持有，不随单个 Agent 退出而卸载。

这套贡献查找规则不自动隔离任意 Service。Preset 自有 Service 必须使用 Cordis `isolate`，否则挂载检查会拒绝其向全局发布；机制见 [dsh-scope](../packages/core/scope/README.md)。

#### 4.3.3 组合变化：新实例、运行实例与恢复

| 变化                                | DSH 的处理方式                                                                     |
| ----------------------------------- | ---------------------------------------------------------------------------------- |
| 进程级用户 Patch 更新               | 重新组合插件树；候选失败时保留最后可用树，成功后按插件生命周期更新                 |
| Preset 组合文件更新                 | 按文件时间戳与大小识别新版本；后续加入的 Agent 使用新版本，已运行 Agent 保留原版本 |
| 子 Agent 通过`composeFrom` 加入组合 | 复用父 Agent 正在使用的版本，不重新按 Preset id 装载                               |
| 空白会话切换 Preset                 | 调用方检查切换资格；新组合可用后再切换作用域关联，失败时保留原组合                 |
| 跨进程恢复会话                      | 按会话记录的 Preset id 解析组合；该 id 不锁定旧配置文件版本                        |

Preset 更新可能使多个版本同时驻留。当前旧版本不会在最后一个 Agent 退出时回收，而是随 Preset 服务释放；频繁修改会增加资源占用。

#### 4.3.4 风险与处理

Preset 挂载需检查必需依赖是否满足，避免发布无法使用的 Agent。用户 Preset 的 `trust` 标签只描述来源信任，不限制插件代码权限；执行限制见[执行安全](#410-执行安全策略与隔离)。

#### 4.3.5 验证依据与演进

机制依据见 [App Boot](../packages/boot/app-boot/README.md)和 [Agent Presets](../packages/preset/agent-presets/README.md)，对应用例见 [Profile](../packages/boot/app-boot/tests/profile.spec.ts)与 [Preset 挂载](../packages/preset/agent-presets/tests/mount.spec.ts)。具体组合仍需验证实际激活、并发实例隔离和更新失败后的行为。

**Roadmap（本文建议）**：完善配置来源追踪、旧 Preset 版本回收，以及跨进程恢复所需的版本保留。

### 4.4 配置与设置：系统结构与运行参数

**需求与约束**

Harness 的组成配置与 Provider 的运行设置：装载哪些插件、使用哪些 Provider、采用哪些运行参数，以及配置从哪里来、如何覆盖、校验和生效。

每项配置由使用它的服务负责解析和校验。
配置提供默认值，会话采用的模型与权限选择由 Session 相关机制保存和恢复；这里只说明配置变更对会话的影响。

插件装配见[组合](#43-组合进程级与-agent-级组装)，具体 Provider 的配置项由对应服务说明。
API Key、访问令牌等凭证的存储、读取与授权流程，见[凭证、授权与身份](#4101-凭证授权与身份)。

#### 4.4.1 配置内容：系统组成、运行参数与会话选择

配置既包含 Harness 自身的选项，也包含 Provider 的选项；按作用和生效方式区分，便于判断 1 次修改会影响什么。

| 配置内容         | 示例                                              | DSH 中的管理方式                                         |
| ---------------- | ------------------------------------------------- | -------------------------------------------------------- |
| 系统组成         | 装载哪个模型适配器，选择本地还是远端执行 Provider | Entry／Patch 声明组合，由插件装载过程应用                |
| 运行参数与默认值 | 工具并发上限、Provider 参数、新会话默认权限       | 插件配置提供初始值；接入 Settings 的选项可由用户设置覆盖 |
| 会话自己的选择   | 当前会话使用的模型与权限模式                      | 由所属服务管理，需回放的选择及实际模型请求写入 Session   |

例如，修改新会话默认权限，影响的是后续创建的会话；已有会话保留自己的权限选择。各配置项的作用范围由使用它的服务定义。

#### 4.4.2 有效值：默认配置与用户覆盖

DSH 的 Settings 按命名空间管理设置，即每个注册方拥有 1 组设置项。
注册方提供 Schema（字段类型、默认值与校验规则）及来自插件配置的基础值，Settings 再应用用户覆盖：

```text
字段默认值 → 插件配置提供的基础值 → 用户设置
                                      后者覆盖前者
```

这是 Settings 的解析顺序；会话是否采用解析后的值，由上 1 节所述的服务规则决定。
未配置 Settings Provider 时，各插件仍可解析自己的 Entry 配置。

“恢复默认”应删除用户覆盖，让后续基础配置变化仍能生效。
例如，把当前默认并发数复制到用户设置，会将它变成固定覆盖值，失去继续采用默认值的效果。

Settings 的对象 patch 递归合并用户层中的字段；Entry Patch 则替换目标 `config`。
2 种更新方式分别见 [Settings](../packages/settings/settings/README.md)和[建立运行骨架](#52-建立运行骨架组件图依赖与作用域)。

#### 4.4.3 保存设置：校验、冲突与失败处理

Settings 服务先校验候选设置，再交由存储 Provider 持久化；保存成功后，更新内存中的有效值并通知订阅方。
各插件负责按自身的生效规则应用新值。
只读 Provider 拒绝写入；非 JSON 值或不满足字段规则的结果，在提交前拒绝。
服务退出时等待已接纳的写入和已开始的通知处理完成。

并发编辑需要分别处理写入顺序和版本冲突。
Settings 在同 1 进程内按命名空间排队写入，并允许调用方携带 `expectedRevision`，拒绝基于旧版本的修改。
文件 Provider 在写锁内重读文件并原子替换，保留其他设置组的修改；多个进程修改同 1 设置组时仍由后写覆盖，不能依靠进程内版本检查防止冲突。

启动时已有设置文档非法，会导致装配失败。
运行中外部编辑无效，则保留最后有效值并告警；某一设置组校验失败可单独处理。
文件更新、监听与失败规则见[文件 Provider](../packages/settings/settings-file/README.md)。

#### 4.4.4 应用设置：何时生效、影响哪些实例

保存设置、计算有效值和实际应用是不同步骤。
Settings 提供不可变的有效值快照，并按提交顺序通知；使用设置的服务决定何时读取新值，以及是否需要重连或重建资源。

例如，DSH 的工具并发设置可在下 1 组调用时读取；正在进行的模型请求使用已经准备并记录的参数，后续修改只在相应读取时点影响新的请求。
需要重连或重建的设置，还需由使用方报告应用结果，并明确失败时保留旧资源还是拒绝后续调用。

模型请求需要记录实际采用的配置，不能仅根据当前设置文件推断过去的请求。
请求记录规则见[建立事实系统](#57-建立事实系统日志持久化与投影)。

#### 4.4.5 验证依据与演进

配置界面应区分默认值、用户覆盖和生效范围。
界面隐藏了敏感字段时，只修改用户选定的字段，避免用不完整数据覆盖整组设置；Settings 的脱敏范围与限制见[凭证、授权与身份](#4101-凭证授权与身份)。

验证应覆盖默认值继承、清除覆盖、非法输入、并发冲突、外部编辑失败，以及新值是否在声明的时点生效。
实现依据见本节链接，对应并发场景见[写入用例](../packages/settings/settings-file/tests/concurrency.spec.ts)。

**Roadmap（本文建议）**：用户难以解释有效值时补充来源与生效范围；跨进程编辑频繁时引入真正的条件写入；资源切换失败难以判断时增加应用状态与回滚反馈。

### 4.5 Agent：执行主体与生命周期

**需求与约束**

交互入口、自动化客户端和编排器需要定位执行主体、提交输入、干预活动并管理其存续，同时允许内部执行策略变化。Agent 领域负责这些稳定操作及其生命周期语义；模型如何选择行动、流程如何推进归入[执行控制](#48-执行控制自治度与确定性)。

成功标准是调用方能区分实例身份、输入提交、执行状态与资源释放；创建失败不会发布半成品，释放完成后不再遗留该实例承诺管理的工作。任务成功仍由目标对应的结果证据判断。

**方案与选择**

**Pattern**：独立短任务可以通过函数或单次 Run 返回结果；持续交互适合保留执行实例，通过消息投递与状态观察分离提交和执行；跨进程长期任务还需要持久调度与恢复协议。几种方案可组合，但各自的完成、取消与恢复语义需要明确。

**DeepSeek Mapping**：DSH 以 Agent 接口承接输入和控制，以 AgentRegistry 定位活跃实例，以 AgentFactory 创建或恢复实例，以 AgentHandle 交付访问与释放责任。默认实现为 ReactLoopAgent，Controller 与其他 Consumer 通过公共接口使用它。

Agent 实例经历以下生命周期：

| 阶段  | 行为                                                     |
| ----- | -------------------------------------------------------- |
| 准备  | Factory 创建 Session、Agent 与作用域，实例尚未对外可见   |
| setup | 关联 Preset，并注册 Agent 局部能力                       |
| 发布  | 将 Session 与 Agent 加入 Registry，并向调用方交付 Handle |
| 活动  | 在`idle`、`running` 和 `maintenance` 状态间切换          |
| 释放  | 取消活动、等待停稳、注销实例并释放 Agent 作用域          |

插件的 mount／unmount 属于 Fiber 生命周期，不是 Agent 生命周期。

#### 4.5.1 对象划分：实例、事实、工厂与句柄

| 对象          | 职责与存续范围                                     |
| ------------- | -------------------------------------------------- |
| Agent         | 活跃执行实例，持有输入、执行状态、Session 与作用域 |
| Session       | 会话事实及其内存投影，持久化后可用于恢复与回放     |
| AgentRegistry | 当前 Runtime 内活跃 Agent 的发现与身份登记         |
| AgentFactory  | 创建或恢复具体实现，协调准备、发布和失败回滚       |
| AgentHandle   | 创建调用方持有的访问与释放句柄，绑定确切实例       |

DSH 的 Agent 与其 Session 共享 SessionId，同一 Registry 中该 id 只对应 1 个活跃实例。
恢复可以沿用 Session 身份，同时创建新的 Agent 对象与运行资源；保留 id 不等于保留旧对象。

Registry 查询返回 Agent，创建或恢复返回 AgentHandle。
前者允许输入与控制，后者额外承担实例释放。

历史中的父子会话关系也不同于当前 Runtime 的实例所有权：带有历史父会话的 Session 恢复后，可以直接作为新的入口 Agent 运行。

#### 4.5.2 输入与状态：提交、唤醒与完成

持续交互允许新输入在已有活动期间到达。
输入接口需要声明何时接纳、是否唤醒、能否影响已经发出的模型请求，以及拒绝或取消后如何处理待执行内容。

DSH 通过 Inbox 接收输入：followup 提交后续任务，steer 在后续执行边界进行引导，inject 补充上下文而不主动唤醒。
队列与 Turn／Step 的具体关系见[Agent 输入投递与 Inbox](#323-agent-输入投递与-inbox)，本节保留调用方需要区分的状态：

| 可观察量                   | 能够说明的事实                   | 仍需另外判断的事实                             |
| -------------------------- | -------------------------------- | ---------------------------------------------- |
| 输入已提交                 | 输入已进入对应投递路径           | 是否被接纳、执行及产生目标结果                 |
| running                    | Driver 正在推进或收尾活动        | 当前是否仍有模型请求、某条输入是否完成         |
| idle                       | 当前没有运行中的 Driver          | Inbox 是否为空、是否存在维护工作、任务是否成功 |
| whenIdle() 完成            | 所观察的整体活动与维护工作已停稳 | 某条消息的结果归属，以及未来是否会被再次唤醒   |
| AgentHandle.dispose() 完成 | 该句柄所拥有的实例完成释放       | 外部副作用是否满足业务目标                     |

例如，空闲 Agent 接收 inject 后可以保留待处理上下文；维护任务也可以占用实例而保持公开状态为 idle。
需要等待停稳时使用相应等待操作，不能仅依据状态字段推断。
多条输入共同影响执行时，逐条结果需要额外的因果关联，见[完成、失败与结果归属](#326-完成失败与结果归属)。

#### 4.5.3 创建与发布：先完成组合，再交付实例

**Invariant（可被发现的执行实例）**：实例进入公共发现范围时，应已满足该接口承诺的初始化条件。否则调用方可能在工具、上下文或依赖尚未准备好时开始执行。

DSH 的创建与恢复共用未发布准备阶段：Factory 建立 Session、Agent 与作用域，执行可信的组合 setup，再发布 Session 和 Agent，并将句柄交给调用方。
setup 负责在 Agent 对外可用前完成能力组装；组装完成后，调用方才能取得实例并启动执行。

准备或发布失败时，由 Factory 回滚本次私有资源。
同 id 并发创建可以同时开始准备，最终只允许 1 个进入 Registry，其余创建失败并清理。
该机制处理当前 Runtime 内的身份冲突，不提供跨进程分布式互斥。

创建期间的取消信号只约束本次创建事务，成功交付后由 Agent 控制和句柄释放管理实例。具体实现原则见[明确约定](#51-明确约定接口状态与所有权)和[管理生命周期](#53-管理生命周期创建发布释放与替换)。

#### 4.5.4 取消、释放与恢复：不同的生命周期操作

取消用于停止当前活动，实例可以继续存在并接受后续输入；释放用于结束实例的存续。
恢复则以持久事实建立新的执行实例，既需要重建会话状态，也需要重新取得当前可用能力。

DSH 的默认取消请求向下传播 Signal，通常同时清理待执行输入，调用方可选择保留 Inbox。
调用方 Fiber 和 Factory Provider 共同持有程序化 Agent 的生命周期；任 1 所有者卸载或句柄主动释放，都汇合到同 1 次释放过程，等待执行停稳并清理作用域、注册关系与 Session 关联。

释放操作必须由资源实现完成实际停止与等待，协作式取消信号只表达请求。
持久 Session 用于重建事实，进程内连接与句柄需要重新建立，未记录的外部操作结果需要另行核查；取消、退出与恢复路径见[控制与恢复主链](#33-控制与恢复主链)。

#### 4.5.5 Provider 替换与多实现路由

上层通过 Agent Seam 定义的接口与公开事件操作 Agent。替代 Provider 必须实现相同的输入、状态、事件和释放语义。

AgentRegistry 只有 1 个 AgentFactory 注册槽。
Runtime 可以在启动组合中替换 Provider，但不能同时注册多个 Factory，再为每次创建直接选择其中 1 个。

多种 Agent 实现需要在同 1 Runtime 中共存时，可以将唯 1 注册的 Factory 实现为路由器。
路由 Factory 根据创建请求选择下游实现；各下游实现仍需满足 Agent Seam 的公共约定。

#### 4.5.6 验证依据与演进

公共语义见 [Agent 运行类型](../packages/core/agent/src/runtime-types.ts)，创建与释放实现见 [AgentLoop Factory](../packages/core/agent-loop/src/index.ts)。[作用域生命周期用例](../packages/core/agent-loop/tests/scope-lifecycle.spec.ts)覆盖未发布 setup、冲突回滚、所有者卸载和释放等待；[取消用例](../packages/core/agent-loop/tests/cancel.spec.ts)与[恢复用例](../packages/core/agent-loop/tests/resume.spec.ts)限定各自的行为范围。接口声明本身不能证明替代 Provider 已满足这些语义。

**Roadmap（本文建议）**：调用方需要逐条验收时补充输入与结果关联；多种执行模型需要同进程共存时设计 Factory 路由；需要跨进程接管时明确持久身份、实例租约和重复执行处理。

### 4.6 数据管理：记录、保存与复用

**需求与约束**

Agent 执行任务时，会产生对话、工具调用和执行结果，也可能接收图片等附件。
系统需要保存这些内容，供后续对话、历史查询和会话恢复使用。
工作区名称、显示顺序等可修改信息，也需要单独管理。

本节说明这些数据由谁保存、如何修改，以及如何供后续任务使用。
模型请求中的信息选择与组织见[模型上下文](#47-模型上下文组装与压缩)，运行数据如何形成投影见[建立事实系统](#57-建立事实系统日志持久化与投影)。

#### 4.6.1 会话日志：保存执行过程

用户提出了什么要求、模型调用了什么工具、工具返回了什么结果，都属于会话执行过程。
按顺序追加这些记录，可以核查历史并恢复对话；代价是需要持续保存日志，并在恢复时读取和处理历史记录。

DSH 用 Session Log 保存执行记录，Session Persistence 负责持久化。
后续模型输入和场景输出由日志生成，见[Session 事实与场景输出](#325-session-事实与场景输出)。
修改后续可见历史时，追加替换或遮蔽记录，保留原始事件，见[消息投影与上下文压缩](#472-消息投影与上下文压缩)。

跨进程恢复要求记录已完成持久化；恢复会话不会重新执行历史工具调用。
具体恢复过程与外部操作结果未知时的处理，见[控制与恢复主链](#33-控制与恢复主链)。

#### 4.6.2 可编辑状态：由所属服务管理

工作区名称和显示顺序需要随用户操作更新。
工作区服务负责定义可修改的字段、校验修改并保存当前值；如需追溯修改过程，还需保留变更记录。

DSH 的 Storage 提供存储支持，Workspace 管理工作区登记及其会话归属。
删除工作区登记只移除管理记录，保留目录、用户文件和会话日志；归档会话也保留历史。
路径识别、归属校验及更新失败的处理见 [Workspace](../packages/workspace/workspace/README.md)。

#### 4.6.3 附件与长结果：单独保存内容

图片和很长的工具输出可以单独保存，会话中只保留引用或预览。
例如，完整测试报告保存为文件，工具结果保留报告预览和读取位置，后续需要时再取回全文。

DSH 使用 2 种机制处理这些内容：

- [Attachment](../packages/attachment/attachment/README.md)：校验并持久化图片，再返回可写入会话的稳定引用。
- [Spill Policy](../packages/spill/spill-policy/README.md)：为适用的工具文本保存完整格式化结果，再返回预览和读取位置；保存失败时保留原结果。上游已丢弃的内容无法在此恢复。

单独保存可以减少直接写入会话的内容，但 Spill 不提供全链路内存或上下文硬上限。
引用指向的内容必须保持可读取；恢复或 fork 后的会话可能共享附件，删除内容前需要检查所有引用者。

#### 4.6.4 历史查询：查找记录与核对来源

查找某次工具调用，可以直接读取会话记录；搜索大量历史内容，可以使用索引。
搜索片段、统计和界面视图由已有记录生成，属于派生数据；它们需要保留与原记录的对应关系，便于核查。
索引和缓存还需在来源变化或自身失效时更新、重建。

DSH 的 [Session Query](../packages/session-query/session-query/README.md) 提供会话与事件读取、父子关系追踪和全文搜索，调用方无需直接读取存储文件。
同一会话同时存在于内存与持久存储时，优先读取内存记录；这不代表两处数据已同步，也不提供跨来源的一致快照。
读取未运行的会话也不会启动 Agent。

Session Query 本身不鉴权，调用方负责限制可见数据。
模型工具按工作区授权，API／Web 等入口需校验调用者身份与会话权限。
查询工具采用精确 cwd 匹配，与 Workspace 的路径识别规则不同，见[查询工具限制](../packages/session-query/tool-session-query/README.md#known-limitations-and-deferred-work)。

会话投影、缓存、统计、标题与遥测的实现原则见[建立事实系统](#57-建立事实系统日志持久化与投影)。

#### 4.6.5 记忆：保留可复用信息

Memory 从历史中选择和提炼值得后续任务使用的信息，例如用户偏好、经验、项目约定或有效的处理方法。
记忆需保留来源、适用范围和时效，支持纠正与遗忘；再次提供给 Agent 前，还需检查访问权限及其与当前任务的相关性。

记忆可能概括错误或随时间过期，因此需要能回到原记录核查。
与重建搜索索引相比，重新生成记忆还必须尊重已有的纠正和遗忘要求。

DSH 的 Session、Query、Storage、Skill 和上下文扩展可用于实现记忆能力，但尚未形成覆盖写入、召回、纠正和遗忘的完整 Memory 服务。

#### 4.6.6 风险、依据与演进

一次操作可能同时写入内容、会话记录和索引。
DSH 的 Storage Hub 不提供跨领域事务保证；各写入方需要约定提交顺序，并处理只完成部分写入的情况。
例如，报告文件已经保存，但会话引用写入失败，就需要处理未被引用的文件。

验证应覆盖写入中断、引用内容缺失、共享附件误删、索引或缓存过期，以及越权查询。
实现依据见各小节链接与 [Session](../packages/core/session/README.md)，验证分层见[验证与交付保障](#七验证与交付保障)。

**Roadmap（本文建议）**：完善外置资源回收、跨存储修复流程，以及可纠正的 Memory 生命周期。

### 4.7 模型上下文：组装与压缩

**需求与约束**

每次请求模型，都需要把指令、工具描述、运行环境和会话历史组织为输入。
会话历史增长后，需要通过裁剪或摘要控制输入量，避免超过模型的上下文上限，也减少了延迟与费用；同时保留任务目标、约束和继续执行所需的信息。

本节讨论输入的选择、组装与压缩。
数据保存与历史查询见[数据管理](#46-数据管理记录保存与复用)，模型及请求参数的配置见[配置与设置](#44-配置与设置系统结构与运行参数)。

#### 4.7.1 上下文组装：选择内容并组织输入

模型上下文包含以下内容，工具描述可能通过独立请求字段传递。

| 内容               | 用途                             | 组装要求                                  |
| ------------------ | -------------------------------- | ----------------------------------------- |
| 提示词             | 说明职责、行为要求与调用协议     | 按当前 Agent 的作用域解析指令、顺序和变量 |
| 工具描述           | 告知模型可调用的工具及参数       | 与当前实际可调用的能力一致                |
| 运行环境           | 提供当前目录、权限、时间等信息   | 使用本次请求有效的值，标明来源            |
| 会话历史与引用内容 | 提供用户任务、工具结果和相关资料 | 选择当前有效消息，解析所需引用，保留来源  |

外部文件、工具结果和检索资料作为任务信息进入请求，其文本不因此获得指令权限。
引用解析需遵守当前访问权限；只有路径或 URL 无法确定当时读到的内容，还需保存实际内容或可确定读取同 1 版本的引用。
记录要求见 [Session 事实与场景输出](#325-session-事实与场景输出)。

**DeepSeek Mapping**：DSH 每个 Step 重新组装上下文。SystemPrompt 汇集当前 Agent 作用域内的提示词与运行环境，Tools 提供可见工具描述，Session Projection 从日志生成本次使用的会话消息。稳定指令保留在请求前缀，动态环境在首次出现或有效变化时形成带来源的日志消息。

替换提示词的扩展需保留启用中的 Tool／Code Mode 等调用协议。
提示词负责告知模型规则，执行限制由能力与策略组件实施，见[能力](#42-能力语义与实现解耦)。

#### 4.7.2 消息投影与上下文压缩

消息投影是从 Session 日志生成当前有效消息的过程；上下文压缩则缩减后续请求使用的历史内容，保留原始日志。

**Pattern**：短会话可保留完整历史；内容增多后可组合以下方式：

- **按需读取**：请求中只放当前需要的资料，减少无关输入，但可能漏取信息；查询与长结果外置见[数据管理](#46-数据管理记录保存与复用)。
- **裁剪工具结果**：缩短已进入历史的长输出，降低占用，但可能丢失细节。
- **摘要较早历史，保留近期原文**：维持最近操作的完整信息，但摘要会增加模型调用成本，也可能遗漏约束或误写结论。

**DeepSeek Mapping**：DSH 的 Basic Compaction 使用 Token Meter 估算上下文占用，并按当前 Provider／Model 的容量判断是否需要压缩。

```text
估算上下文占用
├─ 可容纳 → 继续请求模型
└─ 需要压缩 → 可选：裁剪工具结果 → 重新估算
                                  ├─ 可容纳 → 继续请求模型
                                  └─ 仍过大 → 摘要较早历史，保留近期原文
                                             → 记录摘要与替换范围，再检查占用
```

摘要由单独的模型请求生成。
选择压缩范围时保持工具调用与结果配对，避免只留下其中 1 方；摘要提交后，后续消息投影使用摘要替换对应历史。
例如，较早的排查过程可以概括为已验证的结论、约束和待办，最近 1 轮工具调用与结果仍保留原文。

#### 4.7.3 容量、失败与缓存

**容量估算**

上下文预算需计入提示词、工具描述和历史消息，并为模型输出预留空间。
DSH 在满足复用条件时，以 Provider 返回的 token 用量为依据，结合历史内容的变化估算当前占用；否则，根据字符数和消息结构进行粗略估算。
因此，估算结果在预算内，也不保证实际请求符合 Provider 的容量限制。
用量数据的复用条件见 [Token Meter](../packages/llm/token-meter/README.md)。

如果提示词、工具描述或无法拆分的近期消息本身就超过容量，仅压缩较早历史仍无法使请求满足限制。

**压缩失败**

DSH 会检查摘要是否比原文短，以及压缩后的上下文是否回到预算内。
失败后的处理取决于触发场景：

- **常规自动压缩**：失败时可告警，并使用最后已持久化的有效历史继续请求模型。
- **Provider 已报告上下文溢出**：只有历史确实缩减且替换结果已持久化，才允许重试模型请求。

工具结果裁剪和摘要可能先后提交。
如果裁剪已保存、后续摘要失败，已生效的裁剪仍然保留，后续使用裁剪后的历史。
自动压缩、手动压缩及溢出恢复的完整规则见 [Basic Compaction](../packages/compaction/compaction-basic/README.md)。

**缓存复用**

当请求前缀相同且满足 Provider 的缓存条件时，KV Cache 可以复用这部分内容已有的计算结果。DSH 生成摘要时，会尝试沿用原会话的请求前缀以利用缓存。摘要替换历史后，后续请求的前缀可能变化；切换模型或 Provider 也可能使缓存无法复用。实际收益需根据 Provider 返回的缓存用量确认。

#### 4.7.4 验证依据与演进

验证需分别检查输入构造和压缩质量：

- **输入构造**：请求能否重建、作用域是否隔离、引用是否对应当时内容、工具调用与结果是否配对，以及超大消息和压缩失败时的行为。
- **压缩质量**：是否保留目标、约束、未完成事项和可核查证据；token 减少量只能说明缩减效果。

通用策略见 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（查阅于 2026-09-21）。
DSH 实现依据见 [SystemPrompt](../packages/core/system-prompt/README.md)、[Basic Compaction](../packages/compaction/compaction-basic/README.md)，验证依据见[请求重建用例](../packages/core/agent-loop/tests/request-reconstruction.spec.ts)及[压缩用例](../packages/compaction/compaction-basic/tests/compaction-basic.spec.ts)；通用调用机制见[组织调用](#55-组织调用适配器注册表与执行分发)。

**Roadmap（本文建议）**：按失败原因改进：无关资料过多时优化内容选择，摘要遗漏时加强质量评估与原文取回，容量判断偏差持续出现时完善计量，缓存损失明显时优化前缀组织。

### 4.8 执行控制：自治度与确定性

**需求与约束**

单 Agent 的内部执行架构：哪些行动和路径由模型选择，哪些步骤、状态转换与停止条件由程序控制。
选择方式取决于任务路径的不确定性、失败成本、预算和恢复要求；不同实现仍需满足 Agent 接口约定的输入、状态、取消与生命周期语义。

**方案与选择**

**Pattern**：以执行路径的主要决策者为两端，可以形成 ReAct 主导、混合设计与 Workflow 主导的连续选择。

| 内部执行架构  | 控制权分配                                               | 适用场景与主要代价                                         |
| ------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| ReAct 主导    | 模型根据观察选择下一行动，程序维护调用、执行与反馈循环   | 路径难以预先确定；调用次数与执行路径较难预测               |
| 混合架构      | 程序规定阶段和转换条件，模型在阶段内自主选择行动         | 部分过程固定、部分需要探索；需要维护阶段状态和局部自治规则 |
| Workflow 主导 | 程序规定步骤、分支与结束条件，模型完成指定节点的推理任务 | 路径与检查要求相对稳定；流程覆盖和异常分支的维护成本较高   |

权限、预算和执行隔离适用于所有架构。
这里的自由度主要指模型对执行路径的选择范围；程序控制流程，也不意味着模型输出和外部操作结果具有确定性。

**DeepSeek Mapping**：DSH 默认的 `ReactLoopAgent` 采用 ReAct／工具调用循环，公共 Agent 接口与具体循环实现分离。
以下混合架构与 Workflow 型 Agent 描述可选设计；接入 DSH 时需由具体 Agent Provider 实现并验证相应语义。

#### 4.8.1 ReAct 主导：模型选择执行路径

模型根据上下文提出回答或工具调用；Runtime 校验并执行工具，将结果记录为下 1 次决策的观察。

```text
当前上下文与可用工具
→ 模型提出行动
├─ 回答 → Runtime 判断本轮是否可以结束
└─ Tool Call → 策略校验与执行 → 记录观察 → 后续模型请求
```

模型持续根据新观察调整路径，适合调查、诊断等难以预先列全步骤的任务。
程序负责调用合法性、执行策略和结果记录；若任务有明确验收标准，还需在结束前检查结果证据。
模型可能重复尝试或过早回答，因此需要预算与进展控制。

DSH 的 `ReactLoopAgent` 以 Turn／Step 承载循环，Tools Service 执行工具，Session 保存可重建事实。
具体时序见[执行策略与模型循环](#324-执行策略与模型循环)和[推进执行](#54-推进执行状态机队列与调度器)；Turn 结束与任务成功的区别见[完成、失败与结果归属](#326-完成失败与结果归属)。

#### 4.8.2 混合架构：程序控制阶段，模型选择局部路径

混合架构在同 1 个 Agent 内组合显式状态转换与局部 ReAct 循环。
程序规定阶段目标、允许的行动和进入下 1 阶段的条件；模型在当前阶段内选择具体路径。
也可以由模型提出计划，程序校验后按计划执行，并在指定条件下允许重新规划。

```text
Agent 接纳任务
→ 调查阶段：模型自主检索和验证线索
→ 程序检查证据是否满足阶段要求
→ 修改阶段：模型在允许范围内选择修改与工具调用
→ 程序运行验收
   ├─ 未通过且预算允许 → 返回对应阶段继续处理
   └─ 通过 → 记录结果并结束执行
```

该方式保留局部探索能力，同时明确关键步骤的先后与验收要求。
代价是程序需要维护阶段状态、回退规则和阶段间信息；阶段划分不合理时，模型可能缺少完成任务所需的行动空间。

提示词中的步骤建议属于行为引导；需要保证的阶段转换必须由执行器检查。
「工具可见性」缩小模型的选择范围，实际权限由执行策略落实，见[执行安全](#410-执行安全策略与隔离)。
仅增加权限限制，并不改变 ReAct 的路径决策方式。

DSH 可通过作用域贡献、`agent/pre-step`、工具策略与 `agent/turn-stopping` 等扩展点调整默认循环。
设计需要的阶段转换和调度语义超出现有扩展点时，应由专用 Agent Provider 实现；Provider 替换约定见 [Agent](#45-agent执行主体与生命周期)。

#### 4.8.3 Workflow 主导：Agent 内部的显式流程

Workflow 型 Agent 以脚本、状态机或图定义内部执行过程。
执行器维护当前节点、节点结果与转换条件，按程序规则调用模型或工具；模型负责指定节点的分类、提取、生成等推理任务。

```text
Agent 接纳输入
→ 程序读取并校验资料
→ 模型提取结构化信息
→ 程序校验字段与业务规则
   ├─ 校验失败且可重试 → 带错误信息返回提取节点
   ├─ 无法继续 → 记录原因，等待补充输入或结束
   └─ 校验通过 → 程序生成产物并检查结果
→ 记录结果，结束执行
```

步骤与分支明确时，这种实现便于检查路径覆盖、控制重试范围并定位失败节点。
确定性步骤可以直接调用能力，无需每 1 步都请求模型；若某个节点需要多轮探索，也可以嵌入局部 ReAct 循环，形成混合设计。

显式流程需要为预期的异常、缺失输入和失败结果设计处理分支。
流程走到结束节点，只证明满足了已编码的结束条件；业务成功仍取决于这些条件能否充分检查目标。
脚本或图本身也不提供持久恢复，跨进程续行需要保存节点状态、有效输入与结果，并处理外部副作用的幂等和未决状态。

在 DSH 中将这种设计实现为 Agent Provider 时，需要维持统 1 的输入、状态、取消、等待与释放语义，并让模型实际使用的输入与输出可以从 Session 事实重建。
流程节点可以使用自己的内部状态表示，相关约定见[明确约定](#51-明确约定接口状态与所有权)。

#### 4.8.4 共同控制：预算、取消、进展与完成

3 类架构都需要控制「消耗、等待和无效执行」。
ReAct 在循环中检查，混合架构在局部循环和阶段转换处检查，Workflow 在节点准入与重试路径检查；持续耗时的调用还需要独立的超时与取消机制。

| 控制项                    | 要约束的量                         | DSH 当前覆盖与限制                                              |
| ------------------------- | ---------------------------------- | --------------------------------------------------------------- |
| 单次模型输出上限          | 1 次对话模型请求的输出 token       | AgentOptions.maxTokens 随请求记录；不累计整个 Turn 的成本       |
| 工具并发上限              | 同 1 Agent 执行组中的并行调用数    | maxParallelToolCalls 约束并行安全调用；不代表进程级总配额       |
| 单次工具超时              | 1 次已声明时限的工具调用           | Timeout Policy 传递取消信号；终止依赖工具及下游响应             |
| 重复调用提醒              | 单个 Agent 连续同名、同参数调用    | Repeat Tool Reminder 按阈值提供建议，不阻止调用                 |
| 单次任务总预算与 Deadline | 本次执行的累计成本、步骤数或总耗时 | 默认循环没有内建 Turn 总预算，也没有覆盖全部下游的统一 Deadline |

DSH 默认循环的单次请求上限不能限制整个任务；工具超时只发出取消信号，下游忽略信号时仍可能继续。
执行器需要等待已启动工作停稳，再确认取消或释放完成。
取消语义见[运行中控制](#332-运行中控制与状态收敛)，实现机制见[收敛失败](#58-收敛失败取消超时重试与恢复)。

进展判断应关联已获得的证据、已完成的目标或已消除的缺口。
重复调用可能是合法轮询，执行了新步骤也不必然有进展。
DSH 的重复调用提醒只识别当前进程内连续同名、同参数的调用；`agent/turn-stopping` 只在循环准备结束时触发，不能单独限制持续工具调用。

完成判定需要区分候选答案、执行结束与目标达成。
具有可执行验收规则的任务，应检查产物或外部状态；开放任务需要声明评价标准和人工介入条件。
选择哪种内部架构，都不能以模型自述或流程结束代替结果证据。

#### 4.8.5 验证依据与演进

DSH 的接口依据见 [Agent 运行类型](../packages/core/agent/src/runtime-types.ts)，默认循环实现见 [Agent Loop](../packages/core/agent-loop/src/agent.ts)，现有拦截行为见[循环拦截用例](../packages/core/agent-loop/tests/interception.spec.ts)。
这些依据支持公共接口与默认循环的行为判断；混合或 Workflow 型 Provider 需要分别验证自己的阶段转换、输入接纳、错误处理、取消收敛与请求重建。

架构比较应在相同「任务、可用能力与资源预算」下进行，观察成功率、总成本、延迟和人工介入，并检查失败路径和验收依据，见 [Agent Evaluation](#76-agent-evaluation质量度量与回归决策)。
更少的模型决策不自动意味着更高的任务成功率。

**Roadmap（本文建议）**：任务探索成本过高时，评估将稳定步骤固化为阶段或流程节点；固定流程频繁遇到未覆盖情况时，评估在对应节点增加局部自治。按实际失败补充累计预算、进展信号和完成检查；确有跨进程续行需求时，再设计内部执行状态的持久化与副作用恢复。

### 4.9 用户交互：命令、询问、批准与反馈

**需求与约束**

用户可以控制 Agent 运行、补充信息、批准操作或评价结果。
本节说明这些交互分别表达什么意图、产生什么效果，以及答复失效、等待取消和处理失败时如何处理。

普通任务输入与运行中引导见 [Controller 与入口 Agent](#322-controller-与入口-agent)，权限策略与实际隔离见[执行安全](#410-执行安全策略与隔离)，界面和协议接入见[场景协调](#412-controller场景协调与入口适配)。

**Pattern**：按意图区分交互，避免同 1 个“确认”被解释为不同决定。

| 交互       | 用户表达的意图                       | 处理结果                       |
| ---------- | ------------------------------------ | ------------------------------ |
| 命令       | 执行明确的控制操作，例如切换模式     | 对应处理函数执行操作并返回结果 |
| 询问与答复 | 补充任务所需的信息，例如选择目标目录 | 发起询问的工具或插件取得答复   |
| 批准与拒绝 | 决定某项具体操作是否获得许可         | 执行方据此放行或拒绝该操作     |
| 反馈与评价 | 对已有过程或结果提供意见             | 保存意见，供后续分析           |

每次交互需明确关联的 Agent、请求或评价对象，并区分等待中、已完成、已取消和不可用等状态。
DSH 通过 Commands、User Questions、User Approval 和 Feedback 分别承接这些职责。

#### 4.9.1 命令与询问：控制和信息输入

**命令由用户主动发起。** DSH 直接解析并分发给注册的处理函数，无需模型判断命令含义。处理函数可以修改设置、取消执行或向 Agent 提交引导信息。命令输入、直接返回的文本和调用记录不会自动进入模型上下文；需要模型参与时，由处理函数显式提交输入。具体规则见 [Commands](../packages/interaction/commands/README.md)。

**询问由执行中的工具或插件发起。** 答复应交回对应的请求，再由发起方决定如何继续；例如，询问工具将用户选择作为工具结果提供给模型。计划确认可以使用专门的表单，但改变展示方式不会改变答复含义，也不会自动授予工具执行权限。

DSH 对携带 Agent 的询问，只接受当前存活且未被其他 Agent 管理的入口 Agent；活跃子 Agent 需将未解决的问题交回父 Agent。恢复后的提问资格按当前运行身份判断。
缺少交互 Provider、请求失效或等待取消时，需明确返回失败；保存过问题并不意味着重启后能继续原来的等待。
调用资格与答复格式见 [User Questions](../packages/interaction/user-questions/README.md)。

#### 4.9.2 批准：有限许可与失败处理

**Invariant（需要审批的操作）**：只有收到与当前请求对应的明确许可，操作才能执行。拒绝、取消、无人答复或处理失败均不能视为允许。批准只表示获得许可，操作是否成功仍需查看执行结果；取消等待也不能撤销已经提交到外部系统的动作。

**DeepSeek Mapping**：DSH 的审批请求必须属于尚未结束的 Turn，结果为单次允许、拒绝、取消或不可用。策略 `ask` 允许向已配置的答复方请求决定，`never` 表示需要审批时自动拒绝。当前许可只用于本次操作，不提供长期授权及其撤销存储。审批请求与决定记入日志，模型通过发起方提交的工具结果获知处理情况，审批记录本身不进入模型上下文。

用户作出决定前，需要看到足以判断操作影响的信息。
DSH 当前审批请求包含工具名称、原因和可选调用标识，不包含完整工具参数；如果需要核对完整命令、目标资源或修改内容，就需补齐请求与展示数据。审批结果、记录与失败规则见 [User Approval](../packages/interaction/user-approval/README.md)。

#### 4.9.3 反馈：不可变备注与可编辑评价

DSH 提供 2 类反馈，当前均用于评价与分析，不进入模型上下文，也不直接引导后续执行。

| 类型     | 评价对象与修改方式                                           | 提交后的含义                                     |
| -------- | ------------------------------------------------------------ | ------------------------------------------------ |
| 会话备注 | `/feedback` 追加意见，重复提交分别保留，不能修改或撤回旧备注 | 确认表示已追加到内存日志，不保证已写入磁盘       |
| 消息评价 | 对指定模型回复给出正负评价和备注，支持修改与删除             | 保存前确认目标消息已持久化；版本不匹配时返回冲突 |

会话备注可按部署策略触发会话遥测共享，确认信息需说明当前共享行为；进入发送队列不代表接收端已收到。
消息评价不触发该共享，fork 会话也不复制原有评价。
消息评价的版本检查只协调同 1 服务实例内的写入，不保证跨进程修改互不覆盖。

记录与存储分工见[建立事实系统](#57-建立事实系统日志持久化与投影)，具体提交规则见[会话反馈](../packages/feedback/command-feedback/README.md)与[消息评价](../packages/feedback/message-feedback/README.md)。
若让模型使用反馈，需要明确选择哪些内容，并通过可记录的输入路径提交。

#### 4.9.4 验证依据与演进

验证应覆盖答复是否交给正确请求，以及重复答复、过期请求、缺少 Provider、取消等待和审批拒绝时的结果；命令还需验证实际控制效果，反馈需验证保存确认与并发冲突。
每个入口都需验证请求展示、答复返回和执行继续的完整过程，注册了服务不等于入口已经支持交互。

实现依据见各小节的服务文档，通用调用关系见[组织调用](#55-组织调用适配器注册表与执行分发)。

**Roadmap（本文建议）**：审批信息不足时补齐行动预览；入口行为不一致时建立共享交互用例；确需跨重启等待时保存交互状态并重新关联执行者；反馈需影响后续任务时，再设计明确的模型输入规则。

### 4.10 执行安全：策略与隔离

**需求与约束**

Agent 可以读写文件、启动进程和访问外部服务。
执行安全负责确定并落实访问限制，本节涵盖凭证与身份、权限策略和执行隔离。

**Pattern**：提示词告知规则，执行组件检查权限，操作系统或远程环境实施隔离。文件、网络、进程和凭证需分别确定保护范围，保证只适用于已接入限制的调用路径。

#### 4.10.1 凭证、授权与身份

API Key、访问令牌等凭证用于访问外部服务。
DSH 的 Credentials Provider 负责存取，Authorization Flow 通过登录、验证码等交互取得凭证。
身份认证确认调用者是谁；DSH 的 Anonymous User ID 只关联遥测、反馈与请求，不能作为认证依据。
实现机制见[落实安全](#59-落实安全策略解析执行点与隔离机制)。

配置应通过凭证引用或记录键关联凭证，使用方在需要时读取实际值，界面只展示是否配置及来源等描述。
产品 CLI 下，本地凭证来源依次为：启动时继承的环境、受管凭证文件、项目 `.env`、Harness Home 的 `.env`，前者优先。
来自继承环境的值不可通过凭证服务修改，写入会被拒绝；具体规则见 [Credentials Local](../packages/credentials/credentials-local/README.md)。

Authorization Flow 在本次尝试中通过 Credentials 提交凭证，Authorization 服务观察到提交后才确认完成，避免将已有凭证误作本次授权结果。
同 1 凭证键只允许 1 个授权流程运行；当前流程不能跨重启恢复，删除本地凭证也不等于向签发方撤销授权。
流程与失败处理见 [Authorization](../packages/credentials/authorization/README.md)。

凭证保护还需覆盖存储和输出：

- **存储访问**：本地凭证文件在 POSIX 上采用文件 `0600`、目录 `0700`，阻止其他操作系统用户访问。同用户运行的工具仍可能读取；默认 `workspace-write` 主要限制写入。若需向工具隐藏凭证，应将凭证存取与工具执行环境隔离。
- **输出脱敏**：配置返回、错误、日志和传输内容都可能泄露凭证。当前 Settings 只遍历 Object／Dict／Array，不能完整处理 Union、Intersection、Transform 中的敏感字段，序列化 Schema 中的默认值也可能泄露。远程可见的设置需遵守这些限制，见 [Settings 已知限制](../packages/settings/settings/README.md#known-limitations-and-deferred-work)。

#### 4.10.2 策略解析与执行点

DSH 按职责管理权限，没有统 1 包办所有权限的策略服务。

| 规则         | 管理与执行职责                                                         |
| ------------ | ---------------------------------------------------------------------- |
| 沙箱策略     | Sandbox Policy 解析本次模式与工作区，FS／Shell 等组件按策略执行        |
| 审批策略     | Approval 管理`ask`／`never`，语义见[批准](#492-批准有限许可与失败处理) |
| 工具调用规则 | 插件注册允许、拒绝或请求审批的规则，由 Tool Runtime 执行               |

Permission Presets 组合沙箱模式与审批策略。
工具可见范围由 [Tool Runtime](../packages/core/tools/README.md) 另行管理，隐藏工具本身不构成权限隔离。

**SandboxMode 是沙箱执行策略的 1 部分**，表达文件操作的限制类别：

| 模式                 | 受该策略约束的文件操作               |
| -------------------- | ------------------------------------ |
| `read-only`          | 禁止修改文件，保留后端声明的必要例外 |
| `workspace-write`    | 允许写入工作区及后端声明的临时目录   |
| `danger-full-access` | 跳过 DSH 沙箱隔离，仍受宿主权限约束  |

Sandbox Policy 按“本次显式批准的模式 → Session 最近 1 次模式 → 部署默认值”的优先级取值；工作区使用 Session Header 中的固定 `cwd`，缺失时采用部署回退目录。
Consumer 将解析后的策略交给执行 Provider，而不是自行读取配置推断权限。

```text
操作请求 → 解析有效策略 → 检查本次操作
                       ├─ 拒绝 → 返回原因
                       ├─ 允许 → 按策略执行 → 返回结果
                       └─ 需要审批 → 取得许可后按批准范围执行
```

模式变更写入 Session，供恢复和后续模型请求使用；默认值与变更生效规则见[配置与设置](#44-配置与设置系统结构与运行参数)。
当前模式不包含网络、进程或凭证的独立权限策略，也不保证敏感文件不可读取。

#### 4.10.3 平台机制与隔离强度

**DeepSeek Mapping**：Sandbox Seam 定义进程沙箱接口，Provider 提供隔离机制，Consumer 在启动进程时调用。DSH 的受限 Bash／PowerShell 命令及持久终端使用这条路径，限制覆盖进程及其子进程；文件服务等能力按各自实现落实策略。

本地 Provider 在 Linux 优先使用 Bubblewrap，再尝试 Landlock；macOS 使用 Seatbelt；Windows 使用 ACL Restricted Token。Windows ACL 与部分旧 Linux Kernel 上的 Landlock 标记为 `partial`（部分限制），调用方需保留这一事实。平台例外与运行器检查见 [Sandbox Local](../packages/sandbox/sandbox-local/README.md)。

**Invariant（声明受限的执行路径）**：需要隔离时，必须使用能落实本次策略的执行机制。沙箱不可用时返回 `SANDBOX_UNAVAILABLE`，不能自动改为无限制执行。裁决与执行结果需分别记录，并区分权限拒绝、沙箱故障与程序自身错误。

DSH 将进程内插件和部署配置视为受信任代码。
插件直接调用宿主 API，或能力没有接入策略检查时，不会自动受到工具沙箱限制。
Cordis Scope 的服务可见性、Worker Thread 的执行与终止机制，以及 `node:vm` 的代码上下文，都不能替代不受信任代码所需的权限隔离。

#### 4.10.4 验证依据与演进

验证需从真实执行点检查允许与拒绝、路径别名、跨工作区写入、部分隔离、沙箱不可用和审批后失败。
凭证检查覆盖文件读取、配置返回与诊断输出，包括同用户工具的访问。

补充实现依据： [Sandbox Policy](../packages/sandbox/sandbox-policy/README.md)、[Sandbox](../packages/sandbox/sandbox/README.md)和 [Permission Presets](../packages/interaction/permission-presets/README.md)。

**Roadmap（本文建议）**：按实际缺口补齐遗漏的策略检查和凭证脱敏；需要限制网络或读取时增加对应策略；需要运行不受信任插件时引入进程与权限隔离；远程执行还需明确权限如何传递、验证与撤销。

### 4.11 编排：任务与多 Agent 协作

**需求与约束**

任务是要达成的目标，Turn 是 1 次执行轮次。
1 轮内可以多次请求模型、调用工具；该轮结束后，用户后续输入、Goal 续行或 Schedule 到期都可以触发新1 轮。
因此，同 1 任务可以跨多个 Turn，中间不 1 定有用户交互。

本节讨论任务如何持续推进、何时执行、交给谁执行，以及如何收回结果。
单个 Agent 内部的执行方式见[执行控制](#48-执行控制自治度与确定性)，输入接纳规则见 [Controller 与入口 Agent](#322-controller-与入口-agent)。

**Pattern**：按任务需要选择机制，可以组合使用；增加并发前，先确认工作能独立推进。

| 任务需要                   | 对应机制              |
| -------------------------- | --------------------- |
| 记录目标、协作方式和待办   | Goal／Plan Mode／Todo |
| 1 轮结束后继续未完成目标   | Goal Round Driver     |
| 管理已启动的耗时工作       | Jobs                  |
| 在未来时间继续任务         | Schedule              |
| 按步骤、分支和并发关系执行 | Workflow              |
| 将独立任务交给其他 Agent   | Subagent              |

每项工作都需明确由谁启动、停止和释放资源，结果交给谁，以及重启后如何处理。
调用返回、工作完成和目标达成分别需要对应依据。

#### 4.11.1 会话内协作状态

Goal 保存持续目标及推进状态，Plan Mode 表达协作方式，Todo 保存短期事项清单。
DSH 没有强制 Goal → Plan → Todo 的固定关系；更新 Todo 不会自动启动任务，Plan Mode 也不提供权限隔离。

**DeepSeek Mapping**：DSH 每个 Agent 只保留 1 个当前目标，以带修订号的快照记录变化，通过版本比较拒绝过期修改。Goal Round Driver 在 Agent 空闲、目标处于 active、续行已启用且预算有余量时投递下 1 轮输入。例如，第 1 轮完成实现，目标仍未完成，Driver 可以触发下 1 轮，由 Agent 继续验证，无需用户再次发送消息。

`maxGoalRounds` 只限制已接纳的目标轮次，不计普通用户轮次，也不限制 token、时间或费用。
目标状态可以恢复，自动续行许可只在当前进程有效；恢复会话、fork 或替换 Driver 后，需要显式重新启用。
具体机制见[推进执行](#54-推进执行状态机队列与调度器)。

**Invariant（目标完成判定）**：记录完成状态只表示调用方声明目标已达成。DSH 不提供独立的成功认证器，仍需用产物、测试或外部结果证明完成。

#### 4.11.2 异步任务与调度

**Jobs 管理已经启动的后台工作，Schedule 决定未来何时提交任务。**
2 者的停止、等待和恢复规则不同。

DSH Jobs Local 将工作绑定到具体 Agent 实例及后台执行方。
请求停止后，任务仍处于 Stopping，继续占用并发容量，直到执行方确认结束；取消等待只结束本次等待，不会停止任务。Agent 释放时会取消所属任务并等待结束，启动任务的插件或 Controller 重载则不终止任务。
当前任务记录只在进程内存在，
重启后不恢复。接口与释放规则见 [Jobs Local](../packages/jobs/jobs-local/README.md)。

DSH Schedule 支持延迟、指定时间和固定周期，周期最短为 5 分钟。它保存触发条件与派发记录，到期后等待 Agent 空闲，再通过 Follow-up 提交任务，不打断当前 Turn。

```text
保存定时任务 → 会话运行期间计时 → 到期并等待 Agent 空闲
→ 提交 Follow-up → 保存派发记录 → 后续 Turn 处理任务
```

未运行的会话没有活动计时器，恢复为运行中的会话后才处理过期任务；周期任务只处理最新到期项，不补跑全部错过的次数。
Fork 不继承父会话提醒。
当前插件只接入装载后创建的根 Agent，不接管已有实例或子 Agent，详见 [Schedule](../packages/schedule/schedule/README.md)。

创建和实际删除需保存成功后才确认。
派发时，若 Follow-up 已入队而派发记录尚未持久化就崩溃，恢复后可能重复提交。
派发也不证明模型已完成任务或用户已读；离线准时执行、外部通知和避免重复副作用，需要额外机制。

#### 4.11.3 Workflow：流程主导的编排

本节的 Workflow 在任务层组织步骤、分支和并发，并在指定节点调用 Agent。
单个 Agent 内部采用显式流程的设计见 [Workflow 主导](#483-workflow-主导agent-内部的显式流程)。

DSH Workflow 由独立 Engine 接收脚本并返回运行对象，接口独立于 Agent Driver。
调用方负责收集结果、取消和释放；卸载 Engine 只阻止新运行，已接纳的运行仍由调用方管理。

Worker Provider 限制并发数与总子任务数，在取消或 Worker 失败时清理启动中和已启动的子任务。Worker Thread 避免脚本计算阻塞 Host Event Loop，并支持强制终止；它的隔离范围见[平台机制与隔离强度](#4103-平台机制与隔离强度)。

显式脚本固定控制顺序，但模型生成的脚本仍需校验，模型节点和外部调用的结果也可能变化。
取消不能撤销已经发生的外部操作，恢复业务状态需另行设计幂等与补偿。

当前实现没有持久检查点、跨重启恢复或统 1 的跨 Agent token 预算；并发上限不能代替总成本限制。
接口与执行规则见 [Workflow](../packages/workflow/workflow/README.md)和 [Worker Provider](../packages/workflow/workflow-worker-thread/README.md)。

#### 4.11.4 子 Agent：执行主体委派

子 Agent 适合输入、职责和交付结果明确的独立任务。
父 Agent 提供任务、约束、必要上下文和验收标准，收集回报并核查证据后继续推进。

| 模式                  | 使用方式                   | 结束与后续交互                                      |
| --------------------- | -------------------------- | --------------------------------------------------- |
| One-shot（1 次性）    | 启动 1 次子任务，等待结果  | 通过请求的取消信号停止，调用方收集结果并释放资源    |
| Continuable（可续行） | 保留子会话，可继续发送任务 | 当前轮中断与整体释放分开处理，后续消息经 Inbox 排队 |

DSH 的可续行子 Agent 可以根据已保存的会话重新创建执行实例，这称为冷恢复。
续行管理器负责当前实例的存续，后续任务直接进入子 Agent 的 Inbox，无需另建 Job。
消息入队不代表已经开始或完成，详细结果保存在子会话中。

父子消息按当前活跃实例及父子关系校验权限。
回报要求父 Agent 在线；通知已接收不代表父级已消费，父级消失或释放时也没有持久信箱保证送达。
不能只凭相同 Session ID 接管旧实例的权限。

各 Provider 的上下文、恢复和权限能力需分别确认。
`inheritsParentContext` 只表示继承已完成对话；进程内子 Agent 的权限固定于委派时，不能自行扩大。
当前可续行管理依赖本地 Agent 生命周期，不能推断远程 Provider 同样支持。
实现与限制见 [Subagent](../packages/subagent/subagent/README.md)。
Agent Team 仍属实验方向，尚非稳定产品接口。

#### 4.11.5 验证依据与演进

验证重点是任务能否正确继续和结束：目标恢复后需重新启用、后台停止需等待执行方结束、定时派发可能重复、Workflow 启动中取消需清理子任务，以及子 Agent 冷恢复和父级释放时的回报处理。
并发任务还需检查重复工作、文件冲突、结果遗漏和总资源消耗。

实现依据见各小节链接及 [Goal](../packages/goal/goal/README.md)、[Goal Round Driver](../packages/goal/goal-round-driver/README.md)，通用调度机制见[推进执行](#54-推进执行状态机队列与调度器)。

**Roadmap（本文建议）**：按需求补齐目标完成评估与资源预算、后台任务持久化、Workflow 检查点与幂等处理；扩大跨 Provider 协作前，明确结果交付、授权和取消保证。

### 4.12 Controller：场景协调与入口适配

**需求与约束**

Controller 将用户或程序的操作交给对应的 Agent 或业务服务，并向调用方返回结果。
本节讨论不同入口如何选择调用方式、输出形式和连接结束后的处理规则；会话定位与输入投递见 [Controller 与入口 Agent](#322-controller-与入口-agent)。

例如，同样提交“修复 BUG”，命令行可以等待执行结束后输出答案，浏览器可以先确认接收，再持续展示进度。
两者复用 Agent 能力，但需要各自定义何时返回、返回什么，以及用户断开连接后是否继续执行。

**Pattern**：单次任务适合直接调用 Runtime 并等待结果；长期交互需要管理会话、订阅事件；外部程序通过协议调用，SDK 再将协议操作封装为语言接口。选择入口时需同时考虑交互需求、连接寿命和结果交付方式。

#### 4.12.1 使用方与交互方式

**DeepSeek Mapping**：DSH 为不同使用方提供以下入口。

| 入口                         | 使用方                                 | 交互方式                                       |
| ---------------------------- | -------------------------------------- | ---------------------------------------------- |
| Headless                     | 在命令行执行任务的用户                 | 提交 1 次任务，等待答案后退出                  |
| Web                          | 在浏览器中使用 Agent 的用户            | 持续对话、查看进度、管理多个会话               |
| ACP（Agent Client Protocol） | 支持 ACP 协议的其他程序                | 通过协议创建会话、提交任务、接收答案或取消执行 |
| SDK                          | 用 TypeScript／Python 开发应用的开发者 | 在代码中调用接口，操作 Agent 并获取结果与状态  |

这些入口复用 Harness 能力，由各自的 Controller 适配操作和结果。入口选择取决于使用方及其交互需求。

#### 4.12.2 业务分发、传输与客户端投影

Headless 直接调用 Runtime，不启动服务端口。ACP 与 SDK 都通过标准输入／输出传输 JSON-RPC 消息，但使用不同协议；ACP 的 stdout 专用于协议帧。

「通过协议调用 Harness 的入口」需要分别处理业务操作、协议调用和客户端展示。
以 DSH Web 为例：

| 组件                            | 职责                                                   |
| ------------------------------- | ------------------------------------------------------ |
| API Remotes                     | 提供业务操作，解析操作对应的 Agent、Session 等对象     |
| Typert Gateway                  | 按生成的类型描述校验参数和返回值，分发调用             |
| Connection                      | 传输请求与事件，关联请求和响应，检查请求来源并封装响应 |
| Client Projection（客户端投影） | 将事件与查询结果组织成界面状态                         |

参数校验通过只表示输入符合接口要求。
是否允许操作目标 Agent，仍需在对象解析和业务操作处检查；浏览器传入 Session ID 不会自动获得控制权。

业务调用通过请求与响应返回结果，任务进度和新增会话消息通过事件流持续推送。
组件调用关系见[跨越进程](#510-跨越进程协议流序列化与远程生命周期)。

客户端恢复连接后，需要按数据来源补齐状态。
DSH 的 Remote 转发事件不在重连后重放，客户端需重新查询对应领域状态；Session 记录的恢复规则见[建立事实系统](#57-建立事实系统日志持久化与投影)。

#### 4.12.3 结果返回与连接清理

**结果返回**：入口需要明确何时结束响应，以及响应包含哪些输出。DSH 的两种等待式入口分别采用以下规则：

- **Headless**：等待 Agent 停稳、Session 写入存储后，输出本次执行区间内最后一条非空 Assistant 文本；以最终 Turn 的完成状态决定退出码。
- **ACP**：每会话同时最多处理 1 个 Prompt 请求，等待输入接纳、Agent 整体空闲和输出发送完成后结束响应。期间补充的引导（Steering）也可能贡献结果，因此返回内容（`end_turn`）不 1 定只对应最初提交的 Prompt。

退出码和协议结束原因不证明业务目标达成，判定依据见[完成、失败与结果归属](#326-完成失败与结果归属)。

ACP 只发送已提交的 Assistant 文本与图片，避免将未提交的模型增量和重试内容作为答案，代价是无法逐 Token 输出。
图片读取失败也会使响应失败。
实时展示与可恢复记录的区别见 [Session 事实与场景输出](#325-session-事实与场景输出)。

**连接清理**：每项已接纳操作都应明确由谁负责停止和清理。Controller 只能控制有权操作的 Agent 实例，并按入口约定决定断连后继续执行还是取消释放。发出取消请求不表示工作已经结束，等待与释放规则见[运行中控制与状态收敛](#332-运行中控制与状态收敛)；外部副作用和后台任务分别遵守所属服务的约定。

DSH ACP 将 Agent 的生命周期绑定到连接。
断连时先停止接纳新请求，取消并等待本连接的输入接纳、Agent 活动和输出结束，再清理所属 Agent 的可续行子 Agent，释放所持有的 AgentHandle。
同 1 Context 中其他入口管理的 Agent 不受这次清理影响。
当前 ACP 只创建新会话，不支持会话恢复或完整交互界面，具体限制见 [ACP](../packages/acp/acp/README.md)。

#### 4.12.4 风险、依据与演进

验证重点是操作发给正确会话、返回时机符合协议，以及取消、断连和输出失败后资源能正确清理。
还需覆盖重连补齐状态与冷会话恢复。
协议客户端应通过真实序列化与进程入口验证 stdout 只包含约定输出、错误映射及客户端状态更新；同进程方法调用不能替代这些检查。

实现依据见 [Headless](../packages/bundle/headless/README.md)、[ACP](../packages/acp/acp/README.md)、[API Gateway](../packages/api/gateway/README.md)、[Connection](../packages/client/connection/README.md)、[Host API Proxy](../packages/host/apiproxy/README.md)与 [SDK](../packages/sdk/README.md)。

**Roadmap（本文建议）**：新增入口先验证会话、取消和输出规则；需要跨入口保持一致的行为建立共享用例；独立发布客户端时增加协议兼容策略；断线期间必须可靠送达的事件增加可恢复记录与接收确认。

### 4.13 运行可靠性：故障、取消与恢复

**需求与约束**

模型、Tool、插件、存储和外部系统都可能失败，进程也可能在操作中途退出。
运行可靠性要求系统能够确定受影响的工作、停止依赖它的后续执行、保留仍然有效的事实，并明确结果是成功、失败、取消还是未知。
本节讨论故障处理、取消收敛、恢复和外部副作用；具体发生顺序见[控制与恢复主链](#33-控制与恢复主链)，部署容灾见[生产运营](#83-生产运营部署发布韧性与灾备)。

#### 4.13.1 故障归属与安全状态

处理故障的组件需要知道该故障代表什么，以及失败后哪些状态仍然可信。
可预期的失败应提供稳定类型和处理所需的信息；无法解释的内部异常应停止依赖当前结果的工作，并由拥有受影响状态的组件决定能否继续。

| 故障位置 | 处理责任 |
| -------- | -------- |
| 模型或 Tool 调用 | 调用方根据结构化结果决定重试、继续或结束当前执行 |
| Agent 执行 | Agent Driver 结束受影响的 Step 或 Turn，并记录已确定的结果 |
| 存储与恢复 | 数据所有者拒绝无效记录，保留可验证的已提交内容 |
| 协议与入口 | Controller 向调用方报告失败，并按场景决定是否取消或释放 Agent |
| 外部系统 | 对应能力确认副作用状态，决定复查、重试、补偿或人工处理 |

捕获异常只阻止异常继续传播，不会撤销已经发生的状态修改。
日志记录也不表示系统已经恢复；只有状态所有者重新建立约束，或丢弃受影响状态并停止相关工作，才能安全继续。

**DeepSeek Mapping**：DSH 将普通 Tool 失败保存为结构化 Tool Result，使模型可以在后续 Step 处理；模型请求无法继续时，Agent Loop 结束当前 Turn。
插件或结果处理中的异常不会被转换成成功。
错误处理与结果归属见 [Agent Loop](../packages/core/agent-loop/README.md)和 [Tools](../packages/core/tools/README.md)。

#### 4.13.2 取消、超时与停止完成

取消是停止请求，只有受影响的工作结束并完成资源清理后，停止才算完成。
各层通过 Signal 协作取消；不响应 Signal 的实现可能继续运行，因此调用方不能把“已发出取消”当作“已经停止”。

超时限定某项操作允许等待的时间，并由对应组件转换为失败或取消结果。
模型请求、Tool、进程和入口可以采用不同超时；局部超时不能自动构成覆盖整个任务的 Deadline。
退出码、Signal、是否超时和部分输出是可以同时成立的结果，应分别记录，不能用其中一项推断其他项。

资源所有者负责停止并等待其创建的 Agent、Job、Workflow、子 Agent、进程和监听器。
释放操作需要达到静止状态（quiescence）：不再接纳新工作，受管工作已经结束，迟到回调不会继续修改已释放状态。
各对象的具体规则由所属领域维护，见[插件运行时](#41-插件运行时依赖与生命周期)、[Agent](#45-agent执行主体与生命周期)和[编排](#411-编排任务与多-agent-协作)。

#### 4.13.3 会话恢复与未决工作

恢复是使用持久事实创建新的运行时对象，不是让原进程中的对象继续存活。
Session 可以重建模型历史和领域状态；连接、计时器、句柄、进程及其他内存资源需要重新创建，并分别确认是否支持恢复。

DSH 从持久日志恢复 Session 时保留已完整写入的事件，并修复中断的 Turn、Step 和 Tool 历史。
未开始的 Tool Call 记录为未执行；已经开始但没有结果的调用记录为结果未知。
恢复不会自动重放历史模型请求或 Tool Call，避免把未知副作用再次执行。
Session 持久化与恢复约定见 [Session Persistence](../packages/session/session-persistence/README.md)。

持久 Session 不等于所有任务都可恢复。
例如，进程内 Job 重启后消失，Workflow 没有检查点时不能从中间继续；Schedule 和可续行子 Agent 则按各自保存的事实与运行条件恢复。
调用方需要针对每种对象分别确认保存内容、恢复入口和未决工作的处理方式。

#### 4.13.4 重试、幂等与补偿

外部操作通常跨越 Harness 与目标系统，不能假定与 Session 写入属于同 1 个事务。
如果外部状态已经改变，但进程在结果写入 Session 前退出，恢复后只能确定结果未被记录，不能断言操作没有发生。

安全处理取决于具体能力：优先查询目标状态；可以重复提交时使用幂等键；接收方可能重复处理时使用去重记录；已经提交且需要撤销时执行明确的补偿操作。
无法确认结果时，应显示未知状态并停止依赖该结果的工作，必要时请求人工确认。

重试必须有明确所有者、适用错误、次数或时间预算，并响应取消。
只有暂时性失败且操作可安全重复时才能自动重试；模型重新调用工具也遵守相同条件。
完整的副作用时序见[副作用交付、幂等、去重与补偿](#3351-副作用交付幂等去重与补偿)。

#### 4.13.5 验证依据与演进

验证需要观察最终状态，而不只是确认异常被捕获：取消后受管工作应停止，释放后不应留下活动资源，恢复后历史关系应完整，未知副作用不得显示为成功，重试不得重复产生不可接受的操作。

DSH 的实现依据见 [Agent Loop](../packages/core/agent-loop/README.md)、[Session Persistence](../packages/session/session-persistence/README.md)、[Jobs Local](../packages/jobs/jobs-local/README.md)、[Workflow](../packages/workflow/workflow/README.md)和 [Subagent](../packages/subagent/subagent/README.md)。

**Roadmap（本文建议）**：需要跨组件控制总时限时增加端到端 Deadline；后台工作需要跨进程延续时增加持久任务状态和恢复调度；需要自动恢复外部操作时，由对应能力提供状态复查、幂等和补偿约定。

### 4.14 运行观测与诊断

**需求与约束**

Harness 需要回答某次任务接收了什么输入、执行到哪里、调用了哪些能力、产生了什么结果，以及失败发生在哪个对象和阶段。
运行观测负责产生和关联这些信息，诊断负责根据它们定位问题并说明影响与处理方式。
测试与 Agent 效果评估见[验证与交付保障](#七验证与交付保障)，生产监控与 SLO 见[生产运行与治理](#八生产运行与治理)。

#### 4.14.1 观测信息及其用途

不同信息承担不同职责，不能互相替代。

| 信息 | 用途 | 保证范围 |
| ---- | ---- | -------- |
| Session Events | 保存模型可见输入、输出、Tool 结果和领域状态 | 持久事实，可用于恢复和重建 |
| Agent／Capability Events | 通知运行中的状态变化 | 实时协作，是否持久化由所属机制决定 |
| Logs | 报告插件、路径、失败原因和清理结果 | 面向本地诊断，不是业务状态来源 |
| Telemetry | 将选定的事件、用量、时延和结果交给外部分析系统 | 由采集与传输策略决定，通常不保证送达 |
| Runtime Invariant | 检查运行中对象之间必须成立的关系 | 发现关系错误，不证明任务目标达成 |

Session 是模型执行事实的权威来源；Telemetry 是面向观测系统的副本。
丢失 Telemetry 不应改变 Agent 行为，Telemetry 已入队也不表示接收端已经保存。

#### 4.14.2 关联与定位

观测记录需要携带足以定位所属工作的标识，例如 Session、Agent、Turn、Step、模型请求、Tool Call、Job 或 Workflow Run。
同一操作跨越模型、工具、存储和外部系统时，各层应保留已有标识或建立明确关联，避免只能按时间猜测因果关系。

诊断信息应指出失败对象、执行的操作、违反的规则、已知影响和安全的下一步。
如果结果或状态无法确认，诊断需要明确标记未知，不能用普通错误文本掩盖不确定性。
面向用户的报告还需隐藏凭证和不必要的内部信息，并通过当前入口可见；只写入无人读取的日志不能解决用户正在等待的问题。

#### 4.14.3 观测失败与数据控制

观测代码不能破坏被观测的执行。
事件分发应隔离单个观察者的异常，使其他观察者继续接收；采集或导出失败应报告自身问题，而不是把业务执行改写为失败或成功。
但负责强制策略的拦截器不属于普通观察者，其拒绝结果仍应影响执行。

Telemetry 可能包含提示词、文件内容、Tool 输出和错误详情。
部署方需要在离开进程前决定采集范围、授权、脱敏、保留和删除策略；用于导出的副本可以脱敏，但不能因此改写权威 Session 日志。

**DeepSeek Mapping**：DSH Session Telemetry 可以实时复制 Session 事件，也可以按需读取日志前缀；记录通过 `session-telemetry/record` 处理后交给 Backend。
采集交接是非阻塞且尽力而为，进程崩溃可能丢失队列中的记录；Backend 的 `sharing` 状态和提交反馈都不是送达回执。
当前 OTel Backend 只在明确反馈授权后导出 Session 记录，脱敏规则仍由部署方提供。
实现约定见 [Session Telemetry](../packages/session/session-telemetry/README.md)和 [Session Telemetry OTel](../packages/session/session-telemetry-otel/README.md)。

#### 4.14.4 Invariant 与诊断闭环

Runtime Invariant 应检查某个组件拥有的真实关系，例如已发布 Agent 与 Session 的绑定、已接受运行与其释放责任、Tool Call 与结果的配对。
检查 Service 或方法是否存在，只能说明组件可被查找，不能证明这些运行关系成立。
没有可观察关系时，不应为满足形式而添加固定示例式检查。

发现异常后，诊断还需要连接到处理动作：阻止无效状态继续传播、释放受影响资源、保留可核查事实，并向对应用户或运维入口报告。
是否能够继续执行由状态所有者判断，观测系统本身不负责恢复业务状态。

#### 4.14.5 验证依据与演进

验证应从真实执行入口制造成功、失败、取消和恢复场景，检查记录是否完整关联、敏感内容是否按策略处理、观察者失败是否被隔离，以及诊断是否能指向受影响对象和下一步。
Telemetry 测试还需区分采集、入队、发送和接收，不能只凭一次 `emit` 断言外部系统已收到记录。

DSH 的事实与事件依据见 [Session](../packages/core/session/README.md)和 [Agent](../packages/core/agent/README.md)，Telemetry 实现依据见 [Session Telemetry](../packages/session/session-telemetry/README.md)与 [OTel](../packages/telemetry/otel/README.md)。验证方法见 [Runtime Invariant、可观测性与诊断](#72-runtime-invariant可观测性与诊断)。

**Roadmap（本文建议）**：统一跨 Agent、模型、Tool、后台任务和外部调用的关联信息；为未知结果和持久失效状态提供默认可见的诊断；按实际运维需求补充低噪声 Invariant、指标和 Trace，并明确各 Telemetry 通道的授权与交付保证。

## 七、验证与交付保障

**预期解决**

证明单个 Package、完整 Plugin 组合、协议投影和发布产物在真实使用路径上保持一致，并判断 Agent 在开放任务中的结果质量与执行代价。

**解决方式**

软件验证按风险选择 Unit、Coverage、Snapshot、Browser、Real-API E2E、Built Smoke 和静态 Gates，并以 Runtime Invariant 和可观测数据验证跨模块关系。Agent Evaluation 使用版本化任务集、运行证据、外部结果和人工反馈评价开放任务。

**底层设计**

```text
工程保障
├── 行为验证：Unit / Contract Regression
├── 组合验证：Loader Smoke / Snapshot / Browser
├── 外部验证：Real-API E2E
├── 产物验证：Build / Built Smoke / Publint
├── 静态验证：Typecheck / Lint / Hygiene / Doc Sync
├── 运行验证：Runtime Invariant / Telemetry / Diagnostics
├── Agent Evaluation：任务结果 / 执行轨迹 / 安全 / 成本 / 时延
└── 治理：Agent Note / Compatibility / Release
```

**坑与对策**

- 用覆盖率代替行为证据：Coverage 证明代码被执行，不证明产品按预期工作。
- 只测试手工组装：产品可见 Plugin 需要通过 Loader 和真实 Composition 验证。
- 断言 Agent 自述成功：重新读取文件、运行命令或检查外部状态。
- 混用源码与构建产物：测试默认走 Source Plane，发布入口显式走 Artifact Plane。
- 全量测试成为默认动作：按改动面选择最小充分证据，CI 负责完整矩阵。

**长期演进**

让每类新能力在设计阶段声明验证层级，并使本地、CI、SDK、浏览器和发布流程共享一致的证据标准。

### 7.1 测试分层与真实入口

**预期解决**

用成本与真实性不同的测试层覆盖局部逻辑、组合行为、用户输出和真实 Provider。

**解决方式**

Unit 覆盖局部行为与错误路径；Coverage 执行逐文件门禁；Snapshot 固定协议和用户输出；Browser 验证 Web 投影；Real-API E2E 验证真实模型；Built Smoke 验证发布产物。

**底层设计**

```text
Unit
→ Package 行为、边界条件、事件顺序、生命周期清理
Coverage
→ packages/*/*/src 逐文件覆盖门禁
Snapshot
→ Headless / ACP / SDK 的关键输出与持久日志
Browser
→ Web Client 的真实渲染与交互
Real-API E2E
→ 真实模型与 Provider 行为
Built Smoke
→ plain Node 执行发布后的 lib 入口
```

**坑与对策**

- Mock 整条执行链：只 Mock 昂贵或不确定的外部边界，其下游使用真实实现。
- 快照只覆盖测试专用组合：用户可见行为通过真实 Example 与 Loader 入口产生。
- E2E 只匹配输出关键词：验证实际文件、进程、日志或外部状态。
- 改变模型、协议或用户输出却不更新 Snapshot：同一改动同步更新对应场景。

**相似方案**

### 7.2 Runtime Invariant、可观测性与诊断

**预期解决**

验证运行观测能否完整记录事实、关联同一项工作、隔离观察者故障，并提供足以定位问题的诊断。

**解决方式**

从真实入口制造成功、失败、取消和恢复场景，按照[运行观测与诊断](#414-运行观测与诊断)定义的职责检查 Session Events、实时事件、Logs、Telemetry 和 Runtime Invariant。

| 验证对象 | 检查内容 |
| -------- | -------- |
| 事实完整性 | 模型实际看到的内容和已提交结果能否从 Session 重建 |
| 关联关系 | Session、Turn、Step、请求、Tool Call 和后台工作能否对应到同一执行 |
| 故障隔离 | 观察者异常是否影响执行、其他观察者或资源释放 |
| 诊断质量 | 是否指出失败对象、操作、影响、未知状态和安全的下一步 |
| 数据控制 | 导出内容是否经过授权和脱敏，权威 Session 是否保持不变 |
| 交付语义 | 采集、入队、发送和接收是否分别验证，没有把提交误作送达 |

Harness 的证据链应从输入来源连接到外部结果：

```text
Input Source
→ Decision / Action
→ Observation
→ Claim
→ Verification
→ External Outcome
```

Session 事实证明 Harness 内发生了什么，目标系统的状态证明外部结果；测试需要分别核对，不能用其中一项代替另一项。

**坑与对策**

- 只检查事件数量：同时核对顺序、内容、关联标识和最终状态。
- 只验证正常执行：覆盖取消、部分提交、未知副作用、观察者异常和导出失败。
- 用同进程调用代替真实入口：协议、进程和 Telemetry 传输通过相应边界验证。
- 只断言错误存在：同时验证用户或运维入口能够看到影响和处理方式。

**相似方案**

分布式追踪、审计日志和故障注入采用相似验证方式；Harness 还需核对模型历史、工具副作用和非确定性结果。

**长期演进**

建立跨入口的故障场景集，检查关联信息、未知结果、敏感数据处理和诊断可见性，并将稳定关系接入持续验证。

### 7.3 Source Plane 与 Artifact Plane

**预期解决**

防止源码测试因路径映射通过，但发布后的 `lib/`、Worker、CLI 或协议入口实际不可用。

**解决方式**

静态 Gates 和普通测试通过 TypeScript paths 解析 `src`；只有明确验证发布行为的 Built Smoke 和配置子进程消费 `lib/`。

**底层设计**

```text
Source Plane
├── Typecheck
├── Lint
├── Unit Tests
└── Static Generators

Artifact Plane
├── Package Exports
├── CLI bin
├── Worker Entry
├── Config Subprocess
└── SDK / Protocol Distribution
```

**坑与对策**

- 测试意外加载旧 `lib/`：普通测试统一使用 Source Plane。
- 只在 `tsx` 下运行 CLI：发布入口用 plain Node 执行构建产物。
- Worker 或非 index 入口未验证：为每个独立产物入口增加 Built Smoke。
- 同一模块从 `src` 与 `lib` 各加载一次：保持 Compiler Face 和解析路径明确。

**相似方案**

源码测试与安装包测试、开发服务器与生产 Bundle 验证解决同类问题；这里还需覆盖 Worker、配置 Loader 和多 SDK。

**长期演进**

减少源码与产物之间的隐式差异，并让发布前检查自动识别需要验证的 Artifact 入口。

### 7.5 文档、决策与兼容性验证

**预期解决**

让公开行为、设计理由、代码实现和发布兼容性长期保持一致。

**解决方式**

README 与 JSDoc 记录当前接口和行为；Subsystem 文档记录领域语义；Agent Note 记录非平凡决策与取舍；生成目录和文档 Gates 防止结构漂移。

**底层设计**

```text
Current Contract
├── Source Types / JSDoc
├── Package README
└── Subsystem Reference

Decision Rationale
└── Agent Note

Derived Evidence
├── Generated Catalogs
├── Snapshot Fixtures
└── SDK Expected Outputs
```

**坑与对策**

- 多处复制同一事实：保留一个所有者，其他位置使用链接或高层摘要。
- 文档记录变更过程：稳定文档只写当前状态，取舍进入 Agent Note。

### 7.6 Agent Evaluation：质量度量与回归决策

**预期解决**

判断 Agent 是否完成任务、是否安全高效，以及 Prompt、Model、Tool、Skill 或策略变更是否产生真实改进。

**解决方式**

以版本化任务集驱动离线评估，以生产结果和人工反馈驱动在线评估；将结果质量、轨迹质量、安全、成本和时延组合为发布依据。

**底层设计**

```text
Versioned Task Set + Runtime Variant
→ Isolated Execution
→ Transcript + Artifacts + External State
→ Evaluators
   ├── Deterministic Checks：状态、文件、协议与业务规则
   ├── Rule-based Scores：成本、时延、步骤与违规
   ├── Model Judge：开放式语义质量
   └── Human Review：高风险与争议样本
→ Comparable Metrics
→ Regression Gate / Experiment Decision
```

评估对象必须绑定任务集版本、Harness 版本、模型版本、Prompt、工具集合、配置和随机参数。成功证据优先取自外部结果与可重放事实，而不是 Agent 自述。

**坑与对策**

- 将软件测试等同于 Agent Evaluation：测试验证确定性契约，评估衡量开放任务的效果与代价。
- 只比较最终答案：同时检查执行轨迹、副作用、引用、权限、成本和时延。
- 用 Model Judge 作为唯一裁判：确定性结果优先使用规则验证，并以人工样本校准 Judge。
- 在固定题集上持续调参：隔离开发集、回归集和保留集，监测数据污染与评测过拟合。
- 只优化单一成功率：设置安全、成本和时延硬约束，防止 Reward Hacking。

**相似方案**

软件回归测试、机器学习 Benchmark、在线实验和质量抽检共同构成 Agent 评估体系。

**长期演进**

建立按场景分层的 Golden Set、失败分类、轨迹评分、Judge 校准、线上采样和自动回归门禁。

## 八、生产运行与治理

**预期解决**

让 Harness 在多模型、多用户、持续变更和生产流量下保持推理供给可治理、信任关系可审计、服务运行可恢复。

**解决方式**

在运行时机制之外建立三个平台级闭环：模型治理管理推理供给，安全与合规控制跨主体信任，生产运营保障持续交付。Evaluation 为策略和发布提供质量证据，Memory 作为数据领域向运行时提供经过授权的跨会话信息。

**底层设计**

```text
Runtime Facts + Product Outcomes
├── Model Governance：模型选择、容错与版本控制
├── Trust Governance：身份、数据、扩展与审计
└── Production Operations：发布、容量、韧性与灾备

Observed Results → Evidence → Policy Change → Controlled Release → New Results
```

三个治理领域使用 Runtime 事实与 Evaluation 结果，但不反向侵占 Agent、Session、Tool 和 Capability 的运行时所有权。

**坑与对策**

- 将功能齐全等同于可规模化：必须补齐质量决策、风险控制和运营反馈。
- 将平台策略散落在业务 Plugin：跨场景规则由独立治理服务拥有。
- 用单一指标驱动所有优化：同时约束质量、安全、成本、时延和稳定性。

**长期演进**

形成从离线验证、在线观测、策略调整到受控发布的持续改进系统。

### 8.1 模型治理：路由、容错与版本控制

**预期解决**

在多个模型、Provider 和能力版本之间稳定选择推理资源，并控制可用性、成本、时延和行为漂移。

**解决方式**

为模型声明上下文、Tool Calling、Structured Output、多模态和流式能力；Router 根据任务与策略选择候选；执行层实施限流、重试、Fallback 和熔断；版本系统记录完整请求配置。

**底层设计**

```text
Task Requirements + Policy + Budget
→ Capability Matching
→ Model Router
→ Provider Adapter
→ Rate Limit / Retry / Circuit Breaker / Fallback
→ Normalized Stream and Usage
→ Versioned Evidence + Evaluation
```

模型名称不足以定义行为版本；可复现实验还需绑定 Provider、模型修订、System Prompt、采样参数、Tool Schema 和路由策略。Fallback 必须满足调用所需能力，不得只按可用性盲切。

**坑与对策**

- 将不同模型视为完全可互换：路由前验证上下文、协议和输出能力。
- 对所有错误统一重试：只重试暂态且可安全重放的请求，并限制退避与总预算。
- Fallback 改变安全或数据策略：候选模型必须满足相同的数据、地域和权限约束。
- 只记录最终模型名：同时记录路由理由、尝试链、配置版本和用量。
- 直接全量切换新版本：通过离线评估、Canary、A/B Test 和可回滚发布逐步放量。

**相似方案**

API Gateway、服务发现、负载均衡和 Feature Flag 提供相似控制机制；模型治理还需处理能力差异与非确定性输出。

**长期演进**

实现质量—成本—时延联合路由、动态容量感知、Provider 健康评分和自动回退，并以评估结果约束策略更新。

### 8.2 安全与合规：端到端信任治理

**预期解决**

控制不可信输入、模型输出、扩展代码和外部服务带来的越权、数据泄露、供应链与合规风险。

**解决方式**

建立主体、数据、能力和执行环境四类信任关系；在输入、上下文装配、Tool 调用、外部传输和持久化各阶段执行分层策略，并生成可查询审计记录。

**底层设计**

```text
Identity + Workspace + Data Classification
→ Authorization Policy
→ Context and Capability Filtering
→ Approval for High-risk Effects
→ Sandbox / Egress / Secret Enforcement
→ Audit + Retention + Deletion

Extension Trust
├── Tool / Skill / MCP / Plugin Source
├── Version Lock + Integrity Verification
└── Allow / Revoke / Quarantine
```

Prompt Injection 被视为不可信数据影响决策的问题；防护同时依赖来源标注、指令优先级、最小权限、参数策略、批准和执行隔离。批准只授予一次明确操作，不替代 Sandbox、数据策略或审计。

**坑与对策**

- 只在 Prompt 中要求模型安全：关键约束必须由确定性执行点强制。
- 将 Sandbox 当成完整安全系统：还需身份、授权、网络出口、秘密和数据治理。
- 默认信任安装的 Skill、MCP 或 Plugin：记录来源与版本，限制能力，并支持撤销和隔离。
- 先检索或发送数据再鉴权：权限过滤必须发生在数据暴露与外部传输之前。
- 审计日志无限保存敏感内容：按数据类别执行最小记录、脱敏、保留和删除策略。

**相似方案**

Zero Trust、Policy Enforcement Point、软件供应链安全和数据治理提供相同的职责分离。

**长期演进**

完善多租户隔离、策略即代码、内容来源追踪、扩展签名、数据驻留、合规导出和自动风险响应。

### 8.3 生产运营：部署、发布、韧性与灾备

**预期解决**

让 Harness 在持续变更、流量波动和局部故障下维持明确的服务目标，并能够降级、恢复和回滚。

**解决方式**

以 SLI/SLO 定义用户可感知目标；按资源瓶颈规划容量和背压；通过分阶段发布、健康检查、故障隔离、幂等执行、备份与恢复演练控制变更和事故。

**底层设计**

```text
Build + Evaluation + Security Gates
→ Versioned Artifact
→ Canary / Staged Rollout
→ SLI / SLO Observation
├── Healthy → Continue Rollout
└── Regression → Degrade / Roll Back

Runtime Resilience
├── Admission Control + Queue + Backpressure
├── Timeout + Retry Budget + Circuit Breaker
├── Lease + Heartbeat + Idempotency + Deduplication
└── Backup + Restore + Disaster-recovery Drill
```

服务目标覆盖成功率、端到端时延、首 Token 时延、取消收口、成本和数据持久性。降级策略可减少并发、切换合格模型、关闭非关键能力或转入确定性流程，但不得降低安全和证据标准。

**坑与对策**

- 只监控进程存活：同时观测任务成功、模型质量、队列、依赖和用户结果。
- 无限重试放大故障：使用总重试预算、退避、熔断和幂等键。
- 将进程内 Job 当成分布式任务：跨进程执行需要持久队列、租约、心跳和重复投递处理。
- 发布只验证服务启动：Canary 比较质量、安全、成本和时延，并预先定义回滚条件。
- 有备份但不演练恢复：定期验证恢复点、恢复时间和事件、索引、资源之间的一致性。

**相似方案**

**长期演进**

#### 8.3.4 容量、配额与资源治理

**预期解决**

控制模型、工具、进程、存储和后台任务的资源消耗，使吞吐、时延、成本和可靠性可预测。

**解决方式**

各资源所有者执行局部限制，Settings 和 Plugin Config 提供可调参数，Telemetry 与 Diagnostics 汇总 Usage、Timing、Outcome 和容量信号。

**底层设计**

```text
Resource Governance
├── Model：Context Window / Output Tokens / Retry
├── Agent：Turn / Step / Cancellation
├── Tool：Parallelism / Exclusivity / Timeout
├── Process：CPU / Memory / Sandbox Limits
├── Data：Spill Threshold / Retention / Storage Quota
└── Orchestration：Agent Count / Job Count / Schedule / Workflow Limits

Config / Settings → Local Enforcement → Telemetry → Capacity Decision
```

限制在拥有资源的模块执行：Agent Loop 控制 Tool 并发，Capability Provider 控制外部资源，Compaction 控制上下文压力，Storage Policy 控制持久数据。

**坑与对策**

- 在 Plugin 内硬编码部署参数：变化的上限进入经校验的 Config 或 Settings。
- 只设置全局超时：模型、Tool、子进程和 Workflow 分别在真实异步边界处理取消与收口。
- 用截断掩盖容量问题：超大 Tool 输出使用 Spill，历史压力使用 Compaction。
- 只统计平均时延：同时观察分位数、取消、重试、失败、Token 和资源峰值。
- 限制已触发但执行仍继续：限制必须连接 AbortSignal、Provider 终止能力和最终 drain。

**相似方案**

操作系统配额、服务端 Rate Limit、数据库 Retention 和分布式系统 Backpressure 都在资源所有点执行限制。

**长期演进**

建立跨 Agent 的统一预算分配、Backpressure、成本归因、容量预测和自适应并发。
