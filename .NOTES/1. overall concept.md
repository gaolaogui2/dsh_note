# DeepSeek Harness 全局概念

## 目的

建立 DeepSeek Harness 的静态架构地图。
应能解释 Cordis、Harness、Plugin、Session Log 和 Capability Seam 分别是什么，以及它们为什么会同时出现在这个项目里。

> DeepSeek Harness 用 Cordis 运行 1 棵插件树，通过 Session Log 管理持久事实，通过 Capability Seam 组织可替换能力，最终把模型变成可运行、可扩展的 Agent 系统。

## 从模型到 Agent

模型本身主要负责 1 件事：根据输入生成下 1 段输出，自身不会拥有 1 套完整的 Agent 产品能力。

1 个可用的 Agent 系统还需要解决：

- 给模型提供哪些上下文和指令。
- 允许模型调用哪些工具。
- 如何执行文件、命令、网络等外部能力。
- 如何保存、恢复和回放过程。
- 如何管理权限、安全、取消和失败。
- 如何通过 Web、CLI 或 SDK 与用户和程序交互。

这些围绕模型工作的工程系统就是 harness。

### Tool、Skill 与 MCP

Tool 和 Skill 都是 Harness 可以按需提供给 Agent 消费的可选扩展资源：

- Tool 提供可执行能力。它同时包含模型可见的 meta 以及 Runtime 侧的执行实现；模型通过 `tool_call` 调用它。
- Skill 提供完成某类任务的方法，包括步骤、判断标准、约束和参考资料；Agent 加载 Skill 后，通常按照其中的指导组合使用多个 Tools。

MCP（Model Context Protocol）是 Agent Harness 按需连接外部能力的可选标准协议。MCP
Server 可以向 Harness 暴露 Tools、Resources 和 Prompts；Harness 连接 MCP Server 后，再将其中适用的能力提供给 Agent。
Harness 也可以直接提供内置 Tool 或 Skill，不依赖 MCP。

Tool、Skill 和 MCP 都是 Harness 根据场景选择的扩展机制。
MCP 不是某个具体 Tool 或 Skill：Tool 和 Skill 解决 Agent 消费什么的问题，MCP 解决外部能力如何接入的问题。

## 价值

DeepSeek Harness 的核心贡献，是把这层过去常被封装在具体 Agent 产品内部的工程系统开源，并设计成可以组合和替换的 runtime。

## 核心概念

### 1. Cordis

Cordis 是 DeepSeek Harness 底层的插件运行框架。它提供 Context、Service、Event 和生命周期管理，使多个插件能够发现彼此的能力、按依赖关系激活，并在卸载时撤销注册。

> 解释：Cordis 负责让 1 组插件成为 1 个可运行、可组合、可卸载的系统。

Cordis 本身不是 Agent，也不负责决定 1 次模型请求应该怎样执行。它提供的是通用运行机制，Harness 在它之上定义 Agent 领域。

### 2. Harness

Harness 是模型外围的 Agent runtime。它把上下文、模型、工具、状态、权限、执行环境和交互入口组织成 1 个完整系统。

Harness 不是某 1 个具体界面，也不等于 Agent Loop。
Web、Headless、ACP 和 SDK 都可以使用同 1 套 Harness 能力；Agent Loop 只是其中负责驱动模型与工具交替运行的部分。

Agent Runtime 保持完整，Agent Loop 保持轻薄。
状态、能力、安全、持久化和交互分别由独立插件维护，Loop 只编排 1 次次模型请求与工具执行。
Harness 固定的是底层插件机制、Agent Runtime 的职责划分和跨模块约定；具体能力实现及其组合保持开放。

> 解释：Model 提供生成能力，Harness 负责提供 1 个可执行、可约束、可恢复的系统供 Model 来使用。

### 3. Plugin

Plugin 是 Harness 的基本组成单元。模型适配、工具、Session、Agent Loop、权限策略和 Web 功能都通过插件进入运行时。

因此，插件不是附加在固定核心外面的可选装饰。DeepSeek Harness 的核心能力本身也由插件组成，这就是 `everything is a plugin` 的含义。

Plugin 解决的是组合问题：

- 每项能力可以独立加入或移除。
- 插件通过稳定能力和事件协作。
- 不同运行场景可以选择不同插件组合。
- 插件生命周期结束时，其注册内容可以一同撤销。

> 解释：Harness 不是 1 块固定的大程序，而是 1 棵由 Plugin 组成的运行时树。

### 4. Session Log

Session Log 是 1 次 Agent 会话的持久事实流。用户消息、模型回复、工具调用和结果、Turn 与 Step 等需要恢复和回放的事实都以事件记录。

它遵循 1 个关键原则：

> Model-visible means logged：任何进入模型请求的内容，都必须能从 Session Log 重建。

这使同 1 份事实能够支撑模型历史、恢复、回放、fork、审计、持久化和 UI 投影，减少多个状态副本相互漂移。

Session Log 不等于系统里的全部状态。短暂的运行状态、用户设置、凭证和部分 UI 状态可以由其他所有者管理。
判断某项数据是否进入 Session Log，关键看它是否属于会话的持久事实，尤其是否影响模型看到的内容。

从 Harness 使用者的角度看，已经写入的 Session Event 只能追加，不能原地修改或删除。
Compaction 等操作通过追加事件改变后续模型看到的投影，原始事实仍留在日志中。JSONL、SQLite 等持久化后端可以替换，但它们保存的是同 1 种 Session Event；Session Log 的事实定义与重建语义不是普通存储 Provider 可以任意改变的部分。

> Compaction 是 1 次阶段性的上下文压缩动作：它把 1 段较长的历史内容总结成更短的摘要，供后续模型请求使用。

> Session Log 回答“这个 Agent 会话实际发生过什么”。

### 5. Capability Seam

Capability Seam 是 1 项可替换能力的完整分工，通常包含 3 个角色：

```text
Consumer ──依赖──> Service Definition <──实现── Provider
```

Service Definition 定义稳定的能力语义以及请求、结果和失败类型；Provider 实现这项能力；Consumer 只通过 Definition 使用它。Provider 与 Consumer 互不依赖。

例如，Filesystem capability 的关系是：

```text
dsh-tool-fs ──> ctx.fs <── fs-local / fs-sandbox / fs-e2b
 Consumer       Definition             Providers
```

将本地文件系统替换为 E2B 时，File Tool 的参数、结果和模型使用方式不变。若这种替换要求修改 File Tool，说明 Tool 同时耦合了“模型如何表达文件操作”和“文件如何实际访问”两项职责，原有职责范围没有拆开。

Capability Seam 解决的是替换和演化问题：

- Consumer 不直接依赖具体实现。
- 本地、远程或 sandbox 实现可以替换。
- 能力的配置、失败和生命周期有明确所有者。
- 新场景优先增加 Provider 或 Consumer，而不是复制整套系统。

并非每个 Plugin 都是 Capability Seam。一个事件监听器、UI renderer 或策略插件可能只是扩展现有能力；只有 Definition、Provider 和 Consumer 形成完整协作关系时，才构成一项完整 seam。

Capability Seam 也不是 Cordis 在 Plugin 之上增加的另一套运行时机制。Plugin 负责模块的挂载、卸载、组合和生命周期；Capability Seam 是组织插件间依赖的架构规则。仅仅把代码装进不同 Plugin，仍然可能让 Consumer 直接依赖某个具体实现；Seam 通过职责划分与依赖倒置消除这种耦合。

> Plugin 是组合单元，Capability Seam 是可替换能力的分工方式。

### 当前 Capability Seam 版图

仓库当前生成的[能力图](../docs/capability-seams.md)将 28 个 `ctx.*` Service 明确归类为 `seam`。第一阶段只需要知道覆盖范围，不需要记住全部名称。

- 模型与编排：`llm`、`codeRuntime`、`compaction`、`subagents`、`workflowEngine`。
- 执行环境：`subprocess`、`shell`、`terminals`、`sandbox`、`fs`、`lsp`。
- Agent 可用能力：`web`、`skills`、`jobs`。
- Session 与数据：`attachments`、`sessionPersistence`、`sessionQuery`、`sessionTitle`、`sessionTelemetry`、`storage`、`spillStore`、`fileReferences`。
- 配置与交互：`settings`、`credentials`、`authorization`、`userQuestions`、`approval`、`directoryPicker`。

不是所有 `ctx.*` Service 都是 Capability Seam。`ctx.sessions`、`ctx.tools` 和 `ctx.systemPrompt` 属于稳定的 Core Service；`ctx.agentLoop` 是可替换的组合点；`ctx.e2b` 管理一个共享 E2B 环境的生命周期，而 `fs-e2b` 和 `subprocess-e2b` 分别作为既有 `ctx.fs` 与 `ctx.subprocess` seam 的 Provider。

## 五个关键词如何组成架构

```text
                           DeepSeek Harness
                                  │
                    由一棵 Plugin Tree 组成
                                  │
                    Cordis 负责运行和生命周期
                                  │
                  ┌───────────────┴───────────────┐
                  │                               │
          Session Log                     Capability Seams
          保存持久事实                    组织可替换能力
                  │                               │
       恢复 / 回放 / fork / UI          LLM / FS / Shell / Web / ...
```

这张图包含两条相互独立但同时重要的轴：

- Session Log 管理时间上的连续性：过去发生了什么，以及如何恢复。
- Capability Seam 管理空间上的可替换性：当前系统拥有哪些能力，由谁实现和使用。

Plugin 把这些部分装进运行时，Cordis 管理它们的依赖和生命周期，组合后的整体才是 DeepSeek Harness。

## 与 webpack 类比

DeepSeek Harness 与 webpack 的相似之处，不只是都支持 plugin，而是都把经常变化的实现放进稳定的组合机制。

```text
webpack
└── 组合构建过程中的模块、转换和产物能力

DeepSeek Harness
└── 组合 Agent runtime 中的模型、工具、状态和交互能力
```

这个类比有助于理解它的生态潜力，但二者面对的问题不同。webpack 主要处理构建过程；Agent runtime 还要处理持续状态、不确定模型输出、外部副作用、权限、并发和恢复。

webpack 的 `outputFileSystem` 已经体现了同样的依赖关系：emit 逻辑依赖稳定的文件系统接口，Node `fs`、memfs 或自定义实现提供该接口。它没有额外增加一个名为 Capability Seam 的机制，但实际上形成了一条可替换能力接缝。

```text
webpack emit ──> outputFileSystem <── Node fs / memfs / custom fs
 Consumer           Definition                 Providers
```

DeepSeek Harness 的区别，是把这种分散在 Webpack Compiler、Resolver、Loader 和 FileSystem 中的成熟设计方式统一命名，并作为整个项目的架构规则：一项需要替换实现的能力，应明确 Definition、Provider 和 Consumer 的职责。

因此，“完全插拔”不等于插件可以无约束地修改一切。真正可持续的插件系统依赖：

> 自由扩展 + 严格边界 + 可验证兼容

Cordis 生命周期、Session Log 的事实纪律和 Capability Seam 的角色划分，就是这些边界的基础。

## 容易混淆的边界

### Cordis 不等于 Harness

Cordis 是通用插件运行机制；Harness 是建立在其上的 Agent runtime。

### Harness 不等于 Agent Loop

Agent Loop 负责推进一次次模型请求和工具执行；Harness 还包含状态、能力、安全、持久化和交互入口。

### Plugin 不等于 Capability Seam

Plugin 是部署和组合单元；Capability Seam 是 Definition、Provider、Consumer 之间的能力分工。

### Session Log 不等于数据库

Session Log 定义会话的持久事实；JSONL 或 SQLite 只是保存这些事实的具体方式之一。

### 可插拔不等于无边界

插件通过明确的 Service、Event、事实所有权和生命周期协作。缺少这些约束，组合会变得不可预测。

## 第一阶段总结

可以把 DeepSeek Harness 压缩为下面四句话：

1. Cordis 提供插件运行和生命周期机制。
2. Plugin 组合出完整的 Harness。
3. Session Log 保存 Agent 会话的持久事实。
4. Capability Seam 让模型、工具和执行环境等能力可以替换。

最终形成的整体，不是一个功能固定的 Agent 应用，而是一套用于构造 Agent 系统的开放 runtime。
