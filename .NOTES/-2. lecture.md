# Harness Engineering：以 DeepSeek Harness 为解剖标本

## 1、总览

Agent 由 Model 和 Harness 共同构成。

- Model 负责推理与决策；
- Harness 负责组织上下文、调用模型和工具，并管理状态、权限与运行过程；

Harness 的架构设计取决于实际业务诉求：

- 能力与入口稳定时，可以直接通过代码组装，需要持续替换和复用时，适合插件化与接口分离；
- 任务步骤明确固定时，适合 Workflow，执行过程需要动态决策时，适合使用 Agent Loop ；

这些方案来自成熟的软件架构经验。

业务需求持续变化，底层架构原则的演进相对稳定。

DSH 是面向持续变化场景的开源插件化 Agent Runtime ，预期提供「稳定的能力定义和清晰的生命周期管理」，实现「能力、入口和执行方式能够持续替换、组合与复用」。

统 1 插件模型使局部实现可以独立替换，能力可以跨场景复用，系统也能持续扩展。

开源使得「私有部署」和「深度定制」成为可能，使 DSH 适合作为理解 Harness 工程的标本。

## 2、宏观架构

DSH 以 Cordis 作为插件 Runtime。

Cordis 用 Plugin Tree 管理功能装配与生命周期，再通过 Context 上的 Service 和 Event 建立能力网络。

- Plugin 装配功能，Fiber 承载 Plugin 实例及其生命周期；
- Context 提供作用域和 Service 访问；
- Service Method 提供直接调用入口，Registry 提供能力注册与发现；
- Event 允许 Plugin 在特定运行阶段观察、追加、修改或拦截行为；
- Effect 登记清理函数，在 Plugin 卸载时撤销注册或释放资源。

Registry 是 Service 组织可扩展内容的方式，不是独立的 Cordis 原语。

Plugin 通过 `inject` 声明 Service 依赖，Cordis 据此控制访问、激活条件和作用域解析。

预设 Service 与自定义 Service 在 Cordis 中定位相同。

预设 Service 已有默认装配和 Consumer，自定义 Service 也需要 Consumer 才能进入业务流程。

DSH 在这套机制上组织稳定骨架、运行设施和 Capability Seam。

- 稳定骨架规定 Runtime 的基本组成和职责交接；
- 运行设施提供不同执行方式共同依赖的机制；
- Capability Seam 隔离语义稳定但实现可替换的能力。

Launcher 创建 Cordis 实例并挂载 Loader Plugin。

Loader 负责配置合并与插件装载，Cordis 负责依赖管理、插件激活和生命周期。

Runtime 就绪后，Controller 承接外部交互，并把请求交给可替换的 Agent 执行域。

Agent 执行域负责接收输入、组装上下文、调用模型和工具，并产出运行事实。

这条骨架使用 4 类核心设施：

- Inbox 保存待处理输入；
- System Prompt 汇集上下文贡献；
- Tools 管理模型可用工具；
- Session 记录运行事实，并将事实投影为模型历史、场景输出和恢复状态。

需要独立替换的能力通过 Capability Seam 接入。

1 个完整的 Capability Seam 由 Definition、Provider 和 Consumer 构成。

Definition 定义稳定语义，Provider 提供具体实现，Consumer 使用这项能力。

Agent 和 LLM Seam 构成请求执行的核心。

Persistence、Compaction、Settings 和 Credentials 提供运行支持。

文件、命令、网络、交互与编排 Seam 扩展任务能力。

骨架保持运行过程稳定，设施复用公共机制，Seam 扩展具体实现。

3 者共同构成 DSH 的插件化架构。

## 3、链路

Harness 的运行过程可以分为启动、请求、控制与恢复 3 条主链。

这是理解 Runtime 的通用视角，不代表固定模块或唯一实现。

任务场景主要改变每条链内部的调度、状态和资源策略。

### 3.1 启动主链

启动主链把配置和环境选择转成可运行的 Runtime。

Launcher 创建 Cordis 实例，挂载 Loader Plugin，并汇集 Bundle、Profile、DSH_HOME、命令行 Patch 和启动环境。

Include 按顺序合并配置，Loader 建立 Entry 配置树，Cordis 根据 Service 依赖激活插件，并用 Fiber 管理资源生命周期。

配置顺序决定覆盖结果，Service 依赖决定插件何时激活。

所有必需 Entry 激活后，Runtime 进入就绪状态。

配置、模块、依赖或插件错误会在最早能够定位问题的阶段暴露。

不可恢复的错误会终止启动，并释放已经登记的资源。

### 3.2 请求主链

请求主链把外部输入交给入口 Agent，并把执行过程和结果反馈给调用方。

Controller 适配外部协议，关联会话，定位、创建或恢复入口 Agent，再把用户意图转换为稳定的 Agent 操作。

followup 提交新任务，steer 干预当前执行，inject 补充下次模型请求，cancel 请求停止当前活动。

Agent 需要外部判断时，通过 Interaction 发起询问或批准。

每个 Agent 拥有独立 Inbox。

next-turn 保存待执行的独立任务，next-step 保存影响最近 Step 的增量输入。

Agent Loop 在 Step 边界接纳输入，因此新消息只能影响尚未组装的模型请求。

默认 ReactLoopAgent 用 Driver 承载 1 次活动，用 Turn 处理 1 个任务，用 Step 完成 1 次模型请求及其 Tool Call。

每个 Step 都从 Session、System Prompt、Tool Schema 和模型配置重新组装上下文。

模型给出最终回答时结束 Turn；模型发起 Tool Call 时，工具结果写入 Session，并参与下 1 个 Step。

单个 Agent 默认串行执行，不同 Agent 可以并行。

Controller 可以返回提交回执、等待完成结果，或持续推送增量输出。

消息已提交不代表执行完成，Agent 空闲也不代表任务成功。

需要逐条确认结果时，还必须建立输入与结果之间的因果关系。

### 3.3 控制与恢复主链

控制与恢复主链负责停止活动、释放资源和跨进程恢复。

取消是协作式请求。

Runtime 向受管工作传播取消信号，等待其停止，记录结果并使 Driver 回到空闲。

局部失败由能够解释其语义的执行方处理，无法继续的错误才会结束当前 Turn 或更大范围的活动。

释放遵循资源所有权。

系统停止接收新工作，等待活动任务退出，再由 Cordis 按 Fiber 生命周期撤销已登记资源。

未登记资源和已经发生的外部副作用仍由对应 Provider 处理。

Session Log 保存持久事实，Session Persistence 负责加载、校验和修复日志。

恢复会话时，Runtime 根据 Session ID 重建状态，再创建新的进程内 Agent。

它恢复 Session 身份和已记录事实，不复活旧对象，也不重新执行历史模型请求或 Tool Call。

Runtime 意外中断时，未结束的 Step、Turn 和 Tool Call 会在日志加载时补齐结束状态。

无法确认结果的外部调用会被标记为未知。

Session Log 只能证明 Harness 记录了什么，不能证明外部系统没有发生副作用。

因此，安全恢复还依赖具体能力提供幂等、去重、状态核查、补偿或人工确认。

需要跨进程继续执行的后台任务，还必须额外持久化任务状态和调度信息。
